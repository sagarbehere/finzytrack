## Decisions
- **The cut** (agent): the runner and the first two typed reads, given a path, with no route. A route needs the workspace gate to serve something (only `NoWorkspaces` until BL-0102) and BL-0115's decision on who may call (owner: option 1, M2) built before it serves ledger data, so a route now would serve nothing or serve before its guard. The routes, the container wiring and the envelope's `ledger_version` are BL-0126 (M2); cancelling a running query is BL-0127 (M7). L5-07 is closed; L1-10 stays open for its freshness check (BL-0125). No engine call is made, so no `TODO(BL-0109)`.
- **Spike first** (agent; scratchpad, SQLite 3.53.1): on a `mode=ro` connection with no authorizer, `VACUUM INTO '<path>'` wrote a new file, and `ATTACH`, `PRAGMA`, `pragma_table_info()`, `CREATE TEMP TABLE` and the `dbstat` table all ran. This is ADR-0016's "a read-only open mode alone is not enough", seen on our SQLite, and why every refusal test checks the folder for new or changed files.
- **The authorizer is an allowlist of actions, a check of every read, and a denylist of two functions** (agent; ADR-0016 "an authorizer allowlist (no PRAGMA or pragma_*())"). Actions: `SELECT`, `READ`, `FUNCTION`, `RECURSIVE`; any other is denied, which covers `PRAGMA`, `ATTACH` (and so `VACUUM INTO`, which attaches its target), every write, `CREATE`, transactions and `ANALYZE`. A read passes when it names, in schema `main`, an object of the file itself (read from its `sqlite_schema` on each call, so a new table needs no code change), `sqlite_schema`/`sqlite_master`, or `json_each`/`json_tree`: that keeps out every `pragma_*()` table (SQLite reports them as reads of `pragma_<name>`), `dbstat` and the `temp` schema. A read with no schema is a CTE or subquery of the statement (SQLite reports `COUNT(*)` over a CTE that way) and passes. *(Wrong, superseded in verifier round 1, F2: SQLite reports a column-less read of `dbstat` the same way.)* Functions: every SQLite built-in except `load_extension` (also off in Python by default) and `fts3_tokenizer` (registers a tokenizer from a pointer) only computes, so an allowlist of some 150 function names would add upkeep and no safety; the review is tied to the SQLite version by `test_the_function_denylist_was_reviewed_for_this_sqlite`. SQLite reports names in canonical lower case (`LOAD_EXTENSION` arrives as `load_extension`).
- **User SQL may read the base tables `m_*`** (agent). Confinement is about what a query can reach beyond the mirror, and `m_*` are in the same file; ADR-0015 makes `r_*` the supported surface, a documentation and support promise (README "Three layers": `m_*` "may change any release"), not a security line. Refusing `m_*` would be a product rule users see (rubric item 5); it is not taken here. The M7 user docs say which names are supported.
- **Not set: `trusted_schema` off, `SQLITE_DBCONFIG_DEFENSIVE`** (agent; tie each mechanism to a requirement): the authorizer already applies inside the file's view bodies (reads of `m_*` arrive attributed to the view), the connection cannot write, and the file is the app's own; neither would add a refusal a test could show.
- **A statement that runs and returns no columns is refused as `not_allowed`** (agent): a comment alone, or `REINDEX` on a file with no index, runs as a no-op with no authorizer call; answering it with an empty result would let a non-SELECT pass as a query. Empty text is `invalid` ("There is no statement to run.").
- **Outcomes come from SQLite's result code and the guard's own record, never from message text** (agent; EP-13): a refused function arrives as a plain `SQLITE_ERROR`, so the guard's first refusal decides `not_allowed`; `SQLITE_INTERRUPT` is `timed_out`; `SQLITE_TOOBIG` is `too_large`; `SQLITE_ERROR`/`RANGE`/`MISMATCH` and Python's own `ProgrammingError` (a second statement, a missing parameter) are `invalid` with the message; `CANTOPEN`/`NOTADB`/`CORRUPT` are `MirrorUnavailable`; anything else (a disk error, out of memory) propagates. The reader asks `sqlite_schema` whether its base table exists instead of matching "no such table".
- **Limits are configuration values** (agent; INV-10 style; the rubric lets agents set threshold and bound defaults): 30 s (v0.3's limit, now enforced inside SQLite; v0.3's `wait_for` left the query running on its thread), 10,000 rows (v0.3's Analyze had no cap, its assistant tool 500; a caller may lower it per call, never raise it), 16 MiB per text or blob (`SQLITE_LIMIT_LENGTH`), 64 MiB of rows handed back *(superseded in verifier round 1, F1: these did not bound memory; see the Verifier section)*, the clock read every 10,000 virtual-machine steps (under 3% of a query's time, measured below). Not tuned against a measured need; a hosted deployment sets its own.
- **One connection per call** (agent; INV-10; ARCHITECTURE.md §9.1 "on a worker thread"): opening and confining costs 0.2 ms at 54k, so there is nothing to pool and no state to register (`state_registry.py` unchanged). The runner and the reader hold only a path and their limits.
- **Parameters by name only, never float** (agent; INV-06): `SqlParam = int | str | None`; a decimal goes as its text, as money is stored. Python 3.13's `sqlite3` refuses `?` with a mapping.
- **Time is injected** (agent; EP-10): `monotonic` is a constructor argument defaulting to `time.monotonic`, as in `EngineClient`; the time-limit tests use a clock that moves one second per read, so they use no real time.
- **The test mirror is made from `contracts/mirror-ddl.sql`** (agent; ADR-0054: the main sidecar never imports the engine): the generated snapshot the engine's build is checked against (S0050), so the reads are tested against the tables and views the build writes. The real 54k build was also checked by hand: all of its 53 tables and views answer through the runner.
- **`UserSql` lives in `app.mirror.query`** (agent): ARCHITECTURE.md §2.6 names it with its producers (the recipe validator, the Analyze endpoint), which import the runner anyway.
- **`ledger_errors` returns the total and the first `limit` rows** (agent; INV-10): a broken ledger can have thousands of errors; the notice needs a count and a few. Ledger text (message, entry JSON) is `UntrustedText`; `source_file` is the absolute path the build wrote, and showing it relative to the workspace is the route's (BL-0126); it is `UntrustedText` too since verifier round 1 (F8: an include's file name is ledger text).
- **Deviation from ENGINEERING.md:** none known.

## Verifier
- **Round 1** (head 07795740, range 5848c85f..07795740): **FAIL**, 1 High, 4 Medium, 4 Low. Report and a failing test per finding in the private archive `m1a/s0052-verifier/` (`REPORT.md`, `repros/`). All 18 repro tests failed on 07795740 here too; before numbers below are from the verifier's `mem.py`, `slow.py` and `tempdisk.py`, run here (macOS, SQLite 3.53.1). Fixed in one commit; every finding has its tests in `backend/tests/mirror/`, each failing on 07795740's code (31 in `test_query.py`, 1 in `test_files.py`, 17 in `test_reader.py`; the first two modules import names the fix adds, so they were run against 07795740's `src` with those imports stubbed).
  - **F1 High, fixed: the bounds did not bound.** The result cap was checked after `fetchmany(500)`, one row could hold 2,000 columns of 16 MiB, and SQLite's sorter wrote temp files with only the timeout to stop it. Requirement: INV-10 (every bound real), ADR-0016 (a user query cannot take the sidecar down). Now, each mechanism tied to what it bounds (`QueryLimits` docstring): rows are fetched one at a time and counted as they arrive, by their memory in Python (`sys.getsizeof` of each row, value and column name), and the row that passes the cap is dropped; `SQLITE_LIMIT_COLUMN` (64) and `SQLITE_LIMIT_LENGTH` (250,000 bytes) cap one row, and `QueryLimits` refuses limits where one row (`row_bound`: 4 bytes a character, as Python stores text with one character past U+FFFF) would not fit in `max_result_bytes` (64 MiB); `temp_store = MEMORY`, so the sorter and every temporary table live in SQLite's heap and no query writes a temp file; SQLite's hard heap limit (256 MiB; the 54k mirror's self-join of `postings` needs 64 to 128 MiB) bounds that heap, and a query past it is `too_large` (SQLite's NOMEM arrives from Python as `MemoryError`). Python exposes no per-connection heap limit, and SQLite has none: `PRAGMA hard_heap_limit` is process-wide and can only be lowered, so it bounds all SQLite memory of the main sidecar (only mirror reads use SQLite there), queries running at once share it, and the lowest value set wins; `confine` reads it back and refuses to run above its own value. Hosted fairness between users is BL-0128 (post-v0.4). The query text is capped at 100,000 UTF-8 bytes, which also bounds the column names SQLite makes from it. Stated bound: SQLite's heap limit plus twice `max_result_bytes` in Python. Peak RSS growth and temp disk, before → after (defaults unless noted; one process per attack, `scratchpad/s0052-fix/after.py`): 400 rows of 1 MB under a 1 MB cap +410 MB → `too_large` +0 MB (the value limit); one row of 400 columns of 1 MB +817 MB → `invalid` (too many columns) +1 MB; 60 rows of 16 MB +1,617 MB → `too_large` +0 MB; the sort of 1,500 × 1 MB 0.99 GB temp disk → `too_large`, 0 disk; at the new limits' worst: 2,000 rows of 250 kB → 268 rows, `bytes`, +72 MB; 64 columns of 250 kB → 4 rows, +113 MB; the same in 4-byte text → 1 row, +165 MB; a sort of 1,500 × 200 kB → `too_large` at the heap limit, +270 MB, 0 disk. Cost on the 54k mirror (`measure_mirror_reads.py --runs 10`): open, check and confine 0.22 ms (was 0.19); typical queries unchanged within noise (monthly expenses 30.6 ms, one account's year 15.4, one transaction 12.1, every posting capped at 10,000 rows 32.2, was 37). Cost to users: a text or blob over 250 kB (a `group_concat` over many postings) is `too_large`; a result of more than 64 columns (a join of three posting views) is `invalid`.
  - **F2 Medium, fixed: `SELECT count(*) FROM dbstat` answered.** A column-less read comes with no schema for a stored table, an eponymous virtual table and a CTE of the query alike (traced on SQLite 3.53.1); the guard passed every such read. Requirement: INV-09, ADR-0016's allowlist. Now the name of every read is checked whatever the schema. For a column-less read of a name that is not the mirror's, the guard asks SQLite itself whether the bare name resolves outside the query (`_Resolver`: `SELECT 1 FROM "<name>"` prepared, never run, on its own in-memory connection under an authorizer that records the read and refuses everything); if it does not, the name can only be the query's CTE and the read passes. **Deviation from the round's instruction** ("check the table name for every read", taken literally as an allowlist of names): that would refuse `COUNT(*)`, `SELECT 1 FROM` and `EXISTS` over a CTE, and `SELECT 'a' FROM n` over a recursive series, common in dashboard SQL. Rejected alternative: a denylist from `PRAGMA module_list`, which misses the virtual tables SQLite registers only when first named (`pragma_*`, `json_*`; `module_list` lists neither until used), so it would miss a later one too. The resolver asks the same lookup SQLite uses and covers those (tests: every module of `pragma_module_list` plus three `pragma_*` names never answer a count; `dbstat` in five forms refused; CTE, mirror-table and `json_each` counts answer). Cost: a CTE named like a virtual table (`WITH dbstat AS …`) is refused; harmless. Module docstring corrected.
  - **F3 Medium, fixed: a hot journal raised.** A build killed mid-write leaves a hot `-journal`; on a `mode=ro` open SQLite answers `SQLITE_READONLY_*`. The open's own reads now map `SQLITE_READONLY` (and `SQLITE_ERROR`, a schema that is not the mirror's) to `MirrorUnavailable("not_a_mirror")` (`files.app_read_outcome`); the user query's errors keep their own mapping. Test: the runner on the verifier's hot-journal copy, nothing changed beside it.
  - **F4 Medium, fixed: the runner answered on any file.** `open_mirror` now checks the file before answering: the 100-byte SQLite header (a 0-byte file is SQLite's empty database), then `m_meta` read and checked (`files.read_info`, moved from the reader), and returns `OpenMirror(con, info)`; the runner and the reader both go through it, and `Reader.info()` returns the checked `info`. A purged cache is now `not_a_mirror`, not `invalid`.
  - **F5 Medium, fixed: input Python's sqlite3 cannot take raised.** `_check_input` runs before the open: a lone surrogate in the text or a str parameter, or an int outside SQLite's 64 bits, is `QueryRefused("invalid")`. `Reader.ledger_errors(limit)` takes 1 to 2**63 - 1; outside that it is a caller error (`ValueError`), as a limit of 0 already was: the limit is the app's, not a user's.
  - **F6 Low, fixed:** a parameter that is not an int, a str or None (a float above all, INV-06) is a `TypeError` at run time, not a silent bind.
  - **F7 Low, fixed:** `meta` refuses a NULL, empty or non-text value, a NULL key, more than 64 rows, a `surface_version` that is not 1 to 9 ASCII digits (`int()` also takes other scripts' digits and raised past 4,300), and a table of another shape; `ledger_errors` refuses a row whose values are not of their columns' kinds. Each is `not_a_mirror`.
  - **F8 Low, fixed:** `LedgerError.source_file` is `UntrustedText | None`.
  - **F9 Low, fixed:** a WAL-mode file (header bytes 18 and 19 not 1) is `not_a_mirror` before SQLite opens it, so a read creates nothing beside the file. No cheaper read-only open avoids it: `immutable=1` would read past a hot journal (F3) unseen.
  - L5-07 stays closed: F1, F2 and F9 broke its claim on 07795740, and it holds again with these fixes; its note says so. L1-10's note and `QueryLimits` now state what each bound covers.
