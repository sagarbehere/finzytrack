# S0052: Mirror reads and the hardened QueryRunner

In the main sidecar, read a mirror file that S0050's build wrote, given by its path (nothing publishes yet, BL-0113): the one hardened runner for user SQL that ADR-0016 decides, with its confinement tests, and the first typed read the API will serve, the load's errors with the mirror's own facts (CAP-NOTIFY-SERVER "ledger parse errors (with details)" in M2; the `ledger_version` every envelope carries, §9.1 step 4). ## Decisions
- **The cut** (agent): the runner and the first two typed reads, given a path, with no route. A route needs the workspace gate to serve something (only `NoWorkspaces` until BL-0102) and BL-0115's decision on who may call (owner: option 1, M2) built before it serves ledger data, so a route now would serve nothing or serve before its guard. The routes, the container wiring and the envelope's `ledger_version` are BL-0126 (M2); cancelling a running query is BL-0127 (M7). L5-07 is closed; L1-10 stays open for its freshness check (BL-0125). No engine call is made, so no `TODO(BL-0109)`.
- **Spike first** (agent; scratchpad, SQLite 3.53.1): on a `mode=ro` connection with no authorizer, `VACUUM INTO '<path>'` wrote a new file, and `ATTACH`, `PRAGMA`, `pragma_table_info()`, `CREATE TEMP TABLE` and the `dbstat` table all ran. This is ADR-0016's "a read-only open mode alone is not enough", seen on our SQLite, and why every refusal test checks the folder for new or changed files.
- **The authorizer is an allowlist of actions, a check of every read, and a denylist of two functions** (agent; ADR-0016 "an authorizer allowlist (no PRAGMA or pragma_*())"). Actions: `SELECT`, `READ`, `FUNCTION`, `RECURSIVE`; any other is denied, which covers `PRAGMA`, `ATTACH` (and so `VACUUM INTO`, which attaches its target), every write, `CREATE`, transactions and `ANALYZE`. A read passes when it names, in schema `main`, an object of the file itself (read from its `sqlite_schema` on each call, so a new table needs no code change), `sqlite_schema`/`sqlite_master`, or `json_each`/`json_tree`: that keeps out every `pragma_*()` table (SQLite reports them as reads of `pragma_<name>`), `dbstat` and the `temp` schema. A read with no schema is a CTE or subquery of the statement (SQLite reports `COUNT(*)` over a CTE that way) and passes. Functions: every SQLite built-in except `load_extension` (also off in Python by default) and `fts3_tokenizer` (registers a tokenizer from a pointer) only computes, so an allowlist of some 150 function names would add upkeep and no safety; the review is tied to the SQLite version by `test_the_function_denylist_was_reviewed_for_this_sqlite`. SQLite reports names in canonical lower case (`LOAD_EXTENSION` arrives as `load_extension`).
- **User SQL may read the base tables `m_*`** (agent). Confinement is about what a query can reach beyond the mirror, and `m_*` are in the same file; ADR-0015 makes `r_*` the supported surface, a documentation and support promise (README "Three layers": `m_*` "may change any release"), not a security line. Refusing `m_*` would be a product rule users see (rubric item 5); it is not taken here. The M7 user docs say which names are supported.
- **Not set: `trusted_schema` off, `SQLITE_DBCONFIG_DEFENSIVE`** (agent; tie each mechanism to a requirement): the authorizer already applies inside the file's view bodies (reads of `m_*` arrive attributed to the view), the connection cannot write, and the file is the app's own; neither would add a refusal a test could show.
- **A statement that runs and returns no columns is refused as `not_allowed`** (agent): a comment alone, or `REINDEX` on a file with no index, runs as a no-op with no authorizer call; answering it with an empty result would let a non-SELECT pass as a query. Empty text is `invalid` ("There is no statement to run.").
- **Outcomes come from SQLite's result code and the guard's own record, never from message text** (agent; EP-13): a refused function arrives as a plain `SQLITE_ERROR`, so the guard's first refusal decides `not_allowed`; `SQLITE_INTERRUPT` is `timed_out`; `SQLITE_TOOBIG` is `too_large`; `SQLITE_ERROR`/`RANGE`/`MISMATCH` and Python's own `ProgrammingError` (a second statement, a missing parameter) are `invalid` with the message; `CANTOPEN`/`NOTADB`/`CORRUPT` are `MirrorUnavailable`; anything else (a disk error, out of memory) propagates. The reader asks `sqlite_schema` whether its base table exists instead of matching "no such table".
- **Limits are configuration values** (agent; INV-10 style; the rubric lets agents set threshold and bound defaults): 30 s (v0.3's limit, now enforced inside SQLite; v0.3's `wait_for` left the query running on its thread), 10,000 rows (v0.3's Analyze had no cap, its assistant tool 500; a caller may lower it per call, never raise it), 16 MiB per text or blob (`SQLITE_LIMIT_LENGTH`), 64 MiB of rows handed back, the clock read every 10,000 virtual-machine steps (under 3% of a query's time, measured below). Not tuned against a measured need; a hosted deployment sets its own.
- **One connection per call** (agent; INV-10; ARCHITECTURE.md §9.1 "on a worker thread"): opening and confining costs 0.2 ms at 54k, so there is nothing to pool and no state to register (`state_registry.py` unchanged). The runner and the reader hold only a path and their limits.
- **Parameters by name only, never float** (agent; INV-06): `SqlParam = int | str | None`; a decimal goes as its text, as money is stored. Python 3.13's `sqlite3` refuses `?` with a mapping.
- **Time is injected** (agent; EP-10): `monotonic` is a constructor argument defaulting to `time.monotonic`, as in `EngineClient`; the time-limit tests use a clock that moves one second per read, so they use no real time.
- **The test mirror is made from `contracts/mirror-ddl.sql`** (agent; ADR-0054: the main sidecar never imports the engine): the generated snapshot the engine's build is checked against (S0050), so the reads are tested against the tables and views the build writes. The real 54k build was also checked by hand: all of its 53 tables and views answer through the runner.
- **`UserSql` lives in `app.mirror.query`** (agent): ARCHITECTURE.md §2.6 names it with its producers (the recipe validator, the Analyze endpoint), which import the runner anyway.
- **`ledger_errors` returns the total and the first `limit` rows** (agent; INV-10): a broken ledger can have thousands of errors; the notice needs a count and a few. Ledger text (message, entry JSON) is `UntrustedText`; `source_file` is the absolute path the build wrote, and showing it relative to the workspace is the route's (BL-0126).
- **Deviation from ENGINEERING.md:** none known.

## Measurement (54k)
The demo generator's 54k ledger (`backend/scripts/gen_demo.py --size 54k --anchor 2026-10-28`: 54,018 entries, 108,241 postings), built with `engine/scripts/measure_mirror_build.py` (load 1.37 s, build 1.09 s, file 82.8 MB, incomplete as expected until BL-0120), then `backend/scripts/measure_mirror_reads.py <mirror> --runs 10 --indexes`; macOS on the owner's development machine, warm cache; medians, each max within 1 ms of its median:
- open and confine a connection, run `SELECT 1`, close: 0.19 ms. `Reader.info()` 0.19 ms; `Reader.ledger_errors(200)` 0.19 ms (the demo has no errors).
- user queries over the compatibility views: monthly expenses by account (`GROUP BY` over every posting, 2,880 rows) 32 ms; one account's year (2,688 rows) 15 ms; one transaction by id 11.9 ms; `account_balances` 0.22 ms; every posting, capped at 10,000 rows, 37 ms.
- the time limit's progress handler at its default spacing against nearly off (1e9 steps): 32.1 against 31.2 ms, 36.9 against 36.6 ms: under 3%.
- BL-0122's candidate indexes, on a copy: `(account, transaction_date)` takes one account's year from 15.0 to 2.6 ms; `(transaction_id)` one transaction from 11.9 to 0.26 ms; the two add 89 ms to the build and 12.7 MB to the file. Not added here: the build is the engine's, and no read that needs them exists yet; the numbers are in BL-0122's row.
- Not measured: `/health` while the sidecar reads (BL-0114): no route reads yet, so the sidecar does no read work of its own; with BL-0126.
