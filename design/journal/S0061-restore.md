# S0061: The restore shared by the save's rollback and recovery's per-journal try

## Brief
- Goal: BL-0151's slice 2 (`design/specs/engine-jobs.md` §6.4, §8.1 steps 1-4, §10, §13 "recovery", §14 "Save, durable order" and "Recovery"; ADR-0012 as amended by ADR-0063 and ADR-0064; ADR-0013): **one restore operation** that takes a journal record and the disk, judges each file it names (pre, post or neither), restores from the backups by the save's own durable discipline, deletes our temps by the spec's rule and closes the record with the spec's outcome; used by the **in-engine rollback** (wired into `writer.durable_commit` in place of S0060's `TODO(BL-0151)` seam) and by **recovery's per-journal try** (§8.1 steps 1-4, without the listing). S0060's crash and power-loss sweep is extended so that every crash point of the save, and of the rollback, is followed by recovery, including a crash during recovery and a recovery after that.
- Base: e8bf92a5 (pushed, tree clean).
- **What it builds:**
  - `ledger_engine.ledger.core.recovery` (pure): the per-file judgement of §8.1 step 2, the engine's recovery decision (§12: "the recovery check per file" is a pure function): from what was seen at the file, at the save's temp beside it and at its backup, the verdict `at_pre`, `at_post` or a stop with its cause. The temp rule (review 6 P1) lives here and only here.
  - `ledger_engine.ledger.restore`: `restore(fs, record, journal_dir, ...)` (§8.1 steps 2-4, the rollback's §6.4) and `recover_journal(fs, locks, journal_dir, name)` (step 1, the locks without waiting, then the restore). Outcomes `Resolved`, `Stopped(cause, path)` (the blocking reason `stopped` of §11) and `Failed(cause, path)` (reason `failed`).
  - The writer's rollback: every failure from the journal's `.open` rename on runs the restore at once (§6.4), with the file whose outside save the save itself kept named as `skip` (§6.4 "In a save, the other files are rolled back and the journal resolved"), the folders the save really made (an outside folder that appeared first is never removed), and, after a failed close sync, the record renamed back from `.closed` to `.open` first.
  - The port gains `DirHandle.rmdir` (§8.1 step 3 "a directory the save created is removed if it is empty") and a `Locks` port with `try_lock(path_key)` (§6.1 step 3's lock files `app_local_data/locks/<sha256(path_key)>`, never deleted; §8.1 step 1 "without waiting"); the macOS adapter implements both (`unlinkat(AT_REMOVEDIR)`, `flock(LOCK_EX | LOCK_NB)`); the fake gets both, several injected faults at once (a fault in the save and another in its rollback), and a volume that stores names in NFD (HFS+'s behaviour) for the path guard.
  - The path guard compares names as the volume does (BL-0151 slice-2 note, S0060 red team round 2 overflow 3): the handle's path and the recorded canonical path are compared after NFD, since every macOS volume the save writes on treats two normalizations of a name as one; case stays exact (a folder renamed in case only stops the save or the try: fails closed).
  - The `.closed` record a failed close sync leaves (S0060 verifier Q1): the rollback renames it back to `.open` and syncs before any file is restored, so no power loss can leave a `.closed` record over restored files; then it rolls back like any other failure.
- **The step rule** (written before coding; S0057-S0060 lesson):
  - Effects that may raise: every port operation may raise `OSError` (any errno), and the process may die at any effect. A half-done effect leaves what S0060 states (an exclusive create with its entry and a prefix of its data or no entry; a swap, a rename or an `rmdir` whole or not at all; a sync nothing visible). The pure judgement does not raise. A record that breaks the format never reaches the restore (strict decode: `Unreadable`).
  - **The restore's order:** (0) the journal folder's path guard; for the rollback after a failed close, `.closed` renamed `.open` and the folder synced; (1, recovery only) every lock the record names tried without waiting, in `path_key` order; (2) every file checked, nothing written: the path guard of its folder, what the file, its save temp and (for a file at post) its backup hold, and whether a restore could run there (a regular file with one link, not locked, the swap and the clean-up allowed, a volume with the swap); (3) for each file at post, the save's temp re-checked by the temp rule and removed, then the file restored, root first: a leftover restore temp removed without a check, the restore temp `.<name>.ft-restore-<job>.tmp` written from the backup with the file's mode and synced, swapped in, the displaced entry checked to be the object step 2 saw holding the post bytes (anything else: swapped back, the folder synced at once, stop), the displaced post bytes removed; for a created file, renamed aside to the restore temp, checked the same way, removed (or renamed back, synced, stop); then the save's temps beside files at pre removed whatever they hold (a regular file), and leftover restore temps; **every folder the record names synced** (not only those this try changed: refined while testing, see Decisions); each folder the save created removed if empty, deepest first, then their parents synced; (4) only then `.open` renamed `.resolved` and the journal folder synced.
  - **What each failure leaves:** a failure in steps 0-2 (any `OSError`, a cause found, a lock held) writes nothing to a ledger folder: the journal stays as it was (`.open`; for the close case `.open` once its rename's sync passed, else `.open` or `.closed` as the disk keeps it). From step 3 on, an `OSError` stops at once: every file is whole at pre or post (each swap and rename is whole), the journal stays `.open`, a restore temp may be left (the next try deletes it without a check, §6.4); a displaced check that fails leaves the outside bytes in the file and stops. A crash at any effect leaves the journal `.open` with each file whole, and the next try is idempotent (it finds restored files at pre).
  - **What each outcome claims:** `Resolved`: the journal is `.resolved` and durable, and every file it names durably holds its pre bytes (a created file absent), except the rollback's `skip` file, which holds the outside save the save put back; no temp or restore temp of the save is left; each folder the save made is gone unless it holds other entries. `Stopped(cause, path)`: a cause found on disk (the file holds neither pre nor post or is not a regular file, a temp holds an outside save, a bad backup, a moved or unreachable path, a hard link, a lock flag, a permission, an outside write met at a restore swap, an unreadable record); the journal stays `.open`; no outside byte was deleted. `Failed(cause, path)`: an I/O error from step 3 on, or a held lock; the journal stays `.open`; every file whole at pre or post. Recovery's blocking reason is `stopped` for `Stopped` and `failed` for `Failed` (§8.1, §11).
  - **What the writer tells after its rollback:** `NotSaved(open_journal=False)` when the rollback resolved the journal (or no journal was left `.open`), with `unchanged` from the re-hash (§11's rule); `NotSaved(open_journal=True)` for a failure before the first replace whose rollback did not resolve; `Unfinished` for a failure from the first replace on whose rollback did not resolve; `Landed` only as before. A failure before the `.open` rename is not a rollback (§6.4: "not a rollback: nothing was replaced"); its `.part` stays for recover-all.
  - Anything else raised (a bug) propagates: the job ends `INTERNAL`, never "saved".
- Implements: spec §6.4 (rollback at once from the journal, the checks of §8.1 step 2 first with the temp rule, restore temps under their own names written from the backup and synced before their swap, every swap's displaced check including the swap-back's, the removal of a created file by a rename aside and a check, the last bullet for a failure before the first replace), §6.5 (`.open` → `.resolved`, each rename followed by a sync of the journal folder), §8.1 steps 1-4, §10's rows "journal durable, no replace yet" to "close not yet durable" and its paragraph on a crash during a recovery or a rollback; ADR-0012 (per-file rule, F-1 backup checked, F-5 root first, in-process rollback) as amended by ADR-0063 (recovery writes a recorded path only while it resolves to itself) and ADR-0064 (a failed rollback leaves the journal `.open` and pauses writes; temps cut off mid-write never block; restore temps under their own names); ADR-0013 (every swap hashes what it displaced; hard-linked files refused, applied to the restore swap).

- Risk class / lane: **High / full** (ledger writes, recovery); verifier and data-safety red team.
- **Attack list from probes made before coding** (real APFS, fresh temp folders in the session scratchpad; an HFS+ and a case-sensitive APFS disk image made, mounted there and detached again; macOS 26.6.2):
  - A swap exchanges a file with a folder, a symlink or a FIFO without complaint (`renameatx_np` `RENAME_SWAP`), so the restore must check the kind and identity of the entry it swaps with, before and after the swap.
  - Unlinking a folder answers `EPERM`, not `EISDIR`; `rmdir` answers `ENOTEMPTY` for a folder holding a `.DS_Store`, `ENOTDIR` for a symlink to a folder.
  - `RENAME_EXCL` and an exclusive create refuse an existing file, a folder and a dangling link (`EEXIST`).
  - A hard-linked file at post swapped with the restore temp: the name gets pre, the other link keeps post (`nlink` 2 before): the restore refuses a hard-linked file (the owner's rule, `_hard_links`).
  - An ACL `deny delete` on the file, `deny delete_child` or mode 0555 on the folder: the swap and the rename answer `EACCES`; `access(_DELETE_OK)` sees it first. A `uchg` file: the swap and the unlink answer `EPERM`; reading works.
  - NFC and NFD: APFS (both variants) stores the spelling given and finds the other normalization (normalization-insensitive); `F_GETPATH` answers the stored spelling. HFS+ stores NFD whatever is given, so a folder made under an NFC name answers NFD from `F_GETPATH`. **HFS+ has no `RENAME_SWAP`** (`can_swap` False; a swap answers `ENOTSUP`; `RENAME_EXCL` works), so today a save on an HFS+ volume is refused before anything is written, like exFAT; the NFC point matters once BL-0160's fallback lands. A case-only rename of a folder changes what its open handle reports (`Led` → `led`).
  - A FIFO at a temp or restore-temp name: `read` refuses it without blocking (`EINVAL`), an exclusive create over it answers `EEXIST`, `unlink` removes it.
  - A folder moved away and replaced by a link: a handle opened before reports the moved folder; one opened through the link reports the link's target.

## Decisions
- **Where the restore lives** (agent): `ledger_engine.ledger.restore` (effects through the port) and `ledger_engine.ledger.core.recovery` (the pure judgement, §12's "recovery check per file"). The writer imports the restore for its rollback, so what both need (the handles with the path guard, the owner's hard-link and no-swap rules, `sha256`) moved to `ledger_engine.ledger.handles`; keeping them in `writer.py` would have made an import cycle. The rules are unchanged, each still in one function (`handles.hard_links`, `handles.volume_without_swap`); ADR-0013's amendment named the old place, so a pointer line was **appended** to it (no change to the decision; flagged to the orchestrator, since ADRs are append-only and the owner owns them).
- **`.resolved` carries no reason** (agent; S0060 left it open): §6.5's `.resolved` has only one reason (`not_saved`), so no encoding is needed; a second reason, if one ever comes, gets a suffix of its own.
- **The restore temp's `<job>` is the save's job** (agent; §6.4 writes `.<name>.ft-restore-<job>.tmp` without saying whose job): every try (the rollback and each recovery) then names it from the record alone, so a leftover of a try cut off by a crash is found and deleted without a listing. The save refuses a target at a restore-temp name and an entry standing at one before its first effect, and strict decode refuses a record naming one as a path (recovery deletes restore temps without a check).
- **The save's temps beside files at post are checked again and removed before the files are restored** (agent; §8.1 step 3 lists the restore first): if an editor that held the displaced file open writes into that temp after the checks (S0060 red team finding 2), the stop then happens while the file still holds post, so the next try's temp rule keeps the outside bytes; in the spec's order the file would already be at pre and the next try would delete the temp "whatever it holds".
- **Every folder the record names is synced before `.resolved`** (agent; found by this slice's crash-during-recovery sweep before landing, test `test_a_crash_at_every_effect_of_recovery_then_recovery_again_resolves`): a second try that finds every file already at pre writes nothing, so "every changed directory" read as "changed by this try" left the first try's restore swaps and removals unsynced under a durable `.resolved` (a power loss could then show `.resolved` beside a file at post or a temp of ours). The model's `RS_Sync` already syncs every file the journal names; the code now does the same, and spec §8.1 says so. A directory sync with nothing to flush costs nothing (§6.2).
- **The rollback leaves the file whose outside save the save kept as it is** (`skip`, agent, from §6.4 "In a save, the other files are rolled back and the journal resolved" and the model's `ctl.skip`): the file a swap-back put an outside save back into, and a file that appeared at a created path. Its temp may only be absent or hold our post bytes; anything else (the S0060 r2 M1 case, a second outside save in the temp) stops the restore before it writes anything, so the writer needs no special case for it.
- **Only the folders the save made are removed by its rollback** (`made`, agent): the writer records a folder as made before its `mkdir` (a `mkdir` that answers an error may have happened) and takes it back on `EEXIST`, so an empty folder another program made first is never removed. Recovery, which cannot know, removes every recorded folder that is empty (no bytes can be lost).
- **A failed close is rolled back** (agent; S0060 verifier Q1): the restore renames `.closed` back to `.open` and syncs before restoring any file. Retrying the failed sync and trusting it was rejected (a sync that failed once can answer success the next time without the data having reached the disk). The double failure that remains (the reopening's sync fails too) is told "could not finish" while the disk may keep the saved change; stated in spec §15, and on BL-0151's row for slice 4's text.
- **Stop causes found at the checks are `stopped`, I/O errors from the first write on are `failed`** (agent, from §8.1's wording: step 2 "Any failure ... counts as unrecoverable", step 3 "An I/O error during a restore ... reason `failed`"). A file to restore with a second hard link, a lock flag or a permission or volume that would block the swap stops at the checks (the owner's hard-link rule applied to the restore swap: probed on APFS, it would leave the other link at post).
- **Two checks removed as redundant** (found by mutants, EP-30): the restore's check of what the swap-back would displace (both outcomes keep both outside saves and stop; the swap-back now always happens once, as §6.4 says) and a second kind check of a temp at removal (step 2's judgement already refuses a non-file there; a folder makes `remove` refuse, and a link or FIFO holds no bytes); a per-folder sync after each `rmdir` (the final sync of every created folder's parent covers it).
- **HFS+ has no swap** (probe, before coding): `can_swap` answers False and a swap answers `ENOTSUP` on macOS 26.6.2, so a save on an HFS+ volume is already refused before anything is written, like exFAT (the owner's rule covers it by the volume's capabilities, not by a list). Spec §11 and §15 and BL-0160 now name HFS+. The NFC-on-HFS+ path-guard point is fixed anyway (`same_path`) and tested on the fake's NFD-storing volume; it matters on a real volume once BL-0160's fallback lands.
- **Deviations from ENGINEERING.md:** none known. Two tests use `monkeypatch` on the fake's `MemDir.stat` to inject an error at a read the fake does not number as an effect.
