# S0152: The undo and the create's cleanup remove a folder they made that OneDrive marked read-only (BL-0283; M1b)

## Brief
- **Goal:** on Windows, a folder that a save, a create or a copy made, and that OneDrive then marked read-only, is removed by the undo (the rollback and recovery's try) and by the create's cleanup, as on any other disk. Today every such removal fails, on every try, so recovery after a crash in a OneDrive folder never resolves (INV-32) and a stopped create leaves its folders and says "check the folder". macOS and Linux: byte for byte unchanged.
- **Why (the owner's hand check, 2026-11-26,** Windows 11 with OneDrive, `next` at c2d7fe17; the report stays outside the repository): S0151 works on real OneDrive (the open, the save, an 8-save burst, the rebuild, freed-up files downloaded online, the offline, paused and Q1 refusals naming the file; Q2 ended `NotOpened(INTERNAL)`, the outcome S0149 recorded, BL-0310). S0151 round 1's open question RT-2 is confirmed: a folder made in the OneDrive folder got `READONLY` from OneDrive within 2 s (attributes `READONLY, DIRECTORY, REPARSE_POINT`, in sync); removing its file worked; `rmdir` of the folder was refused, `PermissionError` "Access is denied" (5). The Windows adapter's `rmdir` does not clear the attribute, and its `stat` marks only files `locked`, so no check before the effect sees it. S0132's P7 measured on the runner that Windows refuses to remove a read-only folder and removes it once the attribute is cleared; on OneDrive that "clear, then remove" works is not proven yet (OneDrive might set it again): the hand check's new line asks it.
- **Implements:** the owner's decision of 2026-11-26 (below); engine-jobs §8.1 step 4 (the folders the save made are removed), §8.2 (the create's cleanup removes what it made), §6.1 (the rollback); ADR-0069 (Windows write semantics; a dated amendment, this slice); ADR-0015's amendment of 2026-11-18 says only the mirror's publish clears the attribute: a dated pointer amendment, this slice; IMP-0078 (outcome exact, cause best effort).
- **Capabilities:** none changes status (the write path on Windows is BL-0087's and BL-0283's).
- **Invariants touched:** INV-32 (recovery resolves), INV-01 (no ledger byte lost or torn: the clear never touches a file, never a folder that is not ours), INV-22 (truthful outcome: a removal that still fails after the clear is an `OSError` at the effect, told as today), INV-23 (no path, SID or machine name from the owner's report in the repository).
- **Risk class / lane:** High / full.
- **Review row:** hardening an existing write path (the undo's and the cleanup's removal of a folder): the verifier; the data-safety red team joins on an (a) finding; a fresh round after any product fix.
- **The bytes it protects:** the state the undo and the cleanup leave in the ledger's folder (the folders a save or create made, removed, so recovery can mark the journal `.resolved` and writes resume), and the truth of "undone", "not created" and "resolved". The ledger files' own bytes are already put back before any folder is removed; this mechanism protects none of them and must never touch them: it clears the attribute only on a folder of ours, never on a file (whose read-only attribute the save's `locked` refusal relies on) and never through a link.
- **Which real setup needs this, and can a policy forbid the rest?** Every OneDrive folder on Windows (the owner named typical OneDrive setups supported on 2026-11-21, decision D). The policy options went to the owner before coding: (2) refuse new folders in OneDrive, (3) leave the folder behind; the owner chose (1).
- **Has this mechanism or its family needed two or more fix rounds before?** The family yes: `clear_readonly` itself (S0132: round 1 V1, F1 the linked file, F3, F4; the owner's "Never clear a linked file (Recommended)") and the OneDrive folder rule (S0151: two rounds). So the owner chose the policy before coding (above), and this slice reuses S0132's clearing and S0151's ownership checks instead of adding a new kind of check.
- **Scope (inventory by behaviour, every `rmdir` in product code at the base, `git grep`):** 5 call sites: `ledger/restore.py` `_restore_all` (the rollback's and recovery's undo: the folders the record's `created_dirs` names), `ledger/create.py` `Run._cleanup` twice (a folder the run made, and the target when the run made it; the copy runs on the same writer), `ledger/history.py` `_remove_backups` (a backups folder in the app folder), `mirror/publish.py` `_remove_tree` (already clears, S0132). In: the first three. Out: the history trim (the app folder is in `%LOCALAPPDATA%`, never in OneDrive by default; the trim never fails the save and retries at the next trim; refuse first: no accommodation for a setup no one asked for) and the publish (already clears).
- **Acceptance tests (fail on 9418914f unless tagged):**
  - `engine/tests/fakes/test_memfs.py`: the fake's Windows mode removes a read-only folder only when the caller says it is its own (`rmdir(name, made=True)`), clearing the attribute first; without it refused as before; POSIX mode ignores the flag (`@regression-guard`); a folder that new folders inherit OneDrive's read-only mark from (`outside_new_folders_read_only`) gives it to each folder the port makes.
  - `engine/tests/ledger/test_onedrive_saves.py`: the OneDrive world marks every folder made in it read-only (as OneDrive does), so its existing rollback, recovery, create and sweep tests meet it (they fail on the base); new: recovery after a crash resolves and removes the read-only folder the save made; the rollback removes it and says "not saved"; the create's cleanup removes the read-only folders it made and names nothing kept; must-not-pass: an outside read-only folder (the ledger's own `inc/`, a create target that was there before) is never cleared and never removed; a folder the record names that now holds another entry, and a made folder replaced by another, are kept with their mark (`@regression-guard`: held on the base, where nothing was cleared); the POSIX world's `uchg` made folder still stops recovery with `permission` (`@regression-guard`).
  - `engine/tests/architecture/test_mirror_only_relaxations.py`: `rmdir(..., made=True)` appears only at the three reviewed sites, with a literal `True`; a planted call elsewhere is found.
  - Windows runner (`engine/tests/fs/test_windows.py`): the adapter's `rmdir(name, made=True)` removes a read-only folder (`SetFileAttributesW` through `os.chmod`), `rmdir(name)` still refuses it; a junction to a read-only folder: `ENOTDIR`, the target still read-only; a save that makes a folder, a crash before the close, the made folder set read-only, recovery resolves and removes it, an outside read-only folder (`inc`) left read-only. These run in the next manual CI run.
  - `backend/tests/test_windows_hand_check.py`: the `made_folder` step reports `clear_readonly` and `rmdir_after_clear`; with `--auto` on Windows the script sets the folder read-only itself (no OneDrive on the runner), so the clear-then-remove path runs there.

## Decisions
- **Owner, 2026-11-26, in session, the made folder:** offered "On Windows, the undo and the create's cleanup clear READONLY on a folder this save or create made (named in its journal) just before removing it, as the mirror already does for its own files (clear_readonly). Small slice under BL-0283; runner test with a read-only folder, plus one hand-check line (clear, then remove, in OneDrive)." with the options, cheapest first, (1) this one, (2) "Refuse new folders in OneDrive", (3) "Leave the folder behind". Owner: **"Clear it, then remove (Recommended)"**.
- **Owner, 2026-11-26, in session, the rows:** offered "Close BL-0087 now: Windows saves, opens and recovery behave as built on real OneDrive. Keep BL-0283 open until the made-folder fix lands and one short hand-check rerun confirms it." Owner: **"Close 0087, 0283 after fix (Recommended)"**. So this slice closes BL-0087 (its last items, the docs on the docs repo's `v0.4` branch, landed as e19e80e there, and the owner's check by hand, reported 2026-11-26), and BL-0283 stays in progress until the owner's short rerun after S0152 lands.
- **One form, at the port: `DirHandle.rmdir(name, *, made: bool = False)`** (agent; the brief's "prefer one place"). The caller states that the folder is its own job's; the adapter does the clearing where it holds the object. Rejected: a call to `clear_readonly` before each `rmdir` (three scattered pairs, and the clear and the removal would open the name twice, so a folder put at the name in between could be cleared: the very thing "never clear an outside folder" forbids); a new port method (`rmdir_made`) beside `rmdir` (two names for one removal; `made` keeps the default `rmdir` byte for byte as it was). The publish's `_remove_tree` keeps its own `clear_readonly` (S0132; it clears files too, under the linked-file rule): unchanged.
- **The Windows adapter clears on the object it opened for the removal** (agent): `rmdir` opens the folder for `DELETE` without following a link (as before), refuses a reparse point (`ENOTDIR`, as before), then, only with `made` and only when the attribute is set, opens the same object again relative to that handle with an empty name (`_nt_open(..., h.handle, "")`, as `_reopen` does for a folder handle) for `FILE_LIST_DIRECTORY | FILE_READ_ATTRIBUTES | FILE_WRITE_ATTRIBUTES`, lists it, and writes `FileBasicInfo` without the read-only bit (S0132's code, now `_unset_readonly`, shared with `clear_readonly`), then deletes through the first handle. Write access to the attributes is asked only when needed, so a folder that grants deletion but not attribute writes still goes as before when it is not read-only.
- **Never on a folder that holds an entry** (agent; found by this slice's own must-not-pass test): the restore removes every folder the record names and relies on `ENOTEMPTY` to keep one that holds another program's entry (`_restore_all`: `removable` is every recorded folder; `_check_folders` only skips such a folder in step 2). The first build cleared the attribute before the removal answered `ENOTEMPTY`, so such a folder lost its mark (`test_S0152_must_not_pass_a_read_only_folder_the_record_names_that_now_holds_another_entry_is_never_touched` failed). Now the adapter lists the folder first and answers `ENOTEMPTY` with nothing cleared; the fake checks `ENOTEMPTY` before the clear. **Limit:** an entry another program adds between the listing and the removal, or another failure of the removal (a sharing violation), leaves the folder without the attribute, which stops only the folder's own removal (stated in the adapter's docstring).
- **No retry, no fallback** (agent; PROCESS.md, refuse first): a removal that still fails after the clear (OneDrive setting the attribute again in between, if it ever does) is an `OSError` at the effect, told as today: the rollback leaves the save unfinished, recovery's try `failed` (`io_error`), Retry tries again. Rejected: `FILE_DISPOSITION_IGNORE_READONLY_ATTRIBUTE` (one call, but only with the POSIX disposition, which FAT32 and exFAT refuse, so a second path; and not what the owner chose).
- **Out of scope, by the inventory** (agent): the history trim's `rmdir` of a backups folder (in the app folder, `%LOCALAPPDATA%`, never in OneDrive by default; the trim never fails a save and retries at the next trim; no one asked for an app folder in OneDrive: refuse first) and the publish's (already clears).
- **The fake marks a new folder at once** (agent): OneDrive marks it within 2 s; the fake's mark at the `mkdir` is the earliest it could come, so every later effect meets it. A read-only folder still takes new entries in Windows mode (S0132's P7), so the save itself is unchanged; only the removals meet it. The world sets it on every folder of the OneDrive tree (`worlds.in_onedrive`), so every existing OneDrive test (the rollback, recovery, the create, the four sweeps) now runs with it.
- **The hand check's line runs the engine's own port** (agent; cheaper and stronger than the offered "clear, then remove" in Python): when Python's `rmdir` of the made folder is refused, the script runs `rmdir(name, made=True)` in the engine's interpreter with its placeholder mode pinned (`engine_rmdir_made`, `recorded_mark`'s way), so the owner's rerun tests the product's code in the engine's mode in real OneDrive. Not added: a save that makes a folder and is then undone through the product's path: the test producer only edits existing files, and an undo needs a failure in the middle of a save, which the product offers no way to cause (a fault hook in the product would be new surface for a hand check). With `--auto` on Windows (the CI runner, no OneDrive) the script sets the attribute itself, so the backend's Windows job runs the clear-then-remove path.
- **ADR:** ADR-0069 amended (the Windows write semantics, the owner's decision and what was built) and a pointer amendment on ADR-0015 (its amendment of 2026-11-18 said only the mirror's publish clears the attribute).
