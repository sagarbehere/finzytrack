# S0113: one platform-neutral adapter selection, and the type check once per platform

## Brief
- Goal: the M1a exit CI run on Linux (S0112) fails strict pyright: 51 errors in `engine/src/ledger_engine/fs/darwin.py`, 19 in `engine/tests/fs/test_darwin.py`, 7 in `backend/tests/test_main.py` (macOS-only names). Root cause: the adapter selection `for_this_os()` lives inside the macOS adapter, ten engine modules import it from there, and its docstring promises `UnsupportedPlatform` off macOS while the function returns `DarwinFS` unconditionally (the refusal sat in `DarwinFS.__init__`). Fix the structure: one neutral selection point; the macOS adapter states its platform once; the type check runs per target platform in T0 and T1.
- Implements: the plan the orchestrator proposed to the owner on 2026-11-13 (agent decision: it changes no pinned configuration and adds a gate pass, a tightening; the owner's "I agree with the ownership rule, go ahead" of that day answered the M1b splicing question, not this plan): (1) `ledger_engine.fs.this_os` with `for_this_os` and `legacy_locks_for_this_os`, `UnsupportedPlatform` (an `OSError`, `ENOTSUP`, as before) off macOS; nothing outside `fs/` imports `fs.darwin`; (2) `fs/darwin.py` raises `ImportError` at its top off macOS; its tests skip at module level; the backend's three sites skip per test; (3) `pyright --pythonplatform` per platform in `.githooks/pre-push` and `ci.yml`, configs untouched. ARCHITECTURE.md §2 (engine tree, ports table), §10 (pyright row); spec engine-jobs.md (Where the code is).
- Capabilities: none changed.
- Invariants touched: none (INV-01's write path is unchanged on macOS; INV-24 untouched).
- Risk class / lane: Medium / full (engine write path's import structure; no new write, no new outcome text). Review budget rows: "Other product code" for the engine and backend parts (verifier; fresh round after any product fix); "Tooling, gates" for the gate part.
- Bytes it protects: none new; on macOS every write goes through the same `DarwinFS` as before. Off macOS the outcome stays "refused before any file operation" (`UnsupportedPlatform`).
- §3 step 2: Which real setup needs this, and can a policy forbid the rest? The Linux CI runner (M1a exit) and the coming Linux/Windows ports (BL-0087); the policy "macOS only until BL-0087" is kept, and this slice makes it explicit in one place. Has this mechanism or its family needed two or more fix rounds before? No: the selection was written in S0060 and not reworked since.
- Acceptance tests: `engine/tests/fs/test_this_os.py` (both selections refuse `linux` and `win32` with `ENOTSUP`; on macOS they are the macOS adapters; in a fresh interpreter whose engine modules see `linux` or `win32`, the engine imports, answers handshake and ping, refuses the port, never loads `fs.darwin`, and `fs.darwin` refuses to be imported); `engine/tests/architecture/test_platform_selection.py` (no module of `src/` but `fs/this_os.py` imports `fs.darwin`, any spelling); `scripts/tests/test_pyright_platforms.py` (the script runs each platform, fails on any one failing, fails closed without pyright; the hook and both CI jobs call it). Also: `pyright --pythonplatform Darwin` and `Linux` at 0 errors for both packages.
- Expected doc impact: ARCHITECTURE.md (engine tree `fs/`, ports table, pyright row), `engine/CLAUDE.md` (gates, platforms), `fs/port.py` and `fs/__init__.py` docstrings, spec engine-jobs.md (Where the code is), PROCESS.md §6 (T0 pre-push types), IMPROVEMENTS.md (IMP-0074), backlog (BL-0260). No generated doc changes.
- Open questions: `design/inbox/answered/20261113-windows-type-check-pass.md` (non-blocking; see Decisions).
- Base: 9528d7f5.

## Decisions
- **Windows left out of the per-platform check** (agent; owner asked: `design/inbox/answered/20261113-windows-type-check-pass.md`). The plan named Darwin, Linux and Windows, all at 0. Measured at the base: Windows gives 292 engine and 280 backend errors; after this slice still 142 and 262, all POSIX-only names in product code with no Windows port yet (`app.platform.adapters.engine_group`, `engine_client`, `app_folder`, `ledger_engine.protocol.server`, `ledger.fingerprint`: `os.killpg`, `getpgid`, `signal.SIGKILL`, `fcntl.flock`) and their tests. Getting them to 0 means deciding the sidecar's Windows behaviour now, which is BL-0087's product work, not this refactor. `PLATFORMS = ("Darwin", "Linux")`; BL-0260 (M1b, with BL-0087) adds Windows. Linux, the platform of the failing CI run, is green.
- **The neutral point is a module, `fs/this_os.py`, not `fs/__init__.py`** (agent): every `import ledger_engine.fs.port` runs the package's `__init__`; selecting there would load the macOS adapter (and `ctypes`) with every port import, and `darwin.py` imports `port`, a cycle through the package.
- **`UnsupportedPlatform` moved to `this_os`; `DarwinFS.__init__`'s own platform check removed** (agent): the module-level `ImportError` guard states the platform once; the class can no longer be reached off macOS. On macOS nothing changes: `for_this_os()` still returns `DarwinFS(on_fallback)`, `legacy_locks_for_this_os()` a `DarwinLegacyLocks()`.
- **Pyright follows a `raise`, not a call** (agent; probed with pyright 1.1.414 in the scratchpad): after a module-level `if sys.platform != "darwin": pytest.skip(..., allow_module_level=True)`, or even a call to a helper declared `NoReturn`, pyright on Linux still checks every function defined later in the module (a call ends only its own scope's statements). After `raise ...` it leaves the rest, function bodies included, unchecked. So the tests guard with `raise pytest.skip.Exception(MACOS_ONLY, ...)` (engine: `tests/macos_only.py` holds the reason and the rule; backend: `MACOS_ONLY` in `tests/test_main.py`). This deviates from the brief's `pytest.skip(...)` wording, for that reason.
- **Lazy `DarwinFS()` in four engine tests replaced by `for_this_os()`** (agent): `test_recover_ops.py`, `ledger/test_paths.py`, `ledger/test_history_trim.py` and `scripts/measure_save.py` only needed the real port; the same object on macOS, and no adapter name for pyright off macOS. `test_create_ops.py` patches `DarwinDir` methods, so it keeps its local import behind a `raise` guard.
- **`test_fingerprint.py`'s port check reads the dataclass default** (agent): it built `CopyPorts(fs=for_this_os(), legacy=DarwinLegacyLocks())` only to read `file_state`; off macOS that raised (before and after). It now reads the field default from `dataclasses.fields(CopyPorts)`, which asserts the same thing on every OS.
- **`test_legacy_lock.py` now skips off macOS** (agent): it ran on Linux before (plain `flock`), but imports the macOS adapter, which now refuses to load there; the product never uses it off macOS (Copy refuses with `UnsupportedPlatform` first). Not an enforcement file (INV-26 is pending, BL-0026).
- **The off-macOS subprocess test loads the stdlib and dependencies with the real platform first** (agent): patching `sys.platform` before the first import broke the standard library (`sysconfig` names a module after the platform; `shutil` imports `_winapi` on `win32`). The child imports the engine once for real, drops every `ledger_engine` module from `sys.modules`, sets the platform, and imports the engine again: only the engine's own modules see the other OS.
- **Round 2: the 10 Linux failures of the CI run of 2026-11-13** (agent; `t1 / engine` at 7219c44b, the first run of the engine's tests on Linux since M0). Per test:
  - `test_load_rule.py`, both tree scans (2 failures): platform-neutral by intent. The scan resolves every engine import at run time and reported `fs/this_os.py`'s guarded `from ledger_engine.fs.darwin import ...` as unresolvable, since the adapter refuses to load off macOS. Fixed in the test: off its OS an adapter (`ADAPTER_OS`, which must name every adapter of `fs/`, read as in `test_platform_selection.py`) is a leaf the scan does not follow; its own source is still scanned, a star import from it is refused, and on its own OS nothing changes. No product change: `this_os` imports the adapter only under `sys.platform == "darwin"`.
  - `test_no_resident_ledger.py`, 5 errors: the jobs it runs (open, save, rebuild) need the real port, so it is macOS-only (INV-10's own statement is platform-neutral, but every loading job refuses off macOS before it loads, so on Linux it would check nothing). It already meant to skip there, with `unittest.skipUnless(sys.platform == "darwin", ...)`, the one skip form `check_invariants.py` allows in an enforcement file; but on a plain function that form fires only when the function is called, after its fixtures, and the shared `setup` fixture publishes through the port. Not new since S0113: before it, `DarwinFS()` in the same fixture refused off macOS too. A module `skipif` mark was tried first and refused by `check_invariants.py`; widening that guard was not needed: the fixture's body is now `test_save_ops.save_setup`, which these four tests call first in their body (before any plant, as the fixture ran), so the allowed skip fires before anything needs macOS. `check_invariants.py`'s docstring now says so. A scan of every test under `engine/tests`, `backend/tests` and `scripts/tests` found no other `skipUnless`/`skipIf` test taking a fixture beyond pytest's own.
  - `test_plugin_fingerprint.py::test_the_overlay_load_and_the_real_load_record_the_same_imports`: platform-neutral (Beancount's load and the imports it records). Its child made `rebuild.Ports()` only to call `.load`, and the dataclass makes the file-system port too, which refuses off macOS. The child now reads the `load` default from `dataclasses.fields(rebuild.Ports)`, the same function on macOS (the round-1 precedent of `test_fingerprint.py`). The product needs no change: the rebuild job needs the port.
  - `test_engine_lock.py`, the two S0102 `replaced` cases: not the port. `hold_engine_lock` checks the app folder with plain `os.open`/`fstat` (`st_dev`, `st_ino`), no macOS call. On the CI runner's temp folder the folder removed and made again at once took the freed inode number, so the identity of the start matched and the engine took its lock (the subprocess answered handshake and ping, exit 0, not 4); `removed` passed there. APFS does not reuse the number. So the check cannot see that replacement on such a Linux file system: a product limit for the Linux port, the same family as engine-jobs §6.1 step 8 limit (4) (FAT), now BL-0262 (M1b, with BL-0087), and the spec's limit (4) names it. The `replaced` cases skip off macOS citing BL-0262; a new case `moved aside` (the old folder moved away, the new one made while it exists, then the old removed: another object on any file system) runs everywhere, for the lock and for the engine's exit 4, so the refusal stays checked on Linux. BL-0261 is not widened: `hold_engine_lock` does not go through `app_folder.changed` or the port.
  - What could and could not be verified locally (no Linux here): a scratchpad script (not committed) runs pytest with the engine's own modules seeing `sys.platform == "linux"` (the stdlib and dependencies loaded for real first, as `test_this_os.py`'s child does). On the base it reproduced 7 of the 10 exactly (the two scans and the five errors; skipped count 368, as in CI); the fingerprint failure was reproduced by running its child script the same way (`UnsupportedPlatform` on the base, a fingerprint after the fix); the two `replaced` cases cannot be reproduced on APFS, so their cause is inferred from the CI log (identity equal after `rmtree` + `mkdir`, `removed` passing) and not observed here. The whole engine suite under the simulation: base 2 failed, 5 errors, 9545 passed, 368 skipped; after the fix 0 failed, 9556 passed, 375 skipped (the 5 resident-ledger tests and the 2 `replaced` cases; 11 new tests). The real proof is the next Linux CI run.
- **One script for the per-platform check, `scripts/pyright_platforms.py`** (agent): the platform list lives in one place for the hook and both CI jobs; the passes run in parallel (measured: engine about 8 s, backend about 7 s, both passes). The hook keeps its labels "pyright" and "pyright (engine)", so the gate timer's history continues.

## Hand-off (PROCESS.md §3 step 4; ADR-0057)
- Checks that accept, tag or refuse, each with its must-not-pass test:
  - `this_os.for_this_os` / `legacy_locks_for_this_os` refuse off macOS → `test_other_operating_systems_are_refused[linux|win32]`, `test_off_macos_..._never_loads_the_macos_adapter[linux|win32]`.
  - `fs/darwin.py`'s import guard → the same subprocess test (`imported == "refused"`).
  - The architecture scan → `test_every_spelling_of_an_adapter_import_is_seen` (seven spellings caught, three plain imports passed), `test_only_the_selection_point_imports_an_adapter` (failed on the base with the ten callers).
  - `scripts/pyright_platforms.py` → `test_one_failing_platform_fails_the_check_and_names_it`, `test_a_missing_pyright_fails_closed`; wiring → `Wired.test_pre_push_and_ci_run_the_per_platform_check_for_both_packages` (also refuses any remaining single-platform `.venv/bin/pyright` run).
- Self-mutation (`scripts/mutants.py`, plan in the session scratchpad; the selection guards the write path's port): 7 tried, 7 killed: the port or the locks chosen as macOS on every OS, the adapter imported unconditionally, the adapter's guard switched off, the wrong `errno`, `protocol/copy.py` importing the adapter at module level, `protocol/save.py` importing it lazily by a relative import. No survivor. The gate script: no mutants (tooling; optional).
- Round 2 checks: the load rule's leaf (`off_its_os`) → `test_on_its_own_os_an_adapter_that_cannot_load_is_still_found` (three spellings), `test_off_its_os_a_star_import_from_an_adapter_or_another_missing_module_is_found`, `test_every_adapter_names_its_os`; the leaf itself → `test_off_its_os_an_adapter_is_a_leaf_of_the_scan` (5 spellings) and `test_off_macos_the_selection_point_passes_the_scan`, both failing on the base (6 failures, run against the base scan with the new tests). The engine-lock `moved aside` cases are `@regression-guard`-style (they pass on the base; they keep the refusal checked off macOS). Self-mutation on the leaf (the load rule guards INV-02, which load produces finance results): 5 tried, 5 killed (the leaf on every OS, the leaf for any `fs` module off macOS, a star import accepted off its OS, the `from ledger_engine.fs import darwin` leaf and the plain-import leaf removed). A first plan had a survivor (the leaf for `from <package> import <adapter>` removed): the simulation left the package's `darwin` attribute in place, so the case passed for the wrong reason; the simulation now deletes it, and the mutant is killed. A dead branch (an unimportable `ledger_engine` package) was removed rather than tested.
- Population: the callers of the old selection were found by behaviour, by searching every import of `ledger_engine.fs.darwin` in any spelling over the engine's `src`, `tests` and `scripts` and the backend: 10 product modules (all moved to `this_os`; the architecture test now holds 0), 12 test files and 1 measurement script (moved, or guarded where they test the adapter itself: `fs/test_darwin.py`, `fs/test_legacy_lock.py`, `test_create_ops.py`). Linux pyright errors: engine 70 → 0, backend 7 → 0; Darwin stays 0.
