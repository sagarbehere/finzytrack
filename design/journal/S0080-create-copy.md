# S0080: The `create` job (engine jobs piece 5, first cut)

## Brief
- Goal: BL-0153, engine-jobs piece 5 (BL-0109): the `create` job of `design/specs/engine-jobs.md` §8.2, from the request to the job's answer: an empty target, exclusive writes, read-back, the load check, the commit point, the `.finzytrack/` folder written last, the delete advice, and the answer read from disk after an engine death. Owner, 2026-11-07: "Yes, proceed" (to starting BL-0153 next).
- **Cut (the slice is too big for one hand-off):** this slice builds `create`. `copy` moves to a new row, BL-0196: it needs its own design work that `create` does not (reading the source ledger set inside the job, the refusal when any `.open` journal names a source, the legacy-lock try and re-check of ADR-0062 and BL-0026, documents, and what "loads the same" compares). A create whose ledger stays outside the folder (ADR-0017's external reference, no ledger file written; the load check then reads the user's own ledger, whose errors are advice) is a new row too, BL-0197. Step 8, registering the new workspace, needs the registry and `assess_workspace` (BL-0102, M2): the job answers `Created(folder)` and the caller registers it; `CR_Register` stays planned under BL-0102.
- **What a create is in this slice:** the sidecar sends the target folder, the workspace's files (relative paths and bytes: the starter ledger and anything else in the folder), which of them is the ledger's root, and the files of `.finzytrack/` (the manifest `workspace.json` with a new lineage id, made by `app.workspaces.creation` over the pure `manifest.encode_manifest`; settings later). All of this text is Finzytrack's own. Who builds it (the wizard, "New workspace", the demo) is M3's.
- **The engine's steps** (`ledger_engine.ledger.create`, op `create`, in a fresh engine holding the engine lock):
  1. the target: absent (made with an exclusive `mkdir`, its parent synced) or an existing empty folder; anything else is refused before anything is written (`not_empty`, `not_a_folder`, `no_parent`); the folder rule of §6.1 step 8 (`handles.folder_blocked`) on the folder written in (`permission`);
  2. no source to read (that is copy's);
  3. every folder made with an exclusive `mkdir`, every file with `DirHandle.create` (exclusive, its data synced), then every folder synced; a name that is already taken stops the job (`taken`), leaving the other entry as it is;
  4. read-back: every file equals its bytes (`read_back`);
  5. the load check: Beancount's own load of the root in the target (`beancount_port.real_load`), which must run, report no error and parse only files the job wrote (`load_failed`, `load_errors`, `load_outside`);
  6. the commit point (`gate`/`proceed`, §4);
  7. `.finzytrack.ft-<job>/` made, its files created and synced, the folder synced, renamed to `.finzytrack` with an exclusive rename (on a volume without it, a check that the name is free, then a plain rename: §6.8's accepted instant), the target synced. A `.finzytrack` that appeared meanwhile: our temp folder removed, the job stops (`manifest_taken`) and the foreign one is left as it is, except on a volume without the exclusive rename, where an empty folder put there in the instant between the check and the plain rename is replaced (§6.8's accepted instant; r1 RT8, spec Limit (no exclusive rename)).
  Every stop before step 7 lists the target once to give the delete advice: `wrote` (the job made something there) and `only_ours` (every entry is a name the job writes, holding its bytes or a prefix of them, the temp folder included).
- **Decision asked by the row: should `create` (and later `copy`) read its outcome from disk after an engine death? Yes.** The spec already says so: §1 "Commit point: … After the commit point the job finishes or is resolved from disk", and §8.2 "The manifest in place (step 7), not yet registered: an engine death leaves the job to register the workspace", which the job can only do if it knows whether `.finzytrack` landed. Today `scheduler._lost_outcome` answers `CHANGE_OUTCOME_UNKNOWN` for a create cut past its commit point while the disk can tell: after a `durable_sync` of the target, `.finzytrack` holds our bytes (created) or does not (not created). An answer of "unknown" for a workspace that is complete on disk sends the user to look for a folder they cannot see in the list. The read is the save's pattern (§6.6): the queue keeps the job (`outcome_owed`, now for every writing job), and the work asks a fresh engine for `create_outcome`. The same read after a death **before** the commit point gives §8.2's delete advice ("listed when the job stops"), which no other path can give. When no engine can be had: `CHANGE_OUTCOME_UNKNOWN` past the commit point (the folder may be a workspace), else "Not created" with "check it before you delete anything" (no listing).
- **After a Cancel** the engine has been ended, so nothing lists the folder: the text says "Not created", that the folder may hold an unfinished new workspace, and to check it before deleting anything. Spec §8.2's "listed when the job stops" is narrowed to the paths that can list (a refusal, a failure, an engine death read from disk); keeping the job after a Cancel to list in a fresh engine would add a queue state for advice only (EP-30: a policy covers it).
- **The bytes it protects:** the user's files in the target folder (a non-empty folder is refused before any write; a name that appears is never written over, nor is a `.finzytrack` another program put there), and the truth of the answer: "created" only when `.finzytrack` with our bytes is durable over files that were synced and read back; "you can delete it" only when the folder holds nothing but the job's own bytes.
- Implements: ADR-0064 (P2: write directly, read back, check, manifest last, the manifest write is the commit point), ADR-0063 decision 1 (app-scoped, writes only the new folder), ADR-0008 (exclusive writes, read-back; INV-22 fail closed), ADR-0067 decision 2's exception (all of a create's text is Finzytrack's own, so any Beancount error in it means our text is wrong: it blocks), ADR-0017 (the folder with `.finzytrack/` is the workspace; a new lineage id), spec §1, §2, §4, §8.2, §11, §13, §14.
- Capabilities: CAP-WS-CREATE, CAP-SETUP-FRESH (planned, M3; no status change: the job only, no screen or registry).
- Invariants touched: INV-01, INV-22 (every write passes the contract and fails closed), INV-27 (the folder with `.finzytrack/` is the workspace), INV-29 (nothing registered here). Writing only the new folder is ADR-0063 decision 1 (r1 correction: this line cited INV-30, which is "Opening never writes the folder"); a target inside another workspace's folder or the app's own is not refused yet (BL-0198).
- Risk class / lane: High / full (a new way to write user data). Red team: yes (the orchestrator's, before push).

  - backend `test_engine_queue.py`: a `create` whose engine dies is kept to read its outcome (`outcome_owed`), like a save.

## Decisions
- Copy, external-reference create and registration are cut out as above (agent; the orchestrator's brief allows the cut).
- The outcome after an engine death is read from disk, before and after the commit point (agent; justified in the Brief from spec §1 and §8.2).
- The load check refuses any Beancount error (agent): the files of a create are all Finzytrack's text, so ADR-0067 decision 2's exception ("an error showing that Finzytrack's own text did not parse as intended … blocks") is the rule here, and there is no preview to advise from. The external-reference create (BL-0197) is where errors would be the user's and advice.
- The load check uses `beancount_port.real_load` (Beancount's own loader, never decrypting), not the overlay: it checks the files as Beancount will read them; the load rule's architecture test gains `ledger/create.py` as a second home for the real loads (agent).
- The engine treats `.finzytrack/`'s files as opaque bytes; the sidecar makes the manifest (`manifest.encode_manifest`, `new_lineage_id`), so the format stays in one place (agent).
- An "empty" target has no entry at all; a folder holding only Finder's `.DS_Store` is refused (a stated Limit; the M3 folder picker decides whether to make a new folder instead) (agent).
- On a volume without the exclusive rename, the `.finzytrack` rename is a check that the name is free and a plain rename (§6.8's accepted instant; the rename of a folder over a non-empty one fails, so at worst an empty folder another program made in that instant is replaced) (agent).
- Phases: the create reports `saving` while it writes and `checking_change` during its load (§5.4's existing phases; no protocol change) (agent).
- The queue keeps every writing job whose engine died (`queue._engine_died`: `WRITING`, not only `save`; table version 10), and the scheduler runs a writing job's work after a failed first start (`scheduler._run`), so a create answers from disk. `scheduler._lost_outcome` lost its "past the commit point" branch: no writing job reaches it any more (agent).
- The manifest's bytes are made by the pure `manifest.encode_manifest`; the new lineage id and the `.finzytrack/` file list live in `app.workspaces.creation`, because the workspace format must stay pure (no `uuid`) and `app.platform` may not import `app.workspaces` (the import contracts) (agent).
- Three scheduler tests that pinned the old answer for a create cut by an engine death (`CHANGE_OUTCOME_UNKNOWN`, `ENGINE_STOPPED`) were rewritten: the generic scheduler now keeps the job for its work (`test_engine_scheduler.py::test_a_create_whose_engine_died_is_kept_for_its_work_to_read_the_disk`, `...whose_client_closed_is_left_to_its_work`), and the create's own answers moved to `test_create_job.py`. The API test's `CHANGE_OUTCOME_UNKNOWN` scenario now uses a save whose outcome no engine can read (it held on the base too: `@regression-guard`). These are deliberate changes of expected outcomes, not goldens; the old expectation was the gap BL-0153 named (agent).
- Tests first: the new and changed tests were run against f3759337's source (an archive of the base in the session scratchpad with the slice's test files copied in): engine 16 failed plus `tests/ledger/test_create.py` failing at import; backend `test_create_job.py`, `test_engine_protocol.py` and `test_manifest.py` failing at import, 4 queue cases (create, copy), 3 scheduler tests and the TLA map test failing. Passing on the base, as tagged `@regression-guard`: the API scenario above and the new line of `test_load_rule.py::test_a_planted_real_load_outside_the_rebuild_is_found` (the save stays no home of the real loads); the queue test's `save` cases are the old test's own. (agent)

Just before each removal, the entry must still have that identity. A file must also still hold exactly the job's bytes, read at most that length plus one.
