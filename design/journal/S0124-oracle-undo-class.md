# S0124: a class explains a booked difference only by undoing its own cause (M1b, ADR-0014 amendment of 2026-11-16)

## Brief
- Goal: build the ADR-0014 amendment of 2026-11-16 in the oracle (`scripts/oracle/classify.py`). Since S0123 the oracle compares Beancount's booked result of the old app's write with the intended change booked by Beancount. When the parsed comparison has tagged divergences with classes and the booked result still differs:
  1. take the old app's parsed result;
  2. **undo each tagged class's own cause** on it: for I2, remove the duplicated entries; for every other class, apply the change its eraser names, so the entry reads as intended;
  3. book that again with Beancount's own steps (`semantic_diff.book`, as the reference is booked);
  4. compare it with the intended booked result.
  - Equal: the booked difference is explained by those classes.
  - Not equal: what is left is UNEXPLAINED and blocks, as today.
  No class hides a booked difference by being present. S0123's exception for a FIX-L3-02 lot whose label or date was dropped (same units and costs) becomes a case of this rule: undoing the label drop must give the intended holdings.
- Then run the oracle on the repo's corpora and the demo (copies only, through the harness). Report the verdicts before and after, and update BL-0274: the nasty corpus's I2 cases (coffee and rent held twice, the pad's fill) should be explained if, and only if, removing the duplicates gives the intended booked result. Report each case that stays UNEXPLAINED, with its cause; do not reclassify it away.
- Implements: ADR-0014 and its amendment of 2026-11-16; INV-02; S0123's booked comparison.
- Capabilities: none changes status.
- Invariants touched: INV-02; INV-23, INV-24 (copies only; a T-local report carries counts, classes and case IDs only, no amount, account or lot; `copies.py` unchanged).
- Risk class / lane: Medium / full: tooling whose verdict decides promotion and checks money. Review budget row: **Tooling, gates, measurement**: one verifier round; the fix round fixes only a shape the check's own docstring or must-not-pass list promises to refuse, a false statement of fact, or a finding in a guard of real data or privacy; a High is always fixed.
- The bytes it protects: none; it reports. It must never let a booked difference pass that undoing the tagged classes does not remove.
- Mechanism questions (PROCESS.md §3 step 2): what is it a second opinion on? Whether the old app's result, its known faults undone, means what the intent says, in Beancount's booked terms. The owner chose this over keeping such cases blocking (2026-11-16). Fix-round history: the oracle's classifiers (S0002, S0123: one round each; S0122 reverted).
- Constraints: the legacy app is launched only by the harness, on copies. It never touches the owner's running v0.3 app or the owner's live data folder, and nothing is written into the legacy worktree. Never write that folder's path in any file.
- Acceptance (tests first; each fails on the base commit):
  - **must-pass:** nasty's I2 shape in a small ledger: glob entries duplicated into the root before a `pad`, which is explained once the duplicates are removed; a FIX-L3-02 label drop on a held lot (S0123's exception, now by the rule).
  - **must-not-pass:**
    - an I2 duplicate plus an unrelated money change, where the change is left after the undo;
    - a FIX-L3-02 label drop on a reduction that takes another lot (S0123's A1): undoing the label drop restores the label, so the sale takes the intended lot. If the undo can restore it, it is explained; say which, with the reason;
    - a class tagged on one entry while the booked difference is on another that the undo does not touch.
  - A T-local report carries no amounts.
  - The existing oracle tests stay green, or each change of expectation is listed under Golden changes with its reason.
- Expected doc impact: `classify.py`'s docstring (the rule); the write-path README's oracle line if it states the old rule; BL-0274 updated with the run.
- Open questions: none.
- Base: the commit that records the ADR-0014 amendment (this brief's commit).

## Decisions
- The rule is the owner's (ADR-0014 amendment of 2026-11-16; owner, 2026-11-16, in session: "I accept your recommendations for both questions.", accepting "b. Undo the bug, then compare").
- (agent) **The rule as built** (`classify.booked`, `apply_undo`): the booked results are compared first, as in S0123. Only when they differ and the parsed comparison recorded a cause to undo is the legacy's parsed result (the loader's own parse, now kept for the legacy's result too) changed by each cause's undo, booked again with `semantic_diff.book`, and compared again with the same per-entry and whole-result checks. Equal: no booked row, and the case's `undone` counts name the classes whose causes were undone. Not equal: every difference left is UNEXPLAINED, its note starting "after undoing <classes>:". No undo is recorded for UNEXPLAINED or NOT_APPLIED divergences, so they are never undone.
- (agent) **Each class's undo, from its eraser or its tag** (the brief's question "can each class's undo be defined from its eraser?": yes for every class; I3 has no eraser function and is defined from its tag, below):
  - I10, M28, FIX-L3-02, FIX-L3-05, FIX-L3-15 (a pair: an intended or untargeted entry and the legacy's version): the written entry with the erasers of its class set applied, in the order that made it equal to the intended entry (`classify.undone`), at the place the legacy wrote it. The erasers change the written entry's money only by taking the intended entry's value (units, cost with its label and date, price, an elision), so it books as the intended entry would at that place; metadata and text stay as the parsed comparison judged them.
  - I2, one per shape the parsed comparison tags: a copy left in its glob-included file is taken out (the nasty corpus's shape); an entry moved out of a glob-included file into the root goes back to its line there; an edit written into the root goes to the place of the entry it replaces in the glob file, and that entry, left in place ("glob-included file not rewritten"), is taken out. An I2 "intended entry not written" has nothing to undo, so its money stays a difference.
  - I3 (a generated entry the legacy persisted): taken out, so the load generates it again if it still does. I3 has no eraser: the parsed comparison tags a written entry I3 when a load generates the same entry. Taking it out is exactly the removal of that cause, the same shape as I2's copy, and it is what ADR-0014's amendment says ("removing that class's own cause"). **Consequence, for the orchestrator to confirm:** S0123's must-not-pass "a persisted plugin entry the plugin still generates" (the money held twice) is now explained, like I2's duplicate. Keeping it blocking would need S0123's stand-in rule back beside the undo.
- (agent) **The place is not a class's cause, except for I2.** An undone pair stays where the legacy wrote it, so a reprint that moves an entry past a same-date entry of another file stays a difference (S0122's tie; `test_the_undo_keeps_the_place_the_legacy_wrote_an_entry_at`).
- (agent) **S0123's three exceptions are gone, now cases of the rule:** a FIX-L3-02 pair left out of the per-entry check (`OWN_MONEY`), the end-inventory exception for a dropped lot label or date (`_identity_only`, which applied to every account once any FIX-L3-02 was tagged: `test_a_class_on_one_entry_does_not_explain_a_booked_difference_on_another` shows the balance row it hid), and I3's stand-in count.
- (agent) **The brief's A1 question** (a FIX-L3-02 label dropped on a sale, so FIFO takes another lot): **explained.** The undo puts `{"lot-b"}` back on the written sale, booking takes lot B as intended, and the booked results are equal. Its twin (buy A's cost also changed) is UNEXPLAINED with the lot left reported after the undo.
- (agent) **Reports:** `Report.undone` counts the causes undone per class; the harness writes it as `undone` per case and in the summary. Counts and class names only, so `redact` keeps it in a T-local report (`test_a_t_local_report_names_the_classes_undone_and_no_amount`).
- (agent) **Cost:** the harness now keeps the legacy result's parse (one more parse per case); the undo books once more only for a case whose booked results differ and that has a cause to undo.
- (agent) `model._placed` is now `model.placed` (the undo places entries the same way the reference does); a local variable that shadowed it is renamed.
- (agent) **Order inside the undo:** entries are taken out before others are placed, since an I2 edit goes back to the place of the stale entry it replaces (found by the first full test run: the stale entry's key was overwritten).
- (agent) **Stated limits** (`booked`'s docstring): an entry moved back to a file is ordered after that file's entries only for Beancount's full ties (same date, kind and line); where a file holds several instances of the undone key, the last one is taken.
- (agent, round 1) **I10 is pinned by the reference** (verifier F1, High): an intended entry (an edit's replacement, an import) now gets its booked form from the reference (the intended ledger booked by Beancount, built once in `compare` by `_reference`), so a number the legacy writes into an elided posting is I10 only when it equals exactly what Beancount books for the intended entry. Before, an intended entry had no booked form and `erase_i10` accepted any number; the undo then reset it and re-booking filled in the intended value, so a wrong number (`-10.54` for `-10.5`, inside Beancount's tolerance, no new error) was explained. Without a booked form, or where booking split the entry into more postings (a sale over two lots), nothing is accepted (the safe side: a correct number there is UNEXPLAINED, a stated limit). The false sentence in `erase_i10` ("the new-error check then catches a wrong number") is replaced.
- (agent, round 1) **Not loosened in this fix:** with the reference's booked form at hand, `erase_i10` could also accept a `{}` the legacy bakes on an intended entry when it equals the reference's lot (BL-0274's demo renames with a lot written with its booked date). That would loosen the parsed classifier in a fix round, so `{}` on an intended entry stays not accepted (`Ctx.intended`), as before S0124.
- (agent, round 1) **The other erasers** were checked for a value the reference could now pin: FIX-L3-02's `@@` price is matched exactly to the legacy's own rounding rule (`legacy_unit_price`), FIX-L3-05 needs numerically equal amounts, M28 and FIX-L3-15 touch metadata only, and I10 on an untargeted entry already uses its booked form in the source's load (the legacy bakes what it booked before the edit: the stale baked lot below). None accepts a number booking decides, so none changes.
