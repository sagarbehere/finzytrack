# S0096: The mirror's per-table checksums over the corpus

## Brief
- Goal: BL-0057's second half. Decide, with evidence, what a per-table checksum of the mirror over the corpus ledgers adds over the tests that exist, and build it only for what it adds (EP-30; owner's "tie complexity to the requirement").
  1. **What exists** (orient, checked in the code): `engine/tests/mirror/test_rows.py` (one test per row rule, each over a small hand-written ledger), `test_build.py` (exactness, completeness, the file), `test_commodities.py` (the `commodities` rows rule by rule), `test_inv21.py` (TransactionId, content hash and metadata JSON of the 12 INV-21 cases and the v0.2.2 install equal v0.2.2's goldens), `test_surface.py` (the DDL equals `surface.toml`), and `engine/tests/ledger/test_parity_corpus.py`, whose only mirror check is that the rows **build without a refusal** from every parity load case. No test holds the rows of the realistic ledgers (Beancount's 3,917-row example ledger and its variants, the plugin, include and documents cases, the write corpus) to any value.
  2. **Evidence: what the existing tests miss** (measured before building, `scripts/mutants.py`, plan in the session scratchpad). 18 plausible unintended changes seeded in `ledger_engine.mirror.core.rows`, one per table or rule (a quarter formula off by one month, zero balances kept, the lot order without its label, the training text not trimmed, options sorted, the latest `close` replaced by the earliest, an error's entry dropped, non-ASCII metadata unescaped, the document count by exact key, the first `commodity` declaration kept, a set's elements unsorted, the latest date not the maximum, the commodity usage dates not the extremes, `custom` values stringified, empty tags as `[]`, the tolerance dropped, an account's currencies sorted, prices as `str(Decimal)`), run against every engine test that builds a mirror (`tests/mirror`, the parity corpus, the publish, open and rebuild tests): **7 of 18 passed them all.** The same 18 against a corpus snapshot (built as below): 9 killed, 2 of them among the 7 (the quarter, the training text). Of the other 5: three are equivalent (options order: SQL row order is not part of the surface; the two date mutants: Beancount sorts the entries after every plugin, `loader.run_transformations`, so the first and last seen are the extremes), and two are gaps no corpus ledger reaches (a set in metadata, a price whose `str` has an exponent), closed with row tests from the spec. So the checksum adds catch power the row tests lack, and the row tests catch what the corpus lacks (lot labels, tolerances, a second `commodity` declaration, a second `close`): they are complementary, not redundant.
  3. **What a checksum adds, and what it does not.** It is a change detector, not a correctness check: its expected values are the build's own output (a characterization pin, EP-29), so it can only say "these rows changed", never "these rows are right"; the row tests and the INV-21 goldens stay the correctness checks. What it adds: (a) any change to any row of any table of any corpus ledger fails a gate, whatever caused it: the row code, the overlay load (BL-0123 changes its decimal context next), a Beancount or Python upgrade (ADR-0004; the parity corpus cannot see one, since the overlay and Beancount's loader change together), a plugin's handling; (b) a deliberate change shows its reach: which tables of which cases changed, and their row counts before and after, in the commit's diff of the snapshot. What it does not add: correctness. Determinism was probed: the rows are the same across runs once the temp path and Beancount's `input_hash` are normalized, **but not across hash seeds**: Beancount's `onecommodity`, `close_tree` and `commodity_attr` plugins word their errors and order their entries by set order (`parity/plugins-builtin`), so the generator runs under the engine's `PYTHONHASHSEED=0` (`app.platform.adapters.engine_client`), re-running itself when started otherwise (`check_generated.py` starts generators with `-I`, which ignores the variable).
  4. **The design** (only what (a) and (b) need):
     - **Corpus roots**, inventoried by behaviour, not by name (the file cover corrected after round 1, F2: every file of every case folder, whatever its name, is read by a load as an include, a document Beancount found or a plugin module it imported, sits in a refused case, or is named in `NOT_READ` with its reason; the first version counted only `.beancount`, `.gpg` and `.asc` files): every case row of `corpora/ledgers/write/cases.toml` and `corpora/ledgers/parity/cases.toml`, the parity corpus's generated cases (`parity.generated_cases`: Beancount's example ledger, split over a recursive glob, under custom roots, absolute paths, a missing root, a non-UTF-8 file), every case of `corpora/ledgers/inv21/`, the oracle's `nasty` ledger, and the two roots of the v0.2.2 install fixture. Exact cover check: every `.beancount`, `.gpg` and `.asc` file under `corpora/` is read by some root's load (Beancount's `include` list), is the refused file of a refuse case, or is named as unreached with its reason; and the snapshot's case set equals the inventory.
     - **Encrypted cases**: refused by the overlay load (ADR-0059), so no mirror; the snapshot records the refusal and the refused file (relative), so a case that starts loading, or stops, fails.
     - **Plugin cases** load under `parity.fresh_plugins`, so each case imports its own plugin module.
     - **Normalized**: the case folder's absolute path becomes `<case>` in every text value (metadata JSON `filename`, `documents.filename`, `ledger_errors.filename`, the `filename`, `include` and `documents` options), and `ledger_options.input_hash` (Beancount's MD5 over file names and modification times) becomes `<input_hash>`; the build date and the stamp are fixed. POSIX only (the engine's CI runs on Linux and macOS).
     - **Order**: each table's rows are hashed as a sorted list. Row order in SQL is not part of the surface; where the spec defines an order it is a column (`posting_id`, `balance_id`, ...), which is hashed with the row. Beancount does not sort `glob.glob`'s matches, so what a load sees follows the file system's listing order (BL-0234): in `example-split` 12 `open` entries in different files share date and line number, and (corrected after round 1, F1) in `parity/includes` the two "Duplicate filename parsed" errors swap their ids, which sorting rows cannot hide. **The harness answers every glob in sorted order while a case loads** (`checksums.sorted_listing`, a test-only choice; the product keeps Beancount's order), so the snapshot is the same on every file system.
     - **The artifact**: `corpora/ledgers/mirror-checksums.json`, generated by `engine/scripts/gen_mirror_checksums.py` and listed in `scripts/check_generated.py` (INV-19: never hand-edited; regenerated and compared at pre-commit when a source is staged, and at pre-push; about 1 s): per case, per table, the row count and the SHA-256 of the normalized rows, one table per line. Its sources: the engine's package, its `pyproject.toml` and lockfile, `corpora/ledgers/` and `corpora/workspaces/legacy/`, the parity helper, the checksum helper, the generator.
     - **Review of a change**: `gen_mirror_checksums.py --rows <case> <table>` prints the normalized rows, so a reviewer diffs a table on the base and the head (PROCESS.md §8's side-by-side verdict).
     - **Coverage**: every table of `schema.TABLES` has rows in at least one case, so no table's checksum is vacuous over the whole corpus.
  5. **Must-not-pass**: the loosening mutants of step 2 that survive today are each caught by the check; planted cases: a corpus folder not in the snapshot, a snapshot case with no corpus root, a ledger file no root reads, a table with no rows anywhere, a path outside the case folder left as written, a change in one row of one table changes that table's checksum only.
- Implements: BL-0057 (second half); ADR-0015 (the mirror is a rebuildable cache), ADR-0016, ADR-0024 (Beancount decides what the rows project), ADR-0004 (the pinned Beancount whose upgrade the check makes visible); spec `design/specs/mirror/README.md` ("Not here yet" line), PROCESS.md §7.1 (generated) and §8 (changing an expected output).
- Capabilities: none changes state (CAP-DATA-MIRROR stays partial; nothing user-visible).
- Invariants touched: INV-05 (its surface's content held, not only its DDL), INV-19 (a generated file), INV-23 (synthetic corpus only; the example ledger is generated and never committed; the snapshot holds counts and hashes only), INV-24 (every load from a temp copy).
- Risk class / lane: Medium (tests, a generated artifact and a generator; no write path, no change to the build) / light.
- The bytes it protects: none (no write path); the check keeps the mirror's content, which every read and user query sees, from changing unnoticed.
- Acceptance tests (new; each must fail on the base d535b841, where the generator, the snapshot and the tests do not exist): `engine/tests/mirror/test_checksums.py` (the inventory and the cover check exact; table coverage; normalization; the generator's hash seed; the planted cases above); the snapshot's comparison with a fresh generation is `check_generated.py`'s; `scripts/tests/test_check_generated.py` `MirrorChecksums` (registered with its sources; a staged row change triggers it). The three row tests for the gaps of step 2 (`test_rows.py`: the quarter at its boundaries, a price never in exponent notation, a set in metadata sorted) hold on the base: `@regression-guard`.
- Expected doc impact: `design/backlog.md` (BL-0057 done; BL-0234 for the glob-order finding); `design/specs/mirror/README.md` (Orientation "Main tests", "Not here yet", and "Metadata JSON": a set's elements sorted, which the code did and the spec did not say); `corpora/README.md` (the snapshot); `engine/CLAUDE.md` (how to regenerate and review it); `design/specs/roadmap.md` line on BL-0057; `design/capabilities.toml` unchanged (CAP-DATA-MIRROR lists BL-0057 and stays partial). No user docs (nothing user-visible). No ADR expected (the design applies BL-0057's own row and PROCESS.md §7).
- Open questions: none for the owner before coding, unless step 2's evidence shows the checksum adds nothing (then: stop after this brief and report, per the orchestrator).

## Decisions
- **Build it** (agent; the orchestrator's condition): step 2's evidence shows the check catches changes the row tests let through (the quarter column, the training text), and only it sees a change that comes from outside the row code (a Beancount upgrade under ADR-0004, BL-0123's load change) on realistic ledgers. It is a characterization pin (EP-29): its expected values are the build's output, so it is never the reason to believe a row is right; the journal of the slice that changes a checksum says why (PROCESS.md §8), and `--rows` gives the side-by-side view EP-28 asks of a golden that changes.
- **Hashes, not row dumps** (agent): the hand-written cases' rows are about 400 KB of JSON and the three generated example ledgers about 5.8 MB, and dated rows with amounts would trip the staged-file guard's statement sniff (an exemption is the owner's, IMP-0058). Hashes with row counts keep the file at 932 lines and make a diff name the case and table; `--rows` prints the rows when a reviewer needs them.
- **Rows sorted before hashing** (agent): row order is not part of the SQL surface; ids that carry an order are columns. It does not remove the listing order: an id that follows it (`parity/includes` errors) still moves, so the glob answers are sorted too (round 1, F1). The cost: a pure order change in a table without an id (mutant E05) is not seen, which is what the surface promises.
- **The hash seed** (agent; found by the generator's first double run): see Brief item 3. Under pytest the seed is random, so the snapshot comparison stays in `check_generated.py`, never in a pytest test; `test_the_generator_hashes_as_the_engine_does_whatever_seed_it_is_started_with` starts the generator with seeds 1 and 2, which give different rows without the re-run.
- **The excuse list, `NOT_READ`** (agent): the first draft excused one file (`custom-roots/forgot-the-roots.beancount`) that the exact check found is read, so the list went; round 1's F2 widened the cover to every file of every case folder, and five files no load reads came back, each now named with its reason and held by a claimed-equals-found test: an undated file and a folder for an unopened account in a documents root (Beancount's scan skips both), a documents folder in raw plugin mode (not scanned), and the v0.2.2 install's lock file, `.gitkeep` and app config (no ledgers).
- **Three row tests added, beyond the checksums** (agent): the evidence found three rules with no test that a corpus snapshot cannot reach or should not be the only guard of (the quarter boundary, plain notation for prices, a set's sorted elements); each is a spec line, so a row test is the right check. The training text's trimming (E04) is caught by the snapshot only: the spec (`surface.toml` `training_data.text`) says "joined by spaces" and not "trimmed"; the code trims as v0.2.2 did. Left as is (the snapshot holds it); named in the report.
- **BL-0234** (agent; milestone M7 is a guess, with the QueryRunner's surface work): Beancount's include glob is unsorted, so entry order across files on a tie follows the file system; Beancount's own behaviour, so any change is a parity question for the owner. Not escalated now: no corpus id moves and no write depends on it at M1a.
- **Tests first** (the new tests against `d535b841`'s source, an archive in the session scratchpad, with the checkout's engine venv and the archive first on `PYTHONPATH`): `test_checksums.py` fails at collection (no helper); with the helper copied in but without the generator and the snapshot, 2 fail (the snapshot's cases, the generator's seed) and 17 pass: new tests of new helper code. The three row tests pass there: `@regression-guard`.
- **Privacy-scan workaround** (PROCESS.md §8, one line per false positive): a test literal standing for Beancount's `input_hash` (32 hex characters) tripped `secret-entropy`; the literal is now plain text ("an md5 of names and times"), which the test needs equally. No allow mark, no rule changed.
- **Deviation from ENGINEERING.md:** none known. The generator imports the engine's test helpers (`tests.ledger.parity`, `tests.mirror.checksums`): they are the corpus's single definition of its generated cases, and the generator is test tooling.

## Verifier
- Round 1, head 288939d8: PASS WITH FINDINGS, 0 High, 1 Medium, 3 Low, and a Low on the doc.
- F1 Medium: the snapshot depended on the file system's listing order: on HFS+ `parity/includes` gets its two "Duplicate filename parsed" errors with ids 4 and 5 swapped (Beancount does not sort `glob.glob`), so `check_generated.py` failed there, and would likely fail on CI's ext4. Fixed: `checksums.sorted_listing` answers every glob sorted while a case loads (a harness choice; the product keeps Beancount's order, BL-0234); `test_the_snapshot_is_the_same_whatever_order_the_file_system_lists_files_in` builds the corpus under ascending and descending listings, and its near miss `test_without_the_sorted_listing_the_order_shows_in_the_rows` shows `parity/includes.ledger_errors` differ without the sort. The verifier's HFS+ repro now exits 0. BL-0234, the brief and the helper's docstring corrected: an error id moves too, not only `open` order.
- F2 Low: the file cover counted only `.beancount`, `.gpg` and `.asc` names, missing `write/includes/years/2023-extra.bean` and any extensionless include. Fixed: `corpus_files` takes every file of every case folder; a document Beancount found and a plugin module a load imported count as read; five files no load reads are named in `NOT_READ` with reasons (Decisions).
- F3 Low: `engine/.python-version` was not a source of the snapshot. Fixed: added to `check_generated.py` and to the `MirrorChecksums` meta-test.
- F4 Low: the generator held a third copy of the engine's seed, and the seed test passed with any fixed seed. Fixed: the generator re-runs itself with `fresh_load.environment()`, the environment the engine gives a load it starts; the test compares the generator's rows (started with seeds 1 and 2) with rows built directly in a process with that environment.
- Doc Low: "a set's elements sorted" now says by their JSON text, with the example `{9, 10}` → `[10, 9]` in the README and `rows.json_value`, and the row test pins it. Kept as text order (the code's behaviour; sorting numbers numerically would need a rule for mixed kinds and changes nothing a reader relies on).

The file is new in this slice (never landed), so no landed expected output changed; no further round (tooling with no ledger or user data, no High fix; ADR-0058).
