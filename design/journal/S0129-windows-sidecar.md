# S0129: the sidecar on Windows: the engine's Job Object, the app folder and the locks (M1b slice 8b-3, BL-0281)

## Brief
- Goal: the third part of the Windows port. Make the main sidecar run the engine on Windows, so the product can supervise engines there as it does on macOS and Linux. Today every POSIX-only sidecar function raises `NotOnWindowsError` (`app/platform/adapters/windows_pending.py`, S0127), and `wait_engine_lock` is a no-op on Windows. **The engine still refuses every file operation in the product after this slice** (BL-0206 and BL-0087 follow). The sidecar can start, supervise, drain and end engines on Windows, and the boot answers `engine.unsupported_platform` truthfully there.
- **The engine's process group on Windows** (engine-jobs §5.2, ADR-0064): a **Job Object** per engine, nested in the shell's, with kill-on-close.
  - The drain ends every member, a plugin's child included, before the next engine starts.
  - The engine ends its own job when the sidecar is gone (the Job Object's kill-on-close when the sidecar's handle closes; spec §5.2).
  - The job's CPU is read from the Job Object's accounting (§5.2).
  - "No live member" is defined for Windows.
  - A process that left the job (`CREATE_BREAKAWAY_FROM_JOB`, where allowed) is out of reach, as `setsid` is on POSIX, and gets the advice on the timer.
  - Cancel and retire end the engine through its job.
  - The spawn's flags and environment (`-s -S -B -P`, `PYTHONHASHSEED=0`) are kept.
- **The app folder on Windows** (`app/platform/adapters/app_folder.py`): `prepare` makes and checks it, and its identity, `--app-folder-id`, uses the adapter's identity, the 64-bit volume serial and 128-bit file ID on NTFS and ReFS, never the creation time (S0128 verifier Q-C). The sidecar's computation and the engine's `this_os.folder_identity` agree, tested.
- **Locks on Windows:**
  - `wait_engine_lock` waits for `locks/engine.lock` with `LockFileEx`, as the engine takes it (S0128);
  - the app-instance lock (one running Finzytrack, ADR-0062) with `LockFileEx`;
  - the advice on the timer while the wait lasts (§5.1).
- **A test copy's recorded `born`** (the sidecar's `CopyMark` and `SaveConfine`) uses the same identity on Windows (Q-C).
- **CI:** a `backend-windows` job on `windows-2022` in the manual run runs the backend's tests there. The ones that need the engine to write skip, naming BL-0206 or BL-0087; the Job Object, app folder and lock tests run.
- Implements: ADR-0064 (one engine, its process group), ADR-0062 (one instance), ADR-0063 (the boot's recover-all), ADR-0061 and its amendment of 2026-11-14, ADR-0069; engine-jobs §5.1, §5.2, §5.5, §9.3; BL-0281.
- Capabilities: none changes status.
- Invariants touched: INV-11 (the queue on `UserContainer`), INV-31, INV-32 (recover-all before any open, which on Windows answers unsupported until BL-0087), INV-23, INV-24.
- Risk class / lane: High / full. Review budget row: **Other product code: engine** (supervision, not a write path: the engine still writes nothing on Windows): the verifier; the security red team only if a new input is added. Note: a Job Object that fails to end a plugin's child could let an engine of an earlier job run beside the next one, which ADR-0064's lock and drain exist to prevent. **At the first finding that lets two engines run at once, or an engine outlive its drain, stop and report**: it guards the write path's one-engine rule.
- The bytes it protects: none directly. It upholds the one-engine-at-a-time rule that every write relies on, on Windows.
- Mechanism questions (PROCESS.md §3 step 2): which real setup needs this? Every Windows user. Fix-round history: the process group and drain on macOS (S0053, S0057, S0073, S0076: several rounds), the ports (S0125-S0128).
- Acceptance (tests first; each fails on Windows on the base, which the first CI run shows):
  - on the Windows runner:
    - an engine spawned in a Job Object;
    - a plugin's child drained with it;
    - kill-on-close when the sidecar's handle closes;
    - CPU read from the job;
    - Cancel and retire ending the engine;
    - the engine lock waited for, with the advice on the timer;
    - the app-instance lock;
    - the app folder's identity equal between the sidecar and the engine;
    - the boot's recover-all answering unsupported;
  - the macOS and Linux gates stay green;
  - the CI runs by date and order in the journal.
- Expected doc impact: engine-jobs §5.1, §5.2 (Windows), §14, §15; ARCHITECTURE.md (the sidecar's `engine_group` on Windows); `backend/CLAUDE.md`; BL-0281 closed or narrowed.
- Open questions: none.
- Base: fcae5f30.

## Decisions
- The Windows port's part 3 (owner, 2026-11-17, in session: "1a, split yes, keep red"); the ports' CI runs are the owner's decision of 2026-11-16 (S0125's journal). This slice writes no ledger byte on any OS, so it takes the "Other product code: engine" row, not New write path; the stop rule above covers the one-engine rule it guards.
- **Tests first (agent).** The Windows acceptance tests are `backend/tests/platform/test_engine_windows.py` (it skips off Windows) and `tests/test_main.py::test_on_windows_the_boots_recover_all_runs_in_an_engine_and_answers_the_platform_unsupported`, run by a new `backend-windows` job in `ci.yml`. So that the test commit type-checks for Windows (the pre-push hook runs `pyright_platforms.py`), it carries the interface they name and nothing else: `app.platform.adapters.windows_job.EngineJob`, whose every method raises `NotOnWindowsError` as the base's POSIX-only functions do there, and `Reaped.cpu_ns` (default None, unused on POSIX). No behaviour changes on any OS in that commit; on Windows the tests fail as on the base.

- **The Job Object (agent).** One unnamed job per engine (`app.platform.adapters.windows_job.EngineJob`), made by the client right after the spawn and before the handshake; the engine starts no process before it reads a request, so every process it or a plugin starts is born in the job. Rejected: `CREATE_SUSPENDED` with an undocumented `NtResumeProcess` (Python's `Popen` keeps no thread handle), and `PROC_THREAD_ATTRIBUTE_JOB_LIST` (not reachable through `Popen`); both close a race that cannot arise while the engine waits for its first line. Nesting: the sidecar runs in the shell's job, so the engine's is nested in it (Windows 8 and later); a job Windows refuses fails the start (`start_failed`) and the engine, still alone and having started nothing, is killed. **Limits:** `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` only while the engine runs; at our signal also `JOB_OBJECT_LIMIT_ACTIVE_PROCESS` of 1, so a process a member starts during the end is ended as it is made, before it runs (nothing outside the job can add a member: only the sidecar holds the job's handle). No memory, CPU or UI limits (nothing in the spec asks for them).
- **Breakaway (agent).** The job sets neither `BREAKAWAY_OK` nor `SILENT_BREAKAWAY_OK`, so a member's `CREATE_BREAKAWAY_FROM_JOB` never takes it out of the engine's job: the brief's "where allowed" is answered "never", stricter than POSIX (`setsid` cannot be refused). The first test assumed Windows refuses the call; the 2026-11-18 run 3 showed it succeed on the runner, whose own job allows breakaway; the test was rewritten to ask what matters (run 4: the child stays listed in the engine's job and the drain ends it), so Windows takes the child out of the jobs that allow it and keeps it in ours. Cost: a plugin that needs a child outside every job cannot have one; no Beancount plugin is known to. A process another program starts on a member's behalf (a service, the task scheduler, a COM server, `ShellExecute` through the shell) is still out of reach, as a `setsid` child is: engine-jobs §5.2 "Limit (Windows reach)". It inherits no handle, so never the engine lock; the lock wait before every fresh engine stays the backstop.
- **Kill-on-close (agent).** The sidecar holds the only handle on the job (not inheritable; the engine and its children get none), so when the sidecar ends however it ends, Windows ends every member. The engine's own end-of-input exit on Windows ends only itself (`end_own_group` exits; the job is the sidecar's); with the sidecar alive the drain ends the rest.
- **The drain's "no live member" on Windows (agent).** A process leaves the job's list (and its active count) while it is still exiting, before Windows has closed its handles; its process object is signalled only after that. So our signal, before `TerminateJobObject`, opens and holds a handle on every listed member (checked with `IsProcessInJob`, so a pid that passed to another program is never held), and "no live member" is: the listing succeeded, every listed member could be judged, and every held handle is signalled (`engine_group.live_member_in_job`, pure, tested on every OS; the 20-run drain test on the runner checks that the child's file can be opened with no sharing at the reap). A failed listing or a member that cannot be opened (other than one already gone) counts as live. **Limit:** a member that ended by itself an instant before our signal listed the job, never held, may still be closing its handles at the reap (its own code has stopped): §5.2 "Limit (Windows reach)". The leader is held through its own process handle, so its pid is not reused before the reap.
- **CPU (agent).** The reap reads the job's accounting (`TotalUserTime + TotalKernelTime`, every member's, ended ones included) into `Reaped.cpu_ns`. No OS logs a job's CPU yet (POSIX never read it); logging it is BL-0289, so macOS and Linux are unchanged.
- **Exit code (agent).** `TerminateJobObject` gives every member 137 (`ENDED_BY_US`); a recorded reason wins over the exit status, as on POSIX.
- **The replies on Windows (agent).** Windows pipes cannot be polled, so the reply pump reads to the end of the output (the base's form, kept). That end comes at the drain at the latest: only the engine holds the write end (its protocol copy is not inherited) and no member can leave the job.
- **Locks (agent).** The engine lock: the sidecar's wait holds the app folder without delete sharing (so it cannot be removed, renamed or replaced while held), checks its identity (`AppFolderChangedError` as on POSIX), then opens `locks/engine.lock` only if it exists and takes `LockFileEx` over the whole file, waiting, with the engine's access and sharing, and releases it at once. It makes nothing on Windows: an engine that holds the lock keeps the file open without delete sharing, so a missing file means nobody holds it. Rejected: making `locks/` and the file by path (a second copy of the engine's handle-relative creation for no gain). **The app-instance lock (ADR-0062) is not built here (pushback on the brief):** it does not exist on any OS; it is BL-0100 (M2, open: the second-instance exit, its text, the shell's single-instance plugin, landing with BL-0073). Building only its Windows form now would be a lock nothing takes on macOS or Linux. Its Windows form (`LockFileEx` on a file in the app folder, non-blocking) is noted in BL-0100. For the owner.
- **The app folder's identity (agent).** `windows_files.identity`: `FileIdInfo`'s 64-bit volume serial and 128-bit file ID, `born` = the file ID on NTFS and ReFS; FAT32 and exFAT: the 32-bit serial, the file index and the creation time; any other file system: no `born`. The same rule as the engine's `WindowsDir.identity`/`born`, so `--app-folder-id` is `SERIAL:FID:FID` on NTFS; the runner test compares it with the engine's `port.folder_id` in the engine's interpreter, and a real engine takes its lock with it. The engine's `this_os.folder_identity(fd)` stays POSIX-only (Windows has no folder descriptor): on Windows the engine checks the identity through its adapter (`port.same_folder`), which is what the test compares with. `prepare` syncs the parent with `FlushFileBuffers` on the folder opened for adding a file, as the engine's `WindowsDir.sync`.
- **A test copy's `born` (agent).** `CopyMark` and `SaveConfine` carry what the engine's copy recorded (its adapter's `born`: the file ID on NTFS and ReFS since S0128); the sidecar never computes it, so only their docstrings change.
- **The bytecode directory on Windows (agent).** Not built: the fill works through folder descriptors and `dir_fd`, which Windows has not; the client starts every engine without it there (`_bytecode_for_spawn`), so each engine compiles the engine's code as it imports it (slower starts, nothing wrong; `-B` writes no bytecode). BL-0288, with "measure first". Deviation from engine-jobs §5.1's bytecode rule on Windows, stated as §5.2 "Limit (Windows bytecode)".
- **Engine side (agent).** The test op `test.child` on Windows: the child takes its own `msvcrt.locking` lock on the file's first byte (a `LockFileEx` lock is its taker's and no child inherits it) and the op answers once it holds it. The engine's skips that named BL-0281 now name what they are: its own POSIX group end (the Windows form being the sidecar's job, tested in the backend) and the copy check's POSIX-signal tests (BL-0087).
- **Tests changed after the test-first commit (agent).** Two asserts of `job.member_ids() == []` after the drain were removed: the reap closes the job's handle (its life ends with its drain), so there is no job to list then; the same rule is held by the child's handle being signalled and its file opening with no sharing (drain test), and by the workers' shared file opening with no sharing (spawner test). The backend's POSIX-only skips now say where their Windows counterparts are instead of naming BL-0087 or BL-0281 (`tests/windows_pending.py`).

- **Test-first evidence (agent).** On the test commit 60017d7a (product code as the base, plus the interface stub), the 2026-11-18 run 2's `backend-windows`: every new Windows test failed or errored except two, which pass on the base and are tagged `@regression-guard`: `test_cancel_during_a_request_ends_the_engine_through_its_job` (the base ended the engine alone with `TerminateProcess`) and `test_main.py::test_on_windows_the_boots_recover_all_..._unsupported` (the base's wait returned at once and the engine ran alone). The failures: the Job Object tests with `NotOnWindowsError` (no job), the client's plugin-child cases with `engine.internal` (no Windows `test.child`), the kill-on-close test (no child to start), the lock, advice and identity tests at the fixture's setup (`prepare` raised `NotOnWindowsError`). `test_windows_job_decision.py` fails on the base at import (no `live_member_in_job`; run on macOS).
- **The slice's split (agent; for the orchestrator and the owner).** The same run 2 ran the whole backend suite on Windows for the first time: 170 failed and 23 errors besides this slice's tests, almost all outside BL-0281 (tests written in POSIX paths, the write path Windows refuses until BL-0087, `zoneinfo` without `tzdata` on Windows, the mirror's files, process tests' CRLF; inventory in BL-0290). Making that suite pass is a slice of its own, as S0127 was for the engine's suite, so `backend-windows` runs this slice's tests now and the whole suite with BL-0290 (`ci.yml` says so). The brief said the job runs "the backend's tests there"; this narrows it, recorded here and in BL-0290. One item in it is a product gap, not a test's: the sidecar's civil dates need the `tzdata` package on Windows (a new runtime dependency).
- **CI runs** (the manual run on `next`, by date and order):
  - 2026-11-18 run 1: started before the test commit's push had landed (the S0128 head), cancelled at once; no result.
  - 2026-11-18 run 2 (head 60017d7a, the test commit): `backend-windows` red (the whole suite: 170 failed, 2739 passed, 68 skipped, 23 errors; the new tests as above); `engine-windows` red with exactly the known ten (`test_no_resident_ledger.py` 5, `test_parity_corpus.py` 5; owner's "keep red"); every other job green.

## Hand-off (PROCESS.md §3 step 4; ADR-0057)
- **Checks added or changed that accept, tag or refuse**, each with its must-not-pass test:
  - "No live member" on Windows (`engine_group.live_member_in_job`): a held member not yet ended, a failed listing, a member that could not be judged each count as live: `tests/platform/test_windows_job_decision.py` (every OS); on the runner, a drain that reaps while a child still holds a file: `test_engine_windows.py::test_the_drain_ends_a_plugins_child_and_every_handle_it_held_is_closed_at_the_reap` (20 runs), `::test_a_member_starting_processes_in_a_loop_does_not_outlive_the_drain`.
  - The job's breakaway refusal (no `BREAKAWAY_OK`): `::test_a_member_that_asks_to_leave_the_engines_job_stays_in_the_drains_reach`.
  - Kill-on-close: `::test_a_sidecar_ended_hard_takes_its_engine_and_the_engines_child_with_it`.
  - The end reported only after the job's drain (Cancel, retire, a crash, `close()`): `::test_a_plugins_child_holding_a_lock_is_ended_with_the_engine[...]`.
  - The sidecar's engine-lock wait on Windows refuses a replaced app folder: `::test_the_wait_refuses_an_app_folder_made_again_at_the_same_path`; does not go on while the lock is held: `::test_the_wait_lasts_while_an_earlier_sessions_engine_holds_the_lock`; makes nothing: `::test_with_no_lock_file_the_wait_returns_at_once_and_makes_nothing`.
  - The app folder's identity on Windows: equal to the engine's (`::test_the_app_folders_identity_is_the_engines_the_volume_serial_and_file_id`, which also refuses `born` as the creation time), another after a remove and make again (`::test_a_folder_made_again_at_once_is_not_the_folder_of_the_start`), a file in its place refused at start (`::test_a_file_where_the_app_folder_belongs_is_refused_at_start`), and the engine refusing the lock unless they agree (`::test_the_engine_takes_its_lock_with_the_sidecars_identity`, and `engine_holding`, which asserts the engine took the lock with the sidecar's id).
  - A job Windows refuses fails the start: no test (Windows does not refuse a job on Server 2022 without a quota or a policy the runner lacks); the code path ends the engine and returns `SpawnFailed`, read in review.
- **Loosening mutants** (`scripts/mutants.py`, plan in the session scratchpad): run on macOS for the pure decision, 4 tried, 4 killed: `job-list-alone` (the list alone decides), `job-unjudged-taken`, `job-failed-listing-taken`, `job-any-ended-is-enough`. The Windows-only checks cannot run under `mutants.py` on macOS (their modules do not import there) and a mutant cannot be pushed to `next` for the runner; each is named with the runner test that must kill it, **not run**: no kill-on-close flag (`::test_a_sidecar_ended_hard_...`); `BREAKAWAY_OK` set (`::test_a_member_that_asks_to_leave_...`); `wait_lock` returning at once (`::test_the_wait_lasts_while_...`); the identity check in `_wait_windows` dropped (`::test_the_wait_refuses_an_app_folder_made_again_...`); `born` the creation time on NTFS (`::test_the_app_folders_identity_is_the_engines_...`); `_hold` skipped in `terminate` and `live_member` (the drain test's 20 runs; whether it kills depends on timing, so it may survive: a stated weakness of that test).
- **Population claims:** none beyond the Windows skip reasons: every backend test that named BL-0087 or BL-0281 for process groups, `flock` or the reply pump (`grep` of `tests/` for those IDs: 31 sites in 7 files) now names `test_engine_windows.py`; the ones that name BL-0087 for the write path keep it.
