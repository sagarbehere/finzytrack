# S0041: The cross-process failure-mode spec (BL-0090)

## Brief
- Goal: answer the owner's question of 2026-10-26 ("how can we be reasonably confident that if one of them (e.g. the ledger engine) crashes or becomes unresponsive, all the other programs will know, will not lose data, and will provide the appropriate feedback and action suggestions to the user?") with a spec, `design/specs/failure-modes.md`: for each process (Tauri shell, frontend webview, main sidecar, ledger engine) and each failure (crash, hang, slow, killed for memory, parent gone; plus "fails to start" and "told to stop", which are real and distinct), who notices and how fast, what happens to data on disk and in flight, what the user sees, which action is offered, and the row's test: an existing test by path and name, a test this slice writes, or the open backlog row and milestone that will test it. It opens with a plain-English answer that says what is covered today and what is not. Engine rows name their states against S0040's table (`design/generated/statecharts/engine-supervision.md`). The spec's references are held by a check, so it cannot drift: every pair present once, every cited test exists, every cited backlog row is open with that milestone (a row that closes forces the spec to cite its test), every engine state named exists in the generated reference.

The spec's statements about the write path are checked against ADR-0008/0012/0013/0015 and ARCHITECTURE §9.2 with High-style care, because the owner will rely on them. ## Decisions
- **Where the spec lives** (agent): one file, `design/specs/failure-modes.md`, not inside a future `shell/` spec: it crosses all four programs, and three of its four tables are about programs whose specs do not exist yet. Linked from ARCHITECTURE §2.0 (the engine) and §5 (the shell's supervisor), and from `design/specs/README.md`.
- **Two failures added** (agent; the brief allowed real and distinct ones): "fails to start" (missing or broken files, another protocol version, a refused configuration: handled by different states and messages than a crash) and "told to stop" (quit, logout, shutdown, update: the one path where an in-flight write must not be cut, and where the OS may end the engine directly). Considered and left out, with the reason in the spec's last section: power loss and a full disk (the write protocol's and the log's, not a process's), a second running instance (ADR-0012 Q30, the app-level lock), outside services (typed "unavailable" errors).
- **The spec is checked, not trusted** (agent; PROCESS.md §7 "generate it, test it, or keep it to the why"): `scripts/check_failure_modes.py`, run on the real spec by its meta-test at every push (no hook edit needed). The rule that a cited backlog row must be open is what keeps the spec honest over time: a slice that closes BL-0091 cannot land without citing its test in rows E1-E3, E5, E7. IMP-0030.
- **The log sink no longer reaches the supervision** (agent; S0040 carry-over 3, closed because it was cheap and safe): `EngineClient`'s `Log` effect suppresses `Exception` from the sink. **Deviation from EP-13 ("no swallowing"), recorded:** the swallowed error is the diagnostics channel's own failure, and the line is all that is lost; the structured log already drops a line it cannot write (S0039 `_Handler.handleError`), and the stderr pump drops a failing callback (S0038), so this is the same rule at the one remaining path. Interrupts (`BaseException`) still go on to the `_call` guard; `test_an_interrupt_inside_the_log_sink_still_reaches_the_caller` holds that. Written with `contextlib.suppress` because ruff's SIM105 asks for it.
- **Carry-overs 1, 2, 4-7** (agent): decided in the spec's "Decisions on the carry-overs" section: kept with a reason, and each given to the M2 row that will replace the code (BL-0094 for the stale state and the stop's cause; BL-0095 for the supervisor, the quit sequence, the stderr drain, the SIGTERM window and the `Kill`-effect residual). None of them loses data today; the SIGTERM window and the dead-engine-between-requests gap each lose a log line or show a stale "ready", and the spec says so.
- **What BL-0091 must decide** (agent, recorded on its row): the parent-death rule mid-write (today POSIX cuts the request, Windows finishes it), whether the engine defers the OS's SIGTERM during a commit, time limits for writes (a slow write cannot be told from a hung one) and "outcome unknown" instead of "failed". An in-session recovery without a reopen would amend ADR-0012 and needs the owner then; until then Q30 applies (refuse writes, ask to reopen).
- **No inbox item** (agent): every decision here is either an implementation detail or deferred to the row whose slice will face it with the evidence; nothing changes an ADR, an invariant or the scope. BL-0097 (keeping drafts across a window crash) may become a scope question (rubric 5); its row says so.
- **Not run** (stated, not hidden): no engine code changed, so the engine's own gates were not rerun beyond the pre-push hook at landing; Windows behaviour in the spec (rows E5, E7) is read from the code, not tested (BL-0087 brings the Windows runner from M1b).

## Retro
- What the verifier found: two of five findings were about the check accepting what it silently skipped (rows of other shapes, rows in hidden regions), the classic "a filter that drops what it does not recognise" escape; one was a claim in the prose stronger than its rows, which the check cannot see. A cheaper catch for the first kind: when a check selects items by a pattern, also refuse what looks like an item but fails the pattern (I wrote that rule for the backlog references and not for the row IDs). For the second: read the plain-English summary against the table row by row before hand-off, as a separate pass.
- Self-mutation's two survivors on the fix were both "the fixture never had the shape": a comment longer than one line, a second table with ticked cells.
- Where time went: the behaviour inventory and the write-path facts (reading ADR-0008/0012/0013/0015 and the client against them) took most of it; the check and its tests a quarter; the verifier round's fix about a sixth.
- Orientation gaps: the shell does not start the sidecar yet, which is easy to miss from ARCHITECTURE §5 (written as the target); the spec now says it in its first paragraph. The guard hook refuses shell text with the word for ending a process, so test code went through the file tools again (as in S0038 and S0040).
- Process cost: one implementer pass, one verifier round, one fix pass.
