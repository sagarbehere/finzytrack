# S0138: Copy refuses an EFS-encrypted ledger

## Brief
- Base: `next` at a17209e25cc27f10334461f01e7d9742bd135ac7.
- Goal: BL-0287. On Windows, a Copy (test copy, Copy adoption, "New workspace from settings of…") whose source holds a file that Windows' EFS encrypts is refused before anything is written, so its bytes never land in the clear in the copy's folder. Owner, 2026-11-18, in session: "a", choosing "Refuse Copy of an EFS-encrypted ledger, and state the mirror as a limit". The mirror is already a stated limit (engine-jobs §6.3, "Limit (encrypted ledgers and the mirror)").
- Implements: engine-jobs §8.2 (the copy's step 2), the owner's rule 1a (S0128 round 1), ADR-0059 (an encrypted file is never written).
- Capabilities: CAP-WS-TEST-COPY, CAP-LEGACY-ADOPT, CAP-WS-BRING-IN (all through `ledger_engine.ledger.copy`).
- Invariants touched: INV-22 (a truthful outcome: the refusal says "not copied" and nothing is made). The protection itself is the owner's rule 1a (S0128), not an invariant.
- The bytes it protects: an EFS-encrypted source file's plaintext, which the copy would otherwise write unencrypted into the target (and, through `create`'s staging, nowhere else: the copy writes only in the target).
- Which real setup needs this, and can a policy forbid the rest? A Windows user who turned on EFS for a file or, more often, a folder ("Encrypt contents to secure data" on a Finance folder makes every new file in it encrypted, ledger files and receipts alike). The policy (refuse) is already the owner's choice.
- Has this mechanism or its family needed two or more fix rounds before? The family (S0128's 1a carry-over and EFS refusal) took two rounds in S0128, but the EFS refusal itself needed no fix; this slice reuses it (`EntryStat.encrypted`) and adds no new primitive.
- Mechanism: after the source's load (step 2b) and before step 1, every file the copy would write from the source (ledger file or document) is stat'ed through the file-system port (`copy.encrypted_on`: `fs.resolve`, then the parent's `DirHandle.stat`, the object a link leads to), and one with `EntryStat.encrypted` refuses the copy (`encrypted`, detail `efs`, naming it); an error answering refuses (`source_unreadable`). The re-check before the commit point asks again (encrypting keeps the bytes, so the hash re-check cannot see it). Second opinion: none needed beyond the adapter's `FILE_ATTRIBUTE_ENCRYPTED`, which S0128's runner test already exercises for a file reached by the save; this slice's runner test exercises it for a file reached the way Copy reaches its source (by its path, `chunks`, links followed).
- Risk class / lane: High / full (a write path's refusal).
- Review row: **New write path or write outcome** (verifier + data-safety red team): the refusal adds a new outcome text for a write (`msg:copy.encrypted_efs`, the owner's "Own text (Recommended)").
- Acceptance tests: over the fake (`tests/ledger/test_copy.py -k S0138`: the root, an include, a file outside the folder, a documents-root file; every written file asked; a file encrypted mid-copy; an error answering); on the real disk of every OS through a wrapper of the real port (`tests/ledger/test_copy_efs.py`: root, include, `document` entry's file, documents-root file, a link); on the Windows runner with `cipher /e` (`tests/fs/test_windows.py -k S0138`: root, include, `document` entry's file, documents-root file; in CI a missing EFS fails, never skips); the text (`backend/tests/platform/test_copy_job.py -k S0138`).
- Expected doc impact: engine-jobs §8.2 step 2 and §6.3's limit ("will refuse" becomes "refuses"); the copy's text table (§11) if a text changes; ARCHITECTURE.md's copy line; BL-0287 closed.
- Open questions: both answered by the owner, 2026-11-21, in session (below, Decisions). As brought to the orchestrator before coding:
  1. **Document files.** A copy also writes, byte for byte, every regular file under each `option "documents"` root and every `document` entry's file (`copy._files`). An EFS-encrypted receipt would be written in the clear just as a ledger file would, and the common setup (EFS on a whole folder) encrypts both. The row says "an EFS-encrypted ledger file" and the owner's words "Refuse Copy of an EFS-encrypted ledger"; neither clearly covers document files. Options: (a) refuse when any file the copy writes is EFS-encrypted, ledger or document (same check, same reason; recommended: the same privacy hole, the same cost); (b) ledger files only, document files a stated limit; (c) ledger files refuse, document files copied encrypted (set EFS on the new file): a new mechanism, needs the user's EFS key at write time, more Windows code, not recommended.
  2. **Which reason and text.** A copy's refusal is a `NotCopied` reason worded by `copy_text`, not an `ErrorCode`, so "the save's named reason (`ENCRYPTED_FILE_NOT_EDITABLE`)" does not fit the copy's outcome as built. The copy already has `encrypted` (`msg:copy.encrypted`, for a `.gpg`/`.asc` ledger file): "<file> is encrypted. This version of Finzytrack does not read encrypted ledger files." For an EFS file that text is false (Finzytrack opens and reads an EFS ledger; only saving and copying are refused). Options: (a) reuse the reason `encrypted` with a second text for the EFS case, chosen by a detail (a new outcome text: the "New write path or write outcome" row, verifier and data-safety red team); (b) reuse `encrypted` and its text unchanged (the "Hardening" row, but a misleading text); (c) a new reason `encrypted_by_system` with its own text (new outcome text, same row as (a)). Recommended (a), with a text such as "<file> is encrypted by Windows. Finzytrack does not copy encrypted files, so their contents are never written unencrypted." (the owner's or a wording review's to approve).

## Decisions
- Document files: owner, 2026-11-21, in session: "Refuse any file (Recommended)". Copy refuses if any file it would write is EFS-encrypted, ledger file or document.
- The text: owner, 2026-11-21, in session: "Own text (Recommended)". The reason stays `encrypted`, the EFS case picked by the detail `efs`, with the draft as shown to the owner: "<file> is encrypted by Windows. Finzytrack does not copy encrypted files, so their contents are never written unencrypted." (`msg:copy.encrypted_efs`).
- The text after round 1 (red team F1): owner, 2026-11-21, in session: "Short + left-over line (Recommended)". Always "Not copied. <file> is encrypted by Windows. Finzytrack does not copy encrypted files." (`msg:copy.encrypted_efs`); only when the cleanup left something (a named left-over, or `left` None), instead of the generic left-over sentence: "The unfinished copy in <folder> may hold that file's contents unencrypted. Check it before you delete anything." (`msg:copy.encrypted_efs_left`). The first text's clause "so their contents are never written unencrypted" was false after a re-check refusal whose cleanup could not finish.
- The check sits in `_files`'s `add`, so every file the copy writes from its source passes it by construction (one place, not one per kind); a ledger file is read into memory before it is asked (as the load already did; nothing is written). (agent)
- The re-check asks again, since EFS encryption keeps a file's bytes and so its hash: without it a file encrypted during the copy would end "created" in the clear. The bytes then stood in the target until the stop removed them: a stated limit (engine-jobs §8.2, "Limit (encrypted during a copy)"). (agent)
- A path the port finds leading to nothing is "not encrypted": nothing is copied from it (its read then fails), and the re-check asks again. Fail closed on an error answering (`source_unreadable`). (agent)
- The check is a port function (`CopyPorts.encrypted`, default `encrypted_on`) because the fake's sources are never on the fake disk; `encrypted_on` itself is held on every OS's real disk by `test_copy_efs.py` and on the runner by `cipher /e`. Its second opinion: the runner test reads the attribute apart from the adapter (Python's `os.stat(...).st_file_attributes`) before it runs the copy. (agent)
- Stopped before tests and code: question 1 is outside the owner's recorded choice (the task's instruction), and question 2 decides the review row and a user-facing text (agent, 2026-11-21).
