# S0102: The app folder's identity from start; no blocking open of ledger files

## Brief
- Goal: close BL-0244 and BL-0245 (owner, 2026-11-11, in session: "BL-0244 slice in M1a (Recommended)"; the option as put: "Land S0100 with the spec/ADR claims corrected; then one slice adds the app-folder identity check (device+inode from start), closing both our fill and another program's recreation."). Base commit `51c58167`.
  - **BL-0244.** The sidecar records the app folder's identity `(st_dev, st_ino)` (links followed, as the save and recover-all follow them) once, in `app_folder.prepare`, right after it made or found the folder and before it synced its parent. Every process of ours that writes or syncs in the app folder checks that identity against the object it is about to write in, and refuses when the folder is missing or another object:
    - **the engine** (started with `--app-folder-id DEV:INO`, required with `--engine-lock`): `hold_engine_lock` opens the folder, checks the descriptor's identity, and makes `locks/` and the lock file relative to that descriptor; on a mismatch it takes no lock and ends (stderr line, its own exit code). The ops that write or sync in the app folder (`save`, `recover_list`, `recover_try`, `recover_act`: `OpSpec`'s new `writes_app_folder`) check it first: the save answers `not_saved {app_folder_missing}` with the re-hash, the recovery ops are refused `engine.app_folder_missing`. The save checks it again on the handle it makes `local/` in (step 8), so the check acts on the object written in, not only on what the name held at the job's start. This replaces S0100's `_app_folder_gone` (which compared the request's spelling): a request spelled `<app folder>/./` is now `app_folder_missing` too (case 4).
    - **the sidecar's lock wait** (before every fresh engine): the same check, and `locks/` and the lock file made relative to the checked descriptor. A mismatch is `AppFolderChangedError`; the scheduler feeds `EngineLockFailed(app_folder=True)` and the queue table ends the jobs that needed an engine with `NoEngine(why="app_folder")`, read as `ENGINE_UNAVAILABLE {app_folder_missing}` (new reason, text: quit and reopen). So later jobs no longer end `ENGINE_STOPPED`/`stopped_often` (case 3).
    - **the bytecode fill**: the folder checked and `engine/`, `bytecode/`, `<build>` made relative to descriptors; the compiler child runs with its working folder the build folder and `-X pycache_prefix=.`, so every folder and file it makes is relative to the object we made: in a removed folder its `mkdir`s fail and it can never make the app folder again (probed on APFS: with `workers=0` and `1`, absolute prefix: the app folder made again at 0755; relative: never). `.complete` is written only when the app folder still has its identity and the build path still names the folder we made; else nothing is marked or removed (case 1). The table's discard checks the same before it removes anything.
    - Ownership rule (owner, 2026-11-10): nothing new is written in or above the app folder's parent; the fill on a mismatch removes nothing (what it made is either gone with the old folder or not reachable as ours).
  - **BL-0245.** `fingerprint.file_state` opens without blocking and refuses anything but a regular file (`Unreadable("EINVAL")`), reading through `chunks` as the copy does. Every other read of a ledger-set file of ours, found by behaviour (every `open`, `os.open`, `read_bytes`, `file_digest` in `engine/src` on a path a ledger set names), gets the same rule: the overlay load's read, its `.asc` encrypted test (Beancount's `is_encrypted_file` opens the file), and `precision.of_disk`. Beancount's own real load (the rebuild, the create's check) opens files itself: out of reach without patching Beancount; recorded as a limit with a backlog row.
- Implements: ADR-0012 (dated note on the 2026-11-11 amendment), spec `engine-jobs.md` §5.1, §6.1 step 8 and its "Limit (app folder)", §8.1, §11, §15; ADR-0068 D3 (the engine lock).
- The bytes it protects: a save's journal and backups (they must sit in the folder whose entry the start made durable, else a power loss can drop them while swapped ledger files stay: a torn ledger with no record); and the outcomes it keeps truthful (later jobs say to quit and reopen; a FIFO never hangs a save before its commit point).
- Capabilities: the CAP-WRITE rows of the save and the engine lock (checked at landing).
- Invariants touched: INV-01, INV-22 (fail closed, truthful outcomes), INV-27 (machine-local state), INV-32 (recovery before work).
- Which object each check acts on (S0101 lesson): the engine lock, the fill and the save's step 8 check the descriptor they then write through; the op-start checks (the save before its gate, the recovery ops) check what the path names at that moment, and the writes that follow open by path (a limit, written in §6.1 step 8: only a program that removes or replaces the app folder in that instant).
- Limit kept: on FAT32 and exFAT `st_ino` is the first cluster and can be reused (S0101 round 2); an app folder there is unlikely (the app's own folder is in the user's Library); written in the Limit.
- Risk class / lane: High / full lane (where the journal is written; new outcome on every job). Verifier and data-safety red team (orchestrator).
- Acceptance tests (tests first, failing on `51c58167`): engine `tests/test_engine_lock.py` (the lock refuses a missing or replaced folder and makes nothing), `tests/test_save_ops.py` (replaced folder, `./` spelling, the S0100 red team `test_g`), `tests/test_recover_ops.py` (each recovery op refused), `tests/ledger/test_save.py` (step 8 on a folder replaced after the job's start), `tests/ledger/test_no_blocking_reads.py`, `tests/ledger/test_save.py` (the gate's FIFO: the BL-0245 repro), overlay and precision reads of a FIFO; backend `tests/platform/test_app_folder_identity.py` (identity recorded and passed, the sidecar wait, the fill's child never makes the folder again, from `r2/test_r2_fill.py` and `rt2/fill.py`, no `.complete` on a mismatch, the discard, the queue's reason, texts), `tests/platform/test_engine_scheduler.py` (`ENGINE_UNAVAILABLE {app_folder_missing}` for every later job).
- Expected doc impact: spec `engine-jobs.md` §5.1, §6.1 step 8, §8.1, §11, §15; ADR-0012 note; `contracts/openapi.json`, `contracts/engine-protocol.schema.json`, frontend generated types; `design/generated/engine-job-texts.md`; backlog rows BL-0244, BL-0245 closed, new rows for what stays open.
- Open questions: none (the owner chose the mechanism; the new texts and reason follow it; no rubric item).

## Decisions
- **Where the check lives** (agent; the brief preferred the engine side): in every process that writes, since the sidecar writes too. The engine checks through the protocol's start (`--app-folder-id`, required with `--engine-lock`: argparse refuses the one without the other) for the engine lock and the four ops that write or sync in the app folder (`OpSpec.writes_app_folder`, checked by the server before the handler: a flag the op table states, so a new op cannot skip it by forgetting a call; an import-time assert ties the handler table to it and requires the lock). The sidecar checks it in its lock wait and in the bytecode fill and its discard (`AppFolder.open`). Not in the request params: the identity is the engine's start, not the request's, and the request's spelling was S0100's weakness (case 4).
- **Which object** (agent; S0101 lesson): the engine lock, the sidecar's lock wait and the fill make their folders and files through a descriptor on the checked folder (`dir_fd`), so they act on the object judged. The save's step 8 checks the identity of the handle it makes `local/` in (`_ensure_dir(..., parent_is=)`): the folder judged is the folder written in. The op-start checks (the save before its gate, the recovery ops) judge what the path names then, and the writes after them open by path again: a limit written in §6.1 step 8 (another program, in that instant). Making every recovery write handle-relative from the app folder would be a rework of `recover_all`/`restore` for a race only another program can make; not done.
- **The save's `SavePlan.app_folder` is optional** (agent; deviation from fail-closed by default, recorded): `None` takes the folder at `app_local_data` as it is. Only the in-memory fake's tests pass `None` (about 30 call sites through helpers that have no file system to ask); the protocol always passes the engine's identity, and the server refuses to run the save at all without one (`app_folder.changed` is True when the identity is None). `test_S0102_the_save_op_passes_the_identity_of_its_start_to_step_8` is the must-not-pass for the protocol passing None (mutant E9).
- **The fill's compiler child** (agent; the brief's first option): `-X pycache_prefix=.` with the child's working folder the build folder. Probed on APFS (scratchpad, `engine/.venv` Python 3.13): with an absolute prefix a removed app folder is made again at 0755 by `py_compile`'s `os.makedirs` (`workers=0` and `1`); with the relative prefix it is never made: `workers=1` fails each `mkdir` relative to the removed working folder, `workers=0` fails at once (`multiprocessing` asks `os.getcwd()`). The engines still read with the absolute prefix: the tree is the same (`<prefix>/<absolute source path>`). `compileall`'s worker processes `chdir` to the build folder by path when they start: a folder replaced by then is caught by the check before the mark. On a mismatch nothing is marked and nothing removed: what the fill made is gone with the folder, or in a folder that is no longer the app folder.
- **Later jobs** (agent): a new `ENGINE_UNAVAILABLE` reason, `app_folder_missing` (`msg:unavailable.app_folder_missing`: "Finzytrack's data folder was removed or replaced while Finzytrack was open. Your ledger files are safe. Quit Finzytrack and open it again."), through the queue table (`EngineLockFailed(app_folder=True)` → `NoEngine(why="app_folder")`) and the scheduler (`AppFolderChangedError` from the wait). The table stays pure: the reason is the event's. Every later job waits again before its fresh engine and gets the same answer; a reused engine meets the engine's own check (the save's `app_folder_missing`, the recovery ops' refusal). The open, rebuild, create and copy ops write nothing in the app folder (the inventory below), so they are not checked: on a reused engine they finish, and their next fresh engine meets the wait. A recover-all's fresh engine refused for the folder keeps the generic text: BL-0248.
- **The engine lock's failure** (agent): the engine takes no lock and ends with exit code 4 (stderr names the reason). Only the instant between the sidecar's wait and the engine's own check can reach it (the wait checks first); the job then reads as an engine stop, and the next job's wait gives `app_folder_missing`.
- **Texts** (agent): `msg:save.app_folder_missing` says "is missing or was replaced"; two recovery texts, `msg:recovery.app_folder_missing` (the listing refused; no Retry, which would meet the same folder) and `msg:recovery.failed_app_folder` (a try or an action refused).
- **BL-0245** (agent): `file_state` reads through `chunks` (non-blocking open, `fstat` regular-file check), so a FIFO, a socket or a folder at a ledger path is `Unreadable("EINVAL")`; `streamed_state` (the copy's) is now the same function and was removed (the copy's port uses `file_state`). The overlay load reads with `fingerprint.read_regular`; its `.asc` test refuses a non-regular file before Beancount's `is_encrypted_file` opens it (a stat check then Beancount's open by path: a swap in that instant is the one gap left in our reads); `precision.of_disk` reads with `read_regular` and skips a file that is no longer regular. Beancount's own real load opens files itself: BL-0249. The gate's FIFO case now ends `ledger_changed` or `io_error`, never unchanged.
- **Tests and the hang** (agent): a blocking read in these tests hangs the test, which the gate's hang detector stops; no fixed wait in the tests (as S0081 r2). On the base each FIFO test was run once under a thread with a deadline to record the failure (5 of 5 blocked).
