# S0050: The mirror build, to a fresh SQLite file

## Brief
- Goal: the next piece of M1a's read core after S0049 (roadmap §M1a "the mirror build and atomic publish"; ADR-0015). In the engine, from a ledger loaded by `ledger_engine.ledger.overlay.load`, build the mirror's base tables, `r_*` views and v0.2.2 compatibility views into a fresh SQLite file, as the mirror surface spec defines them (`design/specs/mirror/`, S0021), with the INV-21 goldens (S0022) and the domain vectors' mirror consumer (the `balance` family → `balance_assertions`) passing through the built file; the DDL generated from the build's code, checked against `surface.toml`, and committed as a snapshot (BL-0057, first half).
- The cut (agent; each piece tied to its source):
  - **In:**
    - `ledger_engine/mirror/core/schema.py` (pure): the 18 tables with their columns (name, type, public), the DDL of the `m_*` base tables, the `r_*` views (public columns, plain references only) and the 18 compatibility views (v0.2.2 columns in v0.2.2 order, from `r_<name>`; `meta` from `m_meta`); `export_version` = a hash of that DDL (spec `meta` note).
    - `ledger_engine/mirror/core/rows.py` (pure): the rows of 17 tables from the load result (`entries`, `errors`, `options`), the build date (`today`, injected; EP-10) and the caller's stamp (`ledger_version`, `fingerprint`, `built_at`): `postings` (TransactionId with ordinals, content hash, `source_account`, metadata JSON, account kind; README "Ids", "Metadata JSON"), `accounts`, `balance_assertions` (Beancount's own verdict and difference, and the pad pairing read from Beancount's padding transactions; README "Pad pairing"), `pad_directives`, `prices` (the ledger's), `notes`, `events`, `documents`, `custom_directives`, `stored_queries`, `ledger_options`, `ledger_errors`, `account_balances` and `lots` (as of `today`), `commodity_usage` (ledger end), `training_data`, `meta`. Sums and products in a 64-digit decimal context with `Inexact` trapped: a result that would need rounding fails the build (README "Exact numbers"; INV-06, INV-22).
    - `ledger_engine/mirror/build.py` (shell): `build(loaded, path, today, stamp) -> Built | BuildFailed`: the file must not exist; one transaction; a failed build leaves no file (ADR-0015 "a failed build never publishes"; INV-05). `TODO(BL-0113)` where the publish will go; `TODO(BL-0109)` for the engine job that will call it.
    - Port wrappers for what the builders need from Beancount (types re-exported; the inventory of booked positions per account for `lots`), classed as `WRAPPERS` (S0049's load rule).
    - `contracts/mirror-ddl.sql`, generated (`check_generated.py`), and the test that the built DDL equals `surface.toml` (BL-0057's DDL half).
    - The 54k measurement: the build on the demo generator's 54k ledger, recorded here.

    - BL-0057's second half, per-table checksums over the corpus ledgers, needs every table's rows: with BL-0120. `contracts/mirror-views.md` (ARCHITECTURE §11): not generated; `surface.md` already documents every view column from the same source (see Decisions).
    - The generation publish, pinning, GC and the stale-WAL rule (BL-0113, its own formal model first); mirror reads and the QueryRunner; the workspace-format core (the fingerprint and `ledger_version` arrive as the caller's stamp); the engine job (BL-0109). Indexes on the base tables: the mirror-reads slice, measured against its queries (BL-0122).
  - **Not done, against the request: BL-0119** (assertion balances in one pass). Its premise was that the mirror's `balance_assertions` rows need the balance before each assertion. They do not: the spec reads Beancount's verdict ("0 when it sets a difference on the entry"), and Beancount's `ops.balance.check` (a load stage the overlay runs) already sets `diff_amount` on every failing assertion in one pass. The build reads that; it calls `assertion_balance` nowhere. BL-0119 moves to its real first user, the reconciliation messages (vectors.md: the `balance` family's other engine consumer), see Decisions.

## Decisions
- **The cut** (agent): one slice for the whole build except the `commodities` rows. Every other table is a projection of one entry, option or error, or one of three aggregates the spec defines exactly, so splitting them would have produced a file whose missing tables nobody could tell from empty ones. The `commodities` rows wait for the owner (`design/inbox/20261028-iso-currency-list.md`: the literal "ISO 4217 code" makes gold `XAU` cash; rubric items 2 and 8); BL-0120 holds them, and with them BL-0057's checksums. The price sidecar's rows (BL-0121) wait for the sidecar. Indexes (BL-0122) wait for the reads that need them, so the build carries no cost nobody asked for.
- **BL-0119 not done here; pushback on the request** (agent). The request put BL-0119 in this slice because "the build is its first user". It is not: `surface.toml` says `passed` is "Beancount's balance check: 0 when it sets a difference on the entry" and `diff_number` "Beancount's difference", and Beancount 3.2.0's `ops.balance.check` (run in `PLUGINS_POST` by the overlay load) already walks the entries once and sets `diff_amount` on every failing assertion (read in its source). The build reads that field and never calls `assertion_balance`; the vectors pass through the mirror (`test_balance_vectors.py`). Building a one-pass `assertion_balance` now would serve no caller. BL-0119's text now names its real first whole-ledger caller, the reconciliation messages; its milestone stays M1a because only the owner may move an open item later (`check_deferrals.py`); S0050 proposes M4.
- **The table list lives in code and is checked against the spec, not generated from it** (agent; spec README "Not here yet": "generated from the M1a mirror build's code, which is checked against this spec"). `core/schema.py` names every column next to the builder that fills it; `test_surface.py` compares the built file (read as an outside tool reads it) with `surface.toml`, and `contracts/mirror-ddl.sql` is the generated snapshot. EP-16's "the mirror DDL with column comments → mirror docs" is met by its spirit: the TOML is the one source of the docs (`surface.md`) and the yardstick of the DDL. `contracts/mirror-views.md` (ARCHITECTURE §11) is not generated: it would repeat `surface.md` from the same source, a second document to drift.
- **Base tables carry no keys, constraints or indexes** (agent): the spec asks for none; v0.2.2's `UNIQUE` on lots lost label-twins and a key on `transaction_id` would refuse shared ids (BL-0059). SQLite's default rollback journal, so no `-wal` file sits beside a finished file (ADR-0015's stale-WAL rule is the publish's, BL-0113).
- **Rows first, then the file** (agent; ADR-0015, INV-22): every row is computed before the file is created, so a rounding refusal never leaves a file; any later error removes the file and its journal and is raised. The file is created with `O_EXCL` (a build never writes over anything) and mode `0600` (the ledger's content, for the user's own tools only).
- **`BuildFailed` for rounding, exceptions for the rest** (agent; EP-13): a sum or product that would round is an expected outcome of a ledger with extreme numbers, so the caller gets `BuildFailed("inexact", "<table>.<column>")`; a disk or SQLite error is not, and propagates after the cleanup. When several aggregates would round, the first computed is named (`account_balances`, then `lots`, then `commodity_usage`).
- **Readings of the spec, taken without the inbox** (agent; each consistent with the README's own rules):
  - `source_account` from a legacy key whose value is not text (`TRUE`, a number, a key with no value) is the value's Python text, as the content hash reads the same key (README "Ids": "the value's text"); v0.2.2 crashed the whole export on such a value (`_get_account_type` splits it), so no released value is changed. A key with no value gives the text `None`, as the TransactionId does.
  - `source_account` rule 2 takes the first leg whose metadata has an `import-key` key, whatever its value (the column's text: "carries an `import-key`"); the TransactionId's rule 3, by contrast, skips a key that is not text or is empty (README "Ids" says so for that rule only).
  - JSON of a set (the `commodities` option, a tag set inside an error's entry) lists its elements sorted, so two builds of one ledger give the same text (EP-10); v0.2.2's order was arbitrary, so nothing released is changed.
  - A lot or cost that a plugin hands over without a date or number is written with NULL there, not refused (Beancount's booking always fills them).
  - Lots are ordered by account, commodity, date, cost number, cost currency and label (no label first).
  - `accounts` rows follow the entry order of the `open` kept; `account_balances` and `commodity_usage` rows are sorted by their keys (the spec gives no order; sorted makes the output deterministic, EP-10).
- **The port gains `booked_positions`** (agent; INV-02, ADR-0024): `Inventory.add_position` per posting, as `realization` builds an account's balance, so lots are Beancount's own lots (merged, reduced, dropped at zero). It is a `WRAPPERS` member (S0049's load rule); the port also re-exports the directive types the builders match on.
- **No Decimal operation outside the 64-digit context** (agent; verifier F1, INV-06, INV-22): `abs()` rounds to Python's default 28 digits, so magnitudes use `copy_abs()` (exact, no context); Beancount's inventory merge for `lots` (`port.booked_positions`, `Inventory.add_position`) runs under `decimal.localcontext(EXACT)`, so a merged or reduced lot is exact or the build fails as `lots.units_number`. The wrap keeps Beancount's own rule, only its context changes; on such a ledger the mirror's lot is exact where `realization` would round. The sweep of `rows.py` and `build.py` (every Decimal operation, conversion and comparison): `number()` (`format(d, "f")`, no precision: exact); `json_value` and the content hash (`str(Decimal)`: exact); `account_balance_rows` (`Decimal(0)`, `EXACT.add`, `total != 0`: comparison is exact); `product` (`EXACT.multiply`); `lot_rows` sort key (comparisons) and `booked_positions` (**fixed**); `usage_rows` `abs()` (**fixed**), `EXACT.add`; `balance_rows` writes Beancount's own `tolerance` and `diff_amount` (computed during the load, not here); `build.py` and `schema.py` have no Decimal. The gate for the class is `test_the_rows_do_no_arithmetic_in_the_default_context`: `table_rows` under a default context of one digit with rounding trapped; any operation left in the default context raises. Found while testing, outside this slice: Beancount's parser rounds a written negative number of more than 28 digits, and interpolating such an amount makes the overlay load raise (BL-0123).
- **Incompleteness is explicit** (agent; verifier F2, INV-05, BL-0120): `rows.COMPLETE` (False until BL-0120 builds the `commodities` rows) gives both `Built.complete` (what the publish, running in the same engine job, checks without reading the file) and `meta.build_complete` (`0`/`1`, what a reader of a file checks). The smallest forms the two consumers can check; no per-table status, since only one table is missing. BL-0113's row: the publish refuses `Built.complete` False, so a published generation always says `1` (surface.toml `meta` note).
- **`ledger_errors.line_number` is NULL when Beancount gives a file but no line** (agent; verifier F4): the column is `change = "same"` with origin v0.2.2, and v0.2.2 wrote `err.source.get('lineno')`, NULL; the spec text "0" contradicted its own compatibility mark, so the text changed, not the code. A `LoadError` without a file keeps Beancount's own `lineno` 0.
- **Deviation from ENGINEERING.md:** none known. The core (`mirror/core/`) imports no I/O module (EP-01); the engine has no import-linter purity contract to enforce it (the main sidecar's contract does not cover `engine/`), which is a gap since S0049, not a deviation of this slice.

## Measurement (54k)
The demo generator's 54k ledger (`backend/scripts/gen_demo.py --size 54k --anchor 2026-10-28`: 54,018 entries, 108,241 postings, one file of 8.7 MB), `engine/scripts/measure_mirror_build.py`, macOS on the owner's development machine, warm disk cache: overlay load 1.34 s; rows 0.83 s; build (rows and write) 1.06 s; mirror file 78 MB; peak resident memory of the process 305 MB (the load alone: 193 MB). Two later runs in the same process were slower to load (1.8 s, 2.1 s; the earlier load result is still alive while the next one loads); the first run is what one engine job does. A cold first load (empty disk cache, first imports) took 5.6 s. So a 54k rebuild is about 2.4 s of engine time warm; the save budget (≤ 5 s at 54k, mirror update included, ADR-0008 amendment) is M1b's to measure with the write path. The file's size is mostly metadata JSON (each row carries its absolute file name).
