# S0148: "In use by another program" for a held file, and the share folder that refused (BL-0284, BL-0306)

## Brief
- Base: `bf527399` (`next`).
- Goal: a save that stops because another program holds a ledger file (an editor, antivirus, OneDrive's upload) tells the user so, naming the file, with what to do (close it or wait, then try again), in place of the general "could not read or write" text. No retry (owner). Recovery's blocked screen says the same of a held file. A save stopped by the share's pre-write folder sync names the folder that refused (BL-0306).
- Scope: the fifth slice of BL-0087's split (owner, 2026-11-22, in session: "Split OK. Do V4-1, let's go with your lean"). BL-0284 and BL-0306 as decided (owner, 2026-11-21, in session: "I'm accepting the inbox note as written", `design/inbox/answered/20261121-pace-and-scope.md` change A): one clear "in use, try again" text naming the file, no retry; the share's refused replaces a stated limit; BL-0306 folded into this text (name the folder that refused).
- Implements: BL-0284, BL-0306. Specs: `design/specs/engine-jobs.md` §6.8 (the open-file refusal on Windows, "On a network share"), §11 (the outcome rows and texts), §15 (limits). ADR-0069 (Windows' plain rename) is kept as it is: the replace is not changed, only how its refusal is told.
- Capabilities: CAP-WS-WRITE's save outcomes (no row change beyond the note). Invariants touched: INV-01 (no false "saved"), INV-22 (the outcome's truth); none loosened.
- **The bytes it protects:** the outcome stays truthful. "Not saved" and "unchanged" are said only when they are true; the new text never reaches a save that landed, a rollback that stopped (writes paused) or a recovery that did not resolve, and a non-hold error never gets it.
- **Which real setup needs this, and can a policy forbid the rest?** An editor, antivirus (Windows Defender) or OneDrive holding a ledger file on Windows: common, and the owner's decision covers it. A policy cannot forbid it. On macOS and Linux the new reason is not used (below).
- **Has this mechanism or its family needed two or more fix rounds before?** Yes: the save's outcome texts. S0063 (the save job, two verifier rounds), S0100 (the io_error texts and the re-hash, two rounds, one High), S0136 (the share, four rounds, three fix rounds), S0138 (Copy's EFS text, two rounds, one fix round). The policy question is settled by the owner's decision (one text, no retry); this slice adds no new rule to the outcome, only a cause's wording.
- **Review row:** "New write path or write outcome" (a new outcome text for a write): the verifier and the data-safety red team, with a fresh round after any product-code fix. **Risk class / lane: High / full lane.**
- Acceptance tests (fake first, then the runner):
  - over the fake (`tests/fakes/memfs.py`, Windows mode): a file held at the save's pre-write check is `NotSaved(in_use)`, unchanged, naming it, nothing written; a hold injected at every effect of a two-file save gives `in_use` only on a "not saved" outcome whose rollback resolved, with "unchanged" only when every file is at its old bytes, and never on a landed save, a paused one or an unfinished one; a rollback that meets a held file stays unfinished (writes paused, today's texts); recovery's try on a held file fails with the error kept, and resolves once it is released;
  - must not pass: a plain `OSError` of any errno (`EBUSY` from a POSIX adapter, `EACCES`, `EIO`) never gives `in_use`; an `in_use` without a ledger file gives `io_error`;
  - on the Windows runner (`tests/fs/test_windows.py`): a file opened without delete sharing at the save's check is `in_use`; one opened after the check (with and without delete sharing, the antivirus-like holder) stops the replace as `in_use` and the save rolls back unchanged; the adapter's rename over a held file raises the in-use error, and over a read-only file (no holder) still `EACCES`; a rollback that meets a held file leaves the journal open and recovery fails on it with `EBUSY`, then resolves;
  - the sidecar: the codec takes `in_use`; its text names the file and keeps the re-hash's sentence; `io_error` never says "in use"; recovery's `failed` with `EBUSY` says "in use" on Windows only; the share folder's text names the folder;
  - BL-0306: the share's refused pre-write sync is `NotSaved(io_error, path=None, entry=<folder>)`, unchanged, and its text names the folder.
- Expected doc impact: engine-jobs §6.8 (the open-file refusal's outcome), §11 (a new row and the share folder's text), §15 (the share's refused replaces; the held staging copy); `design/generated/engine-job-texts.md`; `contracts/engine-protocol.schema.json` (the docstring), `contracts/openapi.json` and `frontend/src/api/generated/openapi.ts` (the reason enum); BL-0284 and BL-0306 closed; BL-0087's row (S0148 done); `engine/CLAUDE.md` if it names the in-use error.
- Open questions: none at the brief that hit the rubric. The texts go to the owner before landing (the owner's request).

## Decisions
- **What "the share's refused replaces" means (agent, from the record).** BL-0284's row names only the antivirus case; the phrase comes from the pace note's table (change A) and points at `design/inbox/answered/20261120-ledgers-on-windows-shares.md` point 2: on the CI share another program merely looking at the file made 143 to 183 of 300 replaces fail (0 locally), each with nothing changed. Stated as a limit in engine-jobs §6.8 ("Limit (a share's refused replaces)"), no retry; the 2026-11-22 run 8 measures how many of them the in-use text catches there (the rename probe now runs on the share).
- **One error type, raised by the Windows adapter only (agent).** `fs.port.InUseError(OSError)`, errno `EBUSY`. The adapter raises it for `STATUS_SHARING_VIOLATION` (`_nt_error`, the one place every relative open and set-information call maps a status) and for a plain rename over a held file (below). Every caller that is not the writer keeps failing as on any `OSError` (errno unchanged: the base already mapped a sharing violation to `EBUSY`). Rejected: `errno == EBUSY` in the writer, which would tell macOS's and Linux's own `EBUSY` (a busy mount point, a bind-mounted file) "in use by another program", and Retry would not help there; a platform check in the engine, which the fake could not reach on macOS.
- **The replace's refusal (agent, then owner).** Windows refuses a plain rename over a file any other handle holds with `ACCESS_DENIED`, also when the holder shares deletion (S0130's P3), and the same status means an ACL or the read-only attribute. First built: after that refusal the adapter opened the target for delete access sharing nothing (`WindowsDir._held`) and said "in use" only on a sharing violation there. **Superseded** by the owner's "opetion 2" (below) after the 2026-11-22 run 8: `_held` is removed; the adapter raises every `ACCESS_DENIED` of a plain rename over a file as `fs.port.ReplaceDenied` (`EACCES`, a `PermissionError`, so every other caller fails as before), and only the writer's replace of a file it checked just before (`_best_effort`: delete access granted and not read-only in `_check_target`, `_check_replaced` again before the write) tells it `in_use`. ADR-0069 (the replace itself) is untouched.
- **Where the new text is used: the smallest truthful set (agent).** The writer's `_why`, the one place every port error of the durable order becomes a reason: an `InUseError` met while the save works on one of its files (`handles.on`) is `in_use`, naming that file; with no file (the save's record, its backups folder) it stays `io_error`. The sidecar shows it only for `not_saved` without `open_journal` (before the first replace, or the rollback resolved); a rollback that cannot finish stays `WRITES_PAUSED` with today's Reopen text (the reason is carried and not shown). Recovery's try: `failed` with `EBUSY` on Windows (`recovery_text.holds_are_in_use`) says "Another program is using <file> ... then press Retry", keeping the row's state and actions; elsewhere the system's answer as before.
- **Kept as `io_error`, and why (agent).** The gate's read of a file held without sharing reading (the fingerprint keeps no error kind; rare, an editor's open shares reading); a byte-range lock at a read (`ERROR_LOCK_VIOLATION`, Win32's `ReadFile`, which Python maps to `EACCES`); the Win32 absolute opens (`_open_path`, folders only); recovery's actions (Keep, the deletes), whose failure text names no cause today; Copy and Create (their own texts give the system's answer). Each is in engine-jobs §6.8's "Limit (in use)".
- **BL-0306: `io_error` with the folder, no new reason (agent).** `_try_share_syncs` raises `_Stop(io_error, None, folder)` for any refusal of its sync, so the folder reaches the sidecar as `entry`/`folder`; the text names the folder without saying "network drive", so it stays true for any future `io_error` that names a folder and no file. The variant that says "network drive" would need its own reason (offered to the owner below).
- **The fake follows the adapter (agent).** `MemFS` in Windows mode refuses a held file's removal, renames and `allowed(DELETE)` with `InUseError` (the base answered `EACCES` for the first three, which the adapter never did for a removal); `inject(..., in_use=True)` raises it at any effect. `tests/mirror/test_publish_crash.py`'s held-pointer test now expects `InUseError`.

- **The texts and the brief check (owner).** Owner, 2026-11-22, in session: "1A and 3B, keep the brief check, fold the Mac wording into S0150"; then, after run 8 (below), "opetion 2", which replaces "keep the brief check": an `ACCESS_DENIED` at the replace of a file the save checked just before is told in use, `_held` removed (the reason: in run 8 `_held` caught none of the momentary holds, C:'s 80 and the share's 180 to 187). Recovery's try keeps today's text for `EACCES` (its in-use text only for a sharing violation); the race (an ACL or read-only change between the check and the rename, told in use once) is stated in engine-jobs §6.8. Text 1 is A (`msg:save.in_use`: "…for example an editor, antivirus or OneDrive. Close that program or wait a moment, then try again…"), text 2 (`msg:recovery.failed_in_use`) follows it; text 3 is B (`msg:save.io_error_folder`, no new reason); `WindowsDir._held` stays; the Mac-only advice goes to S0150 (BL-0087's split line).
- **What the 2026-11-22 run 8 shows of `_held` (agent; reopens the premise of "keep the brief check", see "Runs").** The rename probe counts a refusal raised as `PermissionError` (`EACCES`: the adapter's `_held` found no other handle) as `refused`, and one raised as `InUseError` apart, as `in_use` (`test_V_F6_...`, S0148's form). Run 8 printed no `in_use` key on any volume: **none** of C:'s 80 refusals (antivirus, as in S0128's runs 12 and 13) and none of the share's 180 to 187 were told in use; by the time `_held` opened the file, nothing it could see held it (a scan that ends within the instant, or a hold without data access). So what is held for the in-use text on the runner is a holder that stays: `test_S0148_the_plain_rename_over_a_held_file_is_in_use_and_does_nothing[sharing-deletion]` and the save through it, `test_a_file_opened_after_the_check_stops_the_replace_and_the_save_rolls_back_unchanged[antivirus]` (both passed in run 8). A momentary antivirus scan at the replace, the case text 1A was chosen for, is told by today's build as `msg:save.io_error` ("could not read or write main.bean"), truthful but general. Brought back to the owner before landing; the owner chose option 2 ("opetion 2", above).
