# S0141: A lighter push gate for a push that does not land a slice (BL-0308)

## Brief
- Base: `2d55ac42c8602de9867568b5bea179390849a6b9` (`next`).
- Goal: a push whose HEAD commit carries the trailer `Gate: mid-slice` runs only the checks that protect what leaves the machine, and the landing push (no trailer) runs the whole gate as today (owner, 2026-11-21, in session: "I'm accepting the inbox note as written", `design/inbox/answered/20261121-pace-and-scope.md`, change C). The point is time: the gate timer's medians in this clone add up to about 600 s per push, about 480 s of it the backend and engine tests; the mid-slice set is about 22 s.
- Implements: BL-0308; amends ADR-0060's "the T0 pre-push hook is the per-push gate" (the owner's acceptance of change C is the decision; the amendment records it). PROCESS.md §6.
- Capabilities: none (tooling).
- Invariants touched: INV-23 and INV-24 by placement only: their guards (the staged-file guard and the privacy scan, over the pushed commits, their messages, the pushed tag messages and all tracked files) run in both modes, unchanged.
- Risk class / lane: Medium / light. Review row: "Tooling, gates, measurement" with a guard of real data or privacy (INV-23, INV-24) changed in where it runs: the verifier, and a fresh round after any fix.
- The bytes it protects: none (no write path). What it keeps truthful: a pushed commit never skips the privacy and real-data guards, and "landed" still means the whole gate passed on the landed tree.
- Which real setup needs this, and can a policy forbid the rest? Every slice: it pushes three or four times only so that a manual CI run can see the commit. A policy ("do not push mid-slice") would block the manual CI runs that the Windows work depends on; the owner chose the lighter gate.
- Has this mechanism or its family needed two or more fix rounds before? Yes: the push gate (S0031, several rounds) and the guard hook (S0139, three rounds). So the change is kept to one small, fail-closed decision: `check_push.py --mode` prints `mid-slice` only for one exact shape and `full` for everything else; the hook wraps the full-only checks in one `if [[ "$mode" != "mid-slice" ]]` block. `check_push.py`'s ref and tree rules are not touched.

### How a push says it does not land (decided here, cheapest and safest first)
- **Chosen: a trailer in the pushed HEAD commit's message**, exactly the line `Gate: mid-slice` in the message's trailer block (its last paragraph, every line of which has the form `Key: value`, after a subject paragraph), and no other line with the key `Gate` in that block. Read from the raw commit object (`git cat-file commit`), so no git configuration (`trailer.separators`, log encoding) changes the reading. Mid-slice also needs: every pushed ref is a branch update to the commit HEAD (no tag: a tag is a release mark; no deletion-only push). Anything else (no trailer, another value or spelling, two `Gate` lines, the line in the subject or a body paragraph, the mark only on an earlier commit of the range, the script failing) is `full`.
  - Why: the mark travels with the commit, so it is in the history and in the verifier's diff range, and it says which commit was pushed light; the bare `git push origin next` that the sandbox exempts stays bare.
- Rejected: **an environment variable.** The sandbox exempts only a bare `git push origin next` (no prefix), so an agent could not set it per push; one exported in a session would make every later push light, the landing one included, and leaves no record.
- Rejected: **a rule from the branch state** (for example "light unless the subject says `lands`"). Its default is the light gate: an unmarked or misspelled landing would skip the checks. The owner's brief requires the default to be the full gate.
- Rejected: **`git push -o`** (push options): the client-side pre-push hook does not receive them, and the push would no longer be bare.

### The mid-slice set (and one correction to the brief's expectation)
- Always run, in both modes: the push-gate preconditions (`check_push.py`, before any check: every pushed ref is HEAD, a clean tree, no replacement objects; and `--still` after the last check); per pushed range, the staged-file guard and the privacy scan of the pushed commits and messages, and of each pushed tag message; the staged-file guard over all tracked files; the privacy scan of all tracked files; invariants; the workflow parse; and, **beyond the owner's list, the two checks that read only the pushed range: the deferral check and the Cargo 14-day check.** Together they take under a second.
- Why the two are added (a tightening of the owner's list, agent-approved; PROCESS.md §9): a check of the whole tree, skipped at a mid-slice push, runs again at the landing push on a tree that holds every earlier commit, so skipping it costs only a delay. A range check does not: its range starts at the remote's tip (`check_push.py`; `@{u}` for the Cargo check), and a mid-slice push moves that tip. A backlog row deferred in a mid-slice commit would never be compared again (the deferral check runs nowhere else, not in `ci.yml`), and a new Cargo.lock entry would wait for the manual `nightly.yml` run (`--verify-all`). So the brief's expectation ("the manual CI run and the next landing push still run everything, so the cost is a delay, not an escape") holds for the whole-tree checks only; it holds for the range checks because they now run in both modes.
- Full mode only: the check-script meta-tests (and the hook's byte pin in them), the capability map, the generated artifacts, the write corpus, the oracle tests, format, lint, types and tests of the backend, engine, shell and frontend, knip, and the proof that the enforcement tests ran.
- Always: the timer canary before the checks, the time report at the end.

### What stops an agent from marking a landing push as mid-slice, and the cost
- Nothing technical stops it: the gates' self-defence against an agent bypassing them on purpose is frozen (PROCESS.md §9, IMP-0045). What stops it is the rule (PROCESS.md §6 and §3 step 7: the landing commit carries no `Gate:` trailer) and review: the mark is in the commit message, which the verifier's range and `git log` show.
- The cost if one does: the privacy and real-data guards, the preconditions, invariants, the workflow parse and both range checks still ran on that push. The whole-tree checks (tests, lint, types, generated artifacts, the hook pin) run at the next unmarked push, on a tree that holds the landed commit, or in the manual CI run (`ci.yml`), whichever comes first. So it is a delay in finding a failure, not an escape, as long as some later push is unmarked; the milestone exit's manual CI run and its macOS pre-push at the exit commit (roadmap) are the backstop. One check runs only in the hook and not in CI: the proof that the enforcement tests ran (`check_invariants.py --ran`); it too runs at the next full push.

### Acceptance tests (new; each fails on the base)
- `scripts/tests/test_push_mode.py`:
  - `check_push.py --mode` in a scratch repository: the exact trailer gives `mid-slice`; no trailer, and every malformed shape (another value, case or spacing, a carriage return, two `Gate` lines, the mark in the subject, in a body paragraph, in a last paragraph with a prose line, only on the parent commit, in a pushed tag's message), a tag push, a deletion-only push, a ref that is not HEAD, unreadable input, and an environment variable named like the mark give `full`.
  - the real hook's bytes, run in a scratch repository with a stub check timer that records each check's label: a marked push runs exactly the mid-slice set, no more and no fewer; an unmarked push and a malformed mark run every `run` line of the hook; the privacy scans, the staged-file guards and the preconditions run in both modes (must-not-pass); a dirty tree is refused before any check in both modes.
- `scripts/tests/hook_pins/pre-push.pinned` updated in the same commit (the byte pin, `test_hook_pins.py`).
- Base failure: `check_push.py` has no `--mode` (it reads `--mode` as the remote name and prints ranges), and the base hook runs every check on a marked push.

### Expected doc impact

## Decisions
- The mark is a trailer in the pushed HEAD commit (agent; the brief's comparison). It is read from the raw commit object by the stdlib `check_push.py`, which already runs first under the system `python3`; no new script. Its own reader, not `git interpret-trailers`: git's trailer rules depend on configuration (`trailer.separators`) and accept a block that is only partly trailers; ours accept exactly one shape.
- The range checks (deferrals, Cargo dates) run in both modes, beyond the owner's list (agent; a tightening, PROCESS.md §9): their range starts at the remote's tip, which a mid-slice push moves, so skipping them would be an escape, not a delay (Brief).
- The staged-file guard over all tracked files runs in both modes (agent): it is a real-data guard (INV-24) and takes 0.1 s; the owner's list names "the staged-file guard" without saying which.
- The hook was reordered, not branched per check: the always-run checks come first, then one `if [[ "$mode" != "mid-slice" ]]` block holds the full-only checks in their old order (agent). One comparison against an exact string, so any other output runs everything; a failing mode step sets `full`.
- The behaviour test runs the hook's real bytes in a scratch clone with a stub check timer (agent): the test sees which checks the hook would run, not what a reading of its text suggests. The stub runs only `true` and `false` (the canary keeps working); a `mktemp` shim gives the hook's report folder a place in the scratch folder, since macOS `mktemp -d` ignores `TMPDIR` and the sandbox refuses its default folder.
- `scripts/tests/test_engine_gates.py` read the engine block at two spaces of indentation; it now compares the block's lines without indentation (the block moved inside the full-mode block).
- Also logged: IMP-0077; the ADR-0060 amendment of 2026-11-21.
