# S0099: the fingerprint covers the plugin code a load imports (BL-0124)

## Brief
- Goal: a load's fingerprint records what its imports read, so that equal fingerprints mean the next load runs the same plugin code. A plugin source file edited after the preview refuses the save at the gate (`LEDGER_EXTERNALLY_CHANGED`, `design/specs/engine-jobs.md` §6.1 step 4); a plugin edit after a publish makes the published generation stale (the gate's `mirror_stale`, the open's and the rebuild's freshness, publish.md §7, §8); a plugin module the import did not find, which then appears, and a file that appears in a `pythonpath` folder and shadows a module the load found later on the path, change the fingerprint too. The save still runs no load and no plugin (ADR-0068 D1): the gate asks the import system's own path search the same questions, without importing, and hashes the files it names.
- Implements: `design/specs/engine-jobs.md` §1 "Fingerprint" (the plugin part, the last unbuilt one), §6.1 step 4, §6.7, §7; `design/specs/mirror/publish.md` §7, §8; ADR-0008 step 4; ADR-0015 (freshness); ADR-0064; ADR-0068 D1 (the preview's result is the prediction only if equal fingerprints mean equal inputs, plugin code included).
- Capabilities: CAP-DATA-WRITE-GATE (planned, M1), CAP-DATA-MIRROR (partial, M2), CAP-DATA-PLUGINS (planned, M3). No new row.
- Invariants touched: INV-01 and INV-22 (the gate's input: a plugin edit it misses lets a save land on a preview whose new-error list the user acknowledged for other code; fail closed), INV-05 (freshness), INV-02 (only `beancount_port` looks modules up by name), INV-10 (records bounded by the modules a load imports), INV-23 (no path in a log line; the fingerprint stays out of logs as before), INV-30 (nothing is written; the observation imports nothing and writes no bytecode).
- **The bytes it protects:** none of the ledger's bytes are written by this. The outcomes it keeps truthful: (1) the preview's list of new errors that the user accepts with "Save anyway" is the list of the code now on disk, so a save never lands on errors nobody was shown (INV-01; ADR-0067 decision 2; ADR-0068 D1); (2) a generation called fresh describes the ledger as Beancount would load it now, plugin code included (ADR-0015), which is what the gate's mirror check and the open's "fresh, nothing loaded" rest on.
- Risk class / lane: High / full lane (it gates ledger writes). Verifier and a data-safety red team (orchestrator).
- **Decision: which modules count** (agent; the row leaves it to the preview slice, BL-0106; decided here by behaviour):
  - Where `run_transformations` imports from (Beancount 3.2.0 `loader.run_transformations`: `importlib.import_module(name)` for each plugin, inside `sys.path[0:0] = options["pythonpath"]`; a plugin's own imports, at import time or while it runs, search the same `sys.path`). The engine starts with `-s -S -B -P` and a bootstrap that adds only its own site-packages (spec §5.1), so `sys.path` during the plugins is: the `pythonpath` folders (each file's folder whose `insert_pythonpath` is on), then the interpreter's standard library, then the engine's site-packages (the lockfile, `engine/uv.lock`). No user site, no system site-packages, no current folder. A plugin can add more entries itself.
  - **Recorded: every module the load's imports look up through the path search, wherever it is found, with the folders searched, the answer and the bytes of the file found.** Modules the engine imported before the load (Beancount, the engine, the standard library it uses) are not looked up by the load: the process's module cache answers, so no file can change what this load runs; they are out by behaviour, not by a list.
  - **No exemption by location.** A module found in the standard library or the engine's site-packages during the load (`beancount.ops.pad`, a `json` a plugin imports late) is recorded too. Its bytes are fixed by the engine build, so hashing it never changes a result; its *lookup* must be recorded anyway, because a file that appears in a `pythonpath` folder, which comes first, replaces it for the next load (a `wave.py` beside the ledger shadows the standard library's for the plugin that imports it). An exemption list would need the engine's roots named three ways (the bundle, the development venv, the test run) to save microseconds; a wrong root would hide a user file.
  - So "outside the engine's packages" is answered as: everything the load imported, the user-editable part (the `pythonpath` folders and any folder a plugin adds) and the fixed part alike. BL-0202 (copying a ledger's own plugin modules) still decides which of these files a copy brings; that is a different question (what to copy), answered there.
- **Design** (agent):
  - `beancount_port` (the only module that looks modules up by name, INV-02): while a load runs, `importlib.machinery.PathFinder` in `sys.meta_path` is stood in for by a recorder that asks `PathFinder.find_spec` itself and reports each answer (name, folders searched in order, origin, a package's search locations, the file the loader reads: the origin, or the zip archive holding it) before returning the same spec, so the record is the answer the import used. The caches of the path search are invalidated at the start of every load and before every observation, so no stale folder listing answers either. `find_modules(keys)` asks the same questions later without importing.
  - The record hashes the file at the moment of the lookup, before the loader reads it: an edit after that makes the next observation differ (the safe side).
  - The fingerprint gains a `modules` part keyed by (name, folders searched); `observe` asks the path search again and hashes the file found. The encoding's version goes from 1 to 2: every published generation is rebuilt once (a cache, ADR-0015).
  - One load with plugins per engine process: a module an earlier load in the same process imported is in the module cache and is not looked up again, so a second load would run that code without naming it. Every job loads once and a user-code engine is ended after its job (spec §5.1), so this holds; it is stated in the spec and in `imports.py`, and BL-0106 (the preview) carries it. (Changed during the build: see Decisions.)
  - Each consumer of the ledger set follows: the rebuild's used set, stamp, widening and "only an unchanged set is refused" (`rebuild._used`, `_read_by`, `_wider`, the refused branch); `publishing.within` (BL-0212 V1); the open's stamp and `LoadRefused.read` (the overlay's record); the copy's re-check (unchanged code: it compares whole fingerprints).
- **Inventory: the ledger set's parts against every place that records, observes, stamps or compares them** (built from `grep -n 'observe\|\.fingerprint\|LedgerSet(\|Fingerprint.of(' engine/src`, base 0c4b1476):

- **Times and identity:** the record and the observation compare content hashes and the path search's answers, never times; the path search's folder caches (which use folder mtimes) are invalidated before every question, so a coarse-mtime volume cannot hide an appearing file. No remount probe is needed (no file identity is compared).

## Decisions
- **Which modules count: every module the load's imports look up, with no exemption by location** (agent; the brief's reasons). Checked in real engine processes (the sidecar's own bootstrap, `-s -S -B -P`, a spike in the session scratchpad, synthetic ledger): a ledger with `insert_pythonpath`, a plugin that imports `colorsys` at import and `wave` while it runs, and a missing plugin records 6 lookups (Beancount's `ops.documents` and `ops.pad`, the two standard library modules, the plugin, the missing one); the open's stamp handed to a rebuild as its hint loads on the first try with the same `ledger_version`.
- **The record is the path search's own answer** (agent): a recorder stands in for `importlib.machinery.PathFinder` in `sys.meta_path` while a load runs, asks it, reports the answer and returns the same spec. Rejected: a second lookup beside the import (two answers can differ when a file appears in between); comparing `sys.modules` before and after the load (it says what was imported, not what was asked, so a module not found leaves no trace).
- **The file is hashed when it is found, before the loader reads it** (agent): an edit in between makes the next observation differ (the safe side; `test_a_plugin_edited_between_its_lookup_and_its_read_changes_it`). Rejected: wrapping the loaders to hash the bytes they read (exact, but an extension module is read by `dlopen`, which cannot be wrapped). Residual, stated: an edit and its revert both inside that window.
- **The path search's caches are emptied before each load and each observation** (agent): its folder listings are kept by folder modification time, which a coarse-time volume may not change (`test_a_plugin_appearing_in_a_folder_whose_time_is_put_back_changes_it`, `test_the_load_lists_each_folder_afresh`).
- **Zip archives:** a module found in a zip on the path (a plugin can put one there) is hashed by its archive, the file the loader reads.
- **Encoding version 2** (agent): `modules` is a new part; a version-1 stamp does not decode, so its generation is not fresh and is built once more (a cache, ADR-0015). The protocol's example fingerprints and two sidecar test literals move to version 2; `engine/tests/test_schema.py` now checks that every example fingerprint in the contract decodes.
- **Changed during the build: no replay of modules earlier loads imported** (agent). The first build kept, per process, each module a recorded load imported, and named the ones still loaded in every later record, so that two loads in one process would stay truthful. The sidecar's INV-10 scan of the engine (`backend/tests/architecture/test_caches.py::test_the_engine_holds_no_cache_across_jobs`) refused it: a module-level store that outlives a job, and a read of `sys.modules`. Allowing it would loosen a gate (the owner's call), and the requirement it served is met by a rule that already holds: one load with plugins per engine process (every job loads once; a user-code engine is ended after its job, spec §5.1; the copy's second load is in a fresh process). The rule is now stated in spec §1, `imports.py` and `engine/CLAUDE.md`, and BL-0106 (the preview) carries it, since a preview that loads twice would break it. The create's load check keeps no fingerprint, so it records nothing.
- **Tests stand in for fresh engines** (agent): `engine/tests/conftest.py` drops from the module cache, after each test, every module imported during it from a file under the run's temporary folders; a test that loads twice with a plugin drops it in between. Deviation from nothing in ENGINEERING.md; noted because a test-wide fixture now shapes what every load records.
- **Not added:** the copy's check (`copy_check.check_loaded`, the files the copy's load read) does not list module files; which plugin files a copy brings is BL-0202. Save step 3 (every ledger path resolves) does not resolve module files: they are observed, never written.
