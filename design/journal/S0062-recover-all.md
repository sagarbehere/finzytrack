# S0062: Recover-all inside an engine, and the engine operations behind the blocked screen

## Brief
- Goal: BL-0151's slice 3 (`design/specs/engine-jobs.md` §8.1 with "Afterwards", §4's `recover_all` row, §9.2, §11's blocked-screen rows, §15; ADR-0012 as amended, ADR-0063 decision 2 and "Keep the files as they are now", ADR-0064 and its engine-lock amendment). **Recover-all runs inside an engine that holds the engine lock**: the listing (a `durable_sync` of each `local/*/journal/` folder, then `.part` removal and the `.open` records read), each journal's try (S0061's `recover_journal`), and the three blocked-screen operations (Keep, Delete the kept copy, Delete it) are engine operations over the protocol; the sidecar's job only orders them, handles Cancel per journal, an engine's death and the stop bound, and returns a report of which journal blocks which workspace with the texts §11 gives. This closes BL-0151's handshake-to-`flock` gap: no ledger or journal file is read or written by the sidecar, and every recovery op is refused by an engine that does not hold the engine lock.
- Base: e39cee44 (pushed, tree clean).
- **What it builds:**
  - Engine, `ledger_engine.ledger.recover_all` (effects through `fs.port`): `list_journals` (each journal folder synced before it is read; `.part` removed; each `.open` record decoded strictly, or `unreadable`; a folder that cannot be synced or listed is reported `unlisted`), `inspect` (what stands at each file a record names now, and the kept copies beside it, by kind, SHA-256 and size; read-only), `keep` (§8.1 "Afterwards": the ledger-set locks without waiting, every file the record names `durable_sync`ed and every folder synced, then `.open` renamed `.kept` and the journal folder synced; nothing renamed when a sync fails), `delete_kept` and `delete_created` (each removes one regular file, only after the bytes there equal the SHA-256 the user was shown, only at a name the record derives: a kept name `journal.is_kept_name` matches for one of the record's files, or a path the record names as created, through the path guard, under that file's ledger-set lock).
  - Engine protocol: ops `recover_list`, `recover_try` (the try's outcome with cause, path, entry, detail and errno, plus `inspect`'s data when it stopped) and `recover_act` (`keep`, `delete_kept`, `delete_created`); the refusal key `engine.no_engine_lock` for a recovery op on an engine that has not taken the engine lock. Schema regenerated; the sidecar's strict decoders and contract tests follow.
  - Sidecar, `app.platform.engine_jobs.recovery`: the recover-all work (listing, then the actions the blocked screen asked for, then a try of every journal still `.open`), its report (resolved journals for the "undid an interrupted save" notice; blocking journals with reason `stopped | failed | cancelled | not_tried`, cause, path, entry, detail, errno, the record's workspace key, lineage and file `path_key`s, the inspection), and the pure match of a blocking journal to a workspace (§8.1 "Afterwards": by registry key, lineage, or a shared `path_key`; an unreadable record or a folder never listed blocks every open). Retry and Back are the same work run again (a fresh listing, so a record already `.resolved` is not tried and not "failed": red team r1 L7).
  - Queue table and scheduler: a recover-all's Cancel after its listing ends only its engine; that journal counts `cancelled` and the job goes on with the next one in a fresh engine (§4, §8.1); an engine's death during recover-all makes the journal in hand `failed` and the job goes on after the client's backoff (§8.1, §5.3); when no engine can start (the stop bound, an incompatible engine, a failed lock wait) every journal not yet tried is `not_tried` and the job ends with its report (§8.1; model `SpawnStep`'s `rc_spawn` branch). Before the listing, Cancel still ends the job (model I14). The composition root gives the boot's `recover_all` the real work.
  - §11's texts as constants and pure functions in `app.platform.engine_jobs.recovery_text`: the blocked screen per reason and cause (kept copy, created path, permission with the ACL entry, `failed` naming the file, the entry and the system's answer, with the read-only-drive wording for `EROFS`: red team r8 F1), the Keep and Delete confirmations, the undo notice, and a Reopen text for slice 4 that does not promise an undo after `created_path_taken` (r8 overflow 1). No screen exists (M2, BL-0092): the slice stops at the API/engine boundary and records what M2 must show.
  - (Planned here, moved at implementation: the registry's `RECOVERY_BLOCKED` entry. The registry's own rule is "a code joins with the slice that first raises it, with a test through the API"; the open that raises it is BL-0152/BL-0154. See Decisions.)
- **The step rule** (written before coding):
  - Every port operation may raise `OSError`; the engine may die at any effect; the sidecar's job may be cancelled between any two calls. The listing writes only `.part` removals in journal folders; `inspect` writes nothing; `keep` writes only the journal's rename (after syncs that write nothing); each delete removes one file. A failure in any of them writes nothing more and is reported with its errno; a crash leaves the journal `.open` (Keep before its rename) or `.kept` (after), each whole.
  - What each outcome claims: `Kept` only after the rename and the journal folder's sync; a delete's `done` only after the removal and its folder's sync; `resolved` only from `recover_journal`'s `Resolved`. A journal is reported blocking with exactly one reason; every listed `.open` journal ends the run either resolved, kept by an action of this run, or blocking (INV-32: none skipped); a folder that could not be listed, or a run that ended before its listing, blocks every open (fail closed).
  - Nothing the user did not see is deleted: a delete names the SHA-256 from the report and refuses when the bytes differ (a write between the look and the delete; the instant between the engine's check and its `unlink` stays §15's POSIX limit).

## Decisions
- **The listing and every step on disk run in the engine, not the sidecar** (agent; BL-0151 offered "do recover-all's listing and tries inside an engine, or have the engine take the lock before its handshake reply"): the first needs no change to the handshake order S0053 tested and gives a structural rule instead of an ordering: an op that reads or writes ledger or journal files carries `OpSpec.needs_engine_lock`, and an engine that has not taken the lock refuses it (`engine.no_engine_lock`). The sidecar's own lock wait stays as it is (before every fresh engine).
- **Three ops, not six** (agent): `recover_act` carries Keep and both deletes; `recover_try` carries `inspect`'s data for a stopped journal, so the blocked screen needs no further request. Fewer hand decoders on the sidecar, each held to the schema by a recursive mutation test.
- **Delete checks the bytes the user saw** (agent; the owner's "after you've looked at it"): each delete names the SHA-256 the report showed and is refused `changed` when the bytes differ; "after Show both" itself is the screen's (BL-0092). The kept name must be exactly one this journal derives, up to NFD (`journal.derives_kept_name`), not the wide case-folded `is_kept_name` the stop uses: a wider match fails closed for a stop but would remove a file that is not ours for a delete.
- **The blocked screen's actions ride on the next recover-all** (agent): Keep, Delete the kept copy and Delete it are `actions` of a `recover_all` run, applied after its listing and before its tries, so they run in the switch's window, in an engine that holds the lock, on a journal the listing just found `.open` (an action on any other is refused `not_open` without a call), and Retry semantics (recover-all first, owner 2026-10-29) hold for them too. No new job kind.
- **Keep on a read-only drive** (agent, after a probe: an APFS image attached read-only answers `EROFS` to `F_FULLFSYNC` on a folder and a file, plain `fsync` succeeds): Keep takes `EROFS` from a sync as "nothing pending" and goes on, so red team r8 F1's way out ("Keep or a read-write remount clears it") works; any other sync error renames nothing. §15 line.
- **A recover-all that never listed blocks every open** (agent): before its listing there is no engine to read the records with, and ADR-0063 already blocks every open for a journal whose file list cannot be read. The model's `DispatchUnavail` lists in the sidecar; the code does not (that is exactly the read BL-0151's gap is about). A queued recover-all with no engine still ends `ENGINE_UNAVAILABLE` (no report), and `blocking_for(None, ...)` blocks every open. §15 line; the TLA mapping's `DispatchUnavail` row now names only the quit notes (BL-0154).
- **"While saving or undoing"** (agent; red team r2 L4 asked the kept-copy text to say which): only a copy the try itself makes is known to be the undo's (`displaced`, `outside_save_in_temp`); a copy found when the try starts (`kept_copy`) may be the save's or an earlier try's, and the disk does not say, so that text says "saving or undoing a change". §15 line.
- **`RECOVERY_BLOCKED` is not registered here** (agent; the brief planned it): the registry's rule is that a code joins with the slice that first raises it, with a test through the API; nothing raises it until the open (BL-0152/BL-0154). Its fields are fixed by the report (`Blocking`: path, workspace key, reason, cause, errno).
- **An unreadable record is not tried** (agent; model `RC_Next` on `topen`): it blocks as `stopped`/`unreadable` without an engine call.
- **`ledger_locks` made public** (agent): S0061's private `_locks` is the one way to take the ledger-set locks without waiting; Keep and the deletes take them the same way.
- **Deviations from ENGINEERING.md:** none known. The fake job engine gained scripted ops (`scripted`, `CRASH`, `CRASH_TO_BOUND`, `BLOCK`) for these tests.
