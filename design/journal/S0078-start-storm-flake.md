# S0078: a close during the engine's start is logged before the sidecar exits (BL-0176)

## Brief
- Base: d7ad3c60.
- Goal: close BL-0176. `backend/tests/test_main.py::test_a_signal_at_any_line_of_the_start_never_skips_the_engines_close` fails intermittently, more often under parallel load: the stormed sidecar exits 0 and its log holds no line at all, so `engine.closed` is not found. Diagnose first (product defect or wrong test premise), record the root cause, fix the side that is wrong, and prove it with repeated runs under the load that triggered it. Owner, 2026-11-07: "Let's also do the 3 lower priority items you listed, so the slate is clean".
- Root cause (diagnosis below, under Decisions): a **product defect**, not a wrong premise. `EngineClient.close()` never takes the call lock (S0057), so when it comes while a call holds it (here the boot's recover-all starting the first engine, in its handshake), the table's `Close` step, which publishes `Closed` and logs `engine.closed`, runs later on that call's thread. `close()` waits for the drain of the engine it signalled (S0076), not for that step, so `main` returns and the interpreter exits while the call's daemon thread has not yet run it: the log loses `engine.closed`. The engine itself is ended and drained before `close()` returns (or never spawned), so no engine and no engine lock outlive the sidecar; only the close's record is lost.
- Fix: `close()` also waits, within the same bound (`close_wait`, the display delay), until the table's close step has run its effects (`engine.closed` written), unless the close was deferred past a job's commit point (that job is not waited for, as before).
- Implements: spec `design/specs/engine-jobs.md` §5.5 and §9.3 step 4 (`close()` waits at most the display delay); `design/specs/failure-modes.md` E7 ("Logged `engine.closed`"), M7 ("Every path reaches that close: ... a signal at any line of the start or the stop").
- Capabilities: CAP-DATA-ENGINE-JOBS (planned; no row change).
- Invariants touched: none.
- **The bytes it protects:** none. This is not a write path; it keeps the log truthful: a quit during the engine's start is recorded as a close, not left looking like a crash.
- Risk class / lane: **Medium / full lane** (agent). It changes when `close()` returns (later by the time a call thread needs to feed the end it already observed, still bounded by the display delay), not what any engine writes, nor which engine runs. No data-safety red team: the mechanism neither writes ledger or user data nor gates a write (PROCESS.md §4, ADR-0068 D6). The verifier may raise it.
- Acceptance tests:
  - must-not-pass on d7ad3c60, deterministic (no load needed): `backend/tests/platform/test_engine_client.py::test_close_returns_only_once_engine_closed_is_logged_by_the_call_in_flight` (the call in flight's `engine.closed` line is held in the log sink: `close()` has not returned while it is held; returns once it is written), for a call in its handshake and a call in a request;
  - the exclusion kept: `test_a_cancel_or_close_past_the_commit_point_lets_the_job_finish[close]` (close returns while a job past its commit point still runs);
  - the bound kept: `test_close_returns_while_a_call_waits_on_an_engine_our_signal_cannot_end`, `test_close_stops_waiting_for_a_drain_that_does_not_end`;
  - the storm test itself unchanged (its premise holds), repeated under parallel load: counts in Decisions.
- Expected doc impact: failure-modes E7 (the close waits for its record too; the new test named); spec engine-jobs §5.5 and §9.3 step 4 (one clause); ARCHITECTURE.md supervision line on `close()` if it states the wait; `engine_client` module docstring and `close()` docstring; BL-0176 closed. No user docs, no API change, no generated artifact.
- Open questions: none for the owner (not a rubric item: no new bound, no data or finance semantics).

## Decisions
- **Reproduced first, on the base** (agent): the full backend suite at `-n 8` failed the storm test in 1 of 8 runs (`AssertionError: []` from `engine_gone`: the log had no line). A scratch harness ran the storm child 400 times, 28 at a time beside 10 busy-loop processes, with a probe around `EngineClient.close()` recording what it met and the table's state when it returned (`scratchpad/repro2.py`, the test's own `STORM` script with the probe added). On d7ad3c60: **3 of 400 failed, all three the same**: `close()` met a call in flight (`_in_call`, an engine run present) in `Handshaking`, returned with the state still `Handshaking`, the sidecar exited 0, and the log was empty. In every passing run the state was `Closed` when `close()` returned.
- **Root cause: a product defect** (agent). `close()` takes no call lock (S0057), so when a call holds it (here the boot's recover-all, whose engine is in its handshake) the table's `Close` step, which publishes `Closed` and logs `engine.closed`, is run by that call's thread once it reads the end of the engine's output. S0076 made `close()` wait for the drain of the engine it signalled, not for that step. Once the drain was done `close()` returned, `main` returned, and the interpreter exited; the scheduler's job thread is a daemon thread, so when it had not yet been scheduled the line was never written. Parallel load makes that scheduling gap longer, hence "worse under load". `engine.ready` is missing too because the engine never finished its handshake: the whole log was empty, not truncated.
- **What was not lost** (agent): the engine itself. The spawn runs under `_signals`, the lock `close()` marks the end under, so a close either comes before the spawn (the start then returns our end and spawns nothing) or after it (the engine is signalled, and `close()` waits for its drain). No engine and no engine lock outlived the sidecar. So the risk is the truthfulness of the log, and it stays Medium.
- **Rejected: fix the test** (agent). The test's premise holds: E7 and M7 say a close at any line of the start is logged as `engine.closed`, and the product broke that. Accepting a missing line in the test would hide a quit during the boot that reads, in the log, like a crash.
- **The fix waits inside `close()`, under the same bound** (agent): `close()` now waits until the drains are done *and* the table's close step has carried out its effects, all within `close_wait` (the display delay; no new number). A flag `_closed_logged` is set, and `_signals` notified, after the effects of the step that reaches `Closed`, on whichever thread ran it; set after the effects, not when the state is published, because the state is published before the `Log` effect runs (the mutant "flag at publish" shows the difference). A close deferred past a job's commit point (the same test as `_mark_ended`: past commit, no reason recorded) waits for neither, as before: the job finishes and settles the close later. A call our signal cannot end (a stuck process) still cannot hold the quit: the bound cuts the wait, as for the drain.
- **The deterministic test** (agent): `test_close_returns_only_once_engine_closed_is_logged_by_the_call_in_flight[handshake|request]` holds the `engine.closed` line in the log sink, which runs on the call's thread, until released; `close()` must not have returned while it is held (the file's existing `ABSENCE` pattern of S0076) and must return once it is written. `close_wait` there is 4 × `DEADLINE`, beyond every join, so a close that is never woken fails instead of returning at its bound. It fails on d7ad3c60 in 3 of 3 runs, both parameters ("close() returned before engine.closed was written"). The storm test is unchanged: its premise was right.
- **Proof under the load that triggered it** (agent): the same probe harness on the fix: **0 of 400 failed**, `close()` returned with `Closed` in 400 of 400 (base: 3 of 400 failed under the same load). Full backend suite at `-n 8` on the fix: **20 of 20 runs passed** (2165 passed, 24 xfailed each; base here: 1 of 8 failed, S0075: 2 of 2). Read with care: at the base's 1-in-8 rate, 20 clean runs alone would still happen about 7% of the time with no fix; the evidence that the cause is gone is the deterministic test and the probe (0 of 400 runs where `close()` returned before `Closed`, against 3 of 400 on the base).
- **Gates** (agent): backend `ruff format --check`, `ruff check`, `pyright` (0 errors), `lint-imports` (8 kept), `deptry src`, pytest as above; `scripts/run_meta_tests.py` (836 OK); `check_failure_modes`, `check_invariants`, `check_capabilities`, `check_generated`, `check_retired_terms` (0 refused). Engine untouched.
- **Load runs kept clean** (agent): a first 20-run batch of the full suite on the fix was stopped after 6 passing runs and is not counted, because the base `engine_client.py` was put in place for about a second (to re-check the final test on the base) while it ran.

## Verifier
- Round 1, head 1732e012: PASS WITH FINDINGS, 0 High, 0 Medium, 2 Low, 2 questions (report in the orchestrator's hand). One fix round; no second round (Medium slice, no High, no Medium; ADR-0058).
- L1 Low: fixed (test). The test did not kill `if self._closing and not self._closed_logged:` (the flag set by any step after the close request): when the reply comes just before the signal, the call steps to `Ready` and logs `engine.closed` only at `_call`'s final settle. Added the case `answered` (a stand-in writes a progress message and the reply in one write; the call's `on_event` starts the close and waits until it has signalled), which kills that mutant; also `starting` (a fresh start waiting for the previous engine's held drain), `restarting` (a backoff longer than the test) and the bound (`test_close_stops_waiting_for_its_line_at_the_bound`). All five cases fail on d7ad3c60.
- L2 Low: fixed (doc). `design/ARCHITECTURE.md` (the stateful-parts row "Engine client") and `backend/src/app/platform/state_registry.py` now say the close also waits for its own `engine.closed` line. The same grep found spec §14's test list; updated too.
- Q1: done as recommended. `deferred` now also needs the engine still running (`exited` or `leader_exited()`, as `_ending` and `_mark_ended` test it), so a close that meets an engine past its commit point that has already exited by itself waits for its close step within the bound. Safe: such a call has nothing left to finish; it only feeds the stop it has seen. Test held at the call's clock read after the end of output (the first version held the `engine.stopped` line, but by then `End` had cleared `_run`, so it passed on 1732e012 too; replaced).
- Q2: done. `close()`'s docstring says it must not be called from a call's own `on_event` (it would wait the whole bound), as `_call` refuses a nested call. Nothing calls it there today.
