# S0118: the queue's two seams around a save (M1b, BL-0255, BL-0256)

## Brief
- Goal: M1b's fourth slice, settling the two seams the M1a area review found around a save (S0109 F1, F2).
  - **BL-0255** (a rebuild that ends without publishing leaves later writes refused `WORKSPACE_NOT_READY {WARMING}` until a reopen). When the save's gate answers `mirror_stale`, **and when the preview answers `stale` with reason `unpublished` or `not_fresh`**, the job also submits the workspace's background `rebuild` (`rebuild_spec`). A queued one answers `AlreadyQueued`. A refused submit (`ENGINE_QUEUE_FULL`, `WORKSPACE_NOT_OPEN`) is logged with a new registered, content-free event (e.g. `rebuild.not_queued` with the refusal's code); it is never raised and never changes the job's answer. The landed save's existing submits (`save.submit_save`, `writes._confirm_work`) log their refusals the same way, through one shared helper in `rebuild.py`. That way "wait a moment and try again" comes true. The preview is in scope by the owner's choice (below): since S0117 a save is reached only through a preview, and the preview's `stale` comes first.
  - **The rebuild's hint.** The save passes its plan's fingerprint, as it does after a landed save. For the preview, the engine's `stale` answer gains a hint fingerprint:
    - the published generation's stamp, when it decodes **and its root equals the request's root** (the engine's `rebuild` refuses a hint of another root, `protocol/rebuild.py`; `preview.run` answers `not_fresh` for another ledger's generation, `test_another_ledger_s_generation_is_stale`);
    - otherwise the root's own set observed now (`unpublished`, an undecodable stamp, another root's stamp), which the rebuild widens by its `moved` try (§7).
    `other_generation` carries no hint and queues nothing: the mirror may be fresh, and the caller plans again on the current generation. The preview's answer check (`_holds_together` in `app.platform.engine_jobs.preview`) accepts a fingerprint exactly when the answer is `prepared`, or `stale` with `unpublished` or `not_fresh`. The engine's `PreviewResult` docs and `contracts/engine-protocol.schema.json` are regenerated.
  - **BL-0256: closed as a stated limit, no queue change** (owner's decision below). Engine-jobs §3 states that a preview or confirm made before a save's rebuild ran is refused and the user previews again. A preview's generation is fixed when it is queued (`writes.submit_preview`), and a confirm's is its plan's (`_confirm_work`'s `PREVIEW_STALE`), so no queue order can make it succeed. BL-0255 makes the preview again succeed once the rebuild has run. `queue.py`, `TABLE_VERSION` and ADR-0064 do not change.
- Implements: ADR-0015 (writes refused while the mirror is stale); ADR-0068 D1 (the background rebuild after a save); `design/specs/engine-jobs.md` §2 (`rebuild`, `preview` rows), §3 (the limit line), §7; BL-0255; BL-0256 (as a limit).
- Capabilities: CAP-DATA-ENGINE-JOBS, CAP-DATA-WRITE-GATE (status unchanged; row text only if it states the old behaviour).
- Invariants touched: INV-01, INV-22 (no check is loosened: the gate, the preview's baseline check and the confirm's generation check are unchanged; the slice only adds a rebuild submit), INV-10 (the cap of one queued background rebuild per workspace holds), INV-11 (no new state), INV-23 (the new log event carries the job, the workspace key and the refusal code only), INV-28, INV-31 (a rebuild is submitted only for the job's own workspace; `WORKSPACE_NOT_OPEN` refuses it after a switch).
- Risk class / lane: High / full (around ledger writes). Review budget row: **Hardening an existing write path** (owner: "Both rows are hardening of an existing write path, one lane and one kind"):
  - the verifier;
  - the data-safety red team joins only if the verifier reports a class (a) finding;
  - a fresh round after any fix that changes product code, in which only High and (a)/(b) findings are fixed and the rest become backlog rows.
- The bytes it protects: no ledger byte directly; the gate, the preview's baseline check and the confirm's check, which protect the bytes, are unchanged. The outcome it keeps truthful: `WORKSPACE_NOT_READY {WARMING}`'s "wait a moment and try again", which today can stay false until a reopen.
- Mechanism questions (PROCESS.md §3 step 2):
  - **Which real setup needs this, and can a policy forbid the rest?** Any rebuild that ends without publishing, which no policy can forbid: a plugin that crashes in a load, a ledger a sync tool rewrites during the load (`changing`), an I/O refusal, the OS purging the cache folder (`unpublished`), a full queue. The policy option (a stated limit) was taken for BL-0256 and offered for BL-0255's scope; the owner chose the fix for BL-0255.
  - **Has this mechanism or its family needed two or more fix rounds before?** The queue's pure table has (S0053 two verifier fix rounds; S0058 a High; S0069 a High, ADR-0068 D8; S0080 one round), and this slice no longer touches it. The rebuild job (S0070 one round, S0087/S0088 rounds on its publish) and the preview (S0116, S0117 five rounds on the confirm's save) are touched only by an added submit, a hint field and an answer-check widening. **If any finding comes in, the policy option goes to the owner before the first fix round** (owner's instruction for this slice; S0117's retro).
- TLA+ and conformance: **not touched.** Since S0072 the engine-jobs model checks durability only (EP-19, ADR-0068 D5; spec §13), and its trace corpus covers saves, creates, copies and recover-all. Nothing here changes a durable step, and the queue's table and its `check_step` oracle are unchanged. `gen_traces.py --check` must stay green.
- Acceptance tests (tests first; each fails on the base commit):
  - Save (sidecar):
    - a gate answer `refused/mirror_stale` submits one background rebuild of that workspace, with the plan's fingerprint as its hint, and still answers `WORKSPACE_NOT_READY {WARMING}`;
    - a second one while the rebuild is queued gets `AlreadyQueued` and queues nothing more;
    - a refused submit leaves the answer unchanged, does not raise, and logs the new event;
    - no other refusal reason submits a rebuild.
  - Preview (sidecar and engine):
    - `stale` with `not_fresh` or `unpublished` submits the rebuild with the answer's hint;
    - `other_generation` submits none;
    - the engine's `stale` answer carries the published stamp when it decodes and has the request's root, else the root's own set; another ledger's generation gives the root's own set, never a hint the rebuild refuses;
    - the answer check refuses a fingerprint on `refused`, `moved`, `paused` and `stale/other_generation`.
  - End to end (the real engine, a test copy, `tests/workspaces/test_writes_end_to_end.py`'s entry): a save lands and its rebuild is made to end without publishing. The next preview answers `WARMING` and queues a rebuild; once that has run, the preview again prepares a plan. Also the same with the mirror's generation removed (`unpublished`).
  - The landed save's submit, refused, logs the event (today it is dropped silently).

## Decisions
- BL-0256: the owner first chose option (b) (2026-11-14: "For Q1, let's go with option b.", recorded on the BL-0256 row). Before coding, the implementer showed on the real engine that (b) cannot turn a refusal into a success under S0117's generation binding: a preview or confirm queued before a save's rebuild is refused whatever the order, and (b) only swaps which refusal it gets, after a delay. Taken back to the owner as rubric item 4 (`design/inbox/answered/20261114-bl0256-premise.md`). Owner, 2026-11-14, in session: "Stated limit (Recommended)". So no queue change and no ADR-0064 amendment.
- BL-0255's scope covers the preview's `stale` as well as the save's gate, with the engine's `stale` answer carrying a hint fingerprint (owner, 2026-11-14, in session, choosing between "Gate and preview" and "Gate only, as the row says": "Gate and preview (Recommended)").
- Both rows in one slice (owner, 2026-11-14: "Run slice 4 as one slice with the `slice` skill. Both rows are hardening of an existing write path, one lane and one kind."). With BL-0256 now a limit line, the queue table, whose two earlier fix rounds IMP-0072 would bar from a batch, is not changed.
- (agent, from the implementer's stop report) The preview's hint is the stamp only when its root equals the request's root, else the root's own set; without this, the queued rebuild would be refused every time for a generation of another ledger.
- (agent) New backlog row for an S0117 seam BL-0255 makes more reachable: the confirm takes its plan from the store before the gate, so retrying a confirm after the gate's `WORKSPACE_NOT_READY` ("wait a moment and try again") answers `PLAN_ALREADY_CONFIRMED` ("already sent to be saved; check your ledger") for a change that was certainly not saved. Not false, but misleading. Class (d), M1b, with the confirm's HTTP route.

- (agent) The preview's answer check is an "exactly when": a fingerprint comes with `prepared`, or with `stale` `unpublished`/`not_fresh`, and with nothing else; a hinted `stale` without one is `INTERNAL` (INV-22: an answer that does not hold together is never acted on). `tests/api/test_contract_codes.py`'s stale scenario now scripts `other_generation` (no hint), since its old fixture, `not_fresh` without a hint, no longer holds together.
- (agent) `engine.preview`'s `TABLE_VERSION` 1 → 2: the table now also decides the hint. The decision's inputs are unchanged (the hint follows from `stale`).
- (agent) The log event `rebuild.not_queued` carries `job` (the asking job's id), `workspace_key` and `code` (an enum of the queue's refusals: `ENGINE_QUEUE_FULL`, `WORKSPACE_NOT_OPEN`, and `ENGINE_UNAVAILABLE` while the app closes), level `warning`.
- (agent) `save_work`'s `after_saved` becomes `queue_rebuild` (`rebuild.QueueRebuild`, called with the job's context so it can log); it now runs after a landed save and after the gate's `mirror_stale`. `preview.submit_preview` takes the clock and wires the same helper.
- (agent) The end-to-end "rebuild made to end without publishing" refuses the landed save's rebuild submit once (a full queue, one of BL-0255's listed causes), by wrapping the rig's `EngineJobs.submit`; everything else is the real engine on a test copy. The `unpublished` case removes the mirror folder, as the OS purging the cache would.
- (agent) The capability rows CAP-DATA-ENGINE-JOBS and CAP-DATA-WRITE-GATE are unchanged: neither states the behaviour this slice changes.

- Round 1, owner's decisions on the two findings with a class (offered as policy options before the first fix round, as the owner asked for this slice):
  - Verifier V1 (a fresh generation whose `ledger_errors` cannot be read): owner, 2026-11-14, in session: "Align freshness (Recommended)". One rule in the engine: such a generation is not fresh (`publishing.fresh_current`), so the open and the rebuild build it again.
  - Red team RT-F1 (the root-only hint drops the include globs): owner, 2026-11-14, in session: "Narrow the scope (Recommended)". Only `not_fresh` with a readable stamp of this ledger (which carries its globs) queues the rebuild; with no usable mirror the preview stays `WARMING` until a reopen, as before S0118: a stated limit (engine-jobs §2 "Limit (no usable mirror)") and BL-0272.
- (agent, round 1) The answer check (`_holds_together`) now accepts exactly these shapes for a fingerprint: required on `prepared`; allowed, not required, on `stale` with `not_fresh` (a generation of this ledger with a readable stamp gives one, an undecodable or another root's stamp gives none); refused on every other outcome and reason (`refused`, `moved`, `paused`, `stale/unpublished`, `stale/other_generation`). The round-0 bullets above that name `unpublished` hints and the root's own set are superseded by this.
- (agent, round 1) A generation whose error table cannot be read stays `stale/unpublished` at the preview, with no hint: the preview's `read_baseline` reads it as none (unchanged). It is not given a `not_fresh` stamp hint, since the owner's option queues only for `not_fresh`; a reopen, or the rebuild after the next landed save, builds it again now that freshness agrees (V1).
- (agent, round 1) Every other freshness reader checked for V1's gap between "fresh" and "readable as a baseline": `publishing.fresh_current` (the open, with `by="open"`, and the rebuild) now reads the error rows (`Store.errors`, added to the protocol, so the fakes answer it too: `tests/mirror/fake_store.py`); `mirror.publish.fresh` is called only from it; the save's gate (`read_published` + `fresh_on_disk`) needs no error rows (its plan was made by a preview that read them, and a save that lands queues the rebuild that builds the generation again), so it is unchanged; the preview's `read_baseline` already required them. The sidecar's mirror reads (`app.mirror`) decide no freshness.
