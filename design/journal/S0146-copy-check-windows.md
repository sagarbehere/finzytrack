# S0146: The copy check on Windows, a test copy's mark and the `c:\` root (BL-0087's split, part 3)

## Brief
- Base: `b90455c8` (`next`).
- Goal: three of BL-0087's must-fix lines before writes turn on for Windows.
  1. **The copy check's Windows form (`COPY_CHECK`).** `ledger/fresh_load._answer_line` reads the fresh-load child's answer with `selectors` on a pipe, which Windows' `select` refuses (sockets only), so no copy finishes on Windows. A Windows form with the same contract: one answer line or what the child wrote before it ended, whichever comes first; never a wait for the pipe's end (a process a plugin started may hold it open after the child ended or died; BL-0203, S0082 V1); no time limit; once the child has ended, only what is already in the pipe is read. POSIX byte for byte as it is. The child is in the engine's Job Object on Windows (stated with how we know). The tests that skip with `COPY_CHECK` run on Windows (`tests/test_copy_ops.py`, `tests/test_copy_v022_install.py`, `tests/ledger/test_fresh_load.py`, and the two other sites the inventory found: `tests/ledger/test_copy_efs.py`, the note in `tests/fs/test_windows.py`); a test that sends POSIX signals gets a Windows form or a precise skip; `COPY_CHECK` is removed.
  2. **A test copy's mark carries the file ID** (S0128 Q-C): a runner test that the folder mark of a copy's folder (`DirHandle.mark()`'s `born`, the identity the sidecar's `CopyMark` records and the save's `confine` checks) is the folder's file ID on NTFS and ReFS, not its creation time. The app folder's identity: name the runner test that already covers it, or add one.
  3. **The `c:\` root.** The engine's `contract._normal` refuses `c:\…` and `\\?\C:\…` (`path_not_normal`) while the protocol's `AbsPath` and the sidecar take them. Owner, 2026-11-22 (BL-0087's row): the sidecar normalizes a path before it reaches the engine: the drive letter upper case, the `\\?\` prefix off (`\\?\UNC\server\share\…` to `\\server\share\…`), a volume GUID path keeps its prefix. Trace every entry of such a path into the sidecar first and normalize at one boundary.

## Decisions
- **The Windows reader: a named pipe read overlapped, waited on with the child's process handle (agent).** The parent's end of the answer's pipe is a one-instance, local-only, randomly named pipe opened overlapped (`_winapi.CreateNamedPipe` with `FILE_FLAG_OVERLAPPED | FILE_FLAG_FIRST_PIPE_INSTANCE`, `PIPE_REJECT_REMOTE_CLIENTS`), the child's end its standard output. Each read is overlapped and the parent waits for "the read finished" or "the child ended" (`WaitForMultipleObjects` on the read's event and a `SYNCHRONIZE` handle on the child). When the child ended first, the read is cancelled (`CancelIoEx`) and its result taken: bytes that came before the cancel are kept, an aborted read ends the reading. After the child's end a read with bytes in the pipe completes at once, and one with none waits and is cancelled at once, so only what is already in the pipe is read, and a process the child started that holds the pipe never holds the job. No time limit, no thread. Rejected: a blocking reader thread plus `PeekNamedPipe` once the child ended (the brief's suggestion): a synchronous read and a peek on one handle are serialized by Windows' I/O manager, so the peek waits behind the blocked read (asked of the runner by the probe, `anon_peek_behind_read`), and a thread blocked in a read cannot be woken without `CancelSynchronousIo` and its race with a read that just completed. A peek loop after the end was built first and removed (EP-30): with the overlapped read it is never needed (a read after the end never waits on data that is there). `_winapi` is the standard library's own Windows module (`subprocess`, `multiprocessing` and `asyncio` build their pipes on it; typeshed types it), so `fs/`'s rule on `ctypes` is not touched.
- **POSIX unchanged (agent).** `check` branches once on `sys.platform`; the POSIX lines are the base's (indented under the branch), `_answer_line` untouched.
- **A write to a child that closed its input (agent).** Windows answers it with `EINVAL` as well as `EPIPE` (`subprocess`'s own note, bpo-19612, bpo-30418); the Windows form treats both as "the child ended before it read": its exit status tells.
- **The child in the engine's Job Object (agent; how we know).** The child is started with `subprocess.Popen` and no creation flags: Windows makes every process a job member starts a member of its job, and the engine's job sets neither `BREAKAWAY_OK` nor `SILENT_BREAKAWAY_OK` (S0129, `windows_job.py`). Held by a runner test with the sidecar's own `EngineJob`: `backend/tests/platform/test_engine_windows.py::test_S0146_the_copy_checks_child_is_a_member_of_the_engines_job_and_ends_with_its_drain` (an engine in its job runs `fresh_load.check` on a ledger whose plugin names its process and blocks; that process is in the job's member list, and the drain ends it).
- **The fresh-load tests on Windows (agent).** A plugin cannot fork there. The "a process holds the pipe" cases run on every OS with code put before the real child's (`holding`): a process that inherits the child's standard output (through `Popen`'s default standard handles) and never ends. The two fork tests skip on Windows naming it (`NO_FORK`); the drain test has a Windows form (the plugin names its process through `multiprocessing.connection`, the test ends it with `TerminateProcess`, as the Job Object's drain does). Each new case is `@regression-guard` on POSIX (the base's reader holds there) and fails on Windows at the base (the selector refuses the pipe), shown by the CI step "tests first".
- **The copy-op tests on Windows (agent).** Opted in with `windows_port` as the other real-disk modules; paths written into ledger strings through `beancount_text.escaped`; the held legacy lock by portalocker in another process (`test_legacy_lock.legacy_app_saving`); a FIFO case skips (`NO_FIFO`); the two link cases make the link and skip only when Windows refuses it with error 1314 (the privilege); the "other case" spelling of a legacy root runs on NTFS too (it compares names without case, as APFS); `getpgrp` is asserted on POSIX only, the Job Object being the backend test above; a journal's `path_key` on Windows is the engine's own.
- **A test copy's mark (agent).** The copy op reports no mark today (the test copy's job, BL-0267, M3, records it). The runner test takes the mark the way that job will (the port's `DirHandle.mark()` of the folder the copy made), on NTFS and on the ReFS scratch drive: `born` is the file ID (`os.stat().st_ino`, FileIdInfo), not the creation time; a save confined by the mark lands, the same mark with the creation time as `born` is refused `copy_folder_moved`, nothing written (`tests/test_copy_ops.py::test_S0146_a_copys_folder_mark_is_its_file_id_and_a_save_confined_by_it_lands`). **The app folder's identity** is already covered on the runner since S0129: `backend/tests/platform/test_engine_windows.py::test_the_app_folders_identity_is_the_engines_the_volume_serial_and_file_id` (NTFS: `born` is the file ID) and `::test_the_app_folders_identity_is_the_engines_on_each_volume_kind[refs]` (ReFS); nothing added.
- **The trace of absolute paths into the sidecar, and the one boundary (agent).** Every path the engine checks or records reaches it in a request's params: `root`, `app_local_data`, `target`, `source`, `legacy_locks`, `confine.path`, the save's `changes[].path` and `targets[].path`, the recovery's `journal_dir` and `file` (the schema's `AbsPath` positions: 12 ops, 28 positions). Their sources today: the CLI flags `--app-local-data` and `--app-cache` (`main.py`, through `Path.resolve()`), the request dataclasses of `engine_jobs` (`OpenTarget`, `PreviewTarget`, `RebuildTarget`, `SaveRequest`, `CopyRequest`, `CreateRequest`, the recovery's actions) and `workspaces.writes.WriteTarget`/`CopyMark`, none of which a product caller fills yet (the registry is BL-0102, M2; Copy and Create have no route yet), and paths the engine itself sent (a preview's plan, a journal listing). Every request is encoded by one function, `engine_protocol.encode_request` (the client's `_encode`). So the single boundary is the codec: on Windows it puts every value at the op's `ABS_PATHS` in the engine's normal form (`windows_paths.normal`), whatever its source; a test builds the table's population from the schema, so a new path field fails until the codec covers it. A value already normal (the engine's own) is unchanged. **The normal form is the engine's whole one** (`WindowsPaths.normpath`), not only the owner's two rules: the drive upper case and the prefix off, plus `/` as `\`, no doubled or trailing separator, which are Windows' own reading of a path (the same place), so a root typed `c:\Books\` reaches a save. A path the model does not take (`.` or `..` names, a reserved name, a trailing dot, relative) is sent as it is and the engine refuses it, naming why. Stated limit: a mutator's own `request` (the preview's opaque JSON) is not normalized; a mutator that names a file there takes the path from the engine's plan or mirror, which the engine spelled.
- **The engine side of the root (agent).** `tests/test_preview_ops.py::test_S0146_on_windows_only_the_normal_spelling_of_a_root_reaches_a_save` (runner; its expected answers are confirmed by the first CI run, below): a root spelled `c:\…` or `\\?\C:\…` is refused `path_not_normal` at the contract's first step, and the normal spelling's plan lands with its paths unchanged; with the backend's codec tests (`test_S0146_on_windows_every_absolute_path_of_a_request_reaches_the_engine_normalized`) and the twin test against the engine's own model (`test_S0146_the_sidecars_normal_form_is_the_engines_and_passes_its_check`), a root spelled either way reaches a working save.
- **The whole normal form and the opaque `request` (owner).** Owner, 2026-11-22, in session, on the sidecar sending the engine's whole normal form and on a mutator's preview `request` not being normalized (a stated limit): "Confirming both as okay."
- **`/` in a ledger's paths on Windows (owner; no change here).** Owner, 2026-11-22: "keep option 1": the user docs (S0149) say that inside `.bean` files paths are written with `/` on Windows; BL-0301 stays a stated limit. The copy tests write absolute paths in ledger strings with `/` (`Path.as_posix()`) for that reason (run 3: written with `\\` they were refused `cannot_rewrite`, BL-0301's limit, not a defect).
- **Found by the 2026-11-22 run 3 (head fcf9af25), fixed here (agent):**
  - *The reader (product):* `_winapi`'s `GetOverlappedResult` raises `BrokenPipeError` for a read that waited when every writer closed the pipe (I had expected a returned code), so a child that ended without a holder and without a full line made `check` raise instead of answering `failed` (the parse cases and the drain case of `test_fresh_load.py`; the probe's `overlapped_nothing` showed the same). Now caught as the pipe's end.
  - *The copy (product), two POSIX-isms on Windows:* the legacy lock's tail was `"/data/.write.lock"`, so every legacy lock was a malformed plan there (the copy never ran: the absent-lock, legacy-root and v0.2.2 tests); now in the OS's separator (`_legacy_tail`). A documents root's listing names a nested file with `\` (`os.path.join` in `fingerprint.listing`), and `_reserved` split at `/` only, so a `.finzytrack` folder under a documents root was not left out and the copy refused `reserved_name` (the documents-dot and `.finzytrack` tests); now split at the OS's separator too. Both failed closed (no copy made). POSIX unchanged (the separator is `/`).
  - *Tests:* a file the legacy app holds locked cannot be read on Windows (`snapshot` records it by its size); `write_text` needs `encoding="utf-8"` for the NFC/NFD names; the Job Object test now ends the engine's leader before the drain (the drain waits for the leader's exit first, §5.2; the test called it on a live leader, so the hang guard ended pytest with its dump in the captured stream: a test fault; the product drains only after its leader exited).
  - *Probe:* the 300 KB child wrote its bytes on its command line (error 206); now an expression.
  - The probe confirmed: a peek waits behind a blocked synchronous read (`anon_peek_behind_read`: no answer in 5 s); a symbolic link can be made on the runner; each overlapped case read what the child wrote, and a waiting read after the child's end ended `woke 1`, `err=995`.
- **The Job Object test ends only what it started (agent).** `EngineJob.around(proc)` puts only the leader the test started into a new job; every other member is a process that leader (the venv's launcher, the interpreter it starts, the copy check's child) started. The drain and the test's cleanup end that job, and `leader.end()` ends that leader: the pytest process is never in the job. Run 3's silent end was the test's own hang guard (`faulthandler`, `exit=True`) firing while `drain()` waited for a leader that was still alive.
- **Sandbox runs of the backend's process tests (agent; an incident).** Before the owner's rule of 2026-11-22 ("Yes": never run the backend's process tests inside the sandbox, nor a mutant run over them; BL-0309), I ran `test_engine_client.py` and `test_engine_group.py` in the sandbox several times (the backend suite with `-n auto`, then the two modules on the base and the head). The sandbox refuses `os.killpg`, so their stand-in engines' waiting children stayed alive; another agent reported about 4,100 such processes on the owner's Mac, gone once this session was stopped. From then on the backend suite runs here with those files deselected; they run in the push gate and on CI. The base comparison the orchestrator had asked for was withdrawn.
- **`scripts/mutants.py` on Windows (agent; tooling).** Its timeout ended the run's process group with `os.killpg`, which Windows lacks; the reader's hang mutants need the timeout there, so on Windows it ends the run's process tree with `taskkill /F /T`.
