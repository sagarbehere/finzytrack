# S0144: the Cloud Files probe on the Windows runner (BL-0087's split, part 1; BL-0283's facts, M1b)

## Brief
- **Goal:** a prints-only probe on the Windows CI runner, `engine/scripts/probe_windows_cloud.py` (Python `ctypes` over `cldapi.dll`, in the style of `probe_windows_fs.py` and `probe_windows_share_save.py`), run in a new step of the `engine-windows` job in `.github/workflows/ci.yml`. It never fails the job on a finding; a crash of the probe itself fails the step, so it is seen. It records:
  1. whether the runner can run the cloud filter (`fltmc filters`; loading or starting `cldflt` if it is absent), register a sync root (`CfRegisterSyncRoot`) under `RUNNER_TEMP` and connect to it (`CfConnectSyncRoot`, with a FETCH_DATA callback that serves the bytes with `CfExecute` TRANSFER_DATA), with no Microsoft account;
  2. a placeholder file (cloud-only, hydrated, hydrated and pinned) and a placeholder folder as our Windows adapter's own primitives see them: the attributes (`REPARSE_POINT`, `OFFLINE`, `RECALL_ON_DATA_ACCESS`, `RECALL_ON_OPEN`, `PINNED`, `UNPINNED`), the reparse tag, and what `ledger_engine.fs.windows._kind` answers, through the adapter's own calls (`WindowsFS().open_dir` on the sync root, then `stat`, `open_child`, `read`, `sha256` through the port), so the probe sees what the save would;
  3. whether a read through our handle (opened with `FILE_OPEN_REPARSE_POINT`, as `open_child` and `sha256` open entries) hydrates the file through the provider's fetch callback or reads the bare placeholder, compared with Python's plain `open()` (Beancount's read);
  4. the exact error (NTSTATUS, Win32 code, `errno` as the adapter maps it) a read gets while the provider is disconnected (`CfDisconnectSyncRoot`): the "offline" case;
  5. the whole save on a hydrated placeholder, not only its primitives: `allowed` (delete access, and the attribute read the staging copy needs), the file's own sync, the backup's read, a staging file created in the sync-root folder (with `like=` the placeholder, as the save makes it), our rename over the placeholder (`FileRenameInformation` with `ReplaceIfExists`, through the adapter), the folder's sync, the read-back, and what is at the name afterwards (attributes, tag, bytes); the same on a cloud-only placeholder;
  6. how the process's placeholder compatibility mode (`RtlSetProcessPlaceholderCompatibilityMode` and `RtlQueryProcessPlaceholderCompatibilityMode` in `ntdll`) changes items 2 to 5: the default mode and the expose mode.
  The sync root is unregistered at the end (`CfUnregisterSyncRoot`), also on failure.
- **What it is a second opinion on:** Windows' own cloud filter, on which OneDrive is built; not OneDrive's sync engine (the owner's check by hand in S0149 covers that).
- **Implements:** ADR-0069; ADR-0061 and its 2026-11-14 amendment; engine-jobs §6.3, §6.8, §15; BL-0283's decision (`design/inbox/answered/20261121-pace-and-scope.md`, change D); BL-0087's split of 2026-11-22 (owner, in session: "Split OK. Do V4-1, let's go with your lean").
- **Capabilities:** none changes (Windows still does not write in the product).
- **Invariants touched:** none (no product code). INV-23 and INV-24: the probe writes only under `RUNNER_TEMP`; no home path and no run ID enter the repository.
- **The bytes it protects:** none (a probe writing scratch files only); the policy is decided (support the typical OneDrive setups).
- **Which real setup needs this, and can a policy forbid the rest?** Documents redirected to OneDrive, which Windows promotes (common, by the owner's words of 2026-11-21); every other reparse point stays refused.
- **Has this family needed two or more fix rounds before?** No: the probes of S0126, S0132 and S0136 landed in one round. Lesson applied: probe the whole operation on the new kind of volume, not only its primitives; a probe's own bug can look like a finding, so a surprise is first treated as a possible probe bug.
- **Risk class / lane:** Low / light. Review row: tooling, gates, measurement (the verifier, one round, the stop rule). No mutants (prints only).
- **Acceptance tests:** a green manual CI run whose `engine-windows` log answers items 1 to 6. The answers are recorded below as facts marked "probed", each with its consequence for S0148 (the OneDrive slice). If item 1 fails (no sync root on the runner), the journal and the report say so plainly, and the orchestrator brings the owner options before S0148.
- **Expected doc impact:** this journal; one line in the CI job's comment; engine-jobs only if the probe contradicts what it states. (It did: engine-jobs §6.3, `fs/windows.py`'s docstring and BL-0283's row are corrected; Facts 3.)
- **Open questions:** none.

## Decisions
- **No unit test is written first** (PROCESS.md §3 step 3; agent, 2026-11-22): the slice adds no product behaviour, and the script imports only on Windows (`raise SystemExit` elsewhere, as the other Windows probes), so a macOS test could check nothing it does. Its acceptance is the CI log; pyright (strict, Windows platform) and ruff check it at every push.
- **The provider and the reader are two processes** (agent): the probe's main process registers and connects the sync root and serves the fetches; every look and read runs in a child process (the same script, another command). In the product the engine is never the provider: OneDrive's sync engine is another process, and the cloud filter treats the provider's own reads otherwise (`CF_CONNECT_FLAG_BLOCK_SELF_IMPLICIT_HYDRATION`). The placeholder compatibility mode is per process, so each mode gets its own child, and its files (each mode has its own set, so a read in one mode never hydrates what the other mode looks at first).
- **A finding never fails the step; a probe bug does** (agent): every Windows call's refusal (`OSError`, a failed `HRESULT`) is printed as a finding and the probe goes on; any other exception (a `ctypes` or Python error in the probe's own code) is printed as `probe_error` and makes the script end with exit code 1 after the cleanup, so the step fails and the run shows it. A child that runs longer than 15 minutes is stopped and counted as a probe error (a fetch callback that never answers would otherwise hold the job to its 60-minute limit; the cloud filter's own timeout is 60 s).
- **The tests step still runs after a probe bug** (agent): `ci.yml`'s tests step takes `if: success() || steps.cloud_probe.outcome == 'failure'`, so a failing probe makes the job red without hiding the suite's results; any earlier failure still skips the tests, as before.
- **The sync root is also looked at from its parent** (agent): a ledger in a folder below a OneDrive folder is reached by `open_child` through the sync root and the folders under it, and the adapter's `open_child` refuses any reparse point on a folder (`_a_link`: `ELOOP`), so the probe asks it of the sync root and of the placeholder folder.
- **The save is probed as its effects, not by `ledger.save.run`** (agent): the product's save would stop at `not_a_file` wherever `_kind` answers `OTHER`, which item 2 already shows; to answer item 5 the probe runs the save's own sequence on the file, in `writer._check_target`, `_backups` and `_best_effort`'s order (`stat`, `allowed` for delete and for the attribute read, `sync_file`, `read`, `create(staging, like=the file)`, `rename`, `sync`, `read` back), each through the adapter, and goes on past a refusal to show the next step. The backup file itself is not written (it goes to the app's own folder, never the sync root).

- **The probe step stays in `ci.yml`** (agent; the orchestrator's reading, 2026-11-22): it is the slice's product, not a temporary step, so every manual run shows what the cloud filter does on the runner's Windows build; S0148 extends it.

## Facts (probed: the 2026-11-22 run 1 at fb4ff90d, `engine-windows` on `windows-2022`, Windows Server 2022 build 20348, Python 3.13.16; 260 probe lines, `probe_errors` empty, 16 fetches)
Each fact, then its consequence for S0148 (the OneDrive slice).

1. **The runner has the cloud filter and a sync root works without an account.** `CldFlt` is loaded (`fltmc filters`), its service `AUTO_START` and `RUNNING`; `CfRegisterSyncRoot` (the 24-byte policies: hydration full, population always full) and `CfConnectSyncRoot` answered `S_OK`; every `CfCreatePlaceholders`, `CfSetPinState` and fetch's `CfExecute` answered `S_OK`; `CfUnregisterSyncRoot` and the folder's removal worked. *S0148:* its tests can run on a real sync root in CI (this probe's provider, made a test fixture); item 1 did not fail, so no options note is needed before S0148.
2. **The reader's process mode is `disguise_placeholder` (1) without any call; the provider's own is `application_default` (0).** Both are the same `python.exe` (the venv's), the reader started by the provider with no flags. This does not show what a process's default is: Microsoft documents (`RtlSetProcessPlaceholderCompatibilityMode`, Remarks) that "most Windows applications see exposed placeholders by default" and that Windows may give certain applications disguised ones; why the children got disguise is not known (verifier F-1). *S0148:* the mode the product's engine runs in must be established, not assumed: the sidecar starts it with `-s -S -B -P` from the venv in development and from the bundle's interpreter in the packaged app (another executable, perhaps another manifest). S0148 probes the engine as the sidecar starts it, and decides whether the engine sets its mode itself (`RtlSetProcessPlaceholderCompatibilityMode`, pinning disguise or expose) rather than inheriting one.
3. **In the disguise mode no placeholder is a reparse point to the adapter.** Through our handle (`FILE_OPEN_REPARSE_POINT`), `GetFileAttributesW` and `os.lstat`/`os.stat` alike: no `REPARSE_POINT` attribute and tag 0, so `_kind` answers `file` for cloud-only, hydrated and pinned files and `dir` for the placeholder folder and for the sync root seen from its parent; `open_child` opens both folders. A cloud-only file shows `ARCHIVE` and `RECALL_ON_DATA_ACCESS` with 0 bytes allocated; a hydrated one shows `ARCHIVE` only (4096 allocated); a pinned one `ARCHIVE` and `PINNED`. A hydrated placeholder is therefore indistinguishable from a plain file in this mode. *S0148:* in this mode today's adapter reads and saves a OneDrive file (facts 5 and 7); in the expose mode it refuses it (`not_a_file`), as the old statement said, which may be the engine's case. The statement now names both modes (`fs/windows.py`'s docstring, engine-jobs §6.3, BL-0283's row; no behaviour changed). A cloud-only file can be told before reading by `RECALL_ON_DATA_ACCESS` (and `OFFLINE` where exposed), which the offline refusal may use.
4. **In the expose mode (2) every placeholder is `OTHER`.** Cloud-only files: `ARCHIVE`, `SPARSE_FILE`, `REPARSE_POINT`, `OFFLINE`, `RECALL_ON_DATA_ACCESS`, tag `0x9000401A` (`CLOUD_4`); hydrated and pinned files: `ARCHIVE`, `REPARSE_POINT` (and `PINNED`), tag `CLOUD_6`; the placeholder folder and the sync root: `DIRECTORY`, `REPARSE_POINT`, `CLOUD_6` and `CLOUD_7`. The adapter refuses them all: `read`, `sha256`, `sync_file` and `create(like=)` with `EINVAL` "not a regular file", `open_child` of the folder and of the sync root with `ELOOP` "a link", `stat` `other`; `allowed` (delete, the attribute read) still answers True. *S0148:* if the engine exposes placeholders, the adapter needs a cloud kind (the `CLOUD_n` tags, `tag & 0xFFFF0FFF == 0x9000001A`) taken as a file or a folder, and `_a_link` must not refuse a cloud folder; if it disguises them, no kind change is needed but nothing tells a placeholder from a plain file.
5. **Reads download through the provider in both modes.** Three cloud-only files read first through our own handle, through the adapter's `read` (disguise mode) and through `open()` were each fetched once (a `fetch` line naming the reader's process, `required` `[0, size]`) and returned exactly its bytes; afterwards it was hydrated (`RECALL_ON_DATA_ACCESS` gone; in the expose mode `CLOUD_4` became `CLOUD_6`, `SPARSE_FILE` and `OFFLINE` gone). A hydrated or pinned file read without a fetch. In the expose mode our raw handle (no kind check) also downloads: `FILE_OPEN_REPARSE_POINT` does not stop the cloud filter's hydration. The adapter's `sha256` was never the first read of a cloud-only file while the provider ran; it was seen reaching the cloud filter only offline (fact 6, winerror 362) (verifier F-2). *S0148:* re-probe with `sha256` as the first read of one file; the engine's read and Beancount's `open()` read the same bytes; a cloud-only file is downloaded at the first read, so the save's fingerprint and backup reads download it (fine online; offline below).
6. **The offline case** (provider disconnected): a cloud-only file's read fails through our handle and the adapter's `read`/`sha256` with `OSError` `errno` `EINVAL`, `winerror` 362, "The cloud file provider is not running." (`ERROR_CLOUD_FILE_PROVIDER_NOT_RUNNING`; the open succeeds, `ReadFile` fails); Python's `open()`-and-read gives a bare `EINVAL` "Invalid argument" with no Win32 code (Beancount would report that). The file stays cloud-only. A hydrated file reads normally. *S0148:* the named reason ("only in OneDrive, and you are offline") keys on `winerror` 362, on the adapter's read, not on `EINVAL` (which means many things); before Beancount's load reads the file, since its error loses the code. The other `ERROR_CLOUD_FILE_*` codes (for example the network down while OneDrive runs, or a download cancelled) cannot be made by this simulation: the owner's check by hand (S0149) shows what real OneDrive answers offline.
7. **The save's own effects, in the disguise mode, land on a hydrated and on a cloud-only placeholder.** In the writer's order: `stat` `file`, `allowed` (delete, the attribute read) True, `sync_file` ok, the backup read (the cloud-only one fetched here), `create(staging, like=the file)` ok (the staging file a plain file, `ARCHIVE`), `rename` over the placeholder ok, the folder's `sync` ok, the read-back and `open()` read the new bytes, no name left but the file's. **Not observed:** whether the name then holds a plain file or a placeholder: in the disguise mode the two look alike (the probe looked only in that mode after these saves). By reasoning it holds our staging file, which no provider made a placeholder; OneDrive's own reaction (it converts and uploads a new file) is the hand check's. In the expose mode the sequence stops at `sync_file` (`EINVAL`), as the save itself would stop earlier, at `stat` (`not_a_file`, `writer._check_replaced`). *S0148:* re-probe a disguise-mode save, then look at the name in the expose mode (one more `describe` in the expose reader), and check the result with real OneDrive by hand (S0149).
8. **`create(..., like=)` leaves its file when the `like` source is refused** (the expose mode: `create_like` failed `EINVAL`, then the probe's plain create at the same name failed `EEXIST`, `0xC0000035`). This is the port's contract, not a Windows defect: `PosixDir.create` likewise leaves what it made when a step after the exclusive create fails, and the save makes it only at the staging name, which recovery and the rollback take as ours and delete whatever it holds (`ledger/core/recovery.py`, "staging name"). It is unreachable in the product today in either mode: in the expose mode `_check_replaced` refuses the file (`not_a_file`) before any effect; in the disguise mode `like=` succeeds. (The probe's own sequence did not remove the staging file before its plain retry: a probe artefact, gone with the scratch folder.) *S0148:* if it adds a cloud kind for the expose mode, `create(like=)` must read a cloud placeholder as a file, or this path opens.

**The probe's limits** (verifier F-3; its docstring): five children may each run up to 15 minutes, more than the job's 60, so several hung children would cancel the job before its tests; the timeout stops only the venv's `Scripts\python.exe` launcher, not the interpreter it started. Unlikely: the cloud filter times a fetch out at 60 s.

**What the simulation cannot show** (the list for the owner's check by hand, S0149): OneDrive's reaction to our rename turning its placeholder into a plain file (re-upload, a conflict copy, a "file in use" hold); its upload holding a file at a save (BL-0284's text); its conflict copies when one ledger is edited on two PCs; the errors real OneDrive gives offline, with the network down while it runs and with it paused; the mode the packaged engine runs in on a user's PC.
