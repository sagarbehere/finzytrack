# S0132: the Windows pointer swap's two availability gaps (M1b, BL-0294)

## Brief
- Goal: close BL-0294 as the owner decided it (2026-11-18, in session: "I agree with your recommendations on the 4 questions you raised. Proceed accordingly."; `design/inbox/answered/20261118-windows-pointer-swap.md` questions 3 and 4; ADR-0015 amendment of 2026-11-18). Windows writes stay off until BL-0087; this slice changes only what the mirror's publish and its cleanup do on Windows.
  1. **Where the POSIX rename is offered** (question 3, option 2): `WindowsDir.rename_shared` is offered when the volume reports `FILE_SUPPORTS_POSIX_UNLINK_RENAME` (0x400, `GetVolumeInformationByHandleW`'s flags) and is not remote (`remote()`, `FILE_REMOTE_DEVICE`). Otherwise `NotOffered`, nothing done, and the swap takes the plain rename with its stated limit (publish.md §11). Today it decides by the file system's name (`POSIX_RENAME_TYPES = {"ntfs"}`), so a share reporting NTFS refuses every swap with another error.
  2. **Read-only entries** (question 4, option 2): the cleanup and the swap clear the read-only attribute on what they remove or replace in the mirror folder, so a read-only `current.txt` no longer refuses every swap and a read-only generation is removed in its turn.
- **Design** (the orchestrator's notes, checked against the code):
  - The port's `remove` and `rename` stay as they are: the save's `locked` outcome relies on a read-only ledger file being refused (`WindowsDir.stat` reports it `locked`; the save refuses before writing). Clearing is the publish's own act in its own folder: a new port operation `DirHandle.clear_readonly(name)`. Windows: the entry opened relative to the folder handle with `FILE_OPEN_REPARSE_POINT` (a link's own attribute, never its target's), its attributes read, and only when the read-only bit is set, written back without it (`FileBasicInfo`, times left as they are, the attributes masked as `SetFileAttributesW` masks them). No entry: nothing to do. macOS and Linux: a no-op, since a file's mode never stops its removal or a rename over it; macOS's `uchg` flag is not touched (a stated limit, below).
  - Callers, all in `mirror/publish.py`: `clean` before each removal of a file, link or folder, `_remove_tree` before each removal inside a folder and before the folder's own; `swap` before removing a stale temporary pointer or link, and before the rename over `current.txt` (or the folder at it moved aside); `open_folder` before removing a non-folder entry at `mirror/` itself (the workspace's own folder in the app cache, the same ownership).
  - `tests/architecture/test_write_port.py` checks imports only; a new port operation needs no declaration there (checked). It is added to the `DirHandle` protocol (`fs/port.py`), the three adapters and the fake.
  - **The fake** (`tests/fakes/memfs.py`): in Windows mode a read-only file is `outside_lock` (the adapter reports it `locked`, and Windows refuses its removal or a rename over it); `clear_readonly` there is an effect, so the crash, power-loss and I/O-error sweeps of `tests/mirror/test_publish_crash.py` and the model's replay cover it; in POSIX mode it does nothing and is not an effect (the real adapters make no call). Item 1's fake form: the POSIX rename decided per drive by a volume flag and a remote set, never by `fs_types`.
  - **The model** (`formal/tla/mirror-publish/`) is about names; an attribute change moves no name, so no model change, a line in MAPPING.md §6. If the model or ADR-0015 needed a Windows variant that changes a decided rule, the slice stops and reports.
- **Probe first** (S0126's lesson; S0130's: list every handle the product holds on the target). Additions to `engine/scripts/probe_windows_fs.py`, run on the runner's C: and D: (NTFS), the FAT32, exFAT and ReFS scratch volumes, and a new SMB share at `\\localhost\ftshare` created in CI, before any product code:
  - (P6) per volume: `remote`, the flag, and the POSIX and plain renames over a file, alone and under a reader that shares deletion. The question for the share: does it report NTFS and the flag, is it remote, and what does the POSIX rename answer there? (Microsoft documents that SMB does not support `GetVolumeInformationByHandleW`, so `remote()` is asked first.)
  - (P7) the read-only attribute against each handle the product holds on its target: a generation held by SQLite's read-only connection (no delete sharing; the swap's `touch`, the removal before and after clearing, clearing while held); `current.txt` held by the pin's share-all read (each rename over it read-only, clearing while held, the POSIX rename after clearing); a file held by Python's own `open()` (another program); a read-only folder with a read-only file inside (renamed aside, its file removed, the folder removed, before and after clearing).
- The bytes it protects: no ledger bytes; the publish writes only the app's cache folder. It keeps two outcomes truthful on Windows, as S0130 does: a reader reads one whole generation, built from one state the ledger really had; and the save's gate passes only when the published generation describes the disk the plan was made on. The change itself is availability (a publish that lands, a disk that stays bounded); the clearing must never let a reader see a missing or wrong pointer, and must never reach a ledger file (the port's `remove` and `rename` keep refusing a read-only file).
- Mechanism questions (PROCESS.md §3 step 2): which real setup needs this, and can a policy forbid the rest? Both setups are rare (a cache folder on a network share or an old Windows build; a read-only attribute set by the user or a copy or restore tool), and both questions were put to the owner as policy options first; the owner chose the mechanisms (questions 3 and 4, option 2 each). Has this mechanism or its family needed two or more fix rounds before? Yes: the publish took S0085 (1 round), S0087 (2 rounds), S0088 (2 rounds, 1 High fixed: the stamp), S0118, S0130 (1 round). At a class (a) finding the slice stops and reports to the orchestrator.
- What each check here is a second opinion on (S0122's lesson): the runner tests (a share, a read-only pointer and a read-only generation on NTFS and the scratch volumes) are a second opinion on the primitive (does Windows really let the clear through every handle the product holds, and refuse the POSIX rename on a share); the fake's sweeps and the model's replay are a second opinion on the order (no crash, I/O error or power loss between a clear and its removal or rename leaves a reader a missing or wrong pointer). The fake's own rule for read-only (`outside_lock` refuses; `clear_readonly` unlocks in Windows mode) is checked against the runner's answers, never against itself.
- Implements: ADR-0015 (its amendment of 2026-11-18: where the POSIX rename is offered; read-only entries), publish.md §4 step 8, §6, §11; BL-0294.
- Capabilities: none changes status (CAP-DATA-MIRROR's Windows form).
- Invariants touched: INV-05 (the mirror published atomically, rebuildable), INV-24 (tests on scratch folders and a CI share only).
- Risk class / lane: High / full. Review budget row: **New write path** (verifier + data-safety red team; a fresh round after any fix that changes product code).
- Acceptance (tests first; each fails on the base, over the fake on macOS or on the Windows runner):
  - **macOS, over the fake:** a read-only `current.txt` neither refuses the swap nor stays (pointer form), in every crash, I/O error and power loss of the job; a read-only generation and a read-only temporary pointer are removed by the cleanup in their turn; a read-only file inside a folder of the mirror is removed with it; a read-only entry at `mirror/` is replaced by the folder; on a Windows volume without the flag, or a remote one, the swap takes the plain rename and publishes; a ledger file's read-only refusal is unchanged (`remove` and `rename` still refuse a locked file in Windows mode); the POSIX form never calls `clear_readonly` as an effect (link-form sweeps unchanged).
  - **The Windows runner** (`engine-windows`): `rename_shared` is `NotOffered` and does nothing on the share; a publish whose cache folder is on the share lands; a publish lands over a read-only `current.txt` held by a reader sharing deletion; a read-only generation (held by SQLite, then released) is removed by the cleanup after the reader closes; `clear_readonly` clears through each holder P7 names and does nothing on an absent name; `remove` and `rename` still refuse a read-only file.
  - `engine-windows` red on exactly INV-03's five (`test_parity_corpus.py`, BL-0282); `backend-windows` green; `pyright_platforms.py` 0 errors on Darwin, Linux and Windows; the macOS and Linux gates green.

## Decisions
- Slice slug and scope (agent): both parts of BL-0294 in one slice, as the row and the owner's answer pair them; one mechanism family (the publish's swap and cleanup on Windows).
- **Probe before building (agent; S0126's and S0130's lessons).** The first commit is the probe addition, the CI share and this brief; no product code until the runner has answered P6 and P7.
- **The minimum Windows version (agent, a fact to record, not to guess):** Microsoft's pages for `FILE_RENAME_INFORMATION`, `FILE_RENAME_INFO`, `FILE_INFO_BY_HANDLE_CLASS` and `GetVolumeInformationByHandleW` (read 2026-11-18) state no minimum version for `FileRenameInformationEx`, `FILE_RENAME_POSIX_SEMANTICS` or `FILE_SUPPORTS_POSIX_UNLINK_RENAME`; `ntifs.h` guards the `Flags` member by `_WIN32_WINNT_WIN10_RS1` (Windows 10 version 1607). Since the flag decides, an older Windows that does not report it takes the plain rename with its stated limit, never an error; the release notes state that and the build the runner probed.
- **The 2026-11-18 run 21** (head 0ba25a9a; the probe only, Windows Server 2022, `10.0.20348.0`; `engine-windows` red on exactly INV-03's five, 10 230 passed; `backend-windows` green; every other job green). The probe on D: and C: (NTFS), the FAT32, exFAT and ReFS scratch volumes and the CI share `\\localhost\ftshare`:
  - **P6, the share:** it reports **NTFS and the flag `FILE_SUPPORTS_POSIX_UNLINK_RENAME`**, and `remote` is True (`FILE_REMOTE_DEVICE`). The rename with POSIX semantics there is refused `INVALID_PARAMETER` (alone and under a reader that shares deletion); the plain rename lands alone and is refused `ACCESS_DENIED` under that reader. So the file system's name and the flag both say yes on the share: only `remote()` tells it apart. This is BL-0294's red team F1, confirmed: on the base, every swap there fails with `EINVAL`. `GetVolumeInformationByHandleW` answered on the share (Microsoft's page says SMB does not support it; on this build it does), so `remote()` is still asked first.
  - **P6, local volumes:** NTFS (C:, D:): `remote` False, the flag set, the POSIX rename lands alone and under a sharing reader. FAT32 and exFAT: the flag clear, the POSIX rename `INVALID_PARAMETER`; ReFS: the flag clear, `NOT_SUPPORTED`. As S0130's P5, now read from the flag.
  - **P7, the read-only attribute, on NTFS, ReFS, FAT32 and exFAT alike:** a read-only file refuses its removal (`CANNOT_DELETE` with POSIX semantics on NTFS and ReFS, `ACCESS_DENIED` for `DeleteFileW` everywhere) and a rename over it, POSIX or plain (`ACCESS_DENIED`; `OBJECT_NAME_COLLISION` for the plain rename on FAT32 and exFAT). Its modification time can be set (the swap's `touch`). **Clearing the attribute through a handle that shares everything works under every holder the product has:** a read-only SQLite connection (no delete sharing), a reader sharing deletion (the pin), Python's own `open()`. After the clear, the POSIX rename over `current.txt` lands while the sharing reader still holds it (NTFS), the plain rename lands (every volume), and the removal lands once no reader holds the file (SQLite's hold still refuses it, `SHARING_VIOLATION`, as S0130's P1). **A read-only folder refuses its removal** (`CANNOT_DELETE`, NTFS and ReFS) until cleared; renaming it aside works read-only. So the cleanup must clear folders too, not only files.
  - The probe's read-only part could not run on the share: SQLite answered "unable to open database file". Its open there is the store's own form (`Path.as_uri()`, which gives `file://localhost/ftshare/...` for a UNC path). Run 22's probe asks that open alone; if it fails, a mirror cache folder on a UNC path cannot be built at all (outside BL-0294: a new row).
- **Design after the probe (agent):** `rename_shared` asks `remote()` first, then the flag (`_Handle.flags`), and raises `NotOffered` before any call; the file system's name decides nothing (`POSIX_RENAME_TYPES` removed). `clear_readonly` reads the attributes through a handle opened for `FILE_READ_ATTRIBUTES` only and writes them (masked as `SetFileAttributesW` masks, `FILE_ATTRIBUTE_NORMAL` when nothing is left) through a second handle with `FILE_WRITE_ATTRIBUTES` only when the bit is set, so an entry whose ACL denies writing attributes but allows its deletion is no worse off than on the base. The publish calls it before every removal of the cleanup (files, links, folders and what is inside them), before removing a stale temporary pointer, before the swap's rename over `current.txt` (or the aside rename of a folder there), and before removing a non-folder at `mirror/` (the workspace's own folder in the app cache). Folders are cleared because P7 shows a read-only folder refuses its removal.
- **The CI share** is also mapped to a drive (`net use Z:`), and `FT_TEST_SHARE` lists the drive first, then the UNC path: the adapter's share test runs on both; the publish's share test takes the drive (SQLite's URI open of a UNC path is run 22's question).
- **Tests first (macOS, over the fake):** with the fake's Windows-mode `clear_readonly` and the new tests, on the base's publish: `tests/mirror/test_publish_crash.py` 7 failed (the read-only pointer, the bounded folder with read-only entries, the crash and I/O-error sweeps among read-only entries at 1 and 3 prior publishes, a read-only file at `mirror/`), 54 passed; every failure is the fake refusing a read-only entry (`PermissionError: locked`), as Windows does. After the change: 61 passed; the mirror and fake suites 369 passed, 8 skipped; the whole engine suite 10 757 passed, 19 skipped.
