# S0090: Drive identity cleanups: exFAT folder births to the second; S0089's final-round rows

## Brief
- Goal: three rows left by S0089's final round. (1) **BL-0221** (owner, 2026-11-09): on exFAT, recovery compares a recorded folder's creation time with the one it finds **to the whole second**, not to 10 ms, so a folder Finder copied onto an exFAT stick (read as whole seconds while that mount lasts, as its stored 10 ms value after a remount) is still the right folder after a remount; FAT stays exact at its 2 s, APFS and HFS+ unchanged. Also: "Limit (folder changed)" says a summer-time switch counts as a time-zone change on FAT; a file-system type name the record cannot hold no longer passes through the record check to a misleading refusal. (2) **BL-0220** (S0089 final verifier V2-1 to V2-4): `no_folder_id`'s text covers a drive that keeps no creation time at all; stale docstrings and the `TABLE_VERSION` comment fixed; a `wrong_drive` or `unknown_drive` stop names each file's backup in the blocked text and in Keep's confirmation; the verifier's FAT/exFAT crash and power-loss sweep joins `test_writer_best_effort.py`, with a one-file save so the evidence rule is reached, and the evidence rule exercised through the save's own rollback. (3) **BL-0222** (owner: "Keep as stated limit"): §6.3's "Limit (drive identity)" cites the decision; the user-docs sentence waits for M1a's end (light lane), so the row stays open for it.
- Implements: BL-0221, BL-0220, BL-0222 (spec part); ADR-0012 (amended here with the owner's BL-0221 words); `design/specs/engine-jobs.md` §6.3 "Drive identity" and its limits, §11 rows (`no_folder_id`, `no_drive_id`, the drive rows and Keep's), §8.1 "Afterwards"; EP-29, EP-30.
- Capabilities: CAP-WS-RECOVER-FIRST (stays planned).
- Invariants touched: INV-22 (fails closed: a twin stick must still match drive ID, file system and folder birth to the second), INV-32 (every journal ends recovered or blocking: the right exFAT stick is recovered after a remount instead of blocking), INV-01 (the undo is part of the write-safety contract).
- Risk class / lane: High / full lane (it changes what recovery accepts as the right folder). The orchestrator runs the verifier and a data-safety red team scoped to the whole-second rule.
- The bytes it protects: the files on another stick mounted at the ledger's path (recovery never writes there unless drive ID, file system and folder birth to the second all match, and on FAT/exFAT a missing file still needs evidence), and the ledger on the right exFAT stick (undone after a remount, never left half-changed behind a false `wrong_drive`). Also truthful outcomes: the old version's backup named wherever a drive stop leaves a file the user may need to copy back by hand.
- Acceptance tests (new or changed; each must fail on the base dc656deb):
  - `engine/tests/ledger/test_volume_identity.py`: an exFAT folder recorded at X.000 and found at X.990 (and the reverse) is the same folder and recovery resolves; exFAT one second apart, FAT and APFS and HFS+ within the same second (1 ns, 990 ms) stay `wrong_drive` with nothing written; a mark whose file-system type name the record cannot hold is `unknown_drive` on recovery.
  - `engine/tests/ledger/test_handles.py` or the module above: the whole-second rule is a floor (X.999 999 999 and X.000 are one second; a negative time floors down).
  - `engine/tests/fs/test_darwin.py`: the adapter reads a non-ASCII type name without raising; opt-in real exFAT image (`FT_TEST_DISK_IMAGES=1`): a folder given a creation time with a fraction (`setattrlist`, as Finder does), a save cut before its close in that mount session, a remount, recovery resolves.
  - `engine/tests/ledger/test_writer_best_effort.py`: the crash and power-loss sweep over FAT- and exFAT-typed drives, for the world's save and a one-file save (the evidence rule reached; the user's manual copy then resolves); the rollback sweep on them; the save's own rollback meeting a missing file on FAT stops `missing_unconfirmed`, writes nothing and names the backup.
  - `engine/tests/ledger/test_recover_all.py` / protocol: the inspection names a replaced file's backup when it holds the old version, also for a file on another drive.
  - backend `test_recovery_text.py`: the `wrong_drive` and `unknown_drive` screens and Keep's confirmations name the backup; `test_save_job.py` / texts: `no_folder_id` says a drive that keeps no creation time.
- Expected doc impact: `design/specs/engine-jobs.md` (§6.3, §11), ADR-0012 amendment (owner's BL-0221 words), `design/generated/engine-job-texts.md`, `contracts/engine-protocol.schema.json` (the inspection's `backup`), `design/backlog.md` (BL-0220, BL-0221 done; BL-0222 open for the user-docs sentence). ## Decisions
- **Owner, 2026-11-09, in session** (BL-0221), choosing "Compare whole seconds (Recommended)": "On exFAT, folder creation times are compared to the second, not 10 ms. The right stick is always recognized; a twin stick must now match to the second instead of 10 ms (still needs the same format serial, which in practice means a clone). Small change." Recorded in ADR-0012's amendment ("After S0089").
- **Owner, 2026-11-09, in session** (BL-0222), choosing "Keep as stated limit (Recommended)": "Rare (a cut save, then the backup clone plugged in instead of the original); the user docs say: after a crash, plug the original stick back in, not a backup copy. No new file written anywhere." Cited in §6.3's "Limit (drive identity)"; the user-docs sentence waits for M1a's end (light lane), so BL-0222 stays open for it.
- **Probe (macOS 26, raw images made with `newfs_exfat` / `newfs_msdos`, without Finder; session scratchpad `s0090/probe.sh`):** on exFAT, `setattrlist(ATTR_CMN_CRTIME)` with 1762000001.395, 1762000000.995 and 1762000001.999999999 reads 1762000001.000, 1762000000.000 and 1762000001.000 while that mount lasts, and 1762000001.390, 1762000000.990 and 1762000001.990 after a detach and attach. So the mounted value is the **floor** of the stored one (truncation, never rounding), and the stored one the floor of the time set, to 10 ms. A folder made by `mkdir` reads its 10 ms value in both. FAT32 reads the same 2 s value before and after a remount (1762000000.000 for all three), so FAT has no such split and stays exact, as the owner said. Reproduced end to end on a real image without Finder: `test_darwin.py::test_an_exfat_folder_finder_copied_is_still_the_right_folder_after_a_remount` (opt-in `FT_TEST_DISK_IMAGES=1`) is `wrong_drive` on the base and `Resolved` with the rule. Not reproduced: Finder itself (the red team's `s4.sh` drives Finder by AppleScript; this slice did not run it). That `setattrlist` is the call Finder's copy uses is the red team's reading (its X.000 then X.39 matches the probe exactly). This corrects S0089's note "`setattrlist` keeps whole seconds on exFAT": that holds only until a remount; the comment in `test_twin_sticks_on_real_fat_and_exfat_are_never_written` is fixed.
- **How a time is reduced to the second** (agent): the floor of the nanoseconds, `t // 1_000_000_000` (Python's `//` floors, so a time before 1970 goes down too; exFAT cannot hold one, but the rule is total). Both the recorded and the found time are reduced, so X.000 (mounted) and X.390 (remounted) match in either order. A rounding would split X.6 from X.000 (mutant `seconds-rounded`). It is done at comparison (`handles.same_birth`), not at recording: the record keeps what was read and its format 6 is unchanged, so no INV-17 version bump and no older record to read differently. Only `exfat` is in `WHOLE_SECONDS_ON`; FAT, HFS+ and APFS compare exactly.
- **What the rule gives up** (agent, within the owner's decision): a twin exFAT stick (same format serial) whose ledger folder was made in the same second now passes the folder check where it needed the same 10 ms; it then meets the evidence rule (a missing file is put back only with another file of the save on that stick at its old or new bytes), as before. A Finder-copied twin already matched exactly (S0089's stated limit).
- **A file-system type name the record cannot hold** (BL-0221's overflow; agent): **`no_drive_id`, by a rule, not by the record check's exception.** `handles.drive_of` now returns None for a name outside `journal.FS_TYPE` (made public), so the save refuses `no_drive_id` and recovery meeting one says `unknown_drive` (it said `wrong_drive`, "the folder is not the one saved in", which was the misleading part; the save's `no_drive_id` came only through `writer._seen`'s catch of `BadRecordError`). Why not `io_error`: the condition is permanent (Retry cannot help) and the save text for `io_error` says nothing about why; `no_drive_id`'s text, "Finzytrack cannot identify the drive that holds <file> … Keep your ledger on a drive Finzytrack can identify", is true of such a drive, since a drive's identity is its UUID and its type. Why not a new reason: one more contract value and text for a case no probed file system reaches (every macOS type name is ASCII letters and digits within 15 bytes). The darwin adapter reads the name with `errors="replace"` (`fs_type_from`), so a non-ASCII byte becomes U+FFFD and is refused by the rule, never a `UnicodeDecodeError` out of `mark` (it escaped as an unexpected error before). The probe script mirrors the rule.
- **V2-1** (agent): one `no_folder_id` text for both cases, with a conditional way out: "The folder that holds <file> has no creation time that Finzytrack can read, so Finzytrack cannot tell it from a folder at the same place on another drive. … If <file> is at the top level of a USB drive, make a folder on the drive, move your ledger into it, and open it from there. Otherwise keep your ledger on another drive, such as your Mac's own disk." The engine could tell the two cases apart (`born` 0 or None), but the reason crosses as one value; a split is not worth a contract change for a refusal whose second case (a drive keeping no creation time) no probed file system has.
- **V2-3** (agent): **done, not "why not".** The inspection now carries `backup`, the backup file's path when the engine read it again and it holds the old version (it replaces `backup_good: bool`; one field, EP-30), for every replaced file, also one behind a drive the try refused (the backup is on the Mac's own disk). After a `wrong_drive` or `unknown_drive` stop, the screen adds per such file "If <file> is missing on the drive that held your ledger, its old version is in <backup>." and Keep's confirmation "If <file> is missing on the drive that held it, it will stay missing. Its old version is in <backup>." (`msg:recovery.drive_backup`, `msg:recovery.keep_drive_backup`). A condition, because the engine did not look into that folder (it may be another drive's) and so cannot say the file is missing; a backup not confirmed is not named. Protocol: a field changed in `recover_try`'s inspection, as `backup_good` was added in S0071 without a protocol version bump (engine and sidecar ship together and the codec is strict both ways); `contracts/engine-protocol.schema.json` regenerated.
- **V2-4** (agent): the verifier's sweep, generalised: `/w/L` on a stick of its own (`STICK`, so the journal folder is not FAT-typed as in the scratch copy), FAT and exFAT, for the world's three-file save and a one-file save. The world's save always has evidence (`inc/a.bean` on the same stick), which is why the scratch sweep counted 0 `missing_unconfirmed` states; the one-file sweep reaches it and asserts so (`bool(seen) is one_file`), checks the stop wrote nothing and names a backup holding the old version, applies the user's copy and requires Retry to finish. The rollback sweep (an I/O error or a crash at each rollback effect, then every power-loss state) runs the same oracle. The save's own rollback meeting a missing file (another program removed it just before the failing folder sync): `Unfinished(missing_unconfirmed)`, nothing written, the journal `.open`, recovery names the backup. All held on the base (`@regression-guard`).
- **V2-2** (agent): `handles.drive_of` and `writer._seen` docstrings say FAT only for the version 4 rule (and name the type-name rule); the `TABLE_VERSION = 3` comment names `missing_unconfirmed` (S0089 added all three causes before landing, so no bump now; this slice adds no cause); `writer.Reason`'s two comments name both cases.
- **Engineering principles:** no deviation. EP-30: one function per rule (`same_birth`, `drive_of`), the record unchanged, one inspection field replacing another.
