# S0077: A link in place of a workspace's journal folder

## Brief
- Goal: close BL-0193. Recover-all's listing (`recover_all.list_journals`, `_sub_dir`) skips a `local/<key>` or `local/<key>/journal` entry that is a link, while the save's writer and its gate (`save.records`) follow the link. A save interrupted there is never recovered and the workspace stays blocked (`WRITES_PAUSED {unfinished_save}`), with no message that names the cause. The owner asked to clear the row (2026-11-07: "Let's also do the 3 lower priority items you listed, so the slate is clean").
- Chosen fix (the row's simpler option, by policy, checked against the code below): Finzytrack's own folders for a workspace (`local/<key>/`, its `journal/` and `backups/`) are real folders.
  1. **The save refuses a link there** (§6.1 step 8, where it makes or checks those folders): `NotSaved(linked_folder)`, naming the link, nothing written in it. The user reads which folder and what to do. The trim already treats these links as "not ours" (spec §15).
  2. **Recover-all never skips a link there silently.** It lists the link's names read-only (it reads no record and removes no `.part` through a link). If the folder holds an `.open` record, or cannot be listed through the link, it is `Unlisted` with `linked: true`, which blocks every open (as a folder that cannot be listed does today). The blocked screen says the folder is a link and to put the real folder back, then Retry. A link that holds no `.open` record blocks nothing.
- Why not only (1): the reviewer's concern holds. An `.open` record already sitting in a linked folder (written before this slice, or moved behind a link after a crash) would keep the save gate refusing while recover-all never lists it: blocked forever with no message. (2) closes that; Retry recovers it once the folder is back.
- Why not "recover-all follows the link": the try, Keep and the deletes all check the journal folder with the path guard (`Handles.at`, `path_moved`) and the protocol's `_journal_dir` check; following would change each of them on the recovery path. Listing names to decide "block or not" changes none of them.
- Out of scope, recorded: a link at `local/` itself is followed by recover-all, the gate and the writer alike (no disagreement, so no BL-0193 case); the trim alone turns off there (spec §15). A link swapped in by another process between the save's folder check and the writer's resolve stays possible, the same accepted limit spec §15 names for a journal folder replaced by a link during a try (a process writing inside the app's own folder only).
- **The bytes it protects:** the ledger files of a save interrupted while its journal folder is (or became) a link: the record and backups that undo it stay where recover-all reads them (the save refuses the link), and an `.open` record behind a link blocks the open until it is recovered instead of being skipped (the half-swapped files are never opened as if whole, INV-32). It also keeps the outcome truthful: the user is told which folder is a link, never a bare "writes paused".
- Implements: ADR-0063 decision 2, spec `design/specs/engine-jobs.md` §6.1 step 8, §8.1 "What", §11, §15.
- Capabilities: CAP-WS-RECOVER-FIRST (planned, M2; no status change).
- Invariants touched: INV-32 (every unfinished save recovered before any workspace opens), INV-01 and INV-22 (the save fails closed).
- Risk class / lane: High / full (ledger write path and recovery). Red team: yes (changes a way a write's outcome is told and what blocks an open).
- Acceptance tests (new; must fail on ff3d883f):
  - engine `tests/ledger/test_recover_all.py`: an `.open` record in a linked `local/<key>/journal` and in a linked `local/<key>` is `Unlisted(linked)`; a linked folder that cannot be listed (a dangling link) is `Unlisted(linked)`; nothing is written through the link (a `.part` stays).
  - engine `tests/ledger/test_save.py` (APFS): a link at `local/<key>`, `journal` or `backups` ends `NotSaved(linked_folder)` naming it, ledger unchanged, nothing written through the link.
  - backend: the codec carries `linked`; the screen text for a linked folder; `CHANGE_NOT_SAVED {linked_folder}` and its text.
  - regression guard: a linked folder holding no `.open` record blocks nothing.
- Expected doc impact: spec §6.1 step 8, §8.1 "What", §11 rows, §15; `contracts/engine-protocol.schema.json`, `contracts/openapi.json` and the generated TS client; ARCHITECTURE.md if it names the listing's rule; backlog BL-0193 closed. User docs: none in this slice (the blocked screen is BL-0092's).
- Open questions: none for the owner. Rubric check: no ADR or invariant changes; the policy forbids a setup Finzytrack never offered (it never makes a link there) and the trim already treats as not ours; it follows the owner's "simplify by policy" (2026-10-30) and the row's own option. Not escalated.

## Decisions
- A link at `local/<key>`, `journal` or `backups` refuses the save at the point the save makes or checks the folder (after the gate, step 8's folder step), not before the gate: one check where the folder is used, no second copy. Outcome `NotSaved(step=backup, reason=linked_folder, entry=<the link>)`, re-hash for "unchanged". (agent)
- Recover-all lists a linked folder's names through the link, read-only; any error there blocks (fail closed: the link may lead to a folder that holds an `.open` record nobody can see, e.g. an unplugged disk). A link to a file blocks too: the user removes or replaces it. (agent)
- A new field `linked` on the listing's unlisted folder, not a borrowed errno, so the screen can say what to do. (agent)
- Recover-all's per-link answer depends on what it finds through the link, not on the link alone: a link holding no `.open` record blocks nothing, so a stray or harmless link never stops every workspace from opening. A consequence, accepted: a link `local/<other>` to a real key folder that holds an `.open` record blocks every open for one run, though the record is also listed and tried under its real folder; the Retry after that try lists the link as empty. (agent)
- Tests first: the new engine and backend tests were run against ff3d883f's source (an archive of the base with the new test files copied in, in the session scratchpad): engine 10 failed (all new except the regression guard), backend 6 new failures plus 2 existing tests whose listing helper now sends `linked` (they fail on base because the base codec refuses the extra key; one more, `test_the_best_effort_drive_notice_is_the_owners_words_in_the_spec`, failed only because the archive held no `design/`). `test_a_linked_folder_with_no_open_record_blocks_nothing` passes on base and is tagged `@regression-guard`. (agent)

## Verifier
### Round 1, head d01806e0 (verifier and data-safety red team)
Verifier: passed with 0 High, 0 Medium, 3 Low. Red team: passed with 0 High, 1 Medium, 2 Low, plus 1 open question. One fix round (orchestrator's triage); no second round (no High, one Medium).
- **Red team M1, Medium: fixed.** If `local/<key>/backups` was a link and the journal held an `.open` record, the record was listed and tried. The try stopped `backup_bad` at the path guard (`restore.py`), although the backups were whole behind the link, so the user was pushed toward Keep. Now the listing does not list such a record. It reports `Unlisted(linked)` naming the backups link, and Retry undoes the save once the real folder is back. The `.part` removal in the real journal is unchanged. Tests: `test_an_open_record_whose_backups_folder_is_a_link_is_not_tried_and_names_the_link` (memfs, with the way out) and `test_recover_ops.py::test_the_listing_names_a_linked_backups_folder_beside_an_open_record_and_lists_no_try` (APFS, the red team's repro). Must-pass: `test_a_linked_backups_folder_with_no_open_record_blocks_nothing`.
- **Red team L1, L2 and verifier F2, Low (the blocked screen's way out): fixed, with one change to the proposed wording.** The screen now says: "Put the real folder back in its place, then press Retry. If there is no real folder (the link is a mistake, or its disk is gone), remove the link, then press Retry." I did not use "Put the real folder back, or remove the link" as one equal choice. Behind a moved folder, removing the link hides an unfinished save, so the ledger would open half-written; the second way out is offered only for when there is no real folder. The save's refusal says "or remove the link". That is safe there: with an `.open` record behind the link, the gate refuses first with `unfinished_save`. Spec §11 rows updated. (agent)
- **Verifier F3, Low: fixed as recommended.** `ENOTDIR` through a link (a link to a file, or a linked key whose `journal` is a file) blocks nothing. No record can exist there, and the save's gate skips the same entries. Dangling links, `ELOOP` and other errors still block, since an unplugged disk may hold a record. Test renamed to `test_a_file_or_a_link_to_a_file_in_local_or_in_place_of_a_journal_blocks_nothing`, which now covers three link shapes. Spec §8.1 updated.
- **Verifier F1, Low: test added.** `test_a_linked_key_folder_with_no_journal_folder_blocks_nothing`, in the file's style and tagged `@regression-guard` (it passes on d01806e0 and kills mutant M2).
