# S0089: Recovery writes only on the drive the journal names; the rebuild counts `document` files

## Brief
- Goal: BL-0188, with BL-0217. (1) Every save journal records, for each folder the save writes in or makes a folder in, the volume UUID of that folder's drive. Before the undo (the save's own rollback, §6.4) or recover-all's try (§8.1) writes anything, each such folder that is there is opened through the path guard and its drive's UUID compared with the recorded one; on a different UUID, a drive with none, or a UUID that cannot be read, the try writes nothing, the journal stays `.open`, and the workspace stays blocked with a text that says to plug in the drive that held the ledger, then Retry. The blocked screen's Delete actions refuse on such a folder; Keep, which writes no ledger byte, skips its syncs there as it does for a folder that is not there. A save on a drive whose UUID cannot be read refuses before its first effect (`no_drive_id`), since its journal could never be undone (the owner: "one without it is refused the same way"). (2) `rebuild._wider` counts every `document` file by itself (no `_under` skip), with the red team's late-stamp repro as a test; a test that a generation without `published_by` is refused; the "eight keys" comment fixed.
- Implements: BL-0188, BL-0217; ADR-0012 (the journal format, amended here with the owner's decision), ADR-0063 decision 2 (recover before open), ADR-0068 D2 (best effort keeps the journal and the undo), ADR-0061 (macOS first); `design/specs/engine-jobs.md` §6.3 "Paths", §6.4, §6.5 (journal format 5), §6.6, §6.8, §8.1, §11, §15; `design/specs/mirror/publish.md` §8; EP-29, EP-30.
- Owner decision for this slice (2026-11-08, quoted in Decisions): "Volume ID in journal (Recommended)".
- Capabilities: CAP-WS-RECOVER-FIRST (stays planned: the screens are BL-0092, the switch BL-0154), CAP-DATA-MIRROR (BL-0217).
- Invariants touched: INV-32 (every journal ends recovered or blocking: a wrong drive blocks), INV-22 (fails closed: no UUID, an unreadable one), INV-01 (the undo is part of the write-safety contract), INV-17 (journal format 4 → 5: an older `.open` record is unreadable and blocks; an older `.closed` one is read by its name), INV-30/INV-27 (journals stay machine-local).
- Risk class / lane: High / full lane (a new refusal on recovery and on the save, on the ledger write path). The orchestrator runs the verifier and a data-safety red team.
- The bytes it protects: the files on another drive mounted at the path a journal names (recovery never writes, renames or deletes there: no restore staging file, no swap, no kept-copy move, no temp removal, no folder removal), and the ledger on the right drive (recovered only there, when it is plugged in again). Also a truthful outcome: a journal is never resolved over a drive whose files the try did not undo.
- Population inventory (before coding; built from the code by behaviour: every port call that writes, renames, removes or syncs in `ledger/restore.py`, `ledger/recover_all.py`, `ledger/handles.py` reached from them):
  - restore (the save's rollback and recover-all's try), on a ledger folder: (R1) a foreign temp moved to its kept name at step 2 (`_check` → `handles.keep`); (R2) what a restore swap displaced removed or kept (`_settle`); (R3) the restore staging create, the exclusive rename to the restore temp, the swap, the best-effort plain or exclusive rename, and their folder syncs (`_put_back`); (R4) a name of ours removed or kept (`_clean`); (R5) every recorded folder synced (`_sync_folders`); (R6) a folder the save made removed (`rmdir`);
  - recover-all's actions, on a ledger folder: (A1) Keep's file and folder syncs; (A2) Delete the kept copy / Delete it (`_delete_one`: one removal and its folder's sync);
  - in the app's own folders (not on a ledger drive; out of this check, by design): the journal's renames (`.closed`→`.open`, `.open`→`.resolved`, `.open`→`.kept`), the listing's `.part` removals, the history trim; the save's own writes (`writer`) are not an undo: they go through the descriptors whose UUID the journal records.
  - Each ledger-folder place reaches the disk only through `Handles.at(folder)` of a folder the record names (the file's folder, a created folder, a created folder's parent); the check sits there, plus a pass over every recorded folder before step 2 writes anything.
- Acceptance tests (new; each must fail on the base 3e47593c):
  - `engine/tests/ledger/test_journal_record.py`: format 5 carries a volume UUID per file and per created folder; decode refuses a record without one, a malformed or nil UUID, two UUIDs for one folder, a created folder's UUID that differs from a file under it; a format-4 record is unreadable.
  - `engine/tests/ledger/test_restore_volume.py` (the fake): recover-all's try and the save's rollback over a journal whose drive at the path now has another UUID, no UUID, or an unreadable one: nothing written (no port effect at all; every file's bytes and modification time the same), the journal `.open`, the outcome `wrong_drive` / `unknown_drive` / `failed`; one wrong folder among several stops the try before any write in the right ones; the matching drive recovers as before; a drive put back gives a resolved try; a different drive with other files at the same path is never written.
  - `engine/tests/ledger/test_recover_all.py`: Delete the kept copy and Delete it refuse `wrong_drive` with nothing removed; Keep on a wrong drive syncs nothing there and keeps the journal as the user asked; inspection shows such a file as not reachable.
  - `engine/tests/ledger/test_writer.py`: the save records each folder's UUID; a drive without one refuses `no_drive_id` before the first effect; an unreadable one is `io_error`, nothing written.
  - `engine/tests/fs/test_darwin.py`: `volume_id` on APFS answers a UUID, the same for two folders of one volume, a different one for another volume; the opt-in volumes (exFAT, FAT, HFS+) answer one too.
  - `engine/tests/ledger/test_rebuild.py`: the red team's late-stamp repro (a `document` file under the documents root, added after the plan and deleted during the load, is `moved`, never stamped late); `engine/tests/mirror/test_publish.py`: a generation without `published_by` is no mirror of this kind.
  - backend: `test_recovery_text.py` (the two drive texts, Keep's added sentence, the Delete refusal), `test_save_job.py` / errors (`no_drive_id` maps to `CHANGE_NOT_SAVED {no_drive_id}` with its text).
- Expected doc impact: `design/specs/engine-jobs.md` (§6.3, §6.5 format 5, §6.8, §8.1, §11 rows by key, §15 limit "drive identity"), `design/decisions/ADR-0012` amendment (the owner's words), `design/generated/engine-job-texts.md`, `contracts/openapi.json` and the frontend's generated types (`no_drive_id`), `design/backlog.md` (BL-0188 and BL-0217 done; a row for Windows and Linux volume identity, ADR-0061), `design/ARCHITECTURE.md` (the port's `volume_id`), `engine/CLAUDE.md` if the write-port line needs it.
- Open questions: none that blocks. A confirmation for the owner (non-blocking, inbox): saving on a network share whose drive reports no UUID is refused by this slice (unprobed here; APFS, HFS+, exFAT and FAT all report one).

## Decisions
- **Owner, 2026-11-08, in session**, choosing "Volume ID in journal (Recommended)": "Each save journal records the drive's volume UUID. Before recovery writes, it checks the drive at that path has the same UUID; if not, it writes nothing, keeps the journal, and blocks that workspace with a message naming the drive ('plug in the drive that held your ledger, then Retry'). v0.4 is unreleased, so every journal will carry the UUID; one without it is refused the same way." Recorded as ADR-0012's amendment of 2026-11-08.
- **One UUID per folder, not per journal** (agent): a ledger may `include` a file on another drive, so each file entry and each created-folder entry carries the drive of its folder (`volume`); `journal.volumes` maps every folder the undo may write in (each file's folder, each created folder and the folder it was made in) to its drive and refuses a record that names one folder on two drives (`volume_conflict`). Format 4 → 5 (INV-17's rule: an older `.open` record is unreadable and blocks; the owner's "one without it is refused the same way" is that block).
- **`st_dev` is not recorded** (agent, against BL-0188's wording "`st_dev` and the volume UUID"): `st_dev` is not stable across mounts and is not unique (probed: `/` and `/private/tmp`, two APFS volumes, answered the same `st_dev` with different UUIDs). The UUID alone is the identity.
- **Where the check sits** (agent): in `Handles.at`, when a folder's handle is first opened, through the descriptor every later write in that folder uses (a descriptor never changes drive), plus a pass over every recorded folder at the start of step 2 (`restore._drives`), so a step-2 write (an outside save moved to its kept name) never happens in a right-drive folder while another folder's drive is wrong (test `test_the_drives_are_checked_before_step_2_moves_an_outside_save_to_its_kept_name`; mutant `restore-no-preflight`). The app's journal and backups folders are not checked: the record is read from there, and they are machine-local (INV-27, INV-30).
- **Outcomes** (agent): another UUID `Stopped(wrong_drive)`, none `Stopped(unknown_drive)` (the owner's "refused the same way"; a separate cause so the text is truthful), a UUID that cannot be read `Failed(io_error)` naming the folder (Retry reads it again, as every other read error of a check). `entry` is the folder, `path` the first record file in it.
- **The blocked screen's actions** (agent; the owner's rule names writes, restores and deletes): Delete the kept copy and Delete it refuse a file on such a drive (`wrong_drive`, `unknown_drive`), removing nothing. Keep writes no ledger byte: on such a drive it syncs nothing (as for a folder that is not there) and renames the journal `.kept` as the user chose; its confirmation says "Finzytrack cannot reach the drive that held these files, so it will not undo the save there, now or later." Refusing Keep would leave a user whose stick is lost no way out but unplugging the other drive. The inspection shows such files as not reachable, never the other drive's files as this save's.
- **A save on a drive that reports no UUID refuses before its first effect** (`no_drive_id`; agent, from "every journal will carry the UUID"): a journal it wrote could never be undone, and the rollback would leave the files half-applied behind a block. This may affect network shares (unprobed here); the owner's confirmation is asked, non-blocking: `design/inbox/20261108-network-share-drive-id.md`. A UUID that cannot be read is `io_error` ("not saved", the targets re-hashed).
- **The drive is named on the screen by the folder where it is mounted now** (agent): the record holds no volume name, and the path (`/mnt/USB/L`) is what a user recognises. Texts: `msg:recovery.wrong_drive`, `msg:recovery.unknown_drive`, `msg:recovery.keep_other_drive`, `msg:recovery.refused_wrong_drive`, `msg:recovery.refused_unknown_drive`, `msg:save.no_drive_id` (generated, S0079).
- **Probe (macOS 26, disk images made with `hdiutil`, in the session scratchpad):** `fgetattrlist(ATTR_VOL_UUID)` with `ATTR_CMN_RETURNED_ATTRS` returns a UUID on APFS, HFS+, exFAT and FAT, the same after a detach and attach; devfs and autofs return none (the returned-attributes bit is clear). Network shares (SMB, NFS) not probed. A real run: a save on exFAT stick A at a mount point, cut before its close; stick B (same volume name) attached at the same mount point: recovery stopped `wrong_drive` with every file of B byte- and mtime-identical and the journal `.open`; A back: `Resolved`, `main.bean` at pre. The opt-in real-volume tests (`FT_TEST_VOLUMES` with the HFS+, exFAT and FAT images) pass, the new `test_a_real_volume_reports_its_own_uuid` included.
- **The fake** (`tests/fakes/memfs.py`): `volume_id` per drive (`dev`), `outside_volume_id`, `outside_volume_error`; and `resolve`'s identity now carries the entry's drive (`(dev, inode)`; it was always `(1, inode)`, so a ledger on a mounted drive could not be saved in the fake at all). Asking for a UUID is not an effect, so the conformance replays are unchanged.
- **BL-0217** (agent): the row's fix ("count `document` files individually in `_wider`, no `_under` skip") taken literally made the S0070 case fail (`test_a_dated_file_under_a_documents_root_in_the_set_is_loaded_on_the_first_try`): Beancount's documents step makes a `Document` for every dated file under a root, and the overlay's fingerprint leaves those out because the root's listing already covers them. So a used `document` file is in the hint when the hint names it or when a root's listing **observed before the load** names it (`rebuild._listed`), never by its path alone; `_under` is gone. That is the same coverage rule the overlay uses (`overlay.load`: `listed`), and closes the red team's case (a folder that can be entered but not listed is not in any listing). Repro as a test; the `published_by` test added as `@regression-guard`; the comment says nine keys.
- **Windows and Linux** (ADR-0061): BL-0218 (M1b, with BL-0087's Windows port).
- **Privacy scan workaround** (one line, per PROCESS.md §8; a finding against the rule for the next reflection): the scan's home-path rule refuses a macOS mount point under `/Volumes/` in tests and docs, so the examples use `/mnt/USB/L` and `/mnt/finance`.
- **Engineering principles:** no deviation. EP-30 (simplify first): one check site (`Handles.at`) serves the rollback, recovery's try and the actions; no new lock, record or state.
- **Tests first** (run on the base 3e47593c before any product code): `test_journal_record.py` and `test_volume_identity.py` failed to collect (no `journal.volumes`, no `Cause.WRONG_DRIVE`); `test_darwin.py`'s three new tests failed (no `volume_id`, no `uuid_from`); the BL-0217 rebuild test failed (`loaded`, expected `moved`); the backend's 8 new cases failed (no texts, `no_drive_id` mapped to `INTERNAL`). `test_publish.py::test_a_generation_without_published_by_is_not_a_mirror_of_this_kind` held on the base (tagged `@regression-guard`; it kills the back-compat default mutant the S0088 verifier named). The fake's semantics test (`test_memfs.py`) was written with the fake's change.
- **Round 1, owner, 2026-11-09, in session, on the network-share question** (my inbox file), choosing "Probe, then keep refusal (Recommended)": "Ship the refusal now (fails closed, never writes on a wrong drive). You run a 1-minute script on a network share you use; if it reports an ID, nothing changes; if not, we decide then whether to add a share identity (server + share name). Network shares stay best-effort where they have an ID." Built: the answer appended to the inbox file, moved to `design/inbox/answered/`; the probe `scripts/probe_drive_id.py` (read-only: it opens the folder and asks its attributes, lists and reads no file); BL-0219 for the follow-up decision; ADR-0012's amendment notes the refusal is owner-confirmed and reverses ADR-0068 D2 only for drives with no ID (verifier F1).
- **Round 1, owner, 2026-11-09, in session, on red team H1**, choosing "Drive ID + folder birth (Recommended)": "The journal also records, for each ledger folder, the folder's creation time (and its file-system type). Recovery writes only when the drive ID AND the folder's creation time match. A stick formatted in the same batch has a 'Finance' folder created at a different moment, so it is refused; only a block-for-block clone (already a stated limit) passes. Cheap: one stat per folder, no file written anywhere new."
- **Journal format 6, not 5** (agent): format 5 lived only in this slice's first commit (8a5cb989, never pushed); still, any change of the record's shape gets a new number, so a format-5 record from that build reads `unknown version` and blocks (INV-17's rule, fail closed), never `malformed` by accident. The per-file `volume` is replaced by `folders`: every folder the undo may write in (each file's folder, each folder the save makes and the folder it is made in), with the drive UUID, the file-system type (`f_fstypename`) and, for a folder that was there before the save, its creation time (`ATTR_CMN_CRTIME`, nanoseconds as the file system keeps them).
- **Pushback on "a folder the save creates records its own birth at creation"** (agent): the record is written before the save makes any folder and never changes after (§6.5: every state is a rename), so a folder the save makes cannot carry its birth without rewriting the journal, a new write path. Instead it records none (`born` null) and is checked by drive and file system; it sits in its parent folder, which existed before the save and whose birth is checked. A drive mounted exactly on a folder the save made, between the crash and recovery, passes on drive and file system alone only if it is a twin (same serial): stated as part of "Limit (drive identity)".
- **Probed creation-time resolution** (macOS 26 disk images): APFS 1 ns, HFS+ 1 s, exFAT 10 ms, FAT 2 s; the top level of a FAT or exFAT drive answers 0 (no creation time kept); devfs returns none. `diskutil info` gives the twin stick's serial UUID (v3) while the kernel answers it a version 4 UUID when its twin is mounted (red team M1 confirmed).
- **A ledger at the top level of a FAT or exFAT drive refuses the save** (`no_folder_id`; agent, failing closed): there the folder birth is 0 on both twins, so the owner's rule would reduce to the drive UUID, which H1 showed is not unique. Asked of the owner, non-blocking: `design/inbox/20261109-fat-top-level-ledger.md`.
- **FAT's creation time is local time with no zone** (agent): macOS reads it in the Mac's zone of the moment, so after the zone changes (travel) the same folder reads a whole number of quarter hours off; a shift of that kind up to 14 hours counts as the same time on `msdos` only (`handles.same_birth`). Not probed (the Mac's zone was not changed); the rule follows FAT's format. exFAT keeps its zone, APFS and HFS+ keep UTC.
- **A version 4 UUID on FAT or exFAT names no drive** (red team M1): a save there refuses `no_drive_id`; recovery meeting one is `unknown_drive` (it cannot tell the right stick when its twin is mounted beside it). APFS's own UUIDs are version 4 and stable, so the rule is for those two file systems only.
- **The path guard runs before the drive check** in `Handles.at` (red team L1): a link in place of a ledger folder is `path_moved` again, and Keep refuses it as S0071 R1-3 decided. A handle whose first check fails is no longer kept open (it was cached before; nothing read it after the refusal).
- **`protocol/recovery.py` `TABLE_VERSION` 2 → 3** (verifier question): its comment shows a version names the table's rule (2 came with a removed cause), so two new causes (`wrong_drive`, `unknown_drive`) are a new rule and a new version.
- **Wording** (verifier questions): Keep's confirmation for `unknown_drive` says "cannot identify", not "cannot reach" (`msg:recovery.keep_unknown_drive`), and both drive sentences say "at least one of these files", since a journal may name folders on several drives.
