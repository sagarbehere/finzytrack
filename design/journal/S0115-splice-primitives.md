# S0115: the splicing primitives, ported from Fava as pure functions over text (M1b, ADR-0009)

## Brief
- Goal: M1b's first slice. Port Fava's source-slicing algorithms (`fava/core/file.py` of Fava 1.30.16, MIT: `find_entry_lines`, `find_insert_position`, the slice replace and delete) into the engine as **pure functions over text**, with an MIT attribution header, plus our `replace_token`: `locate`, `route_insert`, `apply_edits`, `replace_token` in `ledger_engine.ledger.core.source_edit` (ARCHITECTURE.md §2.0's engine tree), with the `Edit` / `EditPlan` types they take. They read no file and write nothing: they take a file's current bytes and the parser's positions in that text, and return the new bytes per file, or a refusal naming why. No dependency on the `fava` package (ADR-0009).
- Implements: ADR-0009 (stage 2 of WS-WRITE: "splicing engine port, pure functions, with property tests"); the `edits` column of `design/specs/write-path/README.md`; ADR-0008 (the primitives are what the contract's `prepare` will call; the contract pipeline itself is a later slice).
- **The ownership rule** (owner, 2026-11-13: "I agree with the ownership rule, go ahead"):
  1. A mutator owns only the spans of the entries its intent row names, located from the parser's positions in the file's **current text**, never from loader output (so no plugin-generated, glob-included or pushtag-expanded entry can be targeted). Each span's first line must show the entry's date and keyword.
  2. An insert goes only where Fava's `insert-entry` options route it, or to the default file, never inside a `pushtag`/`pushmeta` region.
  3. Every byte outside those spans stays byte-identical; line endings and a missing final newline are kept per file; `include`, `option` and `plugin` lines are never re-emitted.
  4. Edits land only in the files the intent row's `files` column allows. Overlapping spans, a non-UTF-8 file, an encrypted (`.gpg`/`.asc`) file, or a span whose first line does not match abort the plan before anything is written.
  5. Many edits per file are planned from one snapshot and applied bottom-up.
- Scope: the edit kinds `insert`, `replace` (whole entry span), `delete`, `replace_token` (exactly one account token on the posting's or directive's own line; never a regex over the file). Out of scope, each with its first consumer: `insert_meta`/`delete_meta`, `option_line`, `new_file` (their mutators' slices); the contract pipeline (ADR-0008) and any save; the semantic diff (step 2).
- Capabilities: CAP-DATA-WRITE stays `planned` (no mutator yet); its note may name the primitives as built.
- Invariants touched: INV-01 (bytes outside the intended change), INV-03 (Beancount's parser is the only source of positions). No invariant text changes.
- Risk class / lane: High / full (ledger write path), but the primitives write nothing to disk. Review budget row: **Other product code** (owner, in the request of 2026-11-14): a verifier, and a fresh round after any product fix. The data-safety red team comes with the contract pipeline that turns edits into saves.
- Mechanism questions (§3 step 2): which real setup needs this: every ledger write v0.4 makes (ADR-0009); the rare setups (encrypted, non-UTF-8 files, entries inside pushtag regions as insert targets, generated entries) are already forbidden by the rule above. Fix-round history: a new mechanism; no earlier slice built it.
- The bytes it protects: every ledger byte outside the owned spans of the planned edits, in every file (they must come out identical), and the owned spans themselves (only the planned text replaces them).
- Acceptance tests (tests first; each must fail on the base commit):
  - Property tests (Hypothesis) over generated ledgers (entries, comments at column 0 and indented, blank lines, CRLF and LF files, a missing final newline, tabs, non-ASCII text, pushtag/poptag and pushmeta/popmeta regions): for any set of non-overlapping edits, every byte outside the owned spans is identical; applying a plan and then its inverse returns the original bytes (WS-WRITE acceptance, `design/backlog.md`); edits planned from one snapshot give the same result in any input order (bottom-up).
  - Refusals, each a must-not-pass test: overlapping spans; a non-UTF-8 file; a `.gpg` / `.asc` file; a span whose first line lacks the entry's date or keyword; a position not from the current text (a stale snapshot: the text's hash differs); a file outside the row's `files`; an insert routed (by an option or by appending to the default file) into a pushtag/pushmeta region; a `replace_token` whose token is not exactly one account token on that line; new text that carries an `include`, `option` or `plugin` line.
  - Routing: Fava's `find_insert_position` semantics (options sorted by date, newest first; only options dated before the entry; the entry's accounts in Fava's order; else the default file), checked against vectors recorded from Fava 1.30.16 itself, with the vectors' source stated.
  - The D1 write corpus (`corpora/ledgers/write/`, `design/specs/write-path/write-corpus.md`): every case that bears on splicing (globs, plugins, pushtag, `{}`, elided amounts, comments, CRLF, no final newline) gets a splice test showing only the target's span changed.
- Expected doc impact: ARCHITECTURE.md §2.0's `core/` line (what is built), `engine/CLAUDE.md` (a pointer to the module and its rules), the attribution (module header; `THIRD_PARTY_NOTICES` if ported source belongs there under the licence check's rules), `design/backlog.md` (WS-WRITE stage 2), CAP-DATA-WRITE's note. No user docs (nothing user-facing).
- Open questions: none (the ownership rule is the owner's, above).
- Base: 0cc01a8e.

## Decisions
- The ownership rule above is the owner's (owner, 2026-11-13: "I agree with the ownership rule, go ahead"; recorded here as the request of 2026-11-14 asked).
- A delete removes exactly the entry's span (agent, from rule 3). Fava's `delete_entry_slice` also removes the blank lines after the entry; those bytes are outside the span, so they stay.
- **Tests first** (agent): the three test files failed on base 0cc01a8e at collection (`ImportError: cannot import name 'source_edit'`), run 2026-11-14 before any product code.
- **Module and purity** (agent): `ledger_engine.ledger.core.source_edit`, no I/O. It calls Beancount's parser and lexer on the bytes it is given through the port (`parse_string`, and two new wrappers `lex` and `custom_accounts`, classed in `WRAPPERS`), as `mirror/core/rows.py` already does from a `core/`. Account tokens are found in the account-grammar home, `grammar.account_token` (EP-23).
- **"Positions from the current text" made structural** (agent): a `Snapshot` holds each file's bytes and SHA-256; a `Span` carries the hash it was located in; an `EditPlan` carries the snapshot's hashes. `apply_edits(current, plan)` refuses `stale_snapshot` when any planned file's bytes differ or an edit's hash is not the plan's, then re-derives every edit from the current bytes (`locate`, `route_insert`, `replace_token` must give exactly the same edit; else `edit_not_located` / `insert_not_routed`). A hand-made span or a moved insert cannot pass.
- **Fava's span kept, plus a whole-entry check** (agent, rule 1): the span is Fava's `find_entry_lines` (stop at a blank line, a whitespace-only line or a line whose first character is not whitespace); Beancount itself ends an entry at the same lines (checked: a blank line, a column-0 comment or heading followed by an indented posting is a syntax error). Fava's span is wrong in one shape: a multi-line string whose next line starts at column 0 ends the span inside the entry, and a replace or delete would leave the rest orphaned. The span must therefore parse alone, with no error, as one entry of the same type, date and posting count (`span_not_whole_entry`). This also refuses an indented directive Beancount keeps after an error.
- **First-line check from the parser only** (agent, after the mutants): the entry the parser found on the target line must have the target's class and date. A second check that lexed the first line for the date and keyword token was removed: the mutants showed each check alone was covered by the other (Beancount reads the entry from those very tokens), and the one shape where the line does not start with them (an indented directive) is refused as not whole.
- **Lines** (agent): split at `\n` only, as Beancount counts lines (a lone `\r` is no line end in Beancount; Fava's universal newlines would split there). A file's line ending is its first line's (Fava); a file with no line end gets `\n` (Fava uses `os.linesep`, which differs per platform). New text must be complete `\n` lines without `\r`, starting at column 0 (an indented first line would join the line above).
- **Final newline** (agent, rule 3): a replace of a span that ends the file without a final newline drops the text's last line end; an append to such a file adds a line end and a blank line before the entry and none after it. Fava would add a final newline in both. An append to an empty file is the entry alone (Fava writes a blank line first).
- **Insert separators as Fava** (agent): before an option line, the entry then a blank line; at the end, a blank line then the entry.
- **Inserts at one point** (agent, rule 5): placed by date, then Fava's order of kinds (`_incomplete_sortkey`), then by text. Fava keeps the input order for ties; the text tie-break makes the result independent of input order, which the property test requires.
- **Routing** (agent): Fava's `find_insert_position` and `parse_options` as written: options sorted by date then line (the load's order; ties across files keep the snapshot's file order, which the caller gives in include order), then newest first; only options dated strictly before the entry; the entry's accounts in Fava's order; `pattern.match` (anchored at the start only); an option with no value is the empty pattern (matches everything); a non-text value, an invalid pattern or an unknown key is skipped; `insert-entry` and `insert_entry` are one key; an unquoted account value is a text. Options come from the current text's parse, never the load: a `fava-option` a plugin made is not seen (Fava would use it), which is rule 1's intent. Routing reads every file of the snapshot, so an encrypted or non-UTF-8 file anywhere in it refuses `route_insert` (its options cannot be read).
- **Fava vectors** (agent): recorded from Fava 1.30.16 itself (its `parse_options` and `find_insert_position`) on Beancount 3.2.0, by `scripts/oracle/record_fava_insert.py`, run in a throwaway environment outside the repository holding only those two packages (and their dependencies). 9 cases, 38 inserts, including same-date ties across three files and the odd options above. A second run gave identical output. The recorder is not in `check_generated.py` (the gates have no Fava environment); its docstring says how to rerun it, and the JSON's `$comment` names the source.
- **Push regions asked of the parser** (agent, rule 2): the text before the insertion point plus a probe transaction is parsed; the probe must get no tag and no metadata beyond its position. A probe the parser cannot place (the file ends inside an open string) is refused too. One prefix parse per distinct point, cached per snapshot.
- **New text** (agent, rule 3, wider than the brief): exactly one entry, no parser error, and no `include`, `option`, `plugin`, `pushtag`, `poptag`, `pushmeta` or `popmeta` token anywhere (Beancount's lexer). Push and pop are added: in new text they would change the tags or metadata of entries outside the span, which rule 3 protects.
- **`replace_token`** (agent): allowed on the entry's own line and on the parser's posting lines (metadata lines are not); `old` must be exactly one account token of the line and `new` must lex as one account token in its place; each place `old` is written is tried and the line lexed again, so text in a comment, a string or a longer account name is never touched. `old == new` is refused. A token edit owns only its characters, so two token edits on one line can share a plan.
- **Overlap** (agent): two ranges overlap when they share a character; an insert point at the start of an edited range overlaps it (an insert before an option line whose own entry is edited), at its end it does not.
- **Bottom-up** (agent, rule 5): the new text is built in one pass over the edits sorted by position, every position the snapshot's. That is the same result as applying bottom-up, in linear time.
- **Inverse** (agent): `revert(current, applied)` restores the old bytes from the recorded splices and refuses `stale_snapshot` when a file is not the bytes the plan made. It works at the text level; the undo mutator (intent table `ws.undo`) may later express its inverse as edits.
- **Encrypted files** (agent): refused by name, `.gpg` or `.asc` in any case, as the overlay and the save's step 0 decide (ADR-0059); so the plain `asc-plain` file is refused too. The suffix tuple is pinned equal to `overlay.ENCRYPTED_SUFFIXES` by a test.
- **Attribution** (agent): the MIT notice and copyright are in the module's header (MIT asks for them in copies of substantial portions; MIT is GPL-2.0-compatible). `THIRD_PARTY_NOTICES` is generated by `check_licences.py` from bundled packages only and has no entry kind for ported source, so it is unchanged. The notice's email address is the author's published one; the privacy scan's visible per-line marker (`privacy-scan: allow email`) excuses that one line, since the licence asks for the notice as written.
- **Push-region replace** (agent): an entry inside a push region parses with the pushed tags and metadata; printing it as parsed would write them into its text. This is the edit producer's duty, not the primitives': BL-0265 (WS-WRITE stage 4).
