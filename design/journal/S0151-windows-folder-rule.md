# S0151: The folder rule on Windows, where a removal is decided per entry (BL-0283, OneDrive; M1b)

## Brief
- **Goal:** a save, its rollback and recovery work in a OneDrive folder on Windows. The owner's hand check on a Windows 11 PC with OneDrive (2026-11-23) refused **every** save into a OneDrive folder with `permission` ("Finzytrack has no permission to change main.bean"; `unchanged=True`; nothing written). On Windows only, the folder rule (`handles.folder_blocked`, `handles.acl_denial`, the undo's `restore._writable`) asks what Windows decides: may entries be added in the folder, and may each entry the save or its undo removes or renames away be deleted; a deny entry counts only if it can reach what the save writes or removes. macOS and Linux: byte for byte unchanged.
- **Why (probed on the owner's PC, 2026-11-23,** with `engine/scripts/diag_onedrive_save.py`, written by the orchestrator, run by the owner; its log is not in the repository):
  - the OneDrive root's DACL is `D:AI(D;CI;DT;;;WD)(A;OICIID;FA;;;SY)(A;OICIID;FA;;;BA)(A;OICIID;FA;;;<user>)`; every folder inside inherits `(D;CIID;DT;;;WD)`: deny Everyone `FILE_DELETE_CHILD`, container-inherit only (subfolders, not files); files have `(A;ID;FA;;;…)`, full access, no deny;
  - the OneDrive folders carry the READONLY attribute, which marks a customized folder on Windows and does not stop writes;
  - on the ledger folder, in every placeholder mode (0, 1, 2): `allowed('.', CHANGE_ENTRIES)` True; `allowed('.', REMOVE_ENTRIES)` **False** (`_reopen(FILE_DELETE_CHILD|FILE_TRAVERSE)`: NTSTATUS 0xC0000022); `allowed('main.bean', DELETE)` True and `READ_XATTRS` True; `acl()` lists the inherited deny `delete_child` with `directory_inherit`. So `handles.folder_blocked` refused on both counts: the `REMOVE_ENTRIES` ask, and `acl_denial`'s "any deny entry";
  - the save's real effects all succeed in that folder, in every mode, through the adapter: `create(tmp, like=main.bean)`, `sync_file`, `rename(tmp → main.bean)`, `sync`, `remove`; Python's `os.replace` too. Windows grants deleting or renaming away an entry if **either** the folder grants `FILE_DELETE_CHILD` **or** the entry itself grants `DELETE`;
  - a local temp folder (no deny entry) passes everything.
- **Implements:** the owner's decision of 2026-11-23 (below; option 1); ADR-0013's amendment of 2026-11-23 (new, this slice), a Windows variant of its two amendments of 2026-10-30 ("Allowlist (Recommended)", "Any subject (Recommended)"; S0061 r6, r7); BL-0283's change D (owner, 2026-11-21: typical OneDrive setups supported); engine-jobs §6.1 step 8 (the folder rule), §8.1 (the undo's checks); ADR-0069 (best-effort mode on Windows); IMP-0078 (outcome exact, cause best effort).
- **Capabilities:** none changes status (the engine's write path on Windows is BL-0087's and BL-0283's, not a row of its own).
- **Invariants touched:** INV-01 (no torn or lost ledger byte: a save the rule now lets through must land or be truthfully refused at its real effect), INV-22 (truthful outcome), INV-32 (recovery in such a folder must resolve). INV-23 (the diagnostic masks SIDs and paths; no SID, home path or machine name in the repository; the runner's test reads its own user SID at run time only).
- **Review row:** hardening, or rather **loosening**, an existing write path's guard: treated as a loosening of a check that guards ledger data. The verifier **and** the data-safety red team, and a fresh round after any product fix. Never batched. Risk class High.
- **Risk class / lane:** High / full.
- **The bytes it protects:** every ledger file in a Windows folder whose ACL denies `delete_child` to containers, and the undo's ability to put files back (the replaced files from their backups, the names of ours and the folders the save made removed).
- **Which real setup needs this, and can a policy forbid the rest?** Every OneDrive folder (owner decision D, typical OneDrive setups), and Windows' own Documents when redirected to OneDrive. A policy can't forbid it: the owner chose "1" over option (2), refusing ledgers in OneDrive folders. What the new form does not cover (any other deny that reaches the save's entries, a folder whose new entries would get no `DELETE`) stays refused: refuse first (IMP-0075).
- **Has this mechanism or its family needed two or more fix rounds before?** Yes. The folder rule and its ACL rule were made in S0061 (8 verifier rounds and 8 data-safety red team rounds; the rule itself was changed in rounds 5, 6 and 7: round 5's `inheritable_denial`, round 6's allowlist, round 7's any-subject rule and the journal and backups folders), restated in S0073 part B (verifier r1 F1, the exception stated exactly), and given its Windows DACL read in S0128 and S0135 (V2-Q-B). The policy option (2) went to the owner before coding, as PROCESS.md §3 step 2 asks; the owner chose (1).
- **Under IMP-0078:** the outcome is exact (class (a)); a cause is best effort (class (d)). A refusal that the new form lets through and Windows then refuses at its real effect is an `OSError` at that effect, handled as the sweeps already handle one (the fake's sweeps inject an error at every effect).

## Decisions
- **Owner, 2026-11-23, in session.** Offered: "(1) a Windows form of the folder rule: on Windows ask what Windows decides, namely may the save add entries in the folder, and may each entry it replaces, renames away or removes (and its undo's) be deleted, as already asked per file; and count a deny entry only if it reaches files (object-inherit) or denies adding entries; macOS and Linux unchanged; (2) refuse ledgers in OneDrive folders." Owner: **"1"**. A Windows variant of the owner's rule of 2026-10-30 ("Allowlist (Recommended)", "Any subject (Recommended)"; `handles.folder_blocked` / `acl_denial`, S0061), recorded as ADR-0013's amendment of 2026-11-23 and on BL-0283's row.
- **One rule, one place, the OS's fact in the port** (agent; EP-23): the rule stays in `handles.blocking_entry` and `handles.folder_blocked`; what differs on Windows is a fact of the OS, which the port states (`Caps.delete_by_entry`: "a removal is granted by the folder's `delete_child` or the entry's own `DELETE`", True only in the Windows adapter and the fake's Windows mode), and Windows' own answer to `Right.REMOVE_ENTRIES` (the adapter). `folder_blocked` and `restore._writable` are unchanged in code: both ask `REMOVE_ENTRIES` and `acl_denial`, which now passes `by_entry=h.caps().delete_by_entry`. Rejected: an `if sys.platform` in `handles` (the fake's Windows mode could not reach it); a second Right (`REMOVE_OWN`) beside `REMOVE_ENTRIES` (two names for one question; the POSIX adapters would answer both alike).
- **`REMOVE_ENTRIES` on Windows asks Windows, never assumes** (agent; the brief: "State for each why DELETE is granted there, or ask it"): where the folder grants `FILE_DELETE_CHILD` (every plain local folder), the answer is yes as before. Where it refuses it (OneDrive), the adapter asks whether every entry the save makes would grant `DELETE`: the security Windows would give a file and a folder made in it, and a file and a folder made in such a folder (to depth 2, which stands for every depth: a `limit_inherit` entry stops after one level, every other inheritable entry passes on unchanged), built with `CreatePrivateObjectSecurityEx` from the folder's own security descriptor and this process's token (what NTFS assigns a new entry with no security of its own), then `AccessCheck` for `DELETE` (`WindowsDir._may_remove_entries`, `_new_entries_deletable`; asking writes nothing; a DACL we may not read answers no). Why it is needed beyond the deny rule: a missing allow is not a deny entry, so a folder whose allow entries give new files no `DELETE` shows no deny, and without this ask the save would make a staging file it could never remove. Rejected: reading the allow entries ourselves (it needs whom each names, which the owner's rule of 2026-10-30 never asks: S0061 r7 found the membership lookup wrong); a probe file (asking must write nothing).
- **The ACL rule's Windows form is narrower than the offered words** (agent; a tightening inside option 1): a denied `delete_child` counts for nothing wherever the entry reaches (`handles.DECIDED_BY_ENTRY`); the entry's other bits are judged exactly as on macOS (the allowlist: only a non-inheritable deny of the folder-self bits passes). So a container-inherit-only deny of another bit, which the offered words ("count a deny entry only if it reaches files or denies adding entries") would not count, still blocks: it reaches the folders the save makes (a container-inherit `delete` would stop the undo from removing a folder it made; a container-inherit `add_file` would stop the save from writing in it). An entry with a flag no adapter names still blocks. Why narrower: the allowlist is the owner's own form (round 6: each fix that added a bit to a denylist had missed one), and OneDrive's entry passes either way.
- **What each removal relies on** (agent; the brief's inventory, built by behaviour from every caller of `remove`, `rmdir`, `rename`, `rename_excl`, `rename_shared` and `move` on the write path, `git grep` at the base):
  - the file the save replaces and the restore's put-back target: asked `DELETE` on its own before any effect (`writer._check_target`, `restore._check`'s `allowed(base, DELETE)`), as before;
  - the save's staging and temp names, the restore's temp and staging names: new files, made by the save or the restore; covered by `REMOVE_ENTRIES` (their inherited security grants `DELETE`), and the undo asks `DELETE` of each name of ours it removes (`restore`'s loop over `ours`);
  - kept names (an outside save moved aside by `handles.keep`): another program's file, not asked; where it grants no `DELETE`, the move fails with `PermissionError` at its effect, and the try ends `Failed` (`io_error`), never "undone", the outside bytes where they were (test above; a cause of class (d) under IMP-0078, not reworded here);
  - folders the save makes: covered by `REMOVE_ENTRIES` (a folder made here would grant `DELETE`), and the undo asks `DELETE` of each before removing it (`restore._check_folders`); they inherit OneDrive's container-inherit deny, so what is made in them is removed by its own `DELETE`, which the depth-2 ask covers;
  - backups and journals in the app folder (`%LOCALAPPDATA%`, never in OneDrive by default): new files of ours; the app folders pass the same folder rule (`writer._check_app_folder`, `restore._journal_folder`, `recover_all`), so the same ask covers them; the history trim removes only these, never fails the save, and leaves an entry it cannot remove (test above);
  - the create's and the copy's own files and folders (`create.py`, `copy.py` on the create's writer): new entries of the job; the target's parent passes `folder_blocked` (`create.py`), so the same ask covers them;
  - the mirror publish: only the app's cache folder, which is not judged by the folder rule and not in OneDrive; unchanged.
- **The diagnostic** (`engine/scripts/diag_onedrive_save.py`, written by the orchestrator, run by the owner on 2026-11-23, already lint- and pyright-clean) is committed as the tool that found the cause. It writes only its own two scratch folders and masks paths and SIDs in its log.
- **The hand check's report** (`backend/scripts/windows_hand_check.py`): not changed. Adding "what the folder rule answered" would need the backend script to import the engine (`ledger_engine`), which nothing outside `engine/` may do (`scripts/check_engine_boundary.py`), or a new protocol op; the save's own outcome (`permission` with its `entry` and `detail`) already tells it. The owner reruns the hand check after this lands.
- **The fake's Windows mode** (agent): a removal is granted by the folder's side (`_may_remove`) or the entry's (no deny of `delete` on it, a file's own denied `DELETE`, or `ungranted`: no allow grants it, `outside_grant_no_delete`); POSIX mode keeps both sides needed. A new folder gets a file-only inheritable entry as `only_inherit` (to pass to its files) and a `limit_inherit` entry stops after one level, as Windows does (APFS does neither; POSIX mode unchanged).
