# S0081: The `copy` job (engine jobs piece 5b)

## Brief
- Goal: BL-0196, the `copy` job of `design/specs/engine-jobs.md` §8.2 (a test copy, Copy adoption, "New workspace from settings of…"), built on the create's writer (`ledger_engine.ledger.create`, S0080): the sources read inside the job; `RECOVERY_BLOCKED`-style refusal when any `.open` journal names a source (model `NoCopyOverOpenJournal`); the legacy-lock try and re-check (ADR-0062, BL-0026); files outside the source folder and documents copied in; what "loads the same" compares; the copy's own lineage id.
- **Cut (too big for one hand-off):** the conformance replay of the model's create and copy through the engine, with the `CR_*`/`CP_*` markers (`backend/tests/architecture/test_tla_mapping.py` `PLANNED`), moves to a new row, BL-0201. The create and the copy are checked by their own sweeps over the fake until then. Copying a ledger's own plugin modules (Python files beside the ledger, loaded through `insert_pythonpath`) is a new row, BL-0202: until then such a copy does not load the same and is refused, never made half-working.
- **What a copy is in this slice:** the sidecar sends the target folder, the source ledger's root (an absolute path, as the user named it), the files of `.finzytrack/` (a manifest with a **new lineage id** and the root's file name, `app.workspaces.creation.copy_manifest_files`), the app's local data folder (where the journals are) and the legacy write-lock files to try (the caller finds the installs whose config names the source, M3's legacy detection; none for a test copy). Who builds a request (adoption, test copy, "New workspace from settings of…") is M3's.
- **The engine's steps** (`ledger_engine.ledger.copy`, op `copy`, in a fresh engine holding the engine lock; steps 1, 3, 4, 6 and 7 are the create's own code, generalized):
  1. the target, as a create's (§8.2 step 1);
  2. **the sources**, before anything is written into the target:
     a. each legacy lock tried once, without waiting (`LegacyLocks.try_lock`): held, or any error, refuses (`legacy_saving`; fail closed, ADR-0062 decision 2); a free one is held for the copy's file reads; an absent one is remembered;
     b. the source loaded once with the overlay load (`overlay.load`, Beancount's full load, plugins included, never decrypting: an encrypted file refuses, `encrypted`); its `Loaded.fingerprint` is the hash of exactly the bytes it parsed: this is "the fingerprint before reading" of the owner's decision 2 (S0051's extended fingerprint). A root that does not exist refuses (`source_missing`), a file that cannot be read too (`source_unreadable`), a load that cannot run (`source_failed`). The load's result is reduced to its comparison digest (below) and dropped; the plugin modules it imported from outside the engine's install are forgotten, so the copy's load imports its own;
     c. every `.open` journal in `local/*/journal/` is read: one that names a source file by `path_key` refuses (`recovery_blocked`, naming the file); one that cannot be read, or a journal folder that cannot be listed, refuses too (fail closed: spec §8.1 "A journal whose file list cannot be read blocks every open and every copy");
     d. the layout (pure, `ledger_engine.ledger.core.copy_layout`): the folder of the source's root is **B**; a file under B keeps its path relative to B; ledger files outside B go under `outside/` (their paths kept relative to their deepest common folder, so their own relative includes still resolve); each documents root outside B becomes `documents` (more than one: `documents-2`, …; ADR-0017: copied workspaces write `option "documents" "documents"`); a name already used by a copied path gets the next free number. Copied: every ledger file the load parsed, every file under each documents root (the whole folder, as Beancount scans it), and each `document` directive's file that lies under B;
     e. the rewrites (owner's decision 3): only an `include` line whose path, mapped, would read another place (an absolute path, or one reaching outside B), and only the root's `option "documents"` line whose root moves. The new text is the mapped path relative to the file's new folder. A line that cannot be found or rewritten exactly (its string is not the one Beancount parsed, a quote or backslash in a new path) refuses (`cannot_rewrite`, naming the file). Each rewrite keeps the line count, so line numbers stay the same;
  3. the writes, as a create's: exclusive creates and `mkdir`s, but each file's bytes **streamed** from its source in 1 MiB chunks (owner, memory-frugal hosting: never a whole document in memory; a ledger file that needs a rewrite is read whole, as every load reads it), hashed while written. A ledger file whose bytes differ from the load's fingerprint refuses (`source_changed`); a source that cannot be read refuses (`source_unreadable`);
  4. read-back of every file by its SHA-256 and length, read in bounded chunks (never more than its length plus one byte); then the held legacy locks are released (ADR-0062: held "only for the copy's file reads");
  5. **"loads the same"** (below): the copy loaded with the overlay load in the target; it must run (`load_failed`), parse only files the job wrote and scan only documents roots inside the target (`load_outside`), and give the same comparison digest as the source (`load_differs`, naming the first source file and line that differ). Then **the re-check, just before the commit point** (owner's decision 2, ADR-0062's re-check): the source's ledger set observed again equals the load's fingerprint (`fingerprint.observe`), every copied document's source hashes as it was copied, and every legacy lock found absent is still absent; anything else refuses (`source_changed`; a lock file that appeared: `legacy_saving`);
  6. the commit point (`gate`/`proceed`, §4);
  7. `.finzytrack/` last, as a create's (the manifest the request carries, with its new lineage id).
  Every stop cleans up as a create's (owner's decision 1, the same code: `create._Run._cleanup`); after a death, `copy_outcome` reads the disk as `create_outcome` does, naming every entry in the target, since the job's file list is known only to the engine that died (the target was empty when the job began).
- **What "loads the same" compares, and why** (owner's decision 3: decide and justify against the spec): the copy is the same ledger when Beancount's full load of it gives what Beancount's full load of the source gave, read as the same books:
  - **entries**, in load order (after sorting, booking, plugins and validation): every field, metadata included, each entry reduced to a canonical form and hashed. Line numbers are compared (rewrites keep them); file names are compared after mapping the copy's paths back to the source's (`T/outside/…` to the outside files' folder, `T/documents/…` to the old documents root, `T/…` to B), so a `document` entry Beancount made from the documents folder, or a posting's `filename`, compares equal when it names the copied file;
  - **errors**: the same errors, in order, each by kind, source (file mapped back, line), message (paths mapped back) and entry. The same, not none: the source may have Beancount errors (ADR-0067: accounting advises), and the copy must keep exactly them;
  - **options**: every option, paths mapped back, except: `input_hash` (Beancount's cache key from file times and sizes: S0051), the raw strings of `option "documents"` (rewritten by design; compared instead as the documents roots they resolve to, mapped back), and nothing else. `include` and `filename` compare after mapping, so the copy parses the same files in the same places;
  - **ignored**, by design: where the files are (the mapping above), the bytes of the rewritten lines themselves (only what they load is compared), file times. A value of a kind the comparison does not know (a plugin's own object) refuses (`load_differs`): fail closed, never "the same" by guess.
  Why the full load and not a parse: the spec's §2 says the check runs user code, and a copy must keep what plugins make of the ledger. Why the overlay load and not the create's `real_load`: the source needs the fingerprint of exactly what it parsed (the re-check of decision 2 compares against it), and the overlay load equals Beancount's (`tests/ledger/test_overlay.py`); the copy's load uses the same function so both sides are read the same way.
- **The bytes it protects:** the source ledger set and its documents (only ever read: no write, no lock file created, nothing renamed or synced under the source); the user's files in the target folder (the create's rules); and the truth of "copied": a workspace manifest is written only over files that hold the source's bytes as of one moment (no mixed copy: each ledger file equals what the load parsed and still does just before the commit point, each document equals its source then) and load the same as the source; "not copied" then names what the job left, never says "delete".

## Decisions
- **Owner, 2026-11-07, the cleanup** (from an options question, verbatim choice and description): **"Same rule as create (Recommended)"**. A stopped copy removes only what this run made, checked by identity (from the create's own descriptor) and by content. It keeps and names anything it is unsure of (`msg:create.left` style, "copy" for "new workspace"). After an engine death it removes nothing and names every entry at its names. The source ledger is only ever read, never written. Reuse create's code; do not write a second cleanup.
- **Owner, 2026-11-07, a source edited during the copy:** **"Refuse, ask to retry (Recommended)"**. Copy fingerprints each source file before reading it, and again just before its commit point. If anything changed, it stops with a text like "Your ledger changed while Finzytrack was copying it. Try again.", cleans up its own files and writes no manifest. It never produces a mixed copy. Reuse the extended fingerprint (S0051) if it fits.
- **Owner, 2026-11-07, files outside the source folder:** **"Copy them in (Recommended)"**. Copy every file the ledger loads into the new workspace folder. Rewrite only the include lines and the documents option that point outside, so they point to the copies. ADR-0017 already says copied workspaces write `option "documents" "documents"`, so a v0.3 ledger's `../documents/<stem>-<hash>` comes in as `documents/`. The "loads the same" check then confirms that the copy has the same entries as the source. Decide and justify the exact comparison against the spec: entries, errors, options, and what to ignore (for example, the documents path itself and file names in metadata). Because the source ledger may have Beancount errors (accounting advises, ADR-0067), "the same" means the same as the source, not error-free.
- The cut above (BL-0201 the replay and markers, BL-0202 plugin modules) (agent; the orchestrator's brief allows the cut).
- The fingerprint "before reading" is the overlay load's own (`Loaded.fingerprint`): it hashes exactly the bytes the load parsed, so the copy's bytes, the load's result and the re-check all refer to one state. A document's source is hashed while it is copied and hashed again just before the gate (a second read: the extended fingerprint holds only the documents roots' listings, not their bytes) (agent).
- The legacy locks to try are named by the request (the sidecar's legacy detection is M3's); the engine tries each, holds the free ones through the file reads and re-checks the absent ones just before the gate (agent; ADR-0062 decision 2).
- The copy's refusals for a held legacy lock and a blocking journal are the job's values (`legacy_saving`, `recovery_blocked`) with their texts; the API codes `LEGACY_APP_SAVING` and `RECOVERY_BLOCKED` for them are the HTTP layer's, which M3 builds with the screens (as the create's values are not codes either) (agent).
- A `document` directive's file outside B is not copied (decision 3 rewrites only `include` and `option "documents"`). An absolute one keeps naming the original file, so the copy loads the same and reads it there (a stated Limit; the portability check reports it, CAP-WS-PORTABILITY-CHECK); a relative one then names a missing file in the copy, which does not load the same and is refused (agent).
- Copied document files keep their names, encrypted ones included (`.gpg`, `.asc`): they are copied byte for byte, never read as a ledger or decrypted, so ADR-0059 (which is about ledger files) does not refuse them. A ledger file that is encrypted refuses the copy, as the load does (agent).
- The source is loaded by the path the user named (normalized as Beancount normalizes it), not its canonical path, so the copy's file names and the manifest's root are as the user knows them (agent).
- `include` and `pythonpath` compare as sorted sets after mapping back: Beancount builds both sorted by path (`sorted(seen)`, `sorted(pythonpath)`), so their order follows where the files are, not what the ledger says. Found by the first APFS run (agent).
- Journals are matched against the source's ledger files only (parsed and looked-for), not its documents: a save writes only ledger files (agent).
- A new folder inside one of the source's documents roots is refused up front (`cannot_place`, `inside_documents`): its own files would change the source's listing, so the re-check would refuse every try with a misleading "your ledger changed". A recursive `include` glob that would match the copy is left to the re-check and stated as a Limit (copy inside its source) (agent).
- A legacy lock path named twice is tried once (exact text): a second `flock` of our own would see the first as held. Deduplication by `path_key` stays the caller's (BL-0026's row) (agent).
- Each ledger file is read twice (once whole to look for lines to rewrite and to check it against the fingerprint, then streamed into the target, checked again), so no whole file is held while it is written; a file with a rewritten line is written from the bytes read whole. Documents are read twice too (copy, re-check). The cost is stated as Limit (copy time) (agent).
- The collector stays paused for the whole job, as the create's (ADR-0008 amendment), with one explicit `gc.collect()` after the source's load is dropped, so its cycles are freed before the copy's load (agent).
- The create's writer is generalized, not copied: `create.Run` (was `_Run`) takes `Steps` (a job's step 2 and step 5), `NewFile.data` may be `Streamed`, the written bytes are recorded as SHA-256 and length (`_Made.data`), the read-back and the cleanup check compare that by `DirHandle.sha256` (bounded), and `DirHandle.create` takes chunks. The fs port grows `CHUNK` and `sha256`; the macOS adapter and the fake implement both. On the sidecar, `create.FolderJob` is the create's work, shared by the copy (agent).
- Tests first: the new and changed tests were run against ef0161ae's source (an archive of the base in the session scratchpad with the slice's test files copied in): `tests/ledger/test_copy.py`, `test_copy_layout.py`, `test_loads_same.py` and backend `test_copy_job.py` fail at import; `tests/test_copy_ops.py` (12 items), `test_schema.py`'s op list, `test_write_port.py` (the new write-path files) and backend `test_tla_mapping.py` (BL-0201 not an open row there) fail. The `test_darwin.py` additions call `DirHandle.sha256` and a chunked `create`, which the base lacks. (agent)
