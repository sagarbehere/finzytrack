# S0098: numbers Beancount rounds, and a load that never raises (BL-0123)

## Brief
- Goal (since the owner's answer of 2026-11-10, option 3 "Follow Beancount"): the load keeps Beancount's own 28-digit numbers, the ones bean-check and Fava show, and adds one warning per line where Beancount rounded a number: a number written with more than 28 significant digits, and an amount Beancount filled in whose exact value differs. Judged by behaviour (Beancount's lexer, Beancount's own fill at 64 digits). A number Beancount divides (`@@`, `{{ }}`, a filled-in price, cost or quantity) never warns. Beancount's own load raising on a ledger (the interpolation crash, a plugin's `Document(filename=42)`, a plugin failing at import) becomes a refusal naming the file and line, never `engine.internal` or a raise, through the open, the rebuild and the copy's load (S0049's contract). The strict xfail turns into a test of the rounded value with its warning.
- Implements: the owner's answer (`design/inbox/answered/20261110-numbers-beyond-28-digits-divisions.md`, option 3; supersedes `answered/20261028-numbers-beyond-28-digits.md`, option 1, which gets a pointer); ADR-0010 (the overlay load is Beancount's own); spec `engine-jobs.md` §6.7, §7, §8.2, §11; mirror README "Exact numbers". ADR-0015's "content hashes" amendment of 2026-10-29: found applied (its "Amendment (2026-10-29)"); no ADR states a 64-digit load, so no ADR changes.
- Capabilities: CAP-DATA-MIRROR (partial, M2): `ledger_errors` gains the warnings.
- Invariants touched: INV-02 (Beancount's semantics kept: the check reproduces Beancount's fill only to compare, and a test holds it equal to Beancount's), INV-22 (a Beancount failure is a named refusal), INV-21 (no id or content hash changes: the load is unchanged), INV-06 (no float; the written scale is Beancount's), INV-23 (no path in a log line).
- Risk class / lane: High / specialist (finance semantics; owner's decision). Verifier and a finance red team (orchestrator).
- The bytes it protects: none written; it keeps the shown numbers truthful (Beancount's own, with the rounding named) and the open's outcome truthful (a named refusal, not "internal error").
- Acceptance tests: `engine/tests/ledger/test_precision.py` (new), `engine/tests/ledger/test_load_failure.py` (new), `engine/tests/mirror/test_build.py::test_a_written_negative_number_is_rounded_as_beancount_rounds_it_with_a_warning` (was the strict xfail), new cases in `tests/ledger/test_open.py`, `test_rebuild.py`, `test_copy.py`, `tests/test_open_ops.py`, `test_rebuild_ops.py`, `test_copy_ops.py`; sidecar: `tests/platform/test_open_job.py`, `test_rebuild_job.py`, `test_copy_job.py`.

### Where the load runs (inventory by behaviour, 8a7dbe11)
Every call into Beancount's load is in `ledger_engine.ledger.beancount_port` (INV-02; `tests/architecture/test_load_rule.py`). The callers are: `overlay.load` (the open `ledger/opening.py`, the copy `ledger/copy.py`, the copy's fresh-process check `ledger/copy_check.py`), and `port.real_load` (the rebuild `ledger/rebuild.py`, the create's check `ledger/create.py`). The engine's own decimal context is set only in `mirror/core/rows.py` (`EXACT`: 64 digits, `Inexact` trapped). Every other stage runs in Python's default context, 28 digits. Beancount divides in `parser/grammar.py:896` (`@@`), `parser/booking.py:218` and `parser/booking_full.py:720, 750` (`{{ }}`), `booking_full.py:911, 917, 945, 984` (a filled-in quantity, cost or price), and `core/prices.py` (inverse rates).

### Evidence that parked the slice (spikes, scratchpad only; synthetic ledgers)
- The corpus mirror checksums with the overlay load wrapped in `decimal.localcontext(prec=64)`: two tables change, `write/total-price` `postings` and `oracle/nasty` `postings`, `prices`; only the per-unit price of a `@@` line, `1.428571428571428571428571429` → 64 digits. At 28 digits the snapshot is unchanged (control).
- `7 VTI {{100 USD}}` (no sale): at 28 digits `lots` builds; at 64 digits the build is `BuildFailed("inexact", "account_balances.balance")`, so the workspace would not open.
- `Assets:Broker  VTI @ 3 USD` / `Assets:Bank  -10 USD`: the TransactionId changes, `07eb28e8…` at 28 digits, `10178aba…` at 64.
- The crash in the row: `12345678901.123456789012345678 ETH` with the other leg left blank raises `decimal.InvalidOperation` in `interpolate.quantize_with_tolerance`, in both loads and in `bean-check`.
- A plugin that appends `Document(..., filename=42)`: both loads raise `TypeError` in `validation.validate_documents_paths`. No engine process died of it: the open and the rebuild answered `engine.internal`, the copy `Stop("source_failed")`.

## Decisions
- Park before coding, then build option 3 after the owner's answer: "Follow Beancount (Recommended)" (owner, 2026-11-10, in session, to the orchestrator's question; recorded with the option's wording in the answered inbox file).
- **The load's precision stays Beancount's** (owner, above): no decimal context is set around any load stage, the overlay, the rebuild's real load, the copy's fresh-process load, the mirror build's copy of the numbers, or the fingerprint and content hashes; nothing runs at another precision than bean-check. The only wider context is the check's own (64 digits, `precision._SUM`, `_QUANTIZE`), local to one call (`decimal.localcontext` is per thread and per task: nothing leaks), and the mirror's existing `EXACT`. `test_the_load_runs_in_beancounts_28_digit_context` and `test_the_load_leaves_the_context_as_it_found_it` hold it (agent).
- **The sidecar's 28-digit context is consistent with option 3** (agent, checked): the sidecar computes with no ledger number today (`grep Decimal backend/src/app`: JSON decoding with `parse_float=Decimal`, which is exact in any context, the log redaction and the self-check); it reads the mirror's numbers as text. Whoever adds arithmetic on mirror numbers later (recipes, M7) must not run it at 28 digits: the mirror's own sums are exact at 64 and can be longer than 28 (L3-05 holds the quantize rule).
- **Which lines warn, by behaviour** (agent): (1) written: every NUMBER token of Beancount's own lexer (`beancount_port.written_numbers`, the parser's lexer) with more than 28 significant digits as Python counts them (trailing zeros count: their negation loses the scale; leading zeros do not), one warning per line, only in files whose bytes hold a run of more than 28 digits, separators or points (a superset, so most files are never lexed twice); a positive long number warns too, since every sum with it rounds. (2) filled in: a leg Beancount filled in (`__automatic__`, no cost or price on it) whose number has exactly 28 digits (the only shape a rounded result keeps; a coarser quantize gives the exact sum's own value) and whose exact value, Beancount's own fill (`beancount_port.filled_amount`: `compute_residual`, negation, `quantize_with_tolerance`) of Beancount's own booked numbers computed at 64 digits, differs; when even 64 digits round, it warns without the exact amount.
- **Divisions never warn** (agent, as the brief allowed, with the reason): a quotient (`@@`, `{{ }}`, a filled-in price, cost or quantity) has no exact decimal form; Beancount, bean-check and Fava cut it at the same 28 digits, so Finzytrack and the other tools agree and there is nothing to explain. A filled-in leg is not judged when a number of the other postings has exactly 28 digits (the shape of such a cut quotient): `7 TOK @@ 10 USD` with a blank leg fills `-10.00000000000000000000000000`, while the exact product of Beancount's cut price is `-10.000000000000000000000000003`. Its cost: a filled-in leg summed from a written 28-digit number is not judged either (rare; documented in `precision`'s docstring as a limit, with `pad` amounts and balance assertion sums).
- **Where the warnings go** (agent): `Loaded.warnings`, kept apart from `Loaded.errors` so the overlay's errors stay equal to Beancount's loader (INV-03's parity comparison is untouched); the open, the rebuild and the mirror build publish both (`Loaded.reported`; the rebuild reads the parsed files again with `precision.of_disk` before it observes the set again, so a change in between is a moved disk). In the mirror they are `ledger_errors` rows of type `RoundingWarning`, after Beancount's errors; their text keys are the message starts `Number longer than 28 digits` and `Filled-in amount rounded to 28 digits`. The answers' `errors` count both (every row of `ledger_errors`). The future write contract reads its baseline from that table, so a save that adds a long number gets advice, never a block (owner's rule: integrity blocks, accounting advises).
- **A Beancount failure is a refusal** (agent; the design recorded at the park): the overlay's parse, booking, plugin import and validation, and the rebuild's real load, catch an `Exception` from Beancount (not `OSError`, not `EncryptedFileMet`, which keep their paths) and refuse: `number-failed` for `decimal.DecimalException`, `beancount-failed` otherwise (`ledger_engine.ledger.load_failure`). The file and line are those of the innermost traceback frame holding a local `entry` whose metadata names an absolute file and a line from 1 (booking's `_book` has one); else the root, with no line (validation's checks are single expressions with no frame local; a plugin's entry may name no file). The protocol carries `refusal` and `line` on `OpenResult`, and `refused`/`refusal`/`line` on `RebuildResult` with its new outcome `refused`; decision tables `engine.open` v2 and `engine.rebuild` v3 record `refusal` among the inputs; the copy stops with `number_failed` or `beancount_failed`, `path` the file, `detail` the line. The sidecar's open value is `NotLoadable(why, path, line)` (its screen is BL-0154), the rebuild logs `rebuild.not_loaded {why}`; neither tries again (the same ledger fails the same way), and no path reaches a log line (INV-23).
- **The create's load check is unchanged** (agent): it loads only Finzytrack's own new ledger text and already stops with `load_failed` on any exception.
- **Found on the way:** a written expression with a division by zero (`(10/0) USD`) ends the process in Beancount 3.2.0's C parser, bean-check included (exit 139); no `try` can catch it. BL-0236 (M2).
- **The `@@` exclusion was tested before it was written** (agent): the prototype of the filled-in rule flagged `7 TOK @@ 10 USD`, `7 VTI {{100 USD}}` and a real 23 × 9-digit product alike; the 28-digit rule separates them (`test_filled_in_amounts_beancount_did_not_round_never_warn`).

### Changed in round 1 (they replace the bullets above where they differ)
- **Every load starts in Beancount's context** (agent; finance F1): the overlay load and `real_load` run in `beancount_port.beancount_context()`, a fresh copy of `BEANCOUNT_CONTEXT` (Python's default, spelled out because `decimal.DefaultContext` is itself mutable), the caller's context restored after. The fresh-process copy check and fresh load go through the overlay load, so they are covered. Reachability checked first: across jobs it cannot happen today, because an engine that ran user code is retired (`queue._job_done`, `WorkResult.ran_user_code`, both the open and the rebuild set it); within one job, code after a plugin's load (the build, the checks) ran in the plugin's context. Within a plugin ledger's own load the plugin's change stands, as in bean-check.
- **A cut number is told apart by where it came from, not by its digits** (agent; verifier F1, finance F3): a filled-in leg is skipped only when a weight it sums holds a number with all 28 digits that is not written on its posting's own line (Beancount's lexer, per line, lexed only for such candidates). A written 28-digit amount (an 18-decimal token) is judged. The `@@`, `{{ }}` and `{{ }}`-then-`{}` cases still never warn.
- **The filled-in check compares after the same quantize, for every candidate** (agent; verifier F2, finance F5): the "exactly 28 digits" filter is gone; a candidate is any transaction whose weights may need more than 28 digits (`precision._may_round`, a bound from each number's highest and lowest digit and the count of terms, never too small; the carry `9999…9 + 2` sits on its edge). The exact fill is quantized as Beancount quantizes it, so the double rounding case warns. The false docstring claim and the never-warn case that encoded it are gone. Cost on the 54k demo ledger: 42 to 46 ms per load (about 3% of a 1.4 s load), no warning on it.
- **The written warning says what Beancount uses** (agent; finance F6): `-X as written, used as Y` for a signed number; `kept as written, but every sum with it is cut to 28 digits` for a positive one; `in an expression Beancount computes with 28 digits` inside an expression. A number whose value has at most 28 significant digits (trailing zeros not counted: `1.0000000000000000000000000000`, `12345678901234567890123456780`) never warns: Beancount never changes its value, only its scale.
- **Warnings are not errors** (agent; finance F6): the `errors` the open and the rebuild answer are Beancount's own, as bean-check counts them; the warnings are rows of `ledger_errors` (type `RoundingWarning`) only. Reason: bean-check reports none of them, and a count that differs from bean-check's would itself need explaining.
- **The rebuild's second read cannot raise** (agent; verifier F3, data-safety F1): an `OSError` while the warnings read the parsed files again is a moved disk (`moved`, with the set observed again), so no traceback, and no path in it, reaches the engine's log. Reading the bytes the load parsed is not possible for `real_load` (Beancount reads its own files), so the read stays and is caught.
- **A refusal gets a second look** (agent; data-safety F2): the open observes `LoadRefused.read` (what the load had read when Beancount failed) again, the rebuild its set again; a changed disk is `moved`, tried again.
- **The failure's words are true** (agent; verifier F4, finance F4, data-safety F3): `number-failed` only when a decimal error is raised while Beancount works on a transaction it names; the text names "the transaction on line N" and lists the real causes (a number of more than 28 digits, a quantity of 0 with a total price or cost), no longer "shorten the number". A plugin's own decimal error at import is `beancount-failed`. Docstrings of `load_failure`, `messages.LoadRefusal`, the sidecar's `engine.LoadRefusal` and `engine_jobs/opening`, `engine-jobs.md` §6.7, §7, §8.2 and the mirror README follow.
- **Not every exception is Beancount's** (agent; finance F8, data-safety F3): `load_failure.beancounts` keeps a `MemoryError`, and an exception whose innermost frame is the engine's own code (a port wrapper's fault), as the engine's (`engine.internal`); only Beancount's and plugins' faults become a refusal the rebuild never retries.
- **Not mine, left as it is** (orchestrator, to the owner): finance F2, the mirror's own 64-digit sums of two 28-digit token amounts differing from Beancount's 28-digit sums without a warning.
- **Process slip, undone before commit:** `ruff check --fix --select RUF100` treated every `noqa` for an unselected rule as unused and stripped them across the engine; every file this slice did not touch was checked out again, and the stripped directives in my own files were put back from HEAD (checked by comparing each file's `noqa` comments with HEAD's).

- **Finance red team F2, the mirror's own exact sums vs Fava's 28-digit sums** (orchestrator to the owner, not the implementer): owner, 2026-11-10, in session, to the orchestrator's question on the S0098 finance red team's F2: "Keep exact, no warning". The mirror rule is unchanged; the mirror README's "Exact numbers" states the difference with its example. No code change, no backlog row.

### Changed in round 2 (a second fix round on one mechanism: the owner's options note, PROCESS.md §3 step 7)
- **The owner's choice** (owner, 2026-11-10, in session, to the orchestrator's options note): "F1, F2, M1, M2 (Recommended)". The option as put: "Fix the two false outcomes plus the common slowdown and the slice's own token case; the other 8 no-byte findings become backlog rows; then one verifier round on the fix range." The eight are BL-0238 and BL-0239.
- **The rebuild's warnings read only what Beancount parsed** (agent; verifier F1): `beancount_port.real_load(root, parsed)` records each file the loader parses (its `parser.parse_file`, swapped for the call as `_never_decrypt` swaps the decrypt), and `precision.of_disk` lexes those, skipping a path that is no regular file. A missing file or a folder a plugin adds to `options["include"]` no longer makes the rebuild answer `moved` forever, and a data file a plugin names (a CSV) is not lexed as ledger text, so the rebuild sees the same files as the open's warnings.
- **The second look covers what the failed load parsed** (agent; verifier F2): a file parsed outside the set is `moved` with the widened set; the copy observes `LoadRefused.read` again too (a few lines), so a source fixed during its load is `source_changed`, not `number_failed`.
- **Only the lines needed are lexed** (agent; finance M1): `precision.Lexed` lexes a single line, once, when asked (a candidate posting's line, a long digit run's line), never a whole file, and counts them (`lexed`). The 54k demo with one `@@` purchase and a blank leg: 1.034 times the plain load (was 1.32); with a 29-digit run in a comment: 1.032. Limit, in `Lexed`'s docstring: a long digit run on a line inside a string that spans lines may warn (advice only).
- **A negative written number Beancount cut counts as written** (agent; finance M2): `Lexed.as_written` accepts Beancount's 28-digit negation of a number written on the line, and the exact fill uses the number as written for both the weight and the tolerance Beancount infers (the cut also coarsens that tolerance). Both the owner's token cases warn on the filled line: the token sold at a price, and the 18-decimal ETH amount with the other leg blank. So does the token with a fee: from the numbers as written the fill is `...677`, while Beancount gives `...568`. My first round-2 test expected no warning there; that expectation was wrong, and the test now expects the warning, with both amounts.
