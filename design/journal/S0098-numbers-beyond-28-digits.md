# S0098: numbers Beancount rounds, and a load that never raises (BL-0123)

## Brief
- Goal (since the owner's answer of 2026-11-10, option 3 "Follow Beancount"): the load keeps Beancount's own 28-digit numbers, the ones bean-check and Fava show, and adds one warning per line where Beancount rounded a number: a number written with more than 28 significant digits, and an amount Beancount filled in whose exact value differs. Judged by behaviour (Beancount's lexer, Beancount's own fill at 64 digits). A number Beancount divides (`@@`, `{{ }}`, a filled-in price, cost or quantity) never warns. Beancount's own load raising on a ledger (the interpolation crash, a plugin's `Document(filename=42)`, a plugin failing at import) becomes a refusal naming the file and line, never `engine.internal` or a raise, through the open, the rebuild and the copy's load (S0049's contract). The strict xfail turns into a test of the rounded value with its warning.
- Implements: the owner's answer (`design/inbox/answered/20261110-numbers-beyond-28-digits-divisions.md`, option 3; supersedes `answered/20261028-numbers-beyond-28-digits.md`, option 1, which gets a pointer); ADR-0010 (the overlay load is Beancount's own); spec `engine-jobs.md` §6.7, §7, §8.2, §11; mirror README "Exact numbers". ### Where the load runs (inventory by behaviour, 8a7dbe11)
Every call into Beancount's load is in `ledger_engine.ledger.beancount_port` (INV-02; `tests/architecture/test_load_rule.py`). The callers are: `overlay.load` (the open `ledger/opening.py`, the copy `ledger/copy.py`, the copy's fresh-process check `ledger/copy_check.py`), and `port.real_load` (the rebuild `ledger/rebuild.py`, the create's check `ledger/create.py`). The engine's own decimal context is set only in `mirror/core/rows.py` (`EXACT`: 64 digits, `Inexact` trapped). Every other stage runs in Python's default context, 28 digits. Beancount divides in `parser/grammar.py:896` (`@@`), `parser/booking.py:218` and `parser/booking_full.py:720, 750` (`{{ }}`), `booking_full.py:911, 917, 945, 984` (a filled-in quantity, cost or price), and `core/prices.py` (inverse rates).

### Evidence that parked the slice (spikes, scratchpad only; synthetic ledgers)
- The corpus mirror checksums with the overlay load wrapped in `decimal.localcontext(prec=64)`: two tables change, `write/total-price` `postings` and `oracle/nasty` `postings`, `prices`; only the per-unit price of a `@@` line, `1.428571428571428571428571429` → 64 digits. At 28 digits the snapshot is unchanged (control).
- `7 VTI {{100 USD}}` (no sale): at 28 digits `lots` builds; at 64 digits the build is `BuildFailed("inexact", "account_balances.balance")`, so the workspace would not open.
- `Assets:Broker  VTI @ 3 USD` / `Assets:Bank  -10 USD`: the TransactionId changes, `07eb28e8…` at 28 digits, `10178aba…` at 64.
- The crash in the row: `12345678901.123456789012345678 ETH` with the other leg left blank raises `decimal.InvalidOperation` in `interpolate.quantize_with_tolerance`, in both loads and in `bean-check`.
- A plugin that appends `Document(..., filename=42)`: both loads raise `TypeError` in `validation.validate_documents_paths`. No engine process died of it: the open and the rebuild answered `engine.internal`, the copy `Stop("source_failed")`.

## Decisions
- Park before coding, then build option 3 after the owner's answer: "Follow Beancount (Recommended)" (owner, 2026-11-10, in session, to the orchestrator's question; recorded with the option's wording in the answered inbox file).
- **The load's precision stays Beancount's** (owner, above): no decimal context is set around any load stage, the overlay, the rebuild's real load, the copy's fresh-process load, the mirror build's copy of the numbers, or the fingerprint and content hashes; nothing runs at another precision than bean-check. The only wider context is the check's own (64 digits, `precision._SUM`, `_QUANTIZE`), local to one call (`decimal.localcontext` is per thread and per task: nothing leaks), and the mirror's existing `EXACT`. `test_the_load_runs_in_beancounts_28_digit_context` and `test_the_load_leaves_the_context_as_it_found_it` hold it (agent).
- **The sidecar's 28-digit context is consistent with option 3** (agent, checked): the sidecar computes with no ledger number today (`grep Decimal backend/src/app`: JSON decoding with `parse_float=Decimal`, which is exact in any context, the log redaction and the self-check); it reads the mirror's numbers as text. Whoever adds arithmetic on mirror numbers later (recipes, M7) must not run it at 28 digits: the mirror's own sums are exact at 64 and can be longer than 28 (L3-05 holds the quantize rule).
- **Which lines warn, by behaviour** (agent): (1) written: every NUMBER token of Beancount's own lexer (`beancount_port.written_numbers`, the parser's lexer) with more than 28 significant digits as Python counts them (trailing zeros count: their negation loses the scale; leading zeros do not), one warning per line, only in files whose bytes hold a run of more than 28 digits, separators or points (a superset, so most files are never lexed twice); a positive long number warns too, since every sum with it rounds. (2) filled in: a leg Beancount filled in (`__automatic__`, no cost or price on it) whose number has exactly 28 digits (the only shape a rounded result keeps; a coarser quantize gives the exact sum's own value) and whose exact value, Beancount's own fill (`beancount_port.filled_amount`: `compute_residual`, negation, `quantize_with_tolerance`) of Beancount's own booked numbers computed at 64 digits, differs; when even 64 digits round, it warns without the exact amount.
- **Divisions never warn** (agent, as the brief allowed, with the reason): a quotient (`@@`, `{{ }}`, a filled-in price, cost or quantity) has no exact decimal form; Beancount, bean-check and Fava cut it at the same 28 digits, so Finzytrack and the other tools agree and there is nothing to explain. A filled-in leg is not judged when a number of the other postings has exactly 28 digits (the shape of such a cut quotient): `7 TOK @@ 10 USD` with a blank leg fills `-10.00000000000000000000000000`, while the exact product of Beancount's cut price is `-10.000000000000000000000000003`. Its cost: a filled-in leg summed from a written 28-digit number is not judged either (rare; documented in `precision`'s docstring as a limit, with `pad` amounts and balance assertion sums).
- **Where the warnings go** (agent): `Loaded.warnings`, kept apart from `Loaded.errors` so the overlay's errors stay equal to Beancount's loader (INV-03's parity comparison is untouched); the open, the rebuild and the mirror build publish both (`Loaded.reported`; the rebuild reads the parsed files again with `precision.of_disk` before it observes the set again, so a change in between is a moved disk). In the mirror they are `ledger_errors` rows of type `RoundingWarning`, after Beancount's errors; their text keys are the message starts `Number longer than 28 digits` and `Filled-in amount rounded to 28 digits`. The answers' `errors` count both (every row of `ledger_errors`). The future write contract reads its baseline from that table, so a save that adds a long number gets advice, never a block (owner's rule: integrity blocks, accounting advises).
- **A Beancount failure is a refusal** (agent; the design recorded at the park): the overlay's parse, booking, plugin import and validation, and the rebuild's real load, catch an `Exception` from Beancount (not `OSError`, not `EncryptedFileMet`, which keep their paths) and refuse: `number-failed` for `decimal.DecimalException`, `beancount-failed` otherwise (`ledger_engine.ledger.load_failure`). The file and line are those of the innermost traceback frame holding a local `entry` whose metadata names an absolute file and a line from 1 (booking's `_book` has one); else the root, with no line (validation's checks are single expressions with no frame local; a plugin's entry may name no file). The protocol carries `refusal` and `line` on `OpenResult`, and `refused`/`refusal`/`line` on `RebuildResult` with its new outcome `refused`; decision tables `engine.open` v2 and `engine.rebuild` v3 record `refusal` among the inputs; the copy stops with `number_failed` or `beancount_failed`, `path` the file, `detail` the line. The sidecar's open value is `NotLoadable(why, path, line)` (its screen is BL-0154), the rebuild logs `rebuild.not_loaded {why}`; neither tries again (the same ledger fails the same way), and no path reaches a log line (INV-23).
- **The create's load check is unchanged** (agent): it loads only Finzytrack's own new ledger text and already stops with `load_failed` on any exception.
- **Found on the way:** a written expression with a division by zero (`(10/0) USD`) ends the process in Beancount 3.2.0's C parser, bean-check included (exit 139); no `try` can catch it. BL-0236 (M2).
- **The `@@` exclusion was tested before it was written** (agent): the prototype of the filled-in rule flagged `7 TOK @@ 10 USD`, `7 VTI {{100 USD}}` and a real 23 × 9-digit product alike; the 28-digit rule separates them (`test_filled_in_amounts_beancount_did_not_round_never_warn`).
