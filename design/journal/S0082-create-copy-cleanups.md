# S0082: Create and copy cleanups (BL-0203, BL-0199, BL-0200)

## Brief
- Goal: close three small rows S0080 and S0081 left (owner, 2026-11-07: "Do the small cleanup now."):
  1. **BL-0203**, the copy-check child always ends and its channel is tested. A plugin that leaves a non-daemon thread (or raises `SystemExit`) keeps `ledger_engine.ledger.copy_check` alive after it has answered, so the copy job waits until Cancel (against ADR-0063 decision 1, "every wait has an exit"). The child ends itself with `os._exit` once its answer is written and its streams flushed, whatever the plugin left (threads, `atexit` handlers); a plugin's `SystemExit` or other `BaseException` in the load becomes a `failed` answer, not a silent exit. The parent (`fresh_load.check`) reads the one answer line, then waits for the child's exit, so a process the plugin forked that still holds the pipe does not hold the job once the child has answered. Checked: nothing else in the child needs a clean exit (it holds no lock, writes no file, Beancount's pickle cache is off in the overlay load, the engine registers no `atexit` handler; its only buffered output is the answer, closed before the exit, and `sys.stdout`/`sys.stderr`, flushed before it).
  2. **BL-0199**, the after-death wording for the folder itself. After an engine death the outcome read names `.` whenever the target holds nothing at the job's names, even when the job never made it (the user's existing empty folder, or one now holding only another program's file); `msg:create.left_folder` then says "Finzytrack left the folder …". The death read (reason `stopped`, the sidecar's own reason: the engine never answers it) gets its own sentence that does not claim the folder: `msg:create.maybe_made_folder` (and `msg:copy.maybe_made_folder`, the same words through `create_text.folder_text`). The row's situation text for `msg:create.left_folder` is aligned (a live stop that kept only the folder the job made: another program's entry is in it, or its identity could not be read).
  3. **BL-0200**, a created file's identity is only its own descriptor's. `DirHandle.create` returns `tuple[int, int]` (no longer optional: both adapters already read `fstat`; the test wrappers return the inner call's identity). `create.Run._make` reads a later `stat` only for a folder it made; a file whose identity is missing (an adapter breaking the contract) is never matched by a later `stat`, so the cleanup keeps and names it. With it, a test of the stated Limit (cleanup race)'s `mkdir`-then-`stat` instant on the fake.
- **The bytes it protects:** BL-0200: another program's file saved at a name the job just created (never removed on the strength of a `stat` taken after the create). BL-0203: the truth of a copy's "loads the same" verdict (a plugin's output can never forge or spoil the answer) and the copy job's exit (the wait ends when the child has answered). BL-0199: none; it keeps the "not created" text truthful (never claims a folder Finzytrack may not have made).

## Decisions
- **BL-0203: the child ends itself, and the parent reads one line** (agent). `os._exit` in `copy_check.main` (as the row proposed) closes the thread case and also a plugin's `atexit` handler; the parent's switch from `subprocess.run` (which waits for the pipe's end) to one `readline` then `wait` closes the same class for a process a plugin forked (it inherits the answer's descriptor at the fork and keeps the pipe open after the child has ended; S0012 met the same pipe trap on Windows). Both are needed: either alone leaves one case hanging (mutants E2, E4). The answer gained a final newline so the parent knows where it ends.
- **A plugin's `SystemExit` is an answer, not a silent exit** (agent): the load is guarded with `BaseException`, so the copy says `load_failed` naming `SystemExit`; any fault of the channel itself is printed to standard error and the child exits 1 (`failed`, `exit 1`).
- **What is not closed, stated:** a child that never answers (a plugin blocked forever) still ends only by Cancel or Quit anyway, which end the engine's group (the spec's step 5 text); a slow load cannot be told from a stuck one without a time limit, and the owner's rule is no fixed time budgets. That is ADR-0063's exit for this wait. A forked process that left the group (`setsid`) and holds the pipe while the child never answers is the same case.
- **BL-0199: the death read is told by the reason** (agent). The sidecar's reason `stopped` is given only to a value read from disk (or with no engine to read it); the engine never answers it (`ledger_engine.ledger.create.Reason` has no `stopped`). So `create_text.folder_text(..., after_death=v.reason == "stopped")` picks `maybe_made` for `left == (".",)`; a live stop keeps "Finzytrack left the folder …". If a future engine answered `stopped`, the weaker sentence would still be true. No new field on `NotCreated` / `NotCopied` (EP-30: the reason already carries it).
- **The wording** (agent): "Finzytrack may have made the folder <folder>. Check it, and remove it if you do not need it." The row's example ("may hold files of an unfinished new workspace") would be false here: the read found nothing at the job's names. The advice matches `msg:create.left_folder`'s (check, then remove if not needed); the user decides after checking, which covers another program's file in the folder.
- **BL-0200: both options** (agent): the type is non-optional (every adapter and test wrapper already had the identity; the three `test_darwin.py` wrappers and `test_create_ops.py`'s now return it), and `_make` reads a later `stat` only for a folder, so a file with no identity at run time (an adapter breaking the contract) gets `_Made.identity = None`, which no entry matches: the cleanup keeps and names it. The type alone would leave a runtime `None` to the old fallback; the runtime rule alone would leave the contract loose.
- **Tests that pass on the base, tagged @regression-guard:** the plain-ledger happy path, the parent's parsing cases, the broken-pipe case (`subprocess.run` hid it), the APFS `.` round trip, `manifest_taken` with `left=None`, the Limit (cleanup race). The thread, fork and `SystemExit` tests hang or fail on the base (run on the base under an outer `alarm`, outside the tests: all three hung); the BL-0199 and BL-0200 tests fail on the base.
