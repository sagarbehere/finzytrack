# S0116: the contract's prepare: an edit plan checked into a write plan, without writing (M1b, ADR-0008 steps 1-3)

## Brief
- Goal: M1b's second slice (owner, 2026-11-14: "Yes", to starting it after the proposed order). Build `ledger.contract.prepare` in the engine (ARCHITECTURE.md §9.2 step 3): from an `EditPlan` (S0115's `source_edit`) and its `IntendedChange`, run the write-safety contract's checks that come before any write, each failing closed (INV-22), and return `Prepared` (the candidate texts per file, their hashes, the plan's fingerprint, the new error keys for the preview) or `Refused` (a reason naming the step). Serve it as the engine's `preview` op (the job kind `preview` already exists in the sidecar's queue, engine-jobs §2). Drive it with the **test-only edit producer**: a producer in the engine's tests, `(snapshot, request) -> EditPlan + IntendedChange`, for insert, replace, delete and token edits, which the contract tests (and later the Hypothesis model) use since no real mutator exists yet. Nothing is written to disk by any of it.
- The steps (ADR-0008, as amended by ADR-0067 and ADR-0068):
  1. Parse the old and new texts of the edited files with Beancount's parser only.
  2. **Semantic diff = the intended change**: a canonical key per entry (the printer's output without location metadata); every untargeted entry identical; the targeted set exactly the intended inserts, replacements and removals; options, plugins and includes unchanged. Otherwise `Refused` (an integrity refusal: it blocks).
  2b. **Outside-span identity**: the candidate equals the old text with exactly the planned spans replaced (a byte comparison of the complement; S0115's `Applied` records the splices). Otherwise `Refused`.
  3. **The overlay load** of the candidate (`overlay.load`, ADR-0010, the workspace's `LoadPolicy`) and the **error keys** (error type + canonical entry key + message without locations, so a splice that shifts lines does not make old errors new), compared with the baseline (the `ledger_errors` of the published mirror generation the plan was made on). The new ones are the preview's list: **never a refusal** (ADR-0067: integrity blocks, accounting advises); the one exception is a parser error in the text Finzytrack wrote, which blocks (step 1). A load that cannot run (`LoadRefused`) refuses.
  - The plan carries the fingerprint the load read (`Loaded.fingerprint`), which the save's gate checks (engine-jobs §6.1 step 3; spec §6.1 step 5 "No load").
- Out of scope, each with its slice: the sidecar's preview use case, `PlanStore`, the API routes, the confirm and BL-0106's error codes in the registry (slice 3, the confirm, which is a new write path: its ownership rule goes to the owner before coding); BL-0255/BL-0256 (slice 4).
- Implements: ADR-0008 steps 1, 2, 2b, 3 (with ADR-0067's step-3 rule and ADR-0068 D1); ADR-0009 (the producer is an edit producer); ADR-0010 (the overlay load); ARCHITECTURE.md §9.2 step 3; `design/specs/engine-jobs.md` §2 (`preview`), §6.1 step 5; `design/specs/write-path/README.md` (`intent`, the targeted set). Closes at the contract level, or advances: I2, I3, I10 (bytes outside spans), L1-03 (one full load per write: the preview's), BL-0001 (contract-step tests).
- Capabilities: CAP-DATA-WRITE-GATE stays `planned` until a save goes through it (slice 3); its note may name prepare as built.
- Invariants touched: INV-01 (the contract), INV-22 (each step fails closed), INV-03 (the overlay load equals Beancount's), INV-10 (no resident ledger: the load's result is released after the reply).
- Risk class / lane: High / full. Review budget row: **Other product code** (prepare writes nothing): a verifier, and a fresh round after any product fix. The data-safety red team comes with slice 3.
- The bytes it protects: every byte of the candidate texts the plan will hand to the save (step 2 and 2b stop an unintended entry change and any damage outside the planned spans before a save can write them); and the truth of the preview's list of new errors.
- Mechanism questions (§3 step 2): which real setup needs this: every ledger write (ADR-0008); the rare setups are already forbidden (encrypted and non-UTF-8 files, S0115; a load the policy refuses). Fix-round history: the semantic diff and the error keys are new; the overlay load is used, not changed (its family had rounds in S0049, S0051, S0067, S0068, S0098).
- Acceptance tests (tests first; each fails on the base commit):
  - Per step, a fault injected (an exception, an undecidable result) gives `Refused` naming the step, and nothing touches the disk (INV-22's per-step fault test).
  - Step 2 must-not-pass: an edit plan whose result changes an untargeted entry; one whose targeted set differs from the intent (an extra, missing or different entry; a second matching entry); one that changes an option, plugin or include line; a plugin-generated or glob-included entry in the intent.
  - Step 2b must-not-pass: a candidate that differs outside the planned spans (a comment, whitespace, a line ending).
  - Step 3: a new accounting error (a failing balance assertion, a booking error, a plugin error) is listed with its key and never refuses; an error already in the baseline is not new after a splice shifts its line; a parser error in the written text refuses; `LoadRefused` refuses.
  - The D1 write corpus: for each case, the producer's edits through prepare give `Prepared`, with the expected new errors (none on a clean case).
  - The protocol: the `preview` op's messages in `messages.py` and the regenerated `contracts/engine-protocol.schema.json`; the sidecar's codec and its contract test follow (engine/CLAUDE.md).
- Expected doc impact: ARCHITECTURE.md §9.2 step 3 (what is built), §2.0's engine tree; `engine/CLAUDE.md`; `design/specs/engine-jobs.md` §2 if the `preview` op's shape needs a line; the protocol schema (generated); `design/backlog.md` (I2, I3, I10, L1-03, BL-0001 progress); CAP-DATA-WRITE-GATE's note.
- Open questions: none.
- Base: a2e095d6.

## Decisions
- **Orientation** (agent): the brief came written by the orchestrator after its `orient` run; I read the sources it names and did not run `orient` again. No question hit the escalation rubric (below: the one ADR wording point is an internal key, cheap to reverse, and changes nothing written or read from a ledger).
- **Tests first** (agent): `tests/ledger/producer.py` and `tests/ledger/test_contract.py` were written before the product modules; `test_entry_keys.py`, `tests/test_preview_ops.py`, the schema's op list and the sidecar's contract test followed with their modules. The failing run on base a2e095d6 (an export of the base's `engine/`, `corpora/`, `contracts/` and `backend/` in the session scratchpad, the new tests copied in, run against the base's sources): `test_contract.py`, `test_entry_keys.py`, `test_preview_ops.py` fail at collection (`ImportError: cannot import name 'contract'` / `'entry_keys'` / `'preview'`); `tests/test_schema.py::test_every_op_has_a_request_and_a_reply_definition` fails (no `preview` op); `backend/tests/platform/test_engine_protocol.py` fails at collection (`cannot import name 'decode_preview'`); the changed `test_source_edit.py::test_apply_refuses_a_stale_snapshot` fails on base (`apply_edits` took no `Snapshot`).
- **Homes** (agent, ARCHITECTURE §2.0; EP-23): `ledger/core/entry_keys.py` (both keys), `ledger/core/semantic_diff.py` (`IntendedChange`, `Produced`, steps 1, 2, 2b), `ledger/contract.py` (`prepare`), `ledger/preview.py` (the job), `protocol/preview.py` (the op); the printer is reached through a new port wrapper `beancount_port.format_entry` (in `WRAPPERS`). Only the port imports Beancount (`check_engine_boundary.py` clean).
- **The entry key** (agent): first built as the printer's text (ADR-0008's wording); **round 1 (F4)** showed the printer writes a payee `""` and no payee alike, so the key is now the parsed entry's own value (`repr`) without location (entry and posting `filename`, `lineno`), tags and links sorted: exact in every field and every number's decimals, and cheaper (prepare at 54k: 2.15 s, from 2.9 s). The port's `format_entry` wrapper went with it. Recorded in ADR-0008's implementation note of 2026-11-14. What Beancount's parser does not tell apart (a metadata value `Assets:Foo` or `"Assets:Foo"`, `USD` or `"USD"`: one `str`) no key can; step 2b holds those bytes, now also inside a span (F2). `@@ T` and `@ T/u` need no rule: Beancount's parser already stores a total price as the per-unit price, so they are one entry (checked; ADR-0009's "the same intent" holds by itself).
- **The error key is read from `ledger_errors` rows, its entry as the row's JSON without location** (agent; flag for the verifier). ADR-0008 says "error type + canonical entry key + message with locations stripped" and puts the baseline in the mirror's `ledger_errors`; a published row holds the entry only as JSON (`rows.json_value`), from which the printer's text cannot be had. So both sides are keyed by one function over rows (`entry_keys.error_key`): the baseline's rows read from the generation, the candidate's from `rows.error_rows(Loaded.reported)`. The entry JSON is decoded with `parse_float=Decimal` (INV-06; `check_money_dates`) and every `filename` and `lineno` key dropped at any depth. Locations in messages: Beancount 3.2.0's own messages hold no ledger line except a booking error's printed posting (`'lineno': 7`, checked), so `'lineno': N`, `'filename': '...'` and the error's own file followed by `:N` are dropped. Not escalated: the key lives only in a preview's answer (as its SHA-256), decides only which errors are listed, and is cheap to change. Recorded as ADR-0008's implementation note of 2026-11-14 (round 1, F6).
- **Locations are both file and line** (agent): dropping only the line would make every baseline error new whenever the generation's loader spelled a path otherwise than the overlay; the cost is that one error of one text in two files is counted as one key twice (still counted right as a multiset).
- **The baseline** (agent; the orientation asked): read by the engine from the published generation the plan was made on, never passed in. The request names that generation's number; the job refuses `stale` when there is none or it is incomplete (`unpublished`), it is another number (`other_generation`), or it is not this ledger's (`same_ledger`), not this engine build's or DDL's, or not fresh on disk (`not_fresh`). Why read here: the save's gate already reads the published generation in the engine (`read_published`), the rows can be thousands (no reason to send them over the protocol and back), and only the engine can check freshness against the disk it loads. Why the build must match and the date need not: another build may list other errors (its warnings on numbers), which would show as new; `ledger_errors` do not depend on `today`, so a generation of yesterday is still the baseline. `mirror.publish.read_baseline` reads `meta` and the rows through the one handle on `mirror/` (`SqliteStore.errors`, read-only, the same file checks as `meta`).
- **The snapshot is the generation's files** (agent): every file the generation's fingerprint read, read now and each hashed against the fingerprint (else `moved`), so the plan is made on exactly the generation the baseline describes. Order: the root first, then the fingerprint's (sorted) order. **Limit:** `route_insert` breaks a tie between two `insert-entry` options of one date on one line number in two files by this order; Fava breaks it by Beancount's include order. Only two option lines of one date at one line number in two files can tell them apart.
- **The shared parse and a producer** (agent, round 1 question 16): kept shared. A producer that changed a parsed entry's `meta` in place would change step 1's old parse; giving step 1 its own parse costs about 0.5 s at 54k (a tenth of ADR-0008's 5 s), and the producers are this repository's code, reviewed with the contract. Recorded here as the accepted risk.
- **One snapshot, one parse** (agent, performance): the producer, `apply_edits` and step 1 share the snapshot's parses (`apply_edits` now takes a `Snapshot` too; the snapshot keeps the parser's errors and options as well). Each is Beancount's parse of the same bytes, cached by the snapshot; the checks still recompute keys and compare. Measured on the demo generator's 54k ledger (one 8.7 MB file, the owner's Mac, 3 runs, scratch script not committed): before sharing, the producer 1.2 s and prepare 4.0-4.2 s (about 5.3 s, over ADR-0008's 5 s); after, the producer 1.2 s and prepare 2.9 s (about 4.1 s plus the job's reads and observations); with round 1's key, the producer 1.1 s and prepare 2.15 s. BL-0112 measures the whole preview on the product's path.
- **The intended change** (agent): `IntendedChange(inserts, replaces, removes)`: an insertion by its file and key, a replacement by its `Target`, the key the producer read there and the new key, a removal by its `Target` and key. The producer works it out from its request, apart from the edits (the test producer: the parsed entry at the target, the request's text parsed as the file it lands in, a token edit as the parsed entry with the account replaced). Keys of inserted text are computed as the file they land in, since a `document` entry's path depends on it.
- **Step 2's checks** (agent): per edited file, options equal except `dcontext` (the parser derives it from the numbers; checked: inserting a transaction changes only `dcontext`); each target an entry at that line with the intent's key; the plan's replaced and deleted entries exactly the intent's (and none named twice); the new entries equal, as a multiset, the untargeted old entries plus the intended new ones, and the untargeted ones appear in their old order. An intent that names a file the plan does not change is refused.
- **Step 1** (agent): a parser error is refused when the new text has it and the old one has not, by error key as a multiset, so an old parser error that moved is not new.
- **Step 2b** (agent): the planned spans and, since round 1 (F2), the text the plan puts in each are worked out from the plan's edits on the old text, never from `apply_edits`' record (`semantic_diff._planned`: a replace's text, the new account, nothing for a delete, the inserts in `source_edit.insert_key` order with rule 3's separators, all in the file's line ending); the candidate files must be exactly the edited files, the candidate the old text with each span replaced by its planned text, byte for byte, and the record (splices, hash) must agree (F3). Three further checks I first wrote (the insert count per file, a splice's `old` text, `Applied.before`) were removed after the mutants showed each covered by another check (EP-30).
- **Fail closed** (agent, INV-22): each step runs in `_step`, which turns any `Exception` into `Refused(step, "fault", ...)` (a `KeyboardInterrupt` is not caught); a load answering neither `Loaded` nor `LoadRefused` is `undecidable`; a producer's exception is `Refused("plan", "fault")`. Paths must be absolute and normalized (`path_not_normal`): the overlay and `as_before` name files so.
- **The new errors** (agent): the candidate's rows in order; the first copies of a key, up to the baseline's count, are old, the rest new (`entry_keys.new_errors`, the one home: step 1's parser errors and step 3's errors use it). `Prepared.errors` counts Beancount's errors only, as bean-check does (the precision warnings are rows, not errors; S0098).
- **The fingerprint** (agent, spec §6.1 step 4): `ledger_set.as_before(Loaded.fingerprint, pre)`; `tests/test_preview_ops.py` lands a preview's plan through the `save` op, so the save's gate takes it.
- **The `preview` op** (agent): `OpSpec.needs_engine_lock` (it reads ledger, mirror and journal files: engine/CLAUDE.md's rule), `writes_app_folder` false (it writes nothing, as the `open` op). The request is `mutator` (an intent-table id) and `request` (a JSON object the producer reads); `PRODUCERS` is empty in the product, so every mutator is refused `unknown_mutator` until its slice registers a producer; tests register the test producer. Outcomes: `prepared`, `refused` (with `step`), `moved`, `paused`, `stale`. A refusal's subject that is not an absolute path (a plugin's name under a policy that refuses one; not possible on desktop) is answered without a path. Phase `checking_change`; decision table `engine.preview` v1 (counts, step, reason, stale: content-free).
- **§7 for the preview** (agent): the `.open` journal first (nothing loaded over one) and again before answering; the baseline still fresh and the plan's own fingerprint observed again before answering (`moved`). They catch different changes: a file the plan does not edit changed after the snapshot but before the load (only the baseline sees it) and a file only the candidate's load reads, such as a new `document` entry's file (only the plan's fingerprint sees it); each has a test.
- **One load with plugins per process** (agent, BL-0106's S0099 note): the preview loads once (the baseline is the mirror's, not a second load). S0099's module-set equality is checked on the op path in one process with the plugin dropped between the open and the preview (`test_the_preview_s_fingerprint_names_the_plugin_code_the_open_s_stamp_names`); the spike in real engine processes stays in BL-0106.
- **Docs** (agent): ARCHITECTURE.md §2.0 (line 108 and the engine tree) and §9.2 step 3; engine-jobs §2 (`preview`) and §7 (built for the preview); `engine/CLAUDE.md`; the overlay's docstring (its stale `TODO(BL-0106)`); backlog I2, I3, I10, L1-03, BL-0001, BL-0106 and WS-WRITE stage 1; CAP-DATA-WRITE-GATE's note (stays `planned`). The schema regenerated; the sidecar's codec (`decode_preview`, `PreviewAnswer`) and its contract test (examples, mutations, nested mutations). No user docs (nothing user-facing).

## Retro
