# S0128: the engine's Windows file-system adapter and the replace (M1b slice 8b-2, BL-0280 with BL-0218)

## Brief
- Goal: the second part of the Windows port. Build the engine's Windows file-system adapter (`ledger_engine.fs`, beside `darwin.py`, `linux.py` and `posix.py`) with ADR-0069's replace, so the engine's real-disk write-contract tests run on the Windows runner (NTFS, plus the runner's FAT32, exFAT and ReFS scratch drives) with the same contract, write-intent journal, recovery and texts as on macOS and Linux. **Windows still refuses every file operation in the product after this slice** (`this_os` keeps `UnsupportedPlatform` for the product until BL-0206 lands and BL-0087 turns writes on). The adapter is reached by the tests, and the brief's turning-on step is BL-0087's. State how the tests reach it without the product's selector doing so.
- **The ownership rule** (owner, 2026-11-16: "Rule unchanged (Recommended)"): the adapter writes exactly the files and bytes the macOS write path writes; where Windows cannot give a primitive safely, it behaves as the stated refusal or the stated best-effort mode, never a silent fallback.
- **The replace, ADR-0069** (owner, 2026-11-17: "1a, split yes, keep red"): §6.8's best-effort mode on every Windows volume. The journal, synced backups, read-back and `writer._check_replaced` are kept, then one plain rename over the file: `MoveFileExW` with `REPLACE_EXISTING` and `WRITE_THROUGH`, or its handle-relative form `NtSetInformationFile(FileRenameInformation, ReplaceIfExists)`. No `ReplaceFileW`. `caps().swap` is False on every Windows volume, so the writer takes its existing best-effort branch, and the reported mode is shown as on macOS and Linux (the open's notice), with Windows wording.
- **The primitives** (BL-0280; S0126's probe facts):
  - **Handle-relative operations:** opens and renames relative to a folder handle via `NtCreateFile` and `NtSetInformationFile`, not `SetFileInformationByHandle`, which the probe showed refusing them. The path guard and the link checks go through folder handles, as `openat` does on POSIX; reparse points (symbolic links and junctions) are refused or checked as the macOS and Linux link rules.
  - **Durable sync:** `FlushFileBuffers` on files opened for writing, and on folders opened for writing with backup semantics. A read-only handle refuses the flush, so the sync opens for writing. State exactly what is and is not made durable for a rename on each volume kind, as a limit where needed.
  - **Exclusive create and rename:** `CREATE_NEW`, and a rename without replace, both of which refuse an existing name everywhere (probe). The exclusive rename is therefore offered on every volume (A2's rule; `NotOffered` never raised on Windows unless a volume refuses).
  - **Canonical path:** `GetFinalPathNameByHandleW` (normalized; it expands 8.3 short names).
  - **Open files:** a file another program holds open without delete sharing cannot be renamed, replaced or removed. The save refuses truthfully ("not saved", unchanged, naming the file), and recovery stops in the same case.
  - **Locks:** `LockFileEx` for the engine lock, the app-instance lock (sidecar side: state whether it belongs here or in BL-0281) and the legacy app's lock on Windows (INV-26: as the legacy app takes it).
  - **Identity (BL-0218, Windows part):**
    - NTFS and ReFS: the 64-bit volume serial (`GetVolumeInformationByHandleW`, or `FileIdInfo`'s) and the 128-bit file ID (`FileIdInfo`) for folders and files, replacing the creation time on Windows. The probe showed tunnelling gives a folder or file made again at once its predecessor's creation time, though a new file ID.
    - FAT32 and exFAT give no file ID, and their top folder has creation time 0. State their identity rule and limit, as macOS FAT's (§6.3), and the `no_folder_id` or `no_drive_id` refusal where nothing identifies.
    - The app folder's identity text and the engine lock's check (`--app-folder-id`) on Windows.
  - **Names and folding:** NTFS, FAT32, exFAT and ReFS compare without case; only NTFS answers the per-folder case question. `FoldRule` and the case-twin check follow the volume.
  - **Hard links:** NTFS and ReFS only; the save's hard-link refusal as on macOS.
- **Before the adapter writes, the path model's Windows side** (S0127 verifier round 1, now in BL-0280):
  - **F2:** `WINDOWS.parent_and_name("C:\\")` and `("\\\\srv\\sh")` must refuse with `MalformedPathError`, not raise `IndexError`.
  - **F3:** `WINDOWS.normpath` must collapse a doubled separator after the root as `join(split(...))` does.
  - **Q1:** one rule for the canonical root. A volume GUID path or a drive letter, a mapped drive or its UNC path, a server name's case, and 8.3 short names must give one root form, so that §6.3's "never split" holds. State the rule and test it on the runner.
  - Each fix comes with a test; these are pure-model changes on Windows only, and the POSIX pins must stay green.
- **Re-probe** the S0126 C: oddity (a `FILE_EXISTS` at a create right after a replace moved the name away, probably antivirus), and state the result.
- **How it is tested** (owner, 2026-11-16: "Yes, start runs as needed (Recommended)"): push macOS-green commits to `next`, run the manual CI, and iterate. Runs are named by date and order only.
  - The `engine-windows` job's real-disk tests now run (their BL-0280 skips go) on NTFS and the scratch drives.
  - The 5 `test_no_resident_ledger.py` cases (INV-10) should pass now.
  - The `test_parity_corpus.py` cases are BL-0282's, and stay red unless this slice happens to fix them.
- Implements: ADR-0069; ADR-0061 and its amendment of 2026-11-14; ADR-0012, ADR-0068 D2; engine-jobs §5.1, §6.1-§6.8, §8.1, §14, §15; BL-0280, BL-0218 (Windows).
- Capabilities: none changes status (Windows does not write in the product yet).
- Invariants touched: INV-01, INV-22, INV-26, INV-32, INV-10, INV-23, INV-24.
- Risk class / lane: High / full. Review budget row: **New write path or write outcome** (owner, 2026-11-16, for the ports): verifier + data-safety red team; a fresh round after any product fix; in it only High and (a)/(b) findings are fixed; a second fix round on one mechanism needs the owner's options note.
- The bytes it protects: every ledger, journal and backup byte the adapter writes on Windows, by the same durable order, and the truth of "saved", "not saved" and "unchanged" there, including when another program holds a file open.
- Mechanism questions (PROCESS.md §3 step 2): which real setup needs this? Every Windows user (owner, 2026-11-14). Can a policy forbid the rest? Volumes without a safe primitive refuse or take the stated mode. Fix-round history: the ports (S0125: one fix round, three class (a) findings decided by the owner first; S0126 stopped on the swap; S0127 one round, all Low), the save (S0061, S0117: several rounds). **At the first class (a) finding, the policy option goes to the owner before the first fix round.**

## Decisions
- The Windows port's part 2 (owner, 2026-11-17, in session: "1a, split yes, keep red"); ADR-0069's replace; the ownership rule, the CI runs and the New-write-path review are the owner's decisions of 2026-11-16 (S0125's journal).
- **How the tests reach the adapter without the product selecting it (agent).** `ledger_engine.fs.windows` is imported only inside `this_os`, and only when a context variable is on: `this_os.windows_port_under_test()` (tests only; the `windows_port` fixture in `tests/conftest.py`, opted into per module). Off by default, so the product on Windows still refuses every file operation (`UnsupportedPlatform`, `engine.unsupported_platform`) and never loads the module: `tests/fs/test_windows.py::test_the_product_on_windows_still_refuses_file_operations_and_never_loads_the_adapter` (a fresh process on the runner) and the architecture guard `test_the_product_never_turns_the_windows_port_on` (no product module names the switch). Rejected: tests constructing `WindowsFS` directly (they would miss every product path that calls `for_this_os`, the ops among them); an environment variable (the product could inherit it). BL-0087 turns it on by selecting the adapter for good.
- **The engine lock is the one Windows file operation the product takes (agent).** `hold_engine_lock` returned without a lock on Windows (a `TODO(BL-0280)`), so two engines could have run at once there. It now opens the app folder through the adapter, checks its identity (`port.same_folder`: the 64-bit volume serial and the 128-bit file ID), makes `locks/` and the lock file by handle, never through a link, and takes `LockFileEx` over the whole file, waiting (`this_os.engine_lock_folder`, `this_os.take_engine_lock`). Not behind the test switch: it is a guard, it writes only the app folder's `locks/engine.lock`, and the sidecar cannot start an engine on Windows yet (BL-0281). **The app-instance lock** is the sidecar's (`app.platform.adapters`), which refuses on Windows with `NotOnWindowsError` today: it belongs to BL-0281 (the sidecar's Windows side), not here; it must take the same `LockFileEx` range on the same file for the engine-lock wait.
- **The replace (ADR-0069), as built (agent).** `caps()` is `Caps(swap=False, excl=True)` on every Windows volume, so `handles.write_mode` gives `BEST_EFFORT` and the writer's existing branch runs unchanged: staging written and flushed, `writer._check_replaced` just before, then one plain rename over the file. The rename is the handle-relative form, `NtSetInformationFile(FileRenameInformation, ReplaceIfExists=TRUE)` with the folder handle as the target's root (the brief's second option; `MoveFileExW` takes paths, which the path guard cannot hold). `MOVEFILE_WRITE_THROUGH` has no handle-relative counterpart and, by Microsoft's documentation, only matters for a move done as a copy and a delete (another volume), which never happens here; durability comes from the folder's sync after the rename. `swap` raises `NotOffered`.
- **Sync durability per volume kind (agent; stated in engine-jobs §15 "Limit (Windows durability)").** `FlushFileBuffers` on the file's own write handle (`create`), on a write handle opened for `sync_file` (a read-only handle is refused, probed), and on the folder opened again for `FILE_ADD_FILE` (`sync`, probed on all four kinds). What it makes durable for a rename: NTFS and ReFS commit their metadata log on a flush, so a rename synced by its folder survives a power loss whole (one logged operation); FAT32 and exFAT write the folder's entries with no log, so a replace there can lose the old entry and keep no new one (the file then missing, never torn, which recovery puts back from the backup: §6.8, as macOS's FAT). The runner cannot cut power, so none of this is power-cut tested: a limit, as macOS's FAT and Linux's swap types are.
- **Identity per volume kind (agent; BL-0218, Windows).** NTFS and ReFS: `identity()` and `stat`'s `(dev, ino)` are `FileIdInfo`'s 64-bit volume serial and 128-bit file ID (the values Python's own `os.stat` gives there), and `born()` is the file ID, since tunnelling gives a folder made again at once its predecessor's creation time (probed in S0126). The journal's `born` holds that ID (an int; format 6 unchanged). FAT32 and exFAT: no `FileIdInfo` (probed), so `(dev, ino)` are the 32-bit serial and the file index, and `born()` is the creation time (0 at the drive's top level: `no_folder_id`, as on macOS). **Limit (Windows FAT identity):** a FAT or exFAT folder made again at once at the same path gets its predecessor's creation time by tunnelling and may reuse its file index, so it is not told apart (macOS's FAT tells it apart only by the 2 s clock). `volume_id`: the serial as the version 5 UUID Linux already uses (`port.SERIAL_NAMESPACE`, moved there from `fs/linux.py`, value unchanged): 16 hex digits for NTFS and ReFS, `XXXX-XXXX` for FAT32 and exFAT, as udev names the same drives; a remote volume (`FILE_REMOTE_DEVICE`) or another file system has none (`no_drive_id`). File-system types in lower case (`ntfs`, `refs`, `fat32`, `fat`, `exfat`); `fat32` and `fat` join `handles.SERIAL_IDENTIFIED` (twin sticks share a serial; their top level keeps no time), which macOS and Linux never report, so nothing changes there. exFAT's whole-second comparison (`WHOLE_SECONDS_ON`) applies on Windows too.
- **The canonical root rule, Q1 (agent).** A folder's path is `GetFinalPathNameByHandleW(FILE_NAME_NORMALIZED | VOLUME_NAME_DOS)`, the prefix taken off; only a volume with no drive letter or mount folder falls back to `VOLUME_NAME_GUID`. The root therefore depends on the object, never on the spelling that opened it: a short (8.3) name, the prefix, `/`, another case, a link, a `subst` drive and a volume GUID path of a lettered volume all give the drive letter and one key (tests on the runner). The root component's key is folded by ordinal upper case (`Resolved.rules[0]`), so a server name's case cannot split a key. The one place two roots remain is a network spelling (`\\server\share`, a mapped drive, `\\localhost\C$`): a remote volume has no drive ID on Windows, so the save refuses it (`no_drive_id`, as macOS's network shares, BL-0219) and no journal is ever written under a second root.
- **Locks (agent).** The legacy lock (INV-26) as portalocker 3.2.0 takes it on Windows: its default `LOCKER` there is `MsvcrtLocker`, whose exclusive lock is `msvcrt.locking(fd, LK_NBLCK, 0x10000)` at offset 0 (read from the installed 3.2.0 source); the adapter tries `LockFileEx(EXCLUSIVE | FAIL_IMMEDIATELY)` over those first 64 KiB on the file opened read-only and never through a link (S0126 probed that `LockFileEx` and `msvcrt.locking` see each other); `ERROR_LOCK_VIOLATION` is held, anything else raises (Copy refuses). The test's holder is portalocker 3.2.0 itself (its Windows dependency `pywin32` is in the lock file).
- **The open-file refusal (agent).** `allowed(name, Right.DELETE)` opens the file for delete access: granted is yes, access denied no, and a sharing violation (another program holds it without sharing deletion, the usual editor open) raises `OSError` `EBUSY`, so the save stops before its first effect with `io_error`, "not saved", unchanged, naming the file (the outcome text the save already has; a dedicated "in use by another program" wording is a new outcome text, left to BL-0087's turn-on: BL-0284). A file opened after that check makes the rename fail with nothing changed, and the rollback restores what was replaced; recovery stops the same way.
- **Folding (agent).** Every Windows folder compares by ordinal upper case (`FoldRule(upper=True)`); only an NTFS folder whose case-sensitive flag is set (`FileCaseSensitiveInfo`) compares exactly. An answer that cannot be read counts as upper case, the Windows model's key rule (not its `wide` rule, which the journal refuses as a key rule).
- **Links (agent).** Entries below an open folder are opened with `FILE_OPEN_REPARSE_POINT` (never followed); a symbolic link or a junction is a `LINK`, any other reparse point (a cloud placeholder, a deduplicated file) is `OTHER`, refused as `not_a_file` (OneDrive's Files On-Demand among them: BL-0283). `open_child` answers `ELOOP` for a link, as `O_NOFOLLOW` does. Hard links (NTFS, ReFS) are refused by the save as on macOS. `symlink` refuses (`ENOTSUP`) and `readlink` reads no target: the mirror's `current.db` link is ADR-0015's pointer file on Windows (BL-0206). A read-only file is `locked` (Windows refuses to replace it), so the save refuses it (`locked`) before writing.
- **What still needs BL-0206 (agent; the brief's "say which").** The save job (`save.run`) gates on the published mirror (publish.md §7), the open and the rebuild publish it, and the publish makes `current.db` a link: so the save, the open, the rebuild and the preview through their ops, and INV-10's five cases (open, save, rebuild in one engine), need the pointer file and stay skipped (or, for INV-10's enforcement file, red) with `BL_0206`'s reason. The write contract itself runs on Windows below them: the writer's durable commit, rollback and recovery, recover-all's ops and Keep, the create job, the locks.
- **Tests first (agent).** On the base d44062d5, macOS: `tests/fs/test_pathmodel.py`'s F2 and F3 tests fail (11 cases: `IndexError` for a root's parent, the doubled separator kept), and `tests/architecture/test_platform_selection.py`'s new guards and the load rule's Windows entry fail (no Windows adapter). Windows: the CI step "S0128 tests first (temporary step)" runs the slice's Windows tests against the base's engine source on the runner (removed by the slice's last commit); its result is under the CI runs below.

- **Round 1: the owner's decisions** (2026-11-17, in session: "1a, wording ok"): (1a) on Windows a replaced file's new version keeps the old file's own security: its DACL with its protected or inherited state, its hidden and archive attributes and its alternate data streams; an EFS-encrypted ledger file is refused before anything is written; (wording) `msg:save.best_effort_windows` is the owner's text.
- **Round 1: how 1a is built (agent).** `WindowsDir.create(..., like=...)` copies, before the rename, the old file's alternate data streams (`FileStreamInfo`, each opened relative to the file's handle), its hidden and archive attributes, and last its DACL (`GetSecurityInfo`, `SetSecurityInfo` with `PROTECTED_` or `UNPROTECTED_DACL_SECURITY_INFORMATION` by the old descriptor's `SE_DACL_PROTECTED`; last, so an explicit ACL that denies us writing binds only later opens). Not the owner or the SACL: setting either needs a privilege (`SeRestorePrivilege`, `SeSecurityPrivilege`) the user's process does not hold, so the new file is owned by the user who saves, as on macOS. `allowed(name, READ_XATTRS)` now asks for what the copy reads (`READ_CONTROL` and read access). EFS: `EntryStat.encrypted` (Windows only; `FILE_ATTRIBUTE_ENCRYPTED`), refused in `writer._check_replaced` as the new writer reason `encrypted_file`, before the backups (so no plaintext backup is made); the sidecar maps a `not_saved` `encrypted_file` to the existing `ENCRYPTED_FILE_NOT_EDITABLE` ("This change would edit an encrypted file…"), so no new outcome text. The save job's step 0 (a `.gpg` or `.asc` name) is unchanged.
- **Round 1: the switch (agent, verifier F1).** The test-only switch moved into its own module, `ledger_engine.fs.under_test` (a context variable and `windows_port_under_test()`); `this_os` reads `under_test.selected()` only beside a win32 check. The guard now refuses, in every product module but the selection point: any import of `under_test` (any spelling), the switch's names, reflection (`getattr`, `setattr`, `vars`, `__dict__`, `globals`) on a name bound to `this_os`, the switch or the `fs` package, and `contextvars` anywhere but the path model and the switch (iterating a copied context reaches every context variable). The verifier's four shapes and seven neighbours are must-not-pass cases. `engine_lock_folder` and `take_engine_lock` may be named only in `protocol/server.py`. Stated limit: a dynamic import by name is out of an AST scan (`check_engine_boundary.py` allows `import_module`, `__import__` and `exec` only in `ledger/beancount_port.py`).
- **Round 1: the rollback's flush (agent, red team F1, verifier Q-B).** `restore._flush` takes the rollback's `pristine` identities (each target's identity as the save resolved it before its first effect) and skips a file found at its pre bytes as that very object on a file system whose file IDs are never reused (`handles.FILE_ID_TYPES`: `ntfs`, `refs`): the save never replaced it, so it holds no revert of the save to make durable, and the flush's write-open would fail on a file Word or Excel holds sharing reading only. Recovery (`pristine` None) and every POSIX and FAT volume flush as before (inode numbers and FAT file indexes can be reused, so identity there does not prove "never replaced"). **Limit:** on FAT32 and exFAT such a rollback still fails the flush and ends `unfinished` (writes paused; Reopen recovers it once the program lets go).
- **Round 1: rename durability (agent, verifier F6, red team F3).** The rename's source is opened with `FILE_WRITE_THROUGH`; the adapter's own handle rename is now measured for a missing name (300 replaces per volume kind, `test_V_F6_the_adapters_own_rename_never_leaves_the_name_missing`); §6.2 and ADR-0069 say the folder flush committing a rename is relied on, not documented.
