# S0040: The engine supervision as an explicit statechart (BL-0089)

## Brief
- Goal: the ledger engine's supervision becomes the first backend statechart of ARCHITECTURE.md §7: a pure `transition(policy, state, event) -> Step(state, effects)` over an explicit table (`app.platform.engine_supervision`), with every decision the client makes today (start, backoff wait, the restart bound and its window, incompatible, closed, what each stop is called) taken by the table, and `EngineClient` (`app.platform.adapters.engine_client`) reduced to the shell that observes the process (spawn, handshake, reply, timeout, end of stream, exit) and executes the table's effects (spawn, handshake, pause, kill, shut down, log, fail). The engine's lifecycle is logged by the table's `Log` effects through the structured log of S0039, on every start and stop, not only the first start. A generated reference of the table (`design/generated/statecharts/engine-supervision.md`) keeps §7 from drifting (EP-20). The states are named so that BL-0090 (the cross-process failure-mode spec, the next slice) can name each failure against them; BL-0090 is not written here.
- Reference behaviour (S0035, S0038; kept unless a decision below says otherwise): lazy start and restart (the next request starts the engine); backoff 0.5 s, 2 s, 8 s by the number of stops in the window; three stops in 300 s make the engine `unavailable` until the window passes or `reset()`; a stop exactly one window old no longer counts; an engine that speaks another protocol is `incompatible` and never retried until `reset()`; no request is ever resent; a timeout or an invalid reply stops the engine; `too_large` sends nothing and is no stop; `close()` is final; a start is bounded by `RestartPolicy.longest_start`, not the caller's timeout; the boot state in `app.platform.engine_boot`.
- Implements: EP-17 (backend statechart: pure table, exhaustive (state × event) test, Hypothesis random walks), EP-01 (decisions pure, I/O in the shell), EP-20 (the table's reference is generated), ARCHITECTURE.md §7 (backend machines) and §2.0 (supervision), ADR-0054 decision 4 (the sidecar supervises the engine; restart with backoff).
- Capabilities: none (no user-visible behaviour yet; `/api/boot` and `/health` will read the state later).
- Invariants touched: INV-10 (no resident ledger: unchanged), INV-11 (the client's state is still the registered `EngineClient`; its entry text is updated), INV-19 (a new generated file, registered and diff-checked), INV-23 (no data; the new log events carry an enum, a count and `debug_detail` only).
- Risk class / lane: Medium (process supervision; no ledger reads or writes, no user data, no finance) / light. The table's guards (bound, window, backoff, incompatible, closed) are checks that refuse, so they get must-not-pass tests and mutants.
- Acceptance tests (new unless marked):
  - `backend/tests/platform/test_engine_supervision.py`: the exhaustive (state × event) test against the expected table written from this brief (every undefined pair raises `IllegalTransition`; every defined pair lands in its listed states); the backoff delays by stop count; no pause once the backoff has passed; the stop that reaches the bound enters `Unavailable` at once and is logged once; `Unavailable` refuses until the window passes, a stop exactly one window old no longer counts; `Incompatible` and `Closed` never spawn; `reset` clears stops and incompatible but not closed, and keeps a running engine; which events record a stop (spawn failure, handshake failure, timeout, end of stream, invalid reply, exit between requests, an interrupted wait) and which do not (incompatible, an answer, a refusal); the log effects of each lifecycle transition; Hypothesis random walks with these properties: a spawn never happens in `Incompatible` or `Closed` or with the bound reached; every spawn after a stop waits out its backoff; at most `max_crashes` stops are kept; no step both fails the caller and starts work; an engine process exists exactly in `Handshaking`, `Ready` and `Busy` (none is left behind); every emitted state and effect is one its table row declares.
  - `backend/tests/platform/test_engine_client.py` (real engine and stand-ins): the client's state follows the table (`Ready` after a start, `Unavailable` right after the third stop); the lifecycle is logged through the sink on every start and stop (`engine.ready`, `engine.stopped`, `engine.start_failed`, `engine.unavailable`, `engine.closed`); an exception during a backoff pause or a wait leaves the client usable (the next request works, no `IllegalTransition`); the existing S0035 tests unchanged in behaviour.
  - `backend/tests/platform/test_engine_boot.py` (changed): `EngineBoot` reports the first start's state and no longer logs (the client does; one line per start, not two).
  - `backend/tests/platform/test_events.py`: `engine.stopped`'s kinds are exactly the stops a running engine can have (crashed, timeout, protocol_violation).
  - `backend/tests/test_main.py`: one `engine.closed` line per run (the client logs it; `app.main` no longer does).
  - `scripts/tests/test_check_generated.py`: the statechart reference is registered with the table module and its generator as sources.
- Expected doc impact: ARCHITECTURE.md §7 (the engine supervision row and the backend-table paragraph as built), §2.0 (supervision as a statechart; the lifecycle events), §2.2 (package map: `engine_supervision.py`), §6A if it lists events; `design/generated/statecharts/engine-supervision.md` (new, generated); `design/generated/README.md`; `backend/.importlinter` (a purity contract for the table); `platform/state_registry.py` entry text; backlog BL-0089 done (and any new row); roadmap §1 "In M1a so far". No ADR expected (EP-17 and ADR-0054 decision 4 cover it); no user docs.
- Open questions: none for the inbox. Where the clean table and today's client differ, the choice is made in Decisions below.

## Decisions
- **Where and what** (agent): the table is `app.platform.engine_supervision`, a pure module beside the pure codec `engine_protocol`, held pure by a new import contract (`backend/.importlinter`, "The engine supervision table is pure": no adapter, no log writer, no process, thread, file or clock module; every time comes in on an event). `RestartPolicy` moved there (one home; `engine_client` no longer defines it; `selfcheck` and the tests import it from the table). The client keeps all I/O (spawn, pipes, reader threads, waits, kill, reap) and makes no lifecycle decision of its own: it observes, feeds the observation in, and carries out the effects in order.
- **The states and events against the backlog outline** (agent): "restarting with backoff" is `Restarting` (the pause is an effect, its end `BackoffElapsed`); "spawn" is the `Spawn` effect answered by `Spawned` or `SpawnFailed`; "handshake ok or failed" is `HandshakeOk` (which may still carry another protocol number), `HandshakeForeign` (another `v`, or a `protocol.version_mismatch` refusal) and `HandshakeFailed`; "reply" is `Answered` (a result or a refusal: the engine is fine either way); "timeout" is `TimedOut`; "exit" is two events, `Ended` (output ended or input broke with a request in flight) and `Exited` (found dead between requests), because what follows differs (the caller's request fails, or goes on to a restart). Added: `Idle` (never started, or reset), `Busy` (one request in flight), `Send`, `Reset`, `Interrupted`. **No "window passed" event**: nothing in the client observes time between calls, so every `Request` carries the monotonic time and the table prunes its stops (a guard, not an event). A timer that fires when the window passes would be new machinery (a thread) for little gain. Stated limit, for BL-0090: `state` says `Unavailable` until the next request, even after the window has passed.
- **Resting and passing states** (agent): the client's lock serializes every public call (S0035), so `Request`, `Reset` and `Close` are defined exactly in the resting states (`Idle`, `Ready`, `Crashed`, `Unavailable`, `Incompatible`, `Closed`) and are `IllegalTransition` in the passing ones (`Starting`, `Handshaking`, `Busy`, `Restarting`). A test pins it.
- **Behaviour that changed, chosen deliberately** (agent; each is the clean table's reading where the S0035/S0038 client was implicit):
  1. `Unavailable` is entered at the stop that reaches the bound, not computed at the next request. The port's answers are unchanged (the stopping call still gets its own kind, the next one `unavailable`, in the same order as before); only `EngineClient.state` and the log see it earlier. Why: the future `/health` reads the state, and the bound is a fact at the moment of the third stop.
  2. Every start and stop is logged, by the table's `Log` effects through the client's `log` sink (the structured log): `engine.ready` and `engine.start_failed` on every start (S0038 logged only the first, from `EngineBoot`); the new `engine.stopped` (a running engine stopped: kind `crashed`, `timeout` or `protocol_violation`; level warning, a degraded dependency per §6A.5); the new `engine.unavailable` (the stop count; level error, like `engine.start_failed`: §6A.5 lists `Unavailable` under warning as a degraded dependency, but here the engine of every write and BQL query is gone for minutes, not degraded); and `engine.closed` from the client, no longer from `app.main`. `EngineBoot` no longer logs (it would double the first start). Volume is bounded: at most `max_crashes` stop lines and one `engine.unavailable` per window; refusals in `Unavailable`, `Incompatible` and `Closed` log nothing. The new fields are an enum, a count and `debug_detail`, so the redaction corpus covers them by construction (it iterates `EVENTS`); no privacy-posture change.
  3. An exception that reaches a public call mid-way (a signal's `KeyboardInterrupt` or `SystemExit`, a `ValueError` from `Popen` for an argument with a NUL byte, an injected pause that raises) is fed in as `Interrupted` by one guard around every public call (`EngineClient._call`), wherever it landed, and then goes on. An interrupted start is a stop (`start_failed`) and ends what was started; an interrupted request is a stop (`crashed`), as S0035 did for the wait; an interrupted backoff returns to `Crashed` with no new stop (nothing was started). Before, the wait had its own handler, a `Popen` error that was not `OSError` left no stop, and an interrupted pause changed nothing. With explicit passing states a missing rule would leave the table in `Starting` or `Busy` and every later call would raise `IllegalTransition`, so one guard covers them all. The first version had two local handlers; self-mutation (C2) showed a signal can land outside them (between `Send` and the last transition), so they became the one guard.
  4. Only the client's own handshake is read for another protocol. Before, `call("handshake", ...)` was read the same way (the op name decided) and a foreign reply came back as a refusal with the engine left running; now a reply in another `v` to any request is a protocol violation and stops the engine. Edge case; the rule no longer depends on an op name a caller chooses.
  5. A stop's time is taken when the outcome is observed, before the engine is reaped, where S0035 took it after; the backoff is measured from up to `close_timeout` earlier. No test or user can tell; noted for completeness.
- **The table is a tuple of rows, not a dict** (agent): `tests/architecture/test_globals.py` refuses a module-level dict (INV-11). Adding `Rule` to its `RECORD_CALLS` would accept more (a loosening, which needs the owner; S0035's widening was approved by the owner, quoted in its journal). A tuple of plain rows is immutable under the scan's existing rule; `rules()` and `rule_for()` build `Rule` records on each call, and a scan of 34 rows per transition costs nothing next to a process exchange. The three request stops have three handler functions, not a factory, for the same reason.
- **Tests from the spec** (agent; EP-29): the exhaustive test holds the table to `EXPECTED`, written in the test from this brief (10 states × 16 events = 160 pairs, 34 defined); the table's declared targets must equal it, each pair once, and the module's `STATES` and `EVENTS` must be all of them (so the generated reference lists everything). The random walks (Hypothesis, 300 derandomized examples over random policies) drive a model of the shell: a clock, whether an engine process exists, and the pending follow-up; their properties are the brief's.
- **Generated reference** (agent; EP-20): `backend/scripts/gen_statecharts.py` writes `design/generated/statecharts/engine-supervision.md` from the table (states and events with their docstrings, a Mermaid diagram, every row with its targets, effects and note); registered in `scripts/check_generated.py` with the backend's own interpreter, as the engine schema is with the engine's. ARCHITECTURE.md §7's row is an outline that points at it.
- **Not changed, named for BL-0090** (agent): an engine that dies between requests is noticed only at the next request (nothing watches it meanwhile; `state` says `Ready` until then); `close()` waits for a call in flight (the lock), at most `longest_start` plus that call's timeout; a log sink that raised would reach the caller after the state moved (the structured log does not raise; S0039).
- **No ADR, no inbox item** (agent): EP-17 and ADR-0054 decision 4 cover the design; the changes above are internal behaviour with no rubric item (no ledger, finance, data, posture or scope change).
- **Deviation from ENGINEERING.md**: none. The interrupt test signals its own thread (`signal.pthread_kill`) once a stand-in reports the request read; it waits on a condition, never a sleep (EP-28).
