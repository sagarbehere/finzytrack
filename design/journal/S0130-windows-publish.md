# S0130: the mirror publish on Windows: the pointer file and the retried removal (M1b slice 8b-4, BL-0206)

## Brief
- Goal: the fourth part of the Windows port (owner, 2026-11-17: "1a, split yes, keep red"). Make the mirror's generation publish (`design/specs/mirror/publish.md`) work on Windows. Then the open, the rebuild and the save, which all go through the publish or the gate's read of it, run on the Windows runner, and INV-10's five `test_no_resident_ledger.py` cases turn green there. Windows still refuses every file operation in the product after this slice: BL-0087 turns writes on.
- **What changes on Windows.** ADR-0015 decides a pointer file there, since Windows cannot rename over an open file and makes no links without a privilege. Everything else in publish.md is unchanged: the names, the build into its own name, the refusal of an incomplete build, the syncs, the re-check, the stale-journal rule, `meta`, the keep set, the grace period and the cap.
  - **The pointer** (agent: its name and form): a file `current.txt` in the mirror folder whose whole content is exactly one generation name in ASCII (`gen-<N>-<tag>.db`), with nothing before or after it. It is written in two steps. First the port's `create` makes `current.txt.<tag>.tmp` and syncs its data (an entry already at that name is removed first: it is ours). Then one plain rename replaces `current.txt` with it (ADR-0069's replace, `FileRenameInformation` with `ReplaceIfExists`, relative to the folder handle). A folder standing at `current.txt` is first renamed aside, as §4 step 8 does for `current.db`. The `.txt` name means an outside tool never takes the pointer for a database, and Notepad shows which generation is current.
  - **Which form:** the adapter states it, one property per OS (links on macOS and Linux, the pointer on Windows). The publish never guesses the form from a failure.
  - **Current generation** (§6 "Kept"): on Windows, `current.txt` is a regular file whose bounded read is exactly a generation name, and that entry is a regular file of the folder. Anything else means no current generation. `current.db` there is an unknown entry, removed by the cleanup (the folder is ours).
  - **The retried removal** (ADR-0015 amendment of 2026-10-25): a generation that a reader holds open cannot be removed on Windows. The cleanup counts it as failed, logs it content-free and skips it, as §6 already says for any failed removal; the next cleanup tries again. It is never reported as an error.
  - **Readers:** the engine's `current()` reads the pointer through the folder handle. The sidecar's `app.mirror.files.pin` reads it once per request, opening it with read, write and delete sharing, so a pin never blocks a swap. As on POSIX, `mirror/` is first checked not to be a link or a junction (a reparse point).
- **The model** (`formal/tla/mirror-publish/`): expected to need no Windows variant. `P_Swap`'s single step maps to the synced temporary pointer renamed over `current.txt`; the temporary pointer alone is never read, as the temporary link is not. `lk`/`lkpl` stand for the pointer's content: a power loss leaves the old or the new pointer, or none on FAT, which is availability only and is neither property. A refused removal is one of the "any subset" outcomes the cleanup already has. MAPPING.md gets a Windows section stating this, for the verifier to check both ways.
- **Probe first** (S0126's lesson: probe an OS primitive an ADR names before building on it). An addition to `engine/scripts/probe_windows_fs.py`, run on the runner's C: and D: and on the FAT32, exFAT and ReFS scratch volumes, before any product code:
  - (P1) a generation held by a read-only SQLite connection (Python's `sqlite3`): is its removal refused, does a rename of it fail, and does setting its modification time (§4 step 8) work; and after the connection closes, does the removal work?
  - (P2) the pointer swap as built above, at 0, 50 ms and 500 ms between the temporary pointer's write and the rename: how often is the rename refused, and with which error? S0128's run 13 saw antivirus refuse 73 of 300 back-to-back renames over a just-written file on C:, where the app's cache folder lives.
  - (P3) while P2 runs, a reader that opens the pointer with full sharing and reads it: does it ever find the name missing, the content empty, or anything that is neither the old name nor the new one?
  - (P4) the same swaps while the reader uses Python's `open()`, which does not share delete: how many swaps does it refuse? This tells whether the sidecar's pin must open with delete sharing.
- **Stop rules:**
  - If P2 shows the pointer rename refused at the spacing real publishes have (a save, then its rebuild, seconds apart), the fix is a bounded retry of a refused rename, which did nothing, so retrying it is safe. That is BL-0284's family, which the owner asked to see before BL-0087. So the slice stops there and brings an options note, cheapest first (a refused swap ends the job unpublished and the next rebuild tries; a bounded retry in the swap; an engine-wide retry policy shared with BL-0284), before building it.
  - If the model or ADR-0015 turns out to need a Windows variant that changes a decided rule, the slice stops and brings it to the owner.
  - **Not blocking, put to the owner with the slice's report:** CAP-MIRROR-EXTERNAL (M7, release-blocking) promises outside tools a stable read-only path. On Windows a pointer gives no path SQLite can open. Copy path would give the current generation's own file, which outlives its replacement by the grace period, or as long as a tool holds it open, since Windows will not remove it. Recorded as a stated limit and a new M7 row, not decided here.
- Implements: ADR-0015 (the pointer file on Windows; the amendments of 2026-10-25, 2026-11-07, 2026-11-08 and 2026-11-14), ADR-0069 (the replace), ADR-0061 and its amendment of 2026-11-14; publish.md §2-§9, §11; BL-0206.
- Capabilities: none changes status (CAP-DATA-MIRROR's platform note; CAP-MIRROR-EXTERNAL gets a Windows note).
- Invariants touched: INV-05 (the mirror rebuildable, published atomically), INV-10 (its five cases run on Windows), INV-23 (the failed-removal log carries no content), INV-24 (tests on scratch folders only).
- Risk class / lane: High / full. Review budget row: **New write path** (verifier + data-safety red team), the owner's decision for the ports (2026-11-16, S0125's journal).
- The bytes it protects: no ledger bytes; the publish writes only the app's cache folder. It keeps two outcomes truthful on Windows: a reader reads one whole generation, built from one state the ledger really had; and the save's gate passes only when the published generation describes the disk the plan was made on.
- Mechanism questions (PROCESS.md §3 step 2): which real setup needs this? Every Windows user: every open and rebuild publishes into the app's cache folder. Can a policy forbid the rest? A pointer on FAT32 or exFAT (a cache folder on such a volume; where the shell puts it on Windows is not decided yet) can lose both names at a power loss, which costs a rebuild and is stated as a limit, not forbidden. Has this mechanism or its family needed two or more fix rounds before? Yes: the publish took S0085 (1 round), S0087 (2 rounds), S0088 (2 rounds, 1 High fixed: the stamp) and S0118. The swap itself has had one fix (S0087 round 1, red team F6: the folder renamed aside). The pointer is a new primitive beside it, so at the first class (a) finding the owner gets the policy option before the first fix round.
- What a check here is a second opinion on (S0122's lesson): the §9 crash sweeps and the model's trace replay in pointer form are a second opinion on the swap's order (the pointer synced before the rename, never read at its temporary name). The runner's concurrent-reader test is a second opinion on the rename's atomicity, which P3 measures and the code relies on. Neither checks what the other does.
- Acceptance (tests first; each fails on the base, on Windows or in pointer form on macOS):
  - **macOS, over the fake** (`tests/fakes/memfs.py` gains the pointer form): publish.md §9's crash and power-loss sweeps in pointer form (`test_publish_crash.py`); the model's traces replayed in pointer form (`test_publish_conformance.py`); the keep set with the pointer; a pointer holding a non-generation, an empty file, an over-long file or a link means no current generation; `current.db` is removed in pointer form; a refused removal is counted, skipped and removed by the next cleanup.
  - **The Windows runner** (`engine-windows`), with the `windows_port` fixture: INV-10's five (`test_no_resident_ledger.py`) green; the `BL_0206` skips of `tests/mirror/test_publish.py`, `tests/ledger/test_rebuild.py` and `tests/ledger/test_save.py` removed and those tests green on NTFS (and the scratch volumes where a test takes `FT_TEST_VOLUMES`); a swap under concurrent readers never shows a missing or torn pointer; a generation held open by an SQLite reader survives the cleanup and goes at the next cleanup after the reader closes; the replaced generation's modification time is set while a reader holds it.
  - **The sidecar** (`backend-windows`): `pin` reads the pointer, refuses a junction at `mirror/` and a pointer that names no generation, and never blocks a swap (a swap while a pin's read is open succeeds).
  - `engine-windows` red on exactly INV-03's five (`test_parity_corpus.py`, BL-0282); every other job green; `pyright_platforms.py` 0 errors on Darwin, Linux and Windows; the macOS and Linux gates green.
- Expected doc impact: publish.md (Orientation, §2, §4 step 8, §6, §7, §9's rows for the pointer, §10's "not modelled" line, §11's Windows limit replaced by the stated Windows limits, §12); MAPPING.md (the Windows section); engine-jobs.md (the Windows adapter's paragraph); ARCHITECTURE.md (the mirror's row); `fs/windows.py`'s docstring; `engine/CLAUDE.md` (the publish's Windows form); `tests/windows_pending.py` (`BL_0206` gone); BL-0206 closed; BL-0087's split note; a new M7 row for CAP-MIRROR-EXTERNAL on Windows; capability notes (CAP-DATA-MIRROR, CAP-MIRROR-EXTERNAL). ADR-0015 only if the owner's answer to the M7 question or a stop rule needs one.
- Open questions: none blocking at the brief. The CAP-MIRROR-EXTERNAL note above goes to the owner with the report; the probe's stop rule may raise one.

## Decisions
- Slice 8b-4 of the Windows port (owner, 2026-11-17, in session: "1a, split yes, keep red"); the ownership rule, the CI runs and the New-write-path review row are the owner's decisions of 2026-11-16 for the ports (quoted in S0125's journal).
- **Probe before building (agent; S0126's lesson).** The first commit is the probe addition and this brief; no product code until the runner has answered P1-P4.
- **The 2026-11-18 run 6** (head f0dee90f; the probe only; `engine-windows` red on exactly the known ten, INV-10's five and INV-03's five; every other job green). The pointer probe on the runner's D: and C: (NTFS) and the FAT32, exFAT and ReFS scratch volumes:
  - **P1, everywhere:** a generation that a read-only `sqlite3` connection holds cannot be removed (`SHARING_VIOLATION`; its name stays) or renamed, and `NtCreateFile` for delete is refused (`STATUS_SHARING_VIOLATION`). Its modification time can be set through a handle that shares everything. Once the connection closes, the removal works. So SQLite opens without delete sharing, and ADR-0015's retried removal is needed and enough.
  - **P2, everywhere:** with no reader, the pointer swap (a synced temporary pointer, then the adapter's handle rename with `ReplaceIfExists`) was never refused: 0 of 300, 100 and 20 at gaps of 0, 50 and 500 ms on all five volumes. The antivirus refusal S0128 saw on C: did not arise for the pointer, so the brief's first stop rule does not fire.
  - **P3, everywhere:** with a reader that opens `current.txt` sharing read, write and delete and reads it in a loop, the same swap is **refused** `ACCESS_DENIED` whenever a read is in flight: at gap 0, 120 of 300 (D:), 96 (C:), 1 (FAT32), 0 (exFAT), 176 (ReFS); at gap 50 ms, 54, 6, 13, 15 and 62 of 100. The reader never found the name missing, empty or holding anything but a whole old or new name. So the classic rename with replace refuses a target that any handle holds, delete sharing or not. Without a change, a pin during a publish makes the swap fail.
  - **P4, everywhere:** with Python's `open()` as the reader, swaps are refused as often, and the reader's own open is refused (`Permission denied`) while a rename runs.
  - S0126 saw `MoveFileExW(REPLACE_EXISTING)` replace a target held with delete sharing, where P3's handle rename is refused. **Before choosing a mechanism (BL-0256's lesson: facts first), P5 is added:** the same loops with the POSIX-semantics rename (`FileRenameInformationEx`, `REPLACE_IF_EXISTS | POSIX_SEMANTICS`) and with `MoveFileExW`, under shared and plain readers.
- **Tests first (macOS, over the fake's new Windows mode):** on the base's publish, `tests/mirror/test_publish_crash.py` in both forms gave 28 failed, 17 passed. Every pointer-form case failed: the publish tried to make a link, and the Windows fake refuses one, as the adapter does. Every link-form case passed. After the pointer form: 45 passed, the conformance replay in both forms 20 passed, and the whole engine suite 10 738 passed, 12 skipped.
- **The 2026-11-18 run 7** (head fa5ec924; `engine-windows` and `backend-windows` red, every other job green):
  - **P5:** the rename with POSIX semantics (`FileRenameInformationEx`, `REPLACE_IF_EXISTS | POSIX_SEMANTICS`, relative to the folder handle) under a reader that shares deletion was **never refused** on NTFS: 0 of 300 at gap 0 and 0 of 100 at gap 50 ms, on D: and on C:. The reader never found the pointer missing or torn. A reader that does not share deletion still refuses it (`SHARING_VIOLATION`, 100 and 174 of 300). FAT32 and exFAT do not offer it (`INVALID_PARAMETER`, every call), nor does ReFS (`NOT_SUPPORTED`). `MoveFileExW(REPLACE_EXISTING | WRITE_THROUGH)` under a sharing reader is refused as often as the handle rename (232 of 300 on D:, 146 on C:, 128 on ReFS), so S0126's single success was a moment with no read in flight.
  - **`backend-windows`:** 59 passed and 1 failed: the swap-during-read test, whose rename (`os.replace`, the plain rename) was refused (`Access is denied`) while the pin's share-delete handle was open. That is P3's fact, met by the test.
  - **`engine-windows`:** the log was cut by GitHub's limit before pytest's summary. `test_readers_during_continuous_publishes_read_only_whole_generations` flooded it: its reader threads start with an empty context, so the Windows adapter's test switch (a context variable) was off in them and every read refused (`UnsupportedPlatform`). The failures read before the cut:
    - `test_save.py`'s setup errors: its `led` fixture published before `windows_port` was entered, under the POSIX path model (`not_absolute`);
    - `tests/fs/test_windows.py`'s `Caps` comparison (the new `links` field);
    - three `test_rebuild.py` cases outside this slice: two of Beancount's document paths on Windows, one of them showing BL-0282's `re.sub` bug (`Users\runneradminAppData…`), and one that makes a file unreadable with `chmod(0)`, which Windows takes as the read-only attribute;
    - INV-03's five (BL-0282).
- **The swap's rename on Windows (agent, from P3 and P5):** the pointer is renamed over `current.txt` with POSIX semantics where the volume offers it (NTFS; a new port operation, `DirHandle.rename_shared`, chosen by the volume's kind, never by an error). Elsewhere it takes the plain rename, stated in publish.md §11 "Limit (Windows without the POSIX rename)". Every reader of ours shares deletion: the engine's adapter handles, and the sidecar's pin through `windows_files.read_shared`. The adapter's `rename`, ADR-0069's replace of ledger files, is unchanged: it is the owner's decision, and the save's "in use" check relies on it. No retry is added, so BL-0284's question stays the owner's.
- **Fixes from run 7 (tests):** the readers test runs each thread in a copy of the test's context and stops at 20 errors; `led` and `fs` request `windows_port`; `Caps(..., links=False)`; the three rebuild cases skip on Windows, naming BL-0282 or `NO_UID`; the pin test swaps with the POSIX rename, as the engine does. New tests: the adapter's `rename_shared` (it lands under a sharing reader where `rename` is refused; a reader that does not share deletion refuses it; `NotOffered` on the scratch volumes), a publish under a reader holding `current.txt`, and over the fake: the stated fallback off NTFS, and a holder without delete sharing refusing the swap with nothing changed.
- **The 2026-11-18 run 8** (head 3d4a7389): `backend-windows` **green**: the pin tests pass, the swap during a pin's read with the POSIX rename among them. `engine-windows`: 6 failed, 10 058 passed, 197 skipped, 72 errors.   - INV-03's five (BL-0282).
  - **`backend-windows`:** S0129's `test_a_plugins_child_holding_a_lock_is_ended_with_the_engine[close]` failed once, "the close returned before the drain", with no sidecar change in this slice (green in runs 6 to 8).
