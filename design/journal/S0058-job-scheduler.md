# S0058: The engine job scheduler shell, the queue's Unavailable, and the engine-job codes

## Brief
- Goal: the second of BL-0150's slices (`design/specs/engine-jobs.md` §3-§5, §11, §14; ADR-0064): the shell that runs the queue table of S0053 (`app.platform.engine_jobs.queue`) on one thread in the user container against the client of S0057, so that every job reaches the engine through the queue:
  - **The scheduler shell** (`app.platform.engine_jobs.scheduler.EngineJobs`, registered in `platform/state_registry.py` in place of `EngineBoot`): one scheduler thread owns the `QueueState`, feeds every observation in as a table event and carries out the effects; one worker thread runs the job that is running (its engine work through a job context: calls, progress, the `gate` answered by the table's `Proceed`, a fresh engine mid-job); the engine lock wait on its own thread; the display-delay timers on the scheduler thread. Submit, Cancel, a client that goes away and Try again are answered by the table. Each job ends with one outcome: its value, or a `DomainError` with a registry code.
  - **Spawn on demand** (§5.1, §5.5 bullet 7): no engine starts at boot any more. The boot feeds `Boot` (the engine-lock wait, with the advice after the display delay, §5.1) and queues the boot's `recover_all`, which starts the first engine; recover-all has no journals to list yet (its body is BL-0151's), so its engine work is the start alone. The boot then ends its exclusive window (§3; the boot's open is BL-0152/BL-0154). `app.platform.engine_boot` is removed.
  - **The engine lock before every spawn** (S0053 verifier round 2; §5.1, §15 "the next engine then waits for it, with the advice"): the table waits for the lock before every fresh engine, not only at boot, so a failed wait never lets a spawn through: a failed wait ends the jobs that need an engine with `ENGINE_UNAVAILABLE` and the next job that needs one waits again.
  - **The queue's remaining pieces** (model `DispatchUnavail`, `SpawnStep`'s unavailable branch, `AppBgSave`): the table learns the engine's availability from the shell (the client's `Unavailable` and `Incompatible` states; the shell re-reads it after every failure and when the restart window lets a stop go, and Try again resets it); while unavailable, every eligible queued job and a running job that asks for a fresh engine end with `ENGINE_UNAVAILABLE` without an engine (§5.3). `AppBgSave` is the shell's entry for a save the app starts itself (prices), capped at one queued per workspace by the table.
  - **Death reports by the number the `Start` carried** (§5.3): the shell maps each engine the client spawns to the queue's engine number of the `Start` it serves, and reports a death by that number; a death the client reports while the slot is busy is decided by the job's own call (so the start's bytecode retry, §5.1, is never taken for a death). To make an engine's identity stable over a job, the client gains two small things: an `on_engine_spawned(serial)` report, and `call(..., spawn=False)`, which fails instead of starting an engine (the job's engine died: the queue, not the client, decides about a new one).
  - **The codes** (§11; ARCHITECTURE §6.1): `ENGINE_QUEUE_FULL`, `JOB_CANCELLED`, `ENGINE_STOPPED {crashed | killed_by_system}`, `ENGINE_UNAVAILABLE {reason}` join the registry with their class, plain message, data-safety statement and next step, each tested through the API (a test-only route that runs a real scheduler over a fake engine). `killed_by_system` is never produced yet (BL-0094 decides how an end is told apart).
  - **What the user sees** (§5.4, §11; failure-modes E2, E3, E5, E7): a pure description of each job for the UI: its phase ("Starting the ledger engine…", "Reading your ledger…", …), "Waiting for: <the running job's phase>" while queued, "Still working…" after the display delay, Cancel only where a Cancel would change something (so no Cancel for a recover-all between engines, which the table answers with nothing, S0053 round 2), the quit advice "Finzytrack cannot stop the earlier ledger work. Quit and reopen Finzytrack." when the table shows it, and the answer to the waiting user's Cancel behind work they cannot end. The UI that renders it is BL-0092 (M2).
  - **Each engine's end report is logged with its job** (`engine.exit`: the queue's engine number, the kind of the last job that ran on it, who ended it, the exit code or signal, the peak memory; content-free). The job's CPU (§5.2 `RUSAGE_CHILDREN`) stays with BL-0082.
- **The step rule** (added in verifier round 1, F1): a step's new state is taken first and then every one of its effects is carried out. Effects must not raise: our ends on the client (`EngineClient.end`) never raise, from any thread at any time, and Try again's reset of the client is an effect of a table step that runs on a thread of its own (the caller waits only for the step, never for the engine). An effect that raises anyway is a bug: it is logged `jobs.internal_error` and the step's other effects still happen, so no step is left half carried out and a held slot still gets its advice; a request whose own code raises gets its fallback answer, never None. The status is published before a request is answered, so `status()` read after an answer shows that step.
- **Split (agent, by the brief's rule):** the **model-driven conformance tests** (TLC-simulated traces of the small worlds projected onto the queue's state and replayed through the table and this shell over a fake engine port) are not in this slice. They need their own tooling (TLC's simulate mode writing traces, a reader for TLA+ values, the projection from the model's 11 variables onto `QueueState`, and an action-to-event map for about 70 actions) and they replay through the shell, which this slice builds. They become the third BL-0150 slice (S0059); BL-0150's row says so and stays in progress. The shell is built so that replay is possible: the table is still the one decision point, and a fake engine port drives the shell in tests.
- Implements: ADR-0064 decisions 1-5 (and its amendment of 2026-10-28, the engine lock); spec §3 (one scheduler thread per user container), §4 (Cancel through the table, the commit-point step answered with `proceed`, a client that goes away), §5.1 (spawn on demand; the lock before every spawn), §5.2 (our ends carried to the client, the advice on the timer, the end report), §5.3 (death by engine number; Unavailable; the crashed job not run again), §5.4 (the phase, "Still working…"), §5.5 bullets 6-8, §11 (the four codes and the texts of the rows that need no save), §15 (the advice while a lock is held within a session).
- Capabilities: `CAP-DATA-ENGINE-JOBS` (stays planned: the user sees it only with the UI, BL-0092; this slice's code and tests are listed on it).
- Invariants touched: INV-11 (the scheduler is a container-owned state holder, registered; no module state), INV-10 (bounded: at most `max_queued` jobs, one worker, one lock wait, at most two engines in the client's books), INV-01 and INV-22 (the commit point: `Proceed` only from the table's step; a Cancel past it changes nothing in the shell either), INV-28/INV-31 (submits refused for a workspace that is not open; the boot's exclusive window), INV-23/INV-24 (tests in temp folders; no real data).
- Risk class / lane: **High / full.** No ledger byte is written yet, but this is the code that decides at run time whether an engine past its commit point is ended, whether a second engine can start beside one that may still write, whether an engine is spawned while an earlier one may hold the engine lock, and whether a fresh engine is given after user code.

## Decisions
- **The split** (agent, by the brief's rule "if this does not fit one slice ... split it"): the conformance tests from TLC traces are S0059 (BL-0150 stays in progress; its row says what is left). Reason: they are their own tool (TLC's simulate mode writing traces, a reader of TLA+ values, a projection of 11 model variables onto `QueueState`, an action-to-event map for about 70 actions), and they replay through this shell, which had to exist first. The shell is replayable: the table is still the one decision point and every observation enters it as an event; the fake engine port (`backend/tests/platform/fake_job_engine.py`) is the port the replay will drive.
- **The engine lock before every fresh engine, decided by the table** (agent; S0053 verifier round 2 "wait for the engine lock before every spawn, also after a failed wait at boot"; spec §15 "the next engine then waits for it, with the advice (§5.1)"): `QueueState.engine_lock` gains `unchecked`; a fresh `Start` needs `free` and makes it `unchecked`; the dispatch asks for a wait (`WaitEngineLock`, with the advice timer) when a fresh engine is needed and the lock is `unchecked`; a reuse needs none. Rejected: waiting inside the job's worker before the client's start (the table would not know: no advice, and a waiting user's Cancel would not see the job as behind the lock). Within a session the lock is free whenever the previous group has drained (§5.1), so the extra wait costs one thread hop per fresh engine; it matters for a plugin's child that left its group holding the lock, and after a failed wait. Golden change: the S0053 tests' helper answers such a wait at once (below).
- **A failed wait** (agent; S0053 verifier F2's rule kept: an earlier engine may still run, so nothing starts): the table makes the lock `unchecked` and ends the jobs that need an engine now (eligible queued jobs, and a running job that asked for one while it holds none) with `NoEngine("lock_failed")` → `ENGINE_UNAVAILABLE {cannot_start}`; the next job that needs an engine waits again. Rejected: retrying the wait at once (a persistent `OSError` would loop), and keeping the jobs waiting (they would wait for ever with the advice, which says the wrong thing).
- **The engine unavailable comes from the client's state** (agent; spec §5.3; model `DispatchUnavail`, `SpawnStep`): the shell reads `EngineClient.state` after every failed call of a job: `Unavailable` (the bound) and `Incompatible` feed `EngineAvailability(False)`; the window's end is a timer computed with the supervision's own `counted` (the composition root hands the same `RestartPolicy` to both), after which the state is read again; Try again resets the client and feeds `EngineAvailability(True)`. `Incompatible` counts as unavailable until Try again (the model has no incompatible engine; §5.3 says it is never retried). While unavailable no job starts (a reuse neither, as the model's `Dispatch` needs `~Unavail`), and the refusals do not wait for the slot (the model's `DispatchUnavail` has no `SlotFree`). `SpawnStep`'s unavailable branch ends a running job between engines; recover-all's `not_tried` marks there are BL-0151's (the `PARTIAL` row).
- **The client gains two seams** (agent; spec §5.3 "The shell reports a death by that number"): `on_engine_spawned(serial)`, called while the client holds its signal lock right after the spawn, before the engine's threads start (so before its end can be reported, and before a concurrent `end()` can run), and `call(..., spawn=False)`, which fails instead of starting an engine (`crashed`, or `cancelled` after our end, `closed`, the incompatible failure). Without them the client starts an engine inside a job's call by itself (an idle engine that died, the bytecode retry), and the queue could neither name the engine nor keep "fresh after user code": a dead reused engine would be replaced behind the table's back by one that then served the next job as "fresh".
- **Who reports a death** (agent): while the slot is busy, only the job's own failed call (`_JobFailed` → `EngineDied`), never the end report, because one start can spawn two engines (§5.1's bytecode retry: the first ends by itself or with `stop`, and the job goes on); while the slot is idle, the current engine's end report is its death (`EngineDied(number)`). The slot has ended (`EngineEnded`) when no engine the client spawned is left unreported (`_Books.live`, updated on the reporting threads, so an `end()` that races a spawn can never let the slot be freed before that engine is drained).
- **A Cancel that reaches the client before the job's engine has started** (found on self-review; test `test_a_cancel_that_comes_before_the_jobs_engine_has_started_still_ends_that_engine`, 20 runs alone): the client drops an `end()` that comes with no engine and no call in flight, so the job's start would then spawn an engine nobody ends, and the slot would wait for it for ever. Fixed in the shell: a step tells each ended job's worker before it signals the engine, and the worker ends an engine its start returned after its job ended.
- **The codes** (agent; ARCHITECTURE §6.1 left their class and status to this slice): `ENGINE_QUEUE_FULL`, `ENGINE_STOPPED`, `ENGINE_UNAVAILABLE` are `Unavailable` (503, retryable: §11 offers Try again); `JOB_CANCELLED` is `Conflict` (409, not retryable): the request ended by the user's own Cancel, and the edge must answer it with something; no new class. Details: `JOB_CANCELLED {cannot_stop_ahead}` (the UI adds §4's sentence and Quit anyway), `ENGINE_STOPPED {reason: crashed | killed_by_system}` (`killed_by_system` is never produced yet: telling it apart is BL-0094's, `TODO(BL-0094)`), `ENGINE_UNAVAILABLE {reason: stopped_often | cannot_start | closing}` (E1, E6, and the app closing). `JOB_CANCELLED` says nothing about data (`data_safe` False): a cancelled save says "Your ledger is unchanged" only after its files were hashed again (§11's rule, BL-0151). They are tested through the API by a test-only route over a real scheduler and the fake engine, since no product route runs a job yet.
- **The job texts** (agent, UI detail): `app.platform.engine_jobs.text` words §5.4 and §11 for BL-0092's UI. Cancel is offered exactly where the table's Cancel would end the job or the waiting user's request (`queue.cancel_offered`, read from the table itself), so no Cancel shows for a background job, a switch job with nothing ahead, a job past its commit point ("Finishing your change…") or a recover-all between engines; there the advice explains the wait when the slot is held. "Working…" (a job on its engine before its first phase) is the agent's word, §5.4 names no phase for it. The display delay counts from the last change of what a job shows, so a phase change is shown at once (§5.4 "a phase change is shown, never judged").
- **The boot** (agent; §5.5 bullet 7, §9.2): `EngineJobs.start()` feeds `Boot` and queues the boot's `recover_all`, whose work is nothing yet (no journal format exists; `TODO(BL-0151)`) and which runs no user code, so its engine serves the next job; when it ends (any outcome) the boot's window ends (`ExclusiveEnded`; the boot's open and its screens are BL-0152/BL-0154). `EngineBoot` and its state are gone; nothing read its state but tests (BL-0094 builds `/health`'s engine status from `EngineClient.state`).
- **Each engine's end is logged with its job** (`engine.exit`: the queue's engine number, the kind of the last job started on it, who ended it or `none`, the exit code or the signal, the peak memory; every field content-free). The exit is split into `exit_code` and `signal`, both counts, so the line says how the engine ended outside debug mode too (the field BL-0094 asks for; deciding `killed_by_system` from it stays BL-0094's). The job's CPU stays with BL-0082.
- **A job's exception** (ARCHITECTURE §6.3: the job runner is one of the three catch-all places): logged `jobs.internal_error` (the exception's text only in debug mode), the job ends `INTERNAL`, and its engine is retired (`ran_user_code` taken as true). The scheduler's own loop catches too (logged the same way, the loop goes on), so one bad message cannot stop every job.
- **`.importlinter`**: a new contract keeps the queue table pure (no adapters, no scheduler, no observability, no clock, threads or OS) (a tightening; agent-approved, PROCESS.md §9).
- **Deviations from ENGINEERING.md:** EP-28 (waits on a condition with a deadline): the "this did not happen" checks look once after `ABSENCE` = 0.5 s (as in S0053 and S0057). The scheduler's timers (the display delay, the restart window) are waits on the scheduler's inbox with a timeout: they change what is shown or let jobs start, and never end work (§5.4).
- **Limits recorded, not fixed:** Try again calls `EngineClient.reset()`, which takes the client's call lock, on the caller's thread; with a call stuck in the kernel it would wait (no Try again is offered there: the engine is not unavailable while the slot is held, and the advice shows instead). A job's worker thread that is stuck in a call to an engine that never drains stays (one at a time: no other engine starts meanwhile).
- **This journal's name** avoids the retired term `engine-scheduler.md` (the spec's old name, ARCHITECTURE §0; `scripts/check_retired_terms.py` refused the backlog row that cited it).
- **Backlog IDs used:** BL-0150 (in progress: its row says what S0058 built and that S0059 owns the conformance tests), BL-0151 (`TODO` in `_boot`; the `PARTIAL` rows of `SpawnStep`, `DispatchUnavail`, `S_Commit`), BL-0153 (`CR_Commit`, `CP_Commit`), BL-0154 (the quiesce, the switch's window), BL-0094 (`killed_by_system`), BL-0092 (the UI), BL-0082 (CPU). No new rows.
- **The slot is held while a fresh start is under way** (found by a surviving mutant, S18 below): `_Books.starting` counts the fresh `Start`s handed to a worker whose start has not returned; `EngineEnded` waits for it as for an undrained engine. Without it a Cancel processed before the start spawned freed the slot at once, so the next job's fresh engine could start (inside the client, waiting for the drain) beside one the table no longer saw, and a stuck one would show no advice. Test `test_while_a_cancelled_jobs_start_is_under_way_the_slot_is_held`.
- **Close leaves a job past its commit point unanswered** (found on self-review; §4, OutcomeTruthful): answering "not done" there would be untrue (the job finishes, the client's close does not signal it); its outcome is the next start's to tell (§9.3, BL-0154). Test `test_close_leaves_a_job_past_its_commit_point_unanswered`.
- **The client's `_ready_only` does not settle again** (a surviving mutant, C3, equivalent: `_call` settles before every request): the redundant call was removed.

## Golden changes
- `backend/tests/platform/test_engine_queue.py`: the helpers `run` and `submit` now answer a lock wait the dispatch asks for before a fresh engine at once (`through`), as the shell does within a session (§5.1: "Within a session the lock is free whenever an engine starts"), and leave that wait's two effects out; the boot's wait is never answered there. Without it every S0053 test that starts a second fresh engine would see `WaitEngineLock` instead of `Start`. Their expected decisions are unchanged. The oracle (`check_step`) and the sweep cover the new state (`unchecked`, `unavailable`) and events (`EngineLockFailed`, `EngineAvailability`): a fresh start only right after its wait and never while unavailable, a `NoEngine` only while unavailable or after a failed wait and only for an eligible job or a running job that asked, one wait at a time; the sweep grew from 240,160 to 1,707,552 pairs (about 3 s). Why the old expectation is wrong now: S0053's table waited for the lock only at boot, which the S0053 verifier's round 2 and spec §15 do not allow (a failed wait at boot, a child holding the lock within a session).
- `backend/tests/api/test_error_registry.py`: the classes and the retryable set include the four new codes (ARCHITECTURE §6.1 "their class ... join with the engine-jobs slice"; §11's Try again for the three `Unavailable` ones).
- `backend/tests/test_main.py`: `wire` builds `jobs` (an `EngineJobs`) instead of `boot` (an `EngineBoot`); the stop-handler test patches `EngineJobs.start`, the one way the engine can now start, instead of `EngineBoot.start_in_background`. The real-engine boot tests keep their expectations: the boot's recover-all starts the engine at the same moment.
- `backend/tests/architecture/test_tla_mapping.py`: no `PLANNED` row for BL-0150 (`DispatchUnavail` and `AppBgSave` are marked); `PARTIAL`: `Dispatch` and `AdviceTimer` are whole now; `SpawnStep` and `DispatchUnavail` keep recover-all's `not_tried` marks for BL-0151; `S_Commit` moves to BL-0151 and `CR_Commit`, `CP_Commit` to BL-0153 (the shell's part, the table's step and `proceed`, is built; the engine's own gate in those jobs is theirs).
- `frontend/tests/unit/api/contract.test.ts`: the generated code union and the new codes' details.
- Removed with the module they test: `backend/tests/platform/test_engine_boot.py` (`EngineBoot`). Its cases live on in the scheduler's tests: the wait before the first start (`test_no_engine_starts_before_the_boots_wait_for_the_engine_lock_ends_and_the_advice_shows_meanwhile`), a failed wait that starts nothing and is logged (`test_a_failed_wait_for_the_engine_lock_starts_no_engine_and_ends_the_boots_job_unavailable`), a raising log sink (`test_a_log_sink_that_raises_loses_the_line_never_a_decision`).
