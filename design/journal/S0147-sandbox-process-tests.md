# S0147: The backend's process tests skip inside the agents' sandbox (BL-0309)

## Brief
- Base: `e809f25d` (`next`).
- Goal: inside the agents' OS sandbox (macOS Seatbelt, `.claude/settings.json`) the backend tests that start a child process they must end themselves, or that run `ps` or `os.killpg`, skip with a named reason, so they never start what they cannot end; outside it (the pre-push hook's backend test step, `ci.yml`'s backend jobs) they run as today, and a skip by this rule there fails the run.
- Scope: BL-0309's row (owner, 2026-11-22, in session: "Yes"). The incident: `design/journal/S0146-copy-check-windows.md`, Decisions, "Sandbox runs of the backend's process tests".
- **Kind and review row:** tooling and gates. The verifier, one round, the stop rule; a fresh round only if the slice or a fix changes a guard of real data or privacy (INV-23, INV-24). It does not: it touches the test suite's collection, the pre-push hook's backend test line and `ci.yml`'s backend jobs, none of which guards real data or privacy. **Risk class / lane:** Low / light.
- **The bytes it protects:** none (no ledger or user byte). What it keeps: the owner's Mac's process slots.
- **Which real setup needs this, and can a policy forbid the rest?** Every agent session on the owner's Mac (the sandbox is on since S0139). It cannot be forbidden by policy: the sandbox is the owner's decision; the policy until now ("never run them in the sandbox") is what this slice turns into a mechanism.
- **Has this mechanism or its family needed two or more fix rounds before?** None known.
- Implements: BL-0309. Specs: none (test tooling); PROCESS.md §6 (the pre-push hook's backend test step), `backend/CLAUDE.md` (how the backend's tests run).
- Capabilities: none (tooling). Invariants touched: none directly; INV-24 (agents never stop the owner's running app) is not involved: the probe starts and ends only its own child.
- **Design points (settled here):**
  1. **Detection by behaviour.** Once per session, and only when a marked test is collected, `tests/process_control.py` asks the OS: it starts a child in its own process group (`start_new_session`) that ends by itself after 3 s, lists it with `ps -o pid= -p <pid>`, then ends its group with `os.killpg(pid, SIGKILL)` and waits for it. Any refusal (`OSError`, `PermissionError`), a listing without the pid, or a child that did not end by the kill (its exit status is not `-SIGKILL`) is the answer "refused", with the step and the error named. The child ends by itself within 3 s whether the kill works or not, and the probe waits for it, so it never leaves a process. No environment variable is read to detect the sandbox. On Windows there is no process group or `ps` to try and no sandbox in our setup: the answer is "allowed" (a stated limit).
  2. **The population, by behaviour:** every backend test file with a test that starts a child the test itself must end (a stand-in engine, a sleeper, the sidecar, the real engine through an `EngineClient` the test holds), or that runs `ps` or `os.killpg`. Out: children started with `subprocess.run` that end by themselves (even when they start an engine inside), and in-process fakes (`fake_job_engine.FakeEngine`). Marked per module: `pytestmark = pytest.mark.needs_process_control` (a new test in such a file is covered without a step; a new file adds one line). The inventory and its counts are in the Hand-off.
  3. **The must-not-pass guard:** with `FT_REQUIRE_PROCESS_TESTS=1` a refused answer fails the run (a usage error naming the probe's answer) instead of skipping. The pre-push hook's backend test step and `ci.yml`'s `backend` and `backend-windows` jobs set it. The Stop hook (`.claude/hooks/stop_checks.py`) does not run the backend tests, so it needs no edit.
  4. **The engine side:** checked by behaviour (Hand-off); no engine test qualifies, so the engine's conftest is unchanged.
  5. **What fails by hand in the sandbox after this slice:** reported in the Hand-off.
- Acceptance tests (`backend/tests/test_process_control.py`):
  - the probe's decision with each step refused or not (fakes): "allowed" only when every step works; a refused step names itself;
  - the real probe leaves no child: its child is reaped when it returns, and with the kill refused (a fake kill on a real child) it still ends by itself within a few seconds;
  - the rule in a real pytest run (a subprocess on a sample marked test, the probe's answer forced by a test plugin): refused and not required: the test skips with the named reason; refused and required: the run fails naming the answer (the must-not-pass test); allowed and required: the test runs;
  - the backend suite in the sandbox: the marked tests skip, no failure from them, and the probe's answer shown; the landing push (outside the sandbox) runs them all.
  - Loosening mutant: the probe always answers "refused" (it would skip everywhere): caught by the fakes' "allowed" test (and, outside the sandbox, by the required run failing).
- Expected doc impact: `backend/CLAUDE.md` (the marker and the rule), PROCESS.md §6 (the pre-push backend step sets the variable), BL-0309's row (done); the meta-test pin of `.githooks/pre-push`; `scripts/check_invariants.py` unchanged (its stated limits already name "a conftest hook that filters or marks items"); the renumbering of BL-0087's split (S0147-S0149 to S0148-S0150) in its row, BL-0283's row, `engine-jobs.md`, `ledger_engine/fs/windows.py`'s docstring and the S0144 and S0146 journals.
- Open questions: none (the owner decided the policy in BL-0309's row; the rest is test design).

## Decisions
- **The sandbox's refusal is `ps`, not `os.killpg` (agent; probed 2026-11-22, this session).** BL-0309's row and the S0146 journal say the sandbox refuses `os.killpg`. Probed here with children that end by themselves: `os.killpg` on our own child's group works (signal 0 and `SIGKILL`, a group whose leader called `setsid`, a group whose leader was killed while a member lives), `setpgid` works, libproc's `proc_listpids` (the drain's listing) works; running `ps` is refused (`PermissionError: [Errno 1] Operation not permitted: 'ps'`, at exec). So the 33 failures of S0146 were most likely tests whose helpers run `ps` (`alive()` in `test_engine_client.py`, `group_members()` in `test_engine_group.py`, `pid_alive` paths) failing before their own cleanup, leaving stand-ins that wait forever. The probe tries both, so a stricter sandbox that also refuses the group kill is detected the same way.
- **The skip lives in a helper module, not in `tests/conftest.py` (agent).** `scripts/check_invariants.py` refuses a skip form in any `conftest.py` above an enforcement test, and `backend/tests/conftest.py` is above all of them. The root conftest calls `tests.process_control.apply(items)` from its existing `pytest_collection_modifyitems`; the static scan does not follow it, which its stated limits already name ("a conftest hook that filters or marks items"). No enforcement file carries the marker (Hand-off), and the runtime proof (`check_invariants.py --ran`, pre-push) fails a skipped enforcement test whatever skipped it.
- **Per module, not per test (agent).** `test_main.py` and `test_engine_client.py` hold pure unit tests too, which then skip in the sandbox. Marking each spawning test would keep them, at the cost of a list that is easy to get wrong in the direction that leaks; the files are the same set S0146 deselected by hand, so the sandbox's coverage does not shrink from today's.
- **The probe's answer forced only in tests, by a test plugin (agent).** No product or conftest code reads a variable that can force the answer; the acceptance test loads `tests/process_control_forced.py` with `-p` in a subprocess and sets the answer there.
