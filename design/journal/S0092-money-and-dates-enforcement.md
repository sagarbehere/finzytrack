# S0092: Money and dates enforcement (INV-06, INV-07)

## Brief
- Goal: BL-0006 and BL-0007. Build the enforcement INV-06 (money is exact) and INV-07 (civil dates, never a UTC "today") still lack, as far as the code they guard exists at M1a:
  1. **Python money bans** (backend and engine product code, one AST check `scripts/check_money_dates.py` with meta-tests, run over the real trees by its meta-tests and so in the pre-push gate and T1): `float(...)` on a value (a line that is not money says why with `# not money: <reason>`); `Decimal.from_float` and `create_decimal_from_float`; `json.load`/`json.loads`/`json.JSONDecoder` without `parse_float=` (a JSON number with a fraction would come back a float); `math` functions other than `isfinite`, `isinf`, `isnan`, `inf`, `nan` (they turn a `Decimal` into a float). `Decimal(<float literal>)` is ruff's RUF032 (already selected); its must-not-pass test is added for both packages. Decimal arithmetic with a float is refused by pyright strict (typeshed's `Decimal` operators take no float), and `/` on two Decimals is a Decimal in Python, so neither needs a check of its own (verified on planted code, recorded below).
  2. **Python date bans** (same check): `.date()` and `.astimezone()` without an argument (the instant's own zone, UTC for the clock, or the machine's zone read in passing) outside the one home of the civil date, the new `app.domain.dates.civil_date(instant, tz=None)`; the attributes `today`, `utcnow` and `utcfromtimestamp` on anything, so an alias (`d = date; d.today()`) is refused as well as the direct call. The existing ruff bans (`TID251` on `date.today`, `datetime.now`, `utcnow`, `time.*`; the `DTZ` rules on naive datetimes) get must-not-pass tests for `DTZ` in both packages, and the engine's `TID251` bans get theirs (the backend's exist).
  3. **One "today" on the main sidecar:** `app.domain.dates.civil_date` replaces the two copies of `now.astimezone().date()` in `engine_jobs/opening.py` and `engine_jobs/rebuild.py`; the demo anchor's UTC date goes through it with `UTC` given.
  4. **Tests run west of UTC:** the backend's and the engine's suites run under `TZ=America/Los_Angeles` (set in each `tests/conftest.py` before any test, with `time.tzset()`), each with a test that fails when the suite runs at UTC or east of it. `test_rebuild_job.py`'s expected `today` is taken from the spec at an instant where Los Angeles and UTC differ, not from the code's own expression.
  5. **Frontend:** in `src/` outside `src/platform/`, the global `Date` is refused wherever it is referenced (`no-restricted-globals`), which closes BL-0007's aliasing gap (`const D = Date`) by removing the class rather than listing its uses; `globalThis.Date`, `window.Date`, `self.Date` (also computed `['Date']`), any `.Now` (Temporal's system clock) and `parseFloat`/`Number.parseFloat` (float money parsing) are refused there too, and in templates. Tests, e2e and tooling keep S0009's bans.
  6. **Written scale:** INV-06's "written scale is preserved" holds today on the read path: the mirror writes each number with its written scale (`engine/tests/mirror/test_rows.py`, `test_numbers_are_plain_notation_with_the_written_scale`, `10.50`, `-100.00`, `0.00000001`), and the main sidecar's QueryRunner returns that text unchanged (`backend/tests/mirror/test_query.py`, which already asserts `-10.50` comes back as text; found during the slice, so no new golden). The write path that would write amounts does not exist (M1b, BL-0001); its written-scale goldens belong to L3-05 (M4). Cut, named, not invented.
  7. **The frontend `Money` brand** has no money value to brand at M1a (the frontend has no money code, and decimal.js is "pinned when first used", ARCHITECTURE.md §10): cut to a new backlog row tied to the first frontend money value.
- Implements: ADR-0023 (money types, civil dates), ADR-0025 (no float sums), EP-10 (determinism), EP-23 (one "today"); ARCHITECTURE.md §2.3, §2.6.

## Decisions
- **One AST check under `scripts/`, not two package tests** (agent): the backend and the engine need the same rules; one stdlib script with its planted cases in the meta-tests (and a real-tree test there) runs in pre-push and T1 once, as `check_engine_boundary.py` does. PROCESS.md §9's "a new check script only after a real escape" is about the gates' self-defence; this check guards product code and builds what BL-0006/BL-0007 (owner-accepted rows, review:20 §2) name.
- **What the Python check refuses, and what it leaves to ruff and pyright** (agent): ruff already had `TID251` (system clock), `DTZ` (naive datetimes) and `RUF032` (`Decimal(1.5)`); they only lacked tests that fail if a rule is dropped, now added for both packages. Pyright strict refuses `Decimal` with a float in `+ - * /` (checked on a planted file: "Operator "*" not supported for types "Decimal" and "float""), and at run time it is a `TypeError`; `Decimal / int` and `Decimal / Decimal` are `Decimal` (`reveal_type`), so "`/` on Decimal producing float" cannot happen in Python and gets no rule. Comparison of a `Decimal` with a float is allowed by both and is exact in Python, so it is not money loss.
- **`float` as a value, with a reasoned mark** (agent): every float conversion in product code is refused unless its line says `# not money: <reason>`; the two existing ones (a log duration, a log value already a float) are marked. Float literals stay allowed: durations and timeouts use them, and pyright refuses them in Decimal arithmetic.
- **Every JSON decode passes `parse_float=Decimal`** (agent): 8 decodes in 7 files, none of which reads an amount today (the engine protocol, the manifest, the save journal, the fingerprint, the copy check's answer, the self-check's view). With `Decimal` a fractional number stays exact; no decoder accepted a float where these now see a `Decimal` (each checks `int`, `str` or exact bytes), and both suites pass unchanged.
- **`app.domain.dates.civil_date(instant, tz=None)`, not `today(tz, clock)`** (agent): ADR-0023 says "today" is always `today(tz, clock)`. The sidecar sends one request with both the civil date and the instant (`today`, `built_at`), so the clock is read once and both come from that one `now`; a function that read the clock itself would let them straddle midnight. "Today" is `civil_date(clock.now())`; the ADR's meaning (a civil date from the zone and the injected clock, never UTC) is unchanged, so no ADR change. Without `tz` it is the zone the app runs in (on the desktop, the user's), which is what the two copies it replaces did; a hosted deployment will pass the user's zone. ARCHITECTURE.md §2.3 and EP-10 now name it.
- **The demo anchor goes through `civil_date(..., UTC)`** (agent): it is a build fact, deliberately UTC (ADR-0022, its docstring); routing it through the home keeps the check without an exception list.
- **Python aliasing: calls of `.today()`, `.utcnow()`, `.utcfromtimestamp()` on anything** (agent): the engine has fields named `today` (`target.today`, `params.today`, the wire's name), so the attribute itself cannot be refused; a call can. Stated limits in the script: a bound-method alias (`f = d.today; f()`), `getattr` by a computed name, and `datetime.now` through an alias of the class (a clock read, which the Clock port rule and review catch; it is not a UTC "today" by itself). Hardening against deliberate bypass is frozen (PROCESS.md §9).
- **Frontend: refuse the `Date` class in app code** (agent; EP-30): instead of more selectors for each alias shape, `no-restricted-globals` on `Date` in `src/` outside `src/platform/` (the clock adapter's future home, EP-10), so `const D = Date` and `make(() => Date)` fail too; `globalThis`/`window`/`self` `.Date` (and computed `['Date']`, and destructuring) by `no-restricted-properties`. A TypeScript type `Date` is not a value reference and passes (checked). This refuses `new Date(2026, 9, 25)` in app code, which S0009 accepted: no app code uses `Date` (inventory: 0 in `src/`), and ADR-0023 says dates are `Temporal.PlainDate` and "native `Date` is used for no calendar logic". S0009's must-pass case moved to `src/platform` (read from the resolved config: typed linting needs an existing file, and `src/platform/` has none yet) and to test files. `.Now` is refused on any object (Temporal's system clock, also under an alias); `parseFloat` and `Number.parseFloat` (money parsed as a float) with it.
- **INV-06 and INV-07 marked `enforced`** (agent; the rules unchanged; the precedent of S0049 for INV-02 and S0087 for INV-05): each has tests that run at push and in T1 for everything that exists; what is not built yet is named on the "Enforced by" line as planned with its row (the frontend `Money` brand BL-0226, the write path's written scale L3-05, the frontend `today` L3-10), as INV-02 names its frontend port. This records enforcement; it does not add or tighten an invariant. The owner may prefer them pending until the planned parts exist; it is in the report.
- **Cut, with rows** (agent; brief items 6 and 7): the frontend `Money` brand (BL-0226, M2, where the roadmap builds `src/domain` money) and the written-scale goldens on the write path (L3-05, M4; the write path is M1b, BL-0001). Not a deferral of an open row: BL-0006's other parts are built, and the new row carries what has nothing to guard yet.
- **The frontend's vitest suite is not moved west of UTC** (agent): it has no date code; Playwright already runs in Los Angeles (S0030), and the frontend's `today` arrives with L3-10.
- **Expected-output change** (PROCESS.md §8): `frontend/tests/unit/gates.test.ts` "accepts a date built from given parts" in app code is now refused there (the tightening above); the case stands in `src/platform` and test files. `backend/tests/platform/test_rebuild_job.py`'s `TODAY` was the code's own expression (EP-29); it is now the spec's date at an instant where Los Angeles and UTC differ.
- **Tests first** (run against `bbe24aee`'s source, an archive in the session scratchpad with the new and changed tests copied in): `test_check_money_dates.py` errors (no script); `tests/domain/test_dates.py` fails at import (no `app.domain.dates`); both `test_runs_west_of_utc.py` fail (the machine is UTC+5:30); `test_rebuild_job.py` fails 3 tests (the base's `astimezone()` sent the machine's date, 9 November here: the base was correct for the machine's zone, so this failure comes from the zone change, not from a UTC "today" in the base); the 18 new frontend cases failed on the base config. The check itself refused the base tree with 15 findings (5 dates in 3 files, 2 floats, 8 JSON decodes) before the fixes. Passing on the base, tagged `@regression-guard`: the new `DTZ`/`RUF032` cases in `test_gates.py`, `engine/tests/architecture/test_lint_bans.py`, and two frontend must-pass cases.
