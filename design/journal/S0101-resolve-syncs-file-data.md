# S0101: the undo syncs the data of each file it resolves over

## Brief
- Goal: close BL-0243. A journal becomes `.resolved` only when every file it names durably holds its pre bytes (a created file: absent), in its data as well as its entry. Today the restore syncs folders only before `.resolved`; a file an outside editor put back to its pre bytes in place, without a sync, can come back at the save's post bytes (or torn) after a power loss, under `.resolved`, with no journal to undo it. Then BL-0225 F1: the recover replay's outside edits become non-durable as the model's are, so the replay checks what Keep and the undo sync.
- The bytes it protects: the ledger files a journal names, after recovery or the rollback says "resolved" (a half-applied save with no journal is the loss).
- Implements: ADR-0012 (an amendment next to its ownership rule of 2026-11-08), spec `engine-jobs.md` §8.1 step 4, §6.4, §13 (file-system assumption reworded), the model `formal/tla/engine-jobs` (`SyncNamed` covers entries only; a file's own data sync), MAPPING.md.
- Capabilities: CAP-WS-RECOVER-FIRST, CAP-DATA-ENGINE-JOBS (no status change).
- Invariants touched: INV-01, INV-22, INV-32.
- Risk class / lane: High / full lane (ledger writes, recovery).
- Owner decision (owner, 2026-11-11, in session, answering the orchestrator's question): "Flush named files only (Recommended)". The option as put to the owner: "Recovery may open (read-only) and flush the data of each file the journal names, on the drive the journal records (ADR-0012's existing rule), before `.resolved`. It never writes, truncates or renames them. A file it cannot open or flush keeps the journal `.open` (fail closed)."
- Inventory, by behaviour (every place a journal record leaves `.open` for a final state, `grep` of `rename_excl(... State.<X>)` over `engine/src` and the record states of `core/journal.State`):
  1. `.open` → `.resolved`: only `restore.restore` (step 4). It serves recover-all's try (`recover_journal`, op `recover_try`), the save's rollback (`writer._rollback` → `restore`, after any failure past the `.open` rename, a failed close included, `closed=True`). "The undo" is this same function: there is no other undo path. **Changed.**
  2. `.open` → `.kept` (Keep, `recover_all.keep`): already `sync_file`s every named file that is there as a regular file, then its folders, before the rename (S0062, finding N1). **Unchanged; checked by the replay once F1 lands.**
  3. `.open` → `.closed` (the save's close, `writer`): every file it names holds bytes the save wrote itself through `create` (data synced before the swap) or the exclusive rename; a replaced file's old object was `sync_file`d at step 8.0 before its backup. Nothing to add.
  4. `.part` removal (the listing), `.closed` → `.open` (the rollback after a failed close): no file resting on the decision.
- Which files the new flush covers: each replaced file (a pre hash) that step 2 found at its pre bytes (`Verdict.AT_PRE`) and that is there. A file step 3 put back holds the restore's own bytes, written by `create` (data synced) and swapped or renamed in; a created file judged absent has nothing to flush; a taken created path never resolves. The flush is the port's `DirHandle.sync_file` through the folder's guarded handle (`Handles.at`: the path guard and the drive check of ADR-0012's 2026-11-08 amendment), which opens read-only with `O_NOFOLLOW | O_NONBLOCK`, refuses a link, a folder or a FIFO, and checks it opened the entry it `lstat`ed. Any error: `Failed(io_error)`, the journal `.open`, §11's `failed` row ("Finzytrack could not read or change <file>: <system answer>. Then press Retry."; `EROFS`: the read-only-drive row).
- Acceptance tests (new, must fail on the base): `test_S0101_*` in `engine/tests/ledger/test_restore.py`: a file put back to its pre bytes in place, unsynced, after a crashed save, then recovery: `.resolved` only over files durably at pre in every power-loss state; the same by an unsynced save by rename; the flush is ordered before the rename and goes through the guarded handle; an error at the flush keeps the journal `.open` (`Failed`); a link put at the file just before the flush is refused, nothing followed. The rollback's own case (an editor's unsynced revert during the rollback). The model: mutant `rs_no_file_sync` must break `ResolveDurable` (`NoTornLedgerAfterRecovery`) in a small world; the replay (`test_recover_conformance.py`) with non-durable outside edits, which fails on the base's restore.
- Expected doc impact: ADR-0012 amendment; spec §8.1 step 4, §13; MAPPING.md, HOW_TO_RUN.md (timings), the trace corpus regenerated; `engine/CLAUDE.md` if the replay's description changes; backlog BL-0243 done, BL-0225 F1 done or narrowed. No user docs (no new text; the existing `failed` row applies).
- Cost on a normal recovery: one `F_FULLFSYNC` per replaced file found at pre (a typical save names 1-12 files); measured in the hand-off.
- Open questions: none (the ownership question was settled with the owner first).
- Base commit: 5a5d4b55.

## Decisions
- **Simplification pass** (PROCESS.md "Designs checked by a formal model"; agent). One mechanism is added: the restore's flush (`restore._flush`), which serves "`.resolved` means every named file durably holds its pre bytes" (INV-22, INV-32). Can a policy forbid the case? No: the revert is another program's (an editor, `git checkout`, a sync client) and we cannot make it sync. Alternatives weighed: (a) flush every named file that is there, as Keep does: one rule shared with Keep, but an extra `F_FULLFSYNC` per file the restore put back (already synced by `create`), and its mutant on those files is equivalent, so the replay could not tell the code does what it says; rejected. (b) Re-hash after the flush to confirm the bytes: no gain, an editor can write again after the re-hash, and a write after our judgement is that program's own newer edit, not a loss of ours; rejected. (c) Flush in step 2 (at the judgement): a write between step 2 and step 4 would then be unflushed; the flush belongs right before the rename. Chosen: flush each replaced file found at pre, after the last folder sync, before the rename. The model mirrors exactly that: no other mechanism changes.
- **The flush's place** (agent): after step 3's last folder sync (the folders the save made removed, their parents synced) and before the `.resolved` rename; a try that stops (`created_path_taken` included) never flushes, since it never resolves.
- **The model** (agent): a folder sync (`SyncNamed`) now leaves `dpl`, what a file's data may fall back to after an unsynced in-place write; a file's own sync clears it (`S_Backup`, Keep, the new `RS_Flush`, a durable editor's save; a swap gives the file a new, synced object). `ud` (set only by the seeded bug `no_restore_temp_fsync`) became `dpl`. `RS_Flush` flushes `Flushed` (the record's replaced files not put back) and is skipped when that set is empty, as the code makes no `sync_file` then. Mutant `rs_no_file_sync` (breaks `NoTornLedgerAfterRecovery` in `S_fs_weak_recover`; its trace is BL-0243's exactly: R at 2, an unsynced revert to 1, a resolve with 2 still possible), witness `W_RevertFlushed`.
- **The editor may revert** (agent): `EdVals(f)` adds the file's initial bytes `V0` to the editor's own bytes. Without it the model's editor never writes pre bytes, which is why the model could not see BL-0243 even with a correct folder sync. Allowed in every world (a durable revert is a real case too); the S tier still takes 69 s.
- **`EditKept` counts a save's backup** (agent, from the first S-tier run): `S_fs_weak` then broke `ExternalEditNeverSilentlyLost`: the editor reverted R to its pre bytes after the save's backup, unsynced; the save's swap displaced that object, found it byte-identical to the pre bytes and removed it as ours. No byte is lost: the backup holds exactly those bytes (spec §6.4 "deleting it loses nothing", "Limit (same bytes)"). The property never had to say so before, since the editor never wrote pre bytes. The clause is narrow: R only, bytes equal to a save's backup; every mutant still breaks its property.
- **BL-0225 F1** (agent): S0100 found `EdDurable` TRUE in all six recover worlds, so F1's premise did not hold there. Decided by behaviour: a new recover world `S_recover_weak` (base `S_fs_weak_recover`, `EdDurable` FALSE) and the replay writes its outside edits unsynced (`MemFS.outside_write_unsynced`), so the fake holds what the model's `pl` says. After a try, an edit is checked across power-loss states only once a sync made it durable (`Replay.edit_durable`), as the model's `PowerLoss` forgets an unsynced one (§13: that program's loss). Two branches must be walked: "an outside revert left unsynced, flushed before the resolve" and "Keep over an outside edit left unsynced". Self-tests: a try without its flush is caught by the sync rule (`RS_Flush` in `SYNC_STEPS`) and, with that rule disabled, by the durable check alone; Keep without its syncs is caught (`KeptFilesDurable`).
- **Fidelity review of the model against the spec** (agent, one review, PROCESS.md "Designs checked by a formal model"). Spec to model: §8.1 step 4's flush is `RS_Flush`, its failure `IOFail` at `rs_fl` (in `RestPcs`); §13's "a folder sync covers entries only" is `SyncNamed` with `dpl`; every file-data sync of the code has its model step (the save's staging write `S_TempDone`/`S_TempSync`, the replaced file's `sync_file` `S_Backup`, the restore's `create` `RS_Write`, Keep's `sync_file` `Keep`, the flush `RS_Flush`; inventory by `grep sync_file\|fsync` over `engine/src/ledger_engine/ledger`: `writer.py:510`, `recover_all.py:398`, `restore._flush`, and `create`'s own sync; `mirror/publish.py`'s is the mirror model's). Model to spec: `dpl` is cleared only where the code syncs a file or replaces its object with a synced one of ours; `RS_Flush`'s set equals the code's (`Verdict.AT_PRE` with a pre hash = not put back, pre not absent). Vacuity: `W_RevertFlushed` is reached; all 24 witnesses and 29 mutants are as expected. **Found:** the rollback's flush is never reached over a revert of the save's own post bytes (scratch witnesses on `S_fs_weak`: `rs_fl` with an unsynced edit pending is reached, with the post bytes in `dpl` never; the save creates N before it swaps R, so a rollback after R's swap stops at `created_path_taken`, and a second save's pre bytes are not `V0`); `rs_no_file_sync` breaks nothing there. Stated in MAPPING.md §3 with the code test that covers it (`test_S0101_the_rollback_flushes_...`, where the created file comes after the replaced one); no world added (the owner's rule: later findings become tests or rows unless a High data issue, and the code is tested).
- **Probe on real volumes** (agent, S0089/S0090 lesson): HFS+, exFAT and FAT32 disk images in the scratchpad, attached with `-nobrowse`; the opt-in `test_a_save_its_crash_and_its_recovery_on_a_real_volume_without_the_swap` (now with a file found at pre and flushed) passes on all three. A remount cannot show what a power loss keeps (an unmount flushes everything), so the probe shows the read-only flush works there (`F_FULLFSYNC`, or the `fsync` fallback), not durability; durability is the fake's and the model's.
- **Cost** (agent, measured on APFS, `sync_file` of files just written in place, 15 runs): 1 file median 4.1 ms (max 13 ms); 12 files median 5.3 ms (max 56 ms). Only the rollback and recovery pay it.
- Pins moved with the regenerated corpus (agent): `scripts/tests/test_tla_traces.py`'s hash of the save, create and copy traces (changed on purpose: `RS_Flush`, `dpl`, the revert; still 217 rows); the save replay's `STOP_COUNTS` (`{"cut": 1}` to `{}`); the recover replay's regex for a swallowed I/O error (its first trace now fails at the folders' first sync, `rs_clean`, not `rs_w R`). The mirror-publish corpus regenerated: only the engine-jobs generator's recorded hash changed.
