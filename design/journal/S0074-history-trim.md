# S0074: the history trim

## Brief
- Goal: build spec `engine-jobs.md` §6.5's last rule, "The last 16 history records of each kind are kept per workspace; older ones are deleted" (BL-0169; owner, 2026-10-31: "We must prevent the history records from piling up."). Every landed save leaves a `.closed` record in `local/<key>/journal/` and a folder in `local/<key>/backups/`; nothing deletes them. At 54k entries in one file a backups folder is about 8.7 MB, so an unbounded history grows by that per save. 16 per kind is the owner's standing number; not changed here.
- **The bytes it protects** (PROCESS §3 step 2): this is a **delete path**, the first one in the app's own folders. It must never delete (1) an `.open` journal or any backup an `.open` journal names: they are the only copy of the bytes before a half-applied save, and recovery and the blocked screen read them; (2) anything outside `app_local_data/local/<key>/journal/` and `…/backups/`: the ledger folders and kept copies (`<file>.kept-<tag>`) are the user's files (INV-27, INV-30, INV-32); (3) the current save's own `.closed` record: §6.6 tells a dead save's outcome from it, so deleting it would turn "saved" into a false "not saved". What it may delete holds only history: backups of saves that landed (`.closed`), were put back (`.resolved`) or were kept as they are (`.kept`), files of development builds, and backups folders of saves that never wrote a journal.
- Implements: spec §6.5 (the trim rule), §6.1 step 9 (where it runs), §10, §15; the owner's requirement of 2026-10-31 (round 1, verifier F6: the brief cited INV-10, which is about memory, not disk); ADR-0067 (record kinds; dev-build files are not records, the trim may delete them), ADR-0068 D1 (the save in one engine, no load), ADR-0063/INV-32 (never touch what recovery needs), ADR-0064 (engine lock).
- Capabilities: `CAP-DATA-ENGINE-JOBS` (note; BL-0169 leaves its backlog list), `CAP-DATA-BACKUPS` (note: the fixed retention exists; the user-set count is `CAP-SET-BACKUP`, M10).
- Invariants touched: INV-27 and INV-30 (never inside a workspace folder), INV-32 (never what an `.open` journal needs), INV-22 (fails closed: anything not positively history is left).
- Risk class / lane: **High / full** (a new way to delete user data). Data-safety red team after the verifier (PROCESS §4).
- Base: `58814c3e`.

### The rules (decided in this brief, agent; the spec's rule as written)
1. **Which job:** the `save` job, in its own engine, right after the save landed and `committed` was sent (§6.1 step 9), before the final reply. Why there: (a) it holds the engine lock (the `save` op refuses without it), so no save of ours runs beside it and no engine of an earlier session is alive; (b) it ran no user code; (c) it runs once per landed save, so history can never grow past 16 per kind plus the current save, whatever the session length; the rebuild (runs plugins, background, may be dropped) and recover-all (only at boot and switch: a long session would pile up) do not give that bound. ~~The user has already been told "saved" when it starts, so it adds nothing to the wait.~~ Wrong (round 1, verifier F2): the sidecar answers from the final reply, so the trim is inside the user's wait (7 to 11 ms per save, Verifier section). A save that did not land runs no trim (its `.resolved` record is trimmed by the next landed save).
2. **Per workspace** = per registry key folder `local/<key>/`: the trim reads and deletes only in `local/<this save's key>/journal/` and `local/<this save's key>/backups/`. Records of the same workspace under an older key (forgotten and added again) are not trimmed; they stop growing when the key stops saving (honest limit).
3. **A save's history** is everything named after its tag `<session>-<job>` (compared case-folded): its journal entries `<tag>.<suffix>` and its backups folder `backups/<tag>`. The record is never decoded (no field of it is trusted to name what to delete); the backups folder belongs to the record of the same name, by the writer's construction (`journal._check`: `backup_dir`'s last component is the record's name; the writer puts it in the same key).
4. **Kinds** (each keeps its newest 16 on its own): `closed`, `resolved`, `kept` (one record state), `leftover` (only development-build files: `<tag>.done`, `<tag>.mismatch`, `<tag>.r4-attempt-<n>`; ADR-0067), `orphan` (a backups folder with no journal entry of its name: a save that stopped before its journal, or whose `.part` recover-all removed). Ordering: newest first by the entry's modification time (the record's, which renames do not change; an orphan's folder's), ties by name; the current save always counts as the newest of its kind. *(Round 1, verifier F1 and red team F1: an entry dated later than the current save's record counts as older than every other; Verifier section.)*
5. **Never touched** (a save's whole history is left, and it counts in no kind): the current save; any tag with an `.open` or `.part` entry **in any key's journal folder**; any tag a decodable `.open` record anywhere names as its backups folder; any tag with an entry of a suffix the trim does not know (a newer app's state, fails closed); any tag with two record states; any tag with an entry that is not a regular file (journal) or a folder that is not a real folder (backups); any tag whose entry could not be `stat`ed. Names that are not `<tag>.<suffix>` (journal) or `<tag>` (backups) are not ours and are never touched.
6. **Fail closed, never fail the save:** if `local/`, any key's journal folder, or this key's journal or backups folder cannot be listed, or any of them is not a real folder at its canonical path (a link, a moved folder: the path guard), the trim deletes nothing. An error while deleting one save's history leaves the rest of that save's history (the next trim tries again) and goes on to the next. No error of the trim reaches the save's outcome: the save already landed and the user was told "saved".
7. **Order of deletes, and crashes:** per save, the backups folder's files, then the folder, then its journal entries. No syncs: a power loss may bring back any subset of the deletes, which is again only history, and the next trim deletes it again. A crash or power loss mid-trim can never leave a half-deleted backups folder of an `.open` journal, because those are never touched (rule 5); the current `.closed` record was made durable before the trim began.
8. **`.kept` records:** nothing reads them for a decision (grep: `delete_kept` and `inspect` act only on `.open` records; §6.6 reads only the current job's record; no notice reads them). The kept copies themselves are files beside the ledger, named `<file>.kept-<tag>`, outside the trim's scope; deleting a `.kept` record does not touch them. Because kinds are counted apart, ordinary saves never push a `.kept` record out: only a 17th Keep in one workspace does. So no owner question: the spec already lists `.kept` as history.
9. **Port change:** `EntryStat` gains `mtime_ns` (lstat's `st_mtime_ns`); the memfs fake keeps a logical clock per inode, with `outside_mtime` for clock-skew tests.

- Acceptance tests (new; each must fail on `58814c3e`), `engine/tests/ledger/test_history_trim.py` over memfs unless noted:
  - 20 landed saves leave 16 `.closed` records and 16 backups folders, the newest 16;
  - kinds are counted apart (17 `.closed` + 3 `.kept` + 2 `.resolved`: only one `.closed` goes);
  - an `.open` journal of this key and its backups folder, older than everything, stay (must-not-pass); a `.part` likewise;
  - an `.open` in another key's journal folder whose tag (or decoded backups folder) matches a folder here: that folder stays (must-not-pass);
  - a journal folder of another key that cannot be listed: nothing deleted (must-not-pass);
  - a link at `local/<key>/backups` (or `journal`) to a folder holding history-shaped names: nothing deleted through it (must-not-pass, outside scope);
  - a backups folder holding a link or a subfolder: left, with its record (must-not-pass);
  - an unknown suffix `<tag>.verifying`, a non-file journal entry, two record states, an entry whose `stat` fails: that save's history stays (must-not-pass, unclassified);
  - foreign names (`notes.txt`) in either folder stay; kept copies and every byte outside `local/<key>/{journal,backups}` stay byte-identical;
  - development-build files: a `leftover` kind with 16 kept; orphans likewise;
  - the current save is kept even when its clock reads older than every other record (skew);
  - an I/O error at every effect of the trim: the save still answers `Saved`, nothing protected is touched, the next trim converges;
  - a crash at every effect of the trim: §6.6's outcome reads `closed`; protected entries intact;
  - a power loss after every effect: every state holds every protected entry and the current `.closed`, and a later trim converges to 16 per kind;
  - the pure selection (`ledger_engine.ledger.core.history`) under Hypothesis: never selects a protected save; keeps min(16, n) per kind; every selected save is older than every kept one of its kind;
  - the macOS adapter's `mtime_ns` equals `os.lstat` (`engine/tests/fs/test_darwin.py`); the fake's clock (`engine/tests/fakes/test_memfs.py`);
  - the save op's decision carries the trim's counts (`engine/tests/test_save_ops.py`, real APFS).
- Expected doc impact: spec §6.1 step 9, §6.5 (the rule's detail), §10 (a row), §14 (tests), §15 (limits: clock order, older keys, only after a landed save); `engine/CLAUDE.md` (the trim's module, the write-path list); ARCHITECTURE.md package map line; capability notes; backlog BL-0169 → done; roadmap line; the write-port architecture test lists the new module. ## Decisions
- The brief's rules 1-9 are the agent's decisions within spec §6.5 as written (agent). Two changed while building, both found by the new tests:
  - **No record is decoded for protection.** The brief had a readable `.open` record also protect "the backups folder it names". `journal._check` refuses any record whose `backup_dir` does not end in the record's own name, so that folder is always protected by the name already (pinned by `test_a_record_can_only_name_a_backups_folder_of_its_own_name`); the decode was dead weight and is gone (EP-30) (agent).
  - **One sync of `backups/` before any record goes.** The brief said "no syncs". The power-loss sweep showed that unsynced deletes in two folders can land apart, so a power loss could leave a trimmed save's backups folder without its record: an orphan that then waits for 16 others before it goes (up to 16 × 8.7 MB at 54k). One `durable_sync` of `backups/` per trim with something to delete (about 4.5 ms; inside the user's wait, round 1 F2) means a record never goes before its folder's removal is durable; the journal deletes stay unsynced (a record that comes back is history and the next trim deletes it). A failed sync leaves every record (agent).
- Modification time, not names, orders history: session and job ids are random (`uuid4`), so nothing else in a name or a record orders saves. `EntryStat.mtime_ns` (lstat) was added to the port; the current save is always the newest of its kind, so a clock set back can never cost the outcome of §6.6 (agent). Round 1 adds the wrong-date rule (Verifier section).
- The trim's counts ride on the save's decision inputs (`trimmed`, `trim_left`, `trim_skipped`; table `engine.save` version 4), content-free, so a trim that keeps failing will be visible once the decision log is written (BL-0154). No protocol message or schema changed (agent).
- Double guards kept on purpose: `local/`, the key's `journal/` and `backups/`, and each backups entry are checked to be real folders by `lstat` before `Handles.at`'s path guard checks them again (mutants H2, H3, H7 below are equivalent for that reason). On a delete path the second line costs one `stat` each (agent).
- Not escalated: trimming `.kept` records. Nothing reads them (`inspect`, `delete_kept` and `delete_created` act on `.open` records only; §6.6 reads only the current job's record); the kept copies are visible files beside the ledger, out of the trim's scope; kinds are counted apart, so only a 17th Keep in one workspace removes a `.kept` record (agent; spec §6.5 already lists `.kept` as history).
- Gates on the final tree: engine `ruff format --check`, `ruff check`, `pyright` (0 errors), pytest 8920 passed, 1 skipped, 1 xfailed; backend pytest 2125 passed, 24 xfailed, 1 failed: `tests/test_main.py::test_a_signal_at_any_line_of_the_start_never_skips_the_engines_close`, the known flake BL-0176 (passes alone, 2 passed; no backend file changed); `scripts/run_meta_tests.py` 836 OK; `check_invariants`, `check_capabilities`, `check_retired_terms` (0 refused; the spec names the development-build suffixes only through ADR-0067, since the check refuses them in current documents).
- Tests that fail on `58814c3e`: `test_history_trim.py` (import error: the module is new), the three memfs time tests, the macOS `mtime_ns` test, `test_save_ops.py`'s two changed or new tests (decision version 3, no `trimmed`): output in this session, 6 failed + the collection error. `test_a_save_that_does_not_land_trims_nothing` is a regression guard and passes on the base by design.

## Verifier
### Round 1 (verifier and data-safety red team; reports in the owner's private archive, `m1a/s0074-verifier-r1/`, `m1a/s0074-redteam-r1/`)
Verifier: 0 High, 2 Medium, 5 Low. Red team: 0 High, 1 Medium, 4 Low, 1 overflow (pre-existing). One fix round (orchestrator's triage); no second round (no High).
- **Verifier F1 + red team F1, Medium (one mechanism): fixed.** No test told date order from name order (M1, M2 survived), and raw dates let 16 records dated in the future collapse the history to the current save (red team A4). The triage proposed counting a later date as the current save's own (a clamp, ties by name). **Pushed back with evidence:** a simulation (session scratchpad `s0074-fix/sim.py`) and mutant O2 show the clamp gives exactly 7687fadc's result on A4: the clamped records tie with the current save, so they still outrank every earlier save, and each new save pushes out the one before it. The rule built instead: every entry on disk was written before the current save's record, so an entry dated later has a wrong date and counts as **older** than every entry dated at or before the record, in its own date order. It keeps the triage's aims (no collapse, the current save always stays) and is right in both one-move cases: a clock once ahead and then put right (the clock-ahead saves are the older ones and go first, one per save), and a clock set back once (the saves before it go first). The limit (spec §15): after a set-back, once the clock passes the old dates again, those saves count by their dates among the newer ones. Without a readable current `.closed` record, the plain date order holds (agent).
