# S0034: gate time limits are hang detectors from history, not budgets

## Brief
- Goal: the Stop hook stops failing open when its meta-tests run past a fixed timeout, and no T0 gate uses a fixed time number as a budget. (1) The Stop hook does not re-prove what is proven: after a green run it stores a key of the whole working tree (tracked and untracked, not ignored, hashed through a temporary index; the real index untouched) plus the Python version in the clone's git directory, and the same key next time is green at once (the `core.hooksPath` check still runs). (2) Each check's time limit is a hang detector relative to its own measured history: limit = K x the median of its last N green durations (K = 8 after verifier F2), with a floor, and no relative limit until it has a history; a check over its limit is stopped and reported red with the numbers; a check that did not finish never passes, and the hook never crashes. (3) A parallel meta-test runner, `scripts/run_meta_tests.py`, one process per test class (per module when it has module fixtures), that runs exactly the tests `unittest discover -s scripts/tests` runs and fails on any failure, error, import error, early exit or zero tests; used by the Stop hook, the pre-push hook and the T1 `repo-checks` job. (4) The harness's Stop timeout in `.claude/settings.json` becomes a backstop far above any normal run; the hook's own backstop fires first. (5) Pre-push, the same timing pattern without a green cache: each check runs through the timer from the pinned `run` function, a check far over its history is stopped and fails the push with the numbers, slowness alone never fails, and the hook ends with a report of each check's time against its usual time and the total. The "<= 2 min" header and PROCESS.md §6's pre-push budget become the reported-baseline wording. The 30 s pre-commit ceiling is the owner's and does not change.
- Implements: owner direction of 2026-10-26 (Decisions, verbatim); PROCESS.md §6 "Thresholds catch accidents"; IMP-0005; ADR-0060 (the local hooks are the per-push gate).
- Capabilities: none (process tooling).
- Invariants touched: none changed. INV-23 and INV-24 bind the tests (scratch repositories and temporary folders only; nothing private in timing files, which live under the git directory, never in the tree).
- Risk class / lane: Medium / light (tooling; no ledger or user data). One verifier round unless a High finding.
- Acceptance tests: `scripts/tests/test_gate_timer.py` (new: limit rule, history only from greens, hang stops the process group and reports the numbers, a check that cannot start or dies from a signal fails, the CLI exits 0 only for a passed check, the report); `scripts/tests/test_run_meta_tests.py` (new: same IDs as unittest's own command line on the real suite and on fixtures, every failure kind fails, early exit, drift between discovery and run, no tests); `scripts/tests/test_claude_hooks.py` (extended: green cache hit and miss on tracked, untracked, deleted and ignored files, the real index untouched, never stored after a failure or a hang, a crash is red, the backstop below the settings timeout); `scripts/tests/test_hook_pins.py` (the new `run` definition pinned, its shape rules unchanged otherwise, the canary line); `scripts/tests/test_check_invariants.py` (the pre-push marker for `scripts/tests/`).
- Expected doc impact: PROCESS.md §6 (T0 pre-push / Stop hook row and budget, "Thresholds catch accidents"); `IMPROVEMENTS.md` IMP-0027 (process change, with the owner's approval quoted); `.claude/skills/slice/SKILL.md` gate command; the pre-push header; this journal. No ADR: the owner approved the design in session; the IMP entry records it.
- Open questions: none (design approved by the owner in session, 2026-10-26).

## Decisions
- Owner direction, 2026-10-26, verbatim: "Yes, do the stop-hook timeout fix.. but can we do something more intellingent that just bumping up one arbitrarily small number to an arbitrarily higher number? I had discussed this failure mode with you before: An arbitrary budget, especially for things like test timings, inevitably gets exceeded as the development continues and more tests are added. The solution isn't to just bump up the numbers, because they'll eventually be exceeded again."
- Owner approval of the design (items 1-5 of the brief), 2026-10-26, verbatim: "Go ahead with 1–4 for the stop hook and apply the same pattern to the pre-push as well."
- Diagnosis (with the owner, before this slice): `.claude/hooks/stop_checks.py` ran `unittest discover` under `timeout=110`; the 543-test suite takes about 95 s unloaded and 160 s under load, so `subprocess.TimeoutExpired` escaped uncaught, Claude Code treats a crashed Stop hook as non-blocking, and the invariant, capability and privacy checks after it never ran. The harness gave the whole hook 120 s for three checks of up to 110 s each. Measured on the base commit 8434091d (this machine, load average 12-25 on 14 cores): serial meta-tests 98 s, the Stop hook 96 s, the full pre-push hook 161 s (its header says "<= 2 min").
- Hang detector numbers (agent; K raised from 3 to 8 after verifier F2, next line): K = 8, N = 5, at least 3 green runs before a limit applies, a 60 s floor. Hang detection only needs a finite limit; a too-high limit costs only waiting time before a hang is reported, a too-low one fails a healthy check. Back-to-back parallel meta-test runs on this machine took 40, 60, 74 and 81 s (load average 20 to 120), a swing of 2x for one run at a time. The verifier then measured concurrent runs (the runner uses every CPU, so runs at once slow down about linearly): 37 and 44 s alone, 92 s for two at once, 146 s for three at once, 3.7x the solo median, over K = 3. Several agent sessions share this machine (up to 7 seen), so K = 8 covers about as many concurrent CPU-bound runs; the cost is only that a real hang of the meta-tests is reported after about 5 minutes instead of 2. A check stopped as hung tells how to start its history over (delete the times file); doing so only removes the limit until the check has passed 3 times. The numbers are constants in `scripts/gate_timer.py`, tested by `test_gate_timer.Limits`.
- Not budgets either: the Stop hook's own backstop of 1500 s (the harness's Stop timeout is 1800 s; a hook the harness kills fails open, so the hook's own limit must fire first, and `test_the_hook_backstop_is_below_the_harness_timeout` pins the order) and 120 s on single git plumbing calls (`git status`, `git add -A` in a temporary index), which do not grow with the test suites.
- The meta-test runner splits by test class, not by module (agent): per module the wall time was 72 s, bounded by `test_push_gate` (50 tests in one process); per class 40-60 s. A module with `setUpModule`, `tearDownModule` or `load_tests` stays whole, so module fixtures behave as under `unittest discover`. Units start longest first, from their last times (kept in the git directory; a missing or forged file changes only the order). The remaining long pole is one test that privacy-scans the whole history (BL-0080).
- What the runner checks so a parallel run cannot hide a test (agent): the parent discovers with unittest's own loader and the `python3 -m unittest` import path (the current folder, not `scripts/`), each unit's process discovers its module the same way and reports the IDs it started, and the run fails unless every unit reported and the reported IDs equal the discovered ones. `test_run_meta_tests.test_the_real_suite` compares the runner's IDs with those of unittest's own command line (`unittest.main` with `discover -s scripts/tests`, a runner that lists instead of running). Stricter than unittest in one case: a test that ends its process with status 0 passes `unittest discover` and fails the runner.
- The pre-push report runs before the final "tree unchanged" check (agent), so the S0031 rule that the tree check is the last check holds as it was; the report therefore leaves out that one check's time (about 1 s).
- Abuse (agent): the green-cache key file and the times files live in the clone's git directory and agents can write them. A forged key makes the Stop hook green without running its checks, but the Stop hook is a convenience gate an agent could already end-run; the pre-push hook is the authoritative gate and has no cache, so nothing reaches `origin` on a forged key. A forged times file can raise a limit (weaker hang detection: a hung check runs longer before it is stopped) or lower it (a false failure); it can never make a failing check pass, because the timer's exit status comes only from the check's own exit status. The timer itself is now on the pre-push path, so a timer that passed everything would pass every check: the canary line after the pinned `run` fails the push when the timer passes `false`, the pin's shape rules require the canary right after `run`, and the Stop hook runs the same canary. A deliberate change to the timer that special-cases the canary is visible in review like any hook change (`test_hook_pins` docstring); this is not a sandbox.
- The privacy scan's denylist lives outside the repository, so a cached green tree is not re-scanned when the denylist changes (agent). The pre-push hook scans every tracked file at each push, so a new denylist entry still blocks the push.
- Observed, not changed (outside this slice): during the slice this clone's `core.hooksPath` changed from `.githooks` to the absolute path of the same folder (the git config file's time matches another session creating a Claude Code worktree under `.claude/worktrees/`). The hooks still run, but the Stop hook and the session-start hook report "not '.githooks'", so every Stop hook in this clone is red until the owner sets it back. Reported to the owner; agents may not change it.

## Verifier
- Round 1, head bb94ae40: pass with findings (no High). Attacks: 10 (same tests as unittest, concurrent runs, mutants on the timer, the Stop hook and the runner, the cache key against what checks read and against HEAD, backstop arithmetic, the pre-push canary and run IDs, Ctrl-C, bad CLI input and corrupt history). Tests reviewed against the brief.
- F1 Medium: no test that the backstop wins over a longer history limit (a mutant applying the backstop only without history survived). Fixed: `test_the_backstop_wins_over_a_longer_history_limit`.
- F2 Medium: K = 3 trips on ordinary concurrent runs: the parallel runner uses every CPU, and three runs at once took 3.7x the solo median. Fixed: K = 8 (Decisions; PROCESS.md §6 and IMP-0027 updated).
- F3 Low: the cache key ignored which files are tracked, so untracking a file that `git grep` reads (check_capabilities.py) stayed green. Fixed: the key includes a hash of `git ls-files` from the real index (read only); `test_a_file_that_stops_being_tracked_is_checked_again`. Staging a content change alone still does not re-run (`test_staging_a_content_change_alone_is_not_a_new_tree`).
- F4 Low: the key re-check after the run ran outside the backstop. Fixed: every git call in `tree_key` is capped by the time left, and no key is stored past it; `test_the_key_check_after_the_run_stays_inside_the_backstop`.
- F5 Low: surviving mutants (`read-tree --empty`, `except Exception`, wrong report numbers). Fixed with `test_a_tracked_file_that_matches_gitignore_is_part_of_the_key`, `test_an_interrupt_is_red_not_a_crash`, and exact report lines and total in `test_report_lists_this_run_and_the_total`; the report's total now says "no usual yet" when no check has one.
- D1 Low: "one process per module" in the brief, the pre-push comment and the ci.yml step name; corrected to per test class.
- No fresh round: tooling with no ledger or user data, no High fix (PROCESS.md §3 step 5, ADR-0058).

## Retro
- What the verifier found: one real design gap (K too tight once the meta-tests use every CPU; my measurements ran one runner at a time while other sessions loaded the machine, which hid it) and two cache edges (trackedness, the backstop after the run). A cheaper gate could have found F2: measuring two or three runs at once is the obvious test of a limit derived from solo runs.
- Self-mutation before hand-off found a real divergence in the runner (it imported `gate_timer` under its own name), so the planning step paid for itself.
- Where time went: baseline and after measurements (about 15 minutes of wall time on a loaded machine), two mutation runs (about 20 minutes), the verifier (15 minutes).
- Orientation gap: `check_invariants.PUSHED_TEST_ROOTS` reads the pre-push hook's text for `discover -s scripts/tests`; changing the command broke it until the marker followed. It is not in the brief's doc impact; found by its own meta-test.
- Outside the slice, for the owner: this clone's `core.hooksPath` became an absolute path during the session (Decisions), so every Stop hook here is red until it is set back to `.githooks`.
- Process cost: one implementer pass, one verifier round; two commits (the verifier's head is the landed commit's parent, PROCESS.md §3 step 7).
