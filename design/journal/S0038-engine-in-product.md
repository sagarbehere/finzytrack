# S0038: The ledger engine in the product (BL-0083)

## Brief
- Goal: the engine runs wherever the main sidecar runs. The composition root (`app.main`) builds the `EngineClient` and starts the engine at boot on a thread, in parallel with binding the port and printing `FT_READY`; a missing or failing engine is a reported state (a structured event on the sidecar's stderr and a held `EngineBoot` state), never a crash, and the sidecar keeps answering. The engine is closed when the sidecar exits (normal exit and SIGTERM). The engine's stderr is forwarded line by line, through a callback the client takes, as structured events. `shell/sidecar/build_sidecar.py` installs the engine's locked runtime closure and its wheel into `build/sidecar/engine/site-packages/`, beside (not inside) the interpreter's own site-packages that holds the main sidecar (ADR-0056: one interpreter, two separate site-packages). The packaged engine command runs that one interpreter as `python -I -S -B -c <bootstrap> <engine site>`: `-S` keeps the interpreter's own site-packages (the main sidecar's) off the engine's path, the bootstrap adds only the engine's site, and the main sidecar's path never contains the engine's site (ADR-0054 licence separation, both directions). The build verifies the finished tree by running the package's own self-check, the packaged `--smoke-test` proves a real handshake and ping with the packaged engine and the separation, on each OS of the manual packaged run; the acceptance harness starts a real engine per worker (from `engine/.venv`) and refuses a run whose engine did not start.
- Implements: ADR-0054 decisions 1, 4, 5 (the two processes in the product; supervision at boot; the licence separation in the bundle), ADR-0056 (one PBS interpreter, two site-packages, bundle resources), ADR-0061 (macOS first; the three-OS packaged smoke run stays, so the engine must start in the packaged build on Linux and Windows too: written portably, proven only by the owner's manual CI run), ARCHITECTURE.md §2.0, §5, §6A (see open question 1), §9.7, §11; EP-07, EP-13, EP-29, EP-30.
- Capabilities: none changes status (no user-visible behaviour; CAP-DESK-INSTALLERS stays planned for M11).

## Decisions
- **The packaged engine command is `python -I -S -B -c <bootstrap> <engine site>`** (agent; ADR-0056 says one interpreter, two site-packages, and leaves the mechanism open). `-S` skips `site`, so the interpreter's own site-packages (the main sidecar's) are never on the engine's path; the bootstrap (`site.addsitedir(<engine site>)`, then `runpy.run_module('ledger_engine', run_name='__main__', alter_sys=True)`) adds only the engine's site and still processes its `.pth` files. `-I` keeps `PYTHONPATH`, the user site and the cwd out; `-B` because the bundle is read-only and precompiled. Spiked on the PBS tree before writing tests: handshake and ping answered, `sys.path` = stdlib + engine site. Rejected: (a) a venv per process (`pyvenv.cfg` names its base interpreter by absolute path, so it is not relocatable inside an app bundle); (b) a `._pth` file (applies to the whole interpreter, so it would also cut the main sidecar's path; per process only with a copied executable); (c) `PYTHONPATH` (dropped by `-I`, and `engine_env` drops `PYTHON*` on purpose); (d) the engine closure inside the interpreter's own site-packages (the licence separation of ADR-0054 decision 5 would hold only by import discipline, not by construction, EP-30).
- **Where the main sidecar finds the engine** (agent): with no `--engine-venv`, the composition root uses the packaged layout around the running interpreter (`<sys.prefix>/../engine/site-packages`, `sys.executable`), so the shell (M2's supervisor) passes nothing new; `--engine-venv DIR` is for development, tests and the acceptance harness. A missing layout is `engine.start_failed`, not a crash. `build_sidecar.ENGINE_SITE` and `engine_client.ENGINE_SITE_PARTS` are kept equal by a meta-test, which reads the main side's constant by AST (the build script stays stdlib-only and never imports `app`).
- **Parallel start and shutdown** (agent): `EngineBoot.start_in_background()` runs `EngineClient.start()` on a daemon thread before the bind, so `FT_READY` never waits for the engine (tested with a stand-in that delays the real engine by 3 s). The first start's outcome is a state (`EngineStarting` / `EngineReady` / `EngineDown`) for the future `/api/boot` and `/health`, registered in `state_registry` (INV-11). `main` installs a SIGTERM handler that leaves `serve_forever`; the `finally` ignores further SIGTERMs, closes the engine (bounded by `RestartPolicy.close_timeout`) and logs `engine.closed`. The engine's own watchdog and stdin EOF remain the backstop for a killed sidecar.
- **The log** (agent; open question 1): ARCHITECTURE §6A's log (structlog, event registry, redaction, the file) is its own slice, now BL-0088 (M1a, before the first engine operation that reads a ledger). Building a stdlib stand-in of it here would fork §6A's library decision. This slice writes its four events (`engine.ready`, `engine.start_failed`, `engine.stderr`, `engine.closed`) as JSON lines in §6A's line shape on the sidecar's stderr (`app.platform.adapters.stderr_log`), which the sidecar does not persist; the engine holds no ledger yet, so `engine.stderr` carries no ledger text. `EngineClient` takes `on_stderr` (an injected callback, L11-03's direction); a callback that raises is dropped for that engine's run and the tail goes on.
- **Windows** (agent; ADR-0061: written portably, proven only by the manual run): the engine is spawned with `CREATE_NO_WINDOW` (a console program started by a windowless sidecar would otherwise open a console). S0035 built no Job Object: it belongs to the shell's sidecar supervisor (roadmap M2, "the real sidecar supervisor"), which does not exist yet; the engine inherits the sidecar's job once it does. Until then the engine ends on stdin EOF when the sidecar dies on Windows. ARCHITECTURE §2.0, §5 and the engine server's docstring said the Job Object "ends" the engine today; corrected.
- **The build checks the finished tree** (agent; EP-29, EP-30): each site-packages must hold exactly its own locked closure plus its own project (`uv export --frozen --no-dev` names), and neither may hold the other side's top-level packages; then `python -I -B -m app.selfcheck` must show a real handshake and ping, no engine package on the main side and no main-side site on the engine's path (and the reverse). The packaged `--smoke-test` judges the same report again inside the installed app, so the separation is proven on each OS of the manual packaged run, and `packaged.yml` adds a must-not-pass run with `sidecar/engine` moved away on each OS. PBS 20261009's Windows and Linux archives were listed: their site-packages hold only `pip` (trimmed) and `README.txt`, so the exact-closure check holds there too.
- **The harness** (agent): `backend_argv` passes `--engine-venv <repo>/engine/.venv`; after the handshake the launcher waits (at most 60 s, above `RestartPolicy.longest_start`) for the sidecar's `engine.ready` event in its `sidecar.log` and refuses on `engine.start_failed`, a dead sidecar, or no verdict. The `FT_HARNESS_READY` keys are unchanged (the frontend's `policy.ts` checks them exactly).
- **Local proof on macOS** (agent): `python3 shell/package_app.py` built `Finzytrack.app`; `codesign --verify --deep --strict` passed; `shell/smoke_packaged.py` gave `FT_SMOKE_OK` with `"beancount":"3.2.0"` and the engine site inside `Contents/Resources/sidecar/engine/site-packages`; the two must-not-pass runs refused as expected (`the bundled engine failed: start_failed: handshake: crashed: the engine exited with code 1`; `cannot start the bundled interpreter`). Linux and Windows are proven only by the owner's manual `packaged.yml` run (ADR-0061); not run in this slice.
