# S0153: The AppImage's engine failure made visible (phase 1: measure), then fixed (phase 2)

## Brief
- Goal: the next packaged run shows **why** the AppImage's engine-view probe fails (BL-0263; roadmap item 8c, M1b). Today `app.selfcheck` reports only the exception's name ("engine view: CalledProcessError"). On failure the probe now also reports its exit code, the last 4000 characters of its stderr and stdout, its argv, its working folder and the environment it runs under (it sets none of its own: it inherits the parent's; the variables that steer Python, the loader and the AppImage are listed), with the home folder written as `~`. All on one line, after the old text, so the smoke line stays one line and the known reason still matches. **Phase 2 (the fix)** follows after the orchestrator runs `packaged.yml` and hands over the log; this slice fixes nothing.
- Implements: ADR-0056 (the packaged layout), ADR-0061 decision 4b and its amendment of 2026-11-14 (Linux fixme due M1b); spec `shell/src-tauri/src/smoke.rs` (unchanged: it passes the engine's error through verbatim).
- Capabilities: CAP-DESK-INSTALLERS (planned, M11; no status change).
- Invariants touched: INV-23 (nothing private in the repo: tests build home paths at run time; the report masks the home folder), INV-24 (the self-check reads nothing outside the package; the environment is read, never written).
- Risk class / lane: Low / light. Shell and packaging diagnostics: the tooling or product-diagnostic row of the review budget (verifier only, one round, the stop rule).
- The bytes it protects: none; a diagnostic, advisory. No write path, so EP-30's policy question does not arise.
- Which real setup needs this, and can a policy forbid the rest? The default AppImage, the Linux format users run as shipped (ADR-0056); not a rare setup.
- Has this mechanism or its family needed two or more fix rounds before? The packaged smoke check's family: S0112 (the M1a exit runs found this failure and BL-0264) and S0114 (the Windows `main_sites` false positive, the narrowed fixme). One fix each, not two on one mechanism.
- Acceptance tests (new, fail on base): `backend/tests/test_selfcheck.py`: a failing view probe reports its exit code and stderr on one line after the old text; the stderr and stdout are cut to their last 4000 characters; the home folder is masked in every field; the environment listing keeps the Python, loader and AppImage variables and nothing else. `scripts/tests/test_smoke_packaged.py`: the known reason followed by the new detail still counts as expected, and a different failure carrying the same kind of detail does not (regression guards: `smoke_packaged.py`'s matching is unchanged).
- Expected doc impact: `app.selfcheck`'s docstring; ARCHITECTURE.md §5 Packaging (the known reason is the start of the reason, its detail follows); BL-0263's row (first step done). No user docs, no ADR (no decision beyond the backlog row's own "first step").
- Open questions: none for the owner.

**What is known before measuring** (read from the code, not run on the runner): the run at 23b8b5d6 failed in the view probe, not in the start: `report()` gives the start's error first (`error or view_error`), so the AppImage's engine **did** handshake and answer a ping. The two processes use the same interpreter, flags, site and working folder; they differ in the environment. The engine's start gets `engine_env` (the parent's environment without `FT_*` and `PYTHON*`, with `PYTHONHASHSEED=0`); the view probe inherits the parent's environment unchanged. An AppImage launcher that sets a `PYTHON*` variable (such as `PYTHONHOME` or `PYTHONPATH`) breaks a child run without `-E`, as the view probe is, and not the engine. That is the leading hypothesis for phase 2, to be confirmed by the log, not assumed.

## Decisions
- `smoke_packaged.py --expect-fail` already matches by containment (`REASON in reason`), not exact equality, so the known reason followed by the detail still matches; the mechanism is not changed (the orchestrator's instruction). Its limit: a detail that itself contained the whole known reason would also match. The detail is the view probe's own output, which never prints the shell's text "the bundled engine failed: …", so this is recorded, not guarded. Matching on the start of the reason would be stricter; not done, to keep the mechanism unchanged in a measuring slice (agent, 2026-11-26).
- The environment is listed by name prefix (`PYTHON`, `FT_`, `LD_`, `DYLD_`, `APPIMAGE`, `APPDIR`, `ARGV0`, `OWD`), not in full: the view probe sets nothing of its own, and these are the variables that can change how the interpreter or the loader starts, or that the AppImage launcher sets. A full environment would print unrelated values on a user's machine (agent, 2026-11-26).
- No separate AppImage-runtime probe in the workflow: running the bundled interpreter inside the mounted image by hand (`--appimage-mount`) bypasses the launcher, so its environment is not the one that fails, and the job would have to manage a background mount. The self-check's report comes from the failing process itself, under the launcher's environment, which is the measurement phase 2 needs (agent, 2026-11-26).

### Phase 2 decisions
- The detail's `env` is now the environment the probe ran under (`engine_env(os.environ)`), not the parent's, filtered by the same prefixes: the report states what the failing process saw. So a parent `PYTHON*` variable no longer appears there and `PYTHONHASHSEED=0` does (V1-3's test asserts exactly that). The parent's dropped variables are not listed: they cannot affect the probe now (agent, 2026-11-26).
- `--expect-fail` stays: the must-not-pass runs of all three OSes use it, and the `known_failure` matrix key and its `known=()` plumbing stay for a future fixme OS (`test_ci_workflows.py` holds every OS to stating one, empty for strict). Only Linux's value is emptied (agent, 2026-11-26).
- V1-1: masking matches each spelling (as given, `os.path.realpath`, and on Windows both slashes, case-insensitive) with one regex, longest first. Stated limits in `mask_home`'s docstring: Windows 8.3 short names and macOS's firmlinked spelling (under the system's data volume) are not masked (not cheap: the first needs `GetShortPathNameW`, the second a list of firmlinks); on macOS a differently-cased spelling is not masked (the default volume ignores case, but the probe's paths come from the interpreter, spelled as given); a home that is the start of a longer name is masked there too, which hides more, never less (agent, 2026-11-26).
- The privacy scan (INV-23) refused the first commit: home-shaped literals in a docstring and tests, and secret-keyword names with literal values. The paths are now built at run time (`ntpath.join`, `posixpath.join`) and the docstring describes the limits in words; the two fixture lines whose names hold SECRET and PASSWORD carry the scanner's own per-line `privacy-scan: allow secret-entropy` marker, their values being fakes (`x3x`, `x4x`) (agent, 2026-11-26).
- `_is_root` also treats a bare drive (`C:`, `C:\`) as a root, so a home of a drive is never masked into nonsense (agent, 2026-11-26).
