# S0063: The save job end to end

## Brief
- Goal: BL-0151's slice 4 (`design/specs/engine-jobs.md` §6.1 steps 1-7 and 9-11 around S0060's `writer.durable_commit`, §6.6, §11's save rows, §15; ADR-0008 steps 4-6, ADR-0012, ADR-0013, ADR-0062 decision 2, ADR-0064). A confirmed save becomes one engine job that checks before it writes and tells the truth after: the R4-first check, legacy-lock detection, the ledger-set locks, the gate on the disk and the records, the commit's load, the re-check against both the plan and the bytes the load parsed, the commit point, the durable order, "saved", and the outcome read from disk after an engine death.
- Base: 7a8566c8 (pushed, tree clean).
- **What it builds:**
  - Engine, `ledger_engine.ledger.save` (effects through `fs.port`, the `Locks` port and a new legacy-lock port): `run(plan, ...)`: step 1 the records of this workspace (`.open`, `.closed`, `.mismatch` in any `local/*/journal/`, matched by registry key or lineage, §6.5) re-read from disk; an owed R4 refuses with `WRITES_PAUSED {check_pending}` until R4 exists (BL-0152; S0060's plan for this slice); step 2 every legacy `.write.lock` the plan names, deduplicated by `path_key`, tried once each without waiting as portalocker 3.2.0 makes it (ADR-0062 decisions 2 and 5; see Decisions: `flock` directly, portalocker the tests' holder): free is held to the end, absent goes on, held or any error refuses `LEGACY_APP_SAVING`; step 3 the ledger-set locks of every file of the plan's ledger set, the files the save writes and the absent paths, in `path_key` order, waiting (progress `waiting_for_files` only when a lock is not free at once); step 4 the gate under the locks (the disk's fingerprint equals the plan's, the published mirror's equals the plan's, the records again); step 5 the overlay load of the candidate (`overlay.load`); step 6 the re-check: the disk's fingerprint equals the plan's **and** the disk equals what the load parsed (`Loaded.fingerprint` with each candidate file at its pre state); step 7 `gate()`; step 8 `durable_commit`; step 9 `committed()`; step 10 the publish's seam (BL-0113); step 11 the locks released. Python's garbage collector is paused for the job.
  - Engine, the outcome after a death (§6.6): `save.outcome(...)`: the journal folder `durable_sync`ed, then the job's record state read (`.closed` or later, `.resolved`, `.open`, `.part`, none) and, with no record or a `.part`, every target hashed again against its pre bytes.
  - Engine protocol: ops `save` (runs user code; gate and committed events) and `save_outcome` (parse-only), both `needs_engine_lock`; the schema regenerated; the sidecar's strict decoders and contract tests follow.
  - Pure: `ledger.core.ledger_set.decode` (the strict inverse of `encode`, so the plan's fingerprint crosses the protocol), the re-check's rule as a pure function.
  - `writer.Unfinished` carries the restore's stop cause, so the sidecar knows when the rollback stopped at `created_path_taken`.
  - Sidecar, `app.platform.engine_jobs.save`: the save job's spec and work; the pure §6.6 decision `save_outcome`; the mapping of every engine answer to a registry error with §11's text; session ids that never differ only in case.
  - Queue table and scheduler: a running save whose engine dies is not lost: the job asks for a fresh engine and reads its outcome from disk (as recover-all goes on per journal, S0062); when no engine can be had, the answer is `CHANGE_OUTCOME_UNKNOWN` past a gate the engine sent, `ENGINE_STOPPED` before it (nothing was written).
  - Registry: `LEDGER_EXTERNALLY_CHANGED`, `WRITES_PAUSED {unfinished_save | check_pending | check_failed}`, `LEGACY_APP_SAVING`, and one code for a save that did not happen, `CHANGE_NOT_SAVED {reason, path, folder, acl_entry, unchanged}`, worded by its reason (the writer's refusals `hard_linked`, `locked`, `not_a_file`, `permission`, `volume_no_swap`, an I/O error, an engine death found "not saved"); `CHANGE_OUTCOME_UNKNOWN` stays only for "no engine could read the outcome".
  - Measurement: `engine/scripts/measure_save.py` on the demo generator's 54k ledger in scratch, on real APFS: the whole save (gate, load, re-check, durable order) and the cost of S0061's additions (staging rename, temp-entry syncs, `sync_file` per replaced file, the restore's syncs); numbers into BL-0112.
- **The step rule** (written before coding):
  - Every port operation may raise `OSError`; the engine may die at any effect; Cancel may end the engine before the commit point. Steps 1-7 write nothing in a ledger folder, the journal or the backups (only lock files in `app_local_data/locks/`, which are never deleted); every refusal there is `NotSaved`-like with "unchanged" only after a re-hash (§11's rule). After step 7 only `durable_commit` writes, with its own step rule (S0060, S0061).
  - What each answer claims: "saved" only from `Landed` (the closed record durable) or, after a death, from a record found `.closed` or later after the journal folder's sync; "not saved" only from `NotSaved`, `.resolved`, a `.part` or no record; "unchanged" only after every target hashed equal to its pre bytes; "unfinished" from `Unfinished` or an `.open` record, with Reopen, and after `created_path_taken` a Reopen text that promises no undo.
  - Locks and legacy locks are released on every path out (a `finally`), the legacy lock after the ledger-set locks.
- Implements: spec §6.1 steps 1-7 and 9-11 (step 1 as the records check, R4 itself BL-0152; step 10 as a seam, BL-0113), §6.5 (records matched by key or lineage), §6.6, §11 (the save's rows), §15 (lines below); ADR-0008 steps 4-6 and its R4 amendment, ADR-0012 Q29 (locks), ADR-0013 (re-check under the lock), ADR-0062 decisions 2 and 5, ADR-0064 decisions 3 and 7.

## Decisions
- **The save's steps 1-7 and 9-11 run in the engine; the sidecar only asks and maps the answer** (agent; spec §6.1 "Steps 2-11 run in one fresh engine"; S0062's rule that the sidecar never reads a journal or a ledger file): one `save` op runs the whole job (`ledger.save.run`), with the gate's `gate`/`proceed` and `committed` events (protocol version 2 as built in S0057). Its plan arrives as plain data: the changes (each file's whole new text), the plan's fingerprint as its canonical encoding (`ledger_set.decode`, the strict inverse of `encode`, added), the published mirror's fingerprint digest, the legacy-lock paths and the app's folder (`app_local_data`, which must be the engine lock's folder, as for recover-all's ops).
- **Step 1 is the records check until R4 exists** (agent, as S0060's split planned it: "until it lands, an owed R4 refuses with `WRITES_PAUSED {check_pending}`"): every landed save is therefore followed by a refused save until BL-0152; nothing in the product saves yet. Step 1 runs before any lock; step 4 reads the records again under the locks (a record written while the save waited for a lock is seen: tested).
- **Records matched by key or lineage, fail closed** (agent; §6.5): a gating record (`.open`, `.closed`, `.mismatch`) in this key's folder is this workspace's; elsewhere it is decoded and matched by registry key or lineage; one that cannot be read counts as this workspace's, and a journal folder that cannot be listed refuses as `unfinished_save` (it may hold an `.open` record). The owner's bar: a block the user can clear, nothing lost.
- **The re-check** (spec §6.1 step 6, the owner's TLC run `L_save_deep`): the disk equals the plan's fingerprint and `ledger_set.as_before(Loaded.fingerprint, pre)`: the load's own record with each file the save writes put back at its pre state (and a plain-path include of a file the save creates matching nothing), because the load parsed the candidate's bytes for those files and the disk's for every other. Both directions tested, and a third: an include the change drops, edited during the load, refuses too (the plan's half; mutant `recheck_plan_off` showed it untested).
- **The legacy lock: `flock` as portalocker 3.2.0 calls it on POSIX, with portalocker as a test-only dependency** (agent, interim; deviation from ADR-0062's rejected alternative, escalated: `design/inbox/20261030-legacy-lock-primitive.md`, blocks nothing). Adding portalocker 3.2.0 to the engine's runtime brought pywin32 on Windows, which the licence gate cannot check on a Mac (`check-licences: runtime packages not installed in engine/.venv: pywin32`); changing the gate would loosen it, which is the owner's. The adapter makes the same call (read from portalocker 3.2.0's `PosixLocker`) and the tests prove it against a second process that holds the lock with portalocker 3.2.0, exclusive and shared both seen. One function changes if the owner picks option 1. The product names no legacy lock until M3 (BL-0026).
- **The ledger-set locks wait** (`Locks.lock`, a blocking `flock`; spec §6.1 step 3): `waiting_for_files` is sent only when a lock is not free at once; Cancel ends the engine and with it the wait.
- **A save whose engine died is not lost by the queue** (agent; spec §5.3 "a save's outcome is resolved from disk (§6.6)", §6.6; S0062's precedent for recover-all): the table keeps the job (`Running.outcome_owed`, table version 5), its work asks for a fresh engine and calls `save_outcome`, which syncs the journal folder, reads the record's state and re-hashes the targets; the sidecar's pure `save_outcome` decides. Before the commit point too: the disk then says "not saved" and whether the files are unchanged (the model's `DiskOutcome` covers every save crash). When no engine can be had, `CHANGE_OUTCOME_UNKNOWN` if the engine had sent `gate`, `ENGINE_STOPPED` before it (it never got `proceed`, so it wrote nothing). The scheduler runs a save's work even when its first start failed (the job would otherwise wait for ever: mutant `scheduler_save_not_run`). Rejected: the sidecar reading the disk itself (it would need its own `F_FULLFSYNC`, link-safe reads and name folding, duplicating the port; S0062 decided against it); a separate outcome job (an extra job the queue and the model do not have).
- **The model mismatch, recorded for slice 5** (agent): the model ends a save at `EngineCrash` and tells `DiskOutcome` with no engine; the code reads it in a fresh engine. Both replays now map a model save crash to the code's save answering at once (`test_engine_jobs_conformance.py`: the table replay feeds `JobDone` after `EngineDied`, `ends_of` expects `finished`); the outcome read itself is `test_save_job.py`'s.
- **`CHANGE_NOT_SAVED` is one code worded by its reason** (agent; the spec left "slice 4's code"): `hard_linked`, `locked`, `not_a_file`, `permission` (with the folder and the ACL entry, or the app folder when no ledger file is named), `volume_no_swap`, `io_error`, `read_back`, `name_not_utf8`, and `engine_stopped` (a death found "not saved"); details carry `unchanged`, so "Your ledger is unchanged" is said only after the re-hash. The writer's `changed` and `path_moved` are `LEDGER_EXTERNALLY_CHANGED`. All four new codes are `Conflict` (ARCHITECTURE §6.1: state moved, or a pause to clear); `LEGACY_APP_SAVING` is the one retryable.
- **An outside save met at a swap ends "unfinished", not "not saved"** (agent; §11's "outside save during the commit" row rewritten): since S0061 round 1 the outside save goes to its kept name and the undo stops while it exists, so the journal stays `.open` and files may hold the new bytes; "Finzytrack did not save your change" would not be true until the undo. The answer is `WRITES_PAUSED {unfinished_save}` with Reopen, whose blocked screen shows both versions. After the undo stopped at `created_path_taken`, the Reopen text names that file and promises no undo (`writer.Unfinished` now carries the undo's stop cause and file; after a death, `save_outcome` names a created file that stands there).
- **A path that cannot be resolved** (a folder denying search, spec §15) ends `NotSaved(io_error)` naming the file, before anything is written (it was an `engine.internal` refusal).
- **Session ids lower case only** (S0061 red team r3 overflow 4): `engine_jobs.save.new_session_id` (hex), the protocol's `SessionId` pattern `[a-z0-9_]`, and `ledger.save`'s plan check.
- **The closed record's digests** are `not_computed` until R4 defines them (BL-0152's row says how R4 treats them). **The publish (step 10)** is a seam: `published: false` (BL-0113); a refused load is `INTERNAL` until the contract's code (BL-0106).
- **Whole files over the protocol** (agent): the plan carries each file's new text; a file over the 16 MiB line limit cannot be saved until BL-0106 sends edits (spec §15). The 54k demo ledger (8.7 MB in one file) fits.
- **Tests on real APFS for steps 1-7** (agent): the load and the fingerprint read the disk with the loader's own calls, not through the port, so the fake cannot stand in for them; the outcome reading is over the fake (its sync-before-read checked in every power-loss state).
- **Expected outputs changed** (PROCESS.md §8): `test_writer.py`'s twelve `Unfinished(...)` expectations gain the undo's cause and file (a new field, the values read from each run and checked against the scenario: `created_path_taken` where the save had placed `prices.bean`, `kept_copy` after a kept outside save, `foreign` after a read-back mismatch); `test_engine_scheduler.py`'s two "save whose engine died" tests now use a `create` (a save no longer ends there); `test_engine_job_codes.py`'s `CHANGE_OUTCOME_UNKNOWN` scenario likewise; `test_error_registry.py`'s class map and retryable set gain the four codes; `test_schema.py`'s op list gains the two ops.
- **TLA+ code map** (agent): the save's `S_*` actions stay `PLANNED` under BL-0151 in `test_tla_mapping.py` until slice 5's replay walks them (S0060's rule: a marker claims what the replay can show).
- **Round 1: every folder from the app's own down to the journal and backups folders is made durable before the commit point** (verifier F1, High): `_ensure_dir` syncs the parent whether or not it made the folder, and the chain now starts at `app_local_data` itself (its parent synced too): a folder already there may be an earlier engine's `mkdir` whose sync never ran, or the app's folder made by a start just before. Cost measured on APFS in scratch: the four syncs of an existing chain take a median 0.06 ms (20 runs; one outlier 20 ms on the first pass), so `measure_save.py` was not rerun (each of its runs makes a fresh app folder, where the syncs ran before too). Other write paths checked for the same "sync only when made" pattern: the writer's `_backups` (`mkdir` of a new name, always synced) and `_replace`'s new folders (always synced) make folders only fresh; `restore` and `recover_all` make no folder; `protocol.recovery.ledger_locks_in` and `server.hold_engine_lock` (`os.makedirs`, no sync) make only `locks/`, whose files carry no state across a power loss (a lost lock file is re-created). Not the same bug, so unchanged.
- **Round 1: one save, one name, by construction in the sidecar, checked in the engine** (verifier F2, Medium): the orchestrator's suggested fix (the engine refuses a name that is already on disk) does not close F2 alone: the false "saved" happens when a save with a reused name dies (or is refused and dies before its reply) and §6.6 then reads the earlier save's record by that name; a refusal the sidecar never receives cannot stop that. Matching the record's targets and post hashes instead would need the post hashes in `save_outcome`'s params (a protocol change) and still says "saved" for a resent identical request whose first try landed, which is true of the bytes but not of this save. Chosen: `SaveRequest` names no job; `save_work`'s `_Run` makes a random 32-hex job part for every save and uses it for the save and its outcome read (`new_job_name`), so no two saves share a name; and the engine refuses before step 1 (`BadPlanError("name_taken")`, an `INTERNAL` answer, nothing written) a name that already has any record, an R4 count or a backups folder in this key, compared case-folded, so a future caller that breaks the rule is caught before it writes. The verifier's engine-level repro (an earlier `.closed` of the same name read by `outcome`) still reads "closed": that input can no longer arise from the sidecar, and the tests are at the two places that guarantee it.
- **Round 1: an engine refusal past the gate reads the outcome from disk** (verifier F3 = red team M1): `_Run.run` sends an `EngineRefusal` after `GateReached` to `_from_disk()`; before the gate it stays `INTERNAL` ("refused before its gate: it wrote nothing").
- **Round 1: an I/O error at a ledger-set lock or in the load is "not saved", naming the file, with the re-hash** (red team L2), as `_key`'s was; only before the gate (an `OSError` past it is the writer's, and `job.committed()`'s channel error must never become "not saved").
- **Round 1: an `io_error` text no longer says "changed by another program"** (own finding while doing L2): `save_text._unchanged_or_not` read any `path` with `unchanged=False` as a file another program changed, but for `io_error`, `read_back` and `name_not_utf8` the path is the file the error was about (for example the folder that denies search, where the re-hash itself fails). Only `engine_stopped`'s path (§6.6's first file not at its pre bytes) is worded so now; the others say Finzytrack could not check.
- **Round 1, docs only:** step 4's mirror check gets `TODO(BL-0125)` and a sentence in §6.1's "Built in S0063" (verifier Q1, red team L1). L3 and L4 are §15 lines: L4's path cannot go to `WritesPausedDetails.file`, because that field turns the Reopen text into "a file the save was creating is still there" (`reopen_after_created`), which would be false for a journal folder. Red team overflow 3: §4 and §11 now say a save cancelled before its commit point reads "Your request is cancelled." (the code's `JOB_CANCELLED` text): "not saved" is true, but "Your ledger is unchanged" would need a re-hash that a Cancel does not run.
