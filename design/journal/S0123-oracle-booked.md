# S0123: the oracle compares Beancount's booked result (M1b, BL-0275)

## Brief
- Goal: M1b's seventh slice (after S0122 was reverted). The differential oracle (ADR-0014; `scripts/oracle/harness.py`, `classify.py`, `model.py`) asks the old app to make an edit on a copy, then checks that the result **means** what the intent table says: today it compares the **parsed** entries per file (`classify.compare`, with the classes' erasers) and new Beancount errors. Add a comparison of Beancount's **booked** result, so a change of money the parsed entries cannot show is caught:
  - which lot each reducing posting took (its booked cost: number, currency, date, label);
  - the realized gains, as the booked postings carry them;
  - the balance of each account per currency at the end of the ledger;
  - the errors (already compared; keep it).
  The reference is **the intended result booked by Beancount**, compared with the old app's result booked by Beancount. A difference the intended change does not account for is UNEXPLAINED; an existing class explains a booked difference only where its own cause produces it (state each case in the classifier's docstring, or none).
- **The design point to settle first (spike, then build):** the expected change is a set of parsed entries per file (`model.Expected`), not a ledger text. Beancount sorts entries by date, then kind, then **line number, across files** (S0122's verifier: a pure layout change in one file flipped a same-date tie with another file, and FIFO reduced another lot, a gain -10 USD → -20 USD). So the reference must be booked in the order the intended ledger would have.
  - Spike: build the intended ledger's booked result with Beancount's own pipeline, either by booking the expected entries with the ledger's options and plugins in that order, or by producing the intended files' text and loading them.
  - Name the line numbers it uses: untargeted entries keep their places, and the target is at its intended place.
  - Show on S0122's tie repro that the old app's reprint is caught and the intended change is not flagged.

## Finding for the owner: v0.4's own splice can move a same-date tie between files (not fixed here)
- **Yes, it can.** Evidence, a scratch script on the engine's own `source_edit` (`locate`, `Replace`, `apply_edits`) and Beancount 3.2.0: `main.beancount` holds a lunch (2020-01-02), then "buy A" `1 TOK {10 USD}` on 2020-02-01 at line 11, then a FIFO sale with its gain left for Beancount to fill; `sub.beancount` holds "buy B" `1 TOK {20 USD}` on 2020-02-01 at line 12. Editing the lunch's narration and adding two metadata lines to it (a whole-entry replace, two lines longer) moves "buy A" to line 13, below "buy B" in Beancount's order. FIFO then sells B instead of A: the realized gain goes from -20 USD to -10 USD, with no Beancount error. One extra line only ties (line 12 against 12; the root's entries come first in the loader's order, so nothing flips).
- **Why.** Beancount orders entries by date, then kind, then line number, without the file (`data.entry_sortkey`). Any edit that changes a file's line count (a longer or shorter replacement, an insert, a delete) moves every later entry of that file against same-date entries of other files. Fava's splice behaves the same way.
- **What a v0.4 user would see.** The contract's step 2 checks each file's untargeted entries (identical, in order); step 3 lists new errors only. Neither shows a changed lot or gain, so the preview would not show this change of money.
- **How likely.** It needs a reduction left to the booking method (`{}`, FIFO or LIFO) over lots of the same date in different files, and an edit above one of them that changes its line number past the other's. Rare in a hand-kept ledger, plausible in one split per year or per account.
- The owner decides what, if anything, follows (for example: the preview compares the booked result as this oracle now does; or a policy).
