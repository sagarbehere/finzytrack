# S0114: the Windows build check's path false positive fixed; each packaged fixme narrowed to its known failure

## Brief
- Goal: (1) the check that the engine's path holds none of the main sidecar's site-packages (the build's `judge_selfcheck` in `shell/sidecar/build_sidecar.py` and the packaged `--smoke-test`'s `judge_engine` in `shell/src-tauri/src/smoke.rs`) compares the engine's path only against the main sidecar's real site-packages folders, never the interpreter's prefix, on every OS. On Windows `site.getsitepackages()` returns `[sys.prefix, <prefix>\Lib\site-packages]`, so every standard-library entry of the engine's path (`python313.zip`, `DLLs`, `Lib`, the prefix) was "inside" the prefix entry: the only Windows failure of the build's self-check since S0113 (S0112 verifier F1). (2) `packaged.yml` stops hiding whole jobs: no `continue-on-error`; a per-OS `known_failure` makes that OS's first smoke run pass only when it fails with exactly that reason (`smoke_packaged.py --expect-fail`), so a different failure, a failure in a later step, or an unexpected pass fails the run. Linux keeps BL-0263's reason; Windows has no known failure left after (1), so it is strict.
- Implements: ADR-0054 decision 5 (the licence boundary: the engine's GPL-2.0-only closure and the main sidecar never share a process or path), ADR-0056 (packaged layout), ADR-0061 decision 4b (a platform-only failure is `fixme` due M11 with its row); S0112 verifier F1 and F2.
- Capabilities: none changed.
- Invariants touched: none directly (INV-23, INV-24: none of the changed checks reads data).
- Risk class / lane: Medium / light. Review budget row: tooling, gates (one verifier round), as the orchestrator set it; the narrowed check guards the licence boundary, so it gets must-not-pass tests and loosening mutants (PROCESS.md §3 step 4). Note: `backend/src/app/selfcheck.py` ships in the package but runs only from the build and `--smoke-test`, never in the product's own paths.
- Mechanism questions (§3 step 2): which real setup needs this? Every Windows package (a supported platform, ported in M11); no policy can forbid Windows' `getsitepackages()` shape. Fix-round history: this path check was built in S0038 and not fixed since; S0112's five rounds were CI diagnosis, not fixes of this check.
- The bytes it protects: none (build and CI checks; no ledger or user data).
- Acceptance tests: `backend/tests/test_selfcheck.py` (the reported `main_sites` drop the prefix on a Windows-shaped and a unix-shaped `getsitepackages()`, keep every real site-packages), `scripts/tests/test_build_sidecar.py` (a Windows-layout tree: the standard library and the prefix accepted, `Lib/site-packages` and a child refused), `shell/src-tauri/src/smoke.rs` tests (the same on a Windows layout), `scripts/tests/test_ci_workflows.py` (no `continue-on-error`; macOS strict; every non-empty `known_failure` cites an open M11 row; each OS's first smoke run takes the known failure, the others never).
- Expected doc impact: BL-0263 and BL-0264 status text; `ARCHITECTURE.md` §5 "Packaging" (the fixme form); `selfcheck.py`'s and `smoke.rs`' docstrings. No ADR: the decisions are the owner's, recorded here and on the rows.
- Open questions: none (both decided by the owner, 2026-11-13).
- Base: 60446d8f.

## Decisions
- Owner, 2026-11-13 (in session): "Fix the check now (Recommended)" — the Windows build check is a false positive; fix it so the check compares the engine's path only against the main sidecar's real site-packages folders.
- Owner, 2026-11-13 (in session): "Narrow it (Recommended)" — each fixme job passes only when it fails with exactly its known failure, and fails the run otherwise, including when it unexpectedly passes.
- Where fix 1 sits (agent): in the report, not the judges. `app.selfcheck.main_site_packages` drops only the interpreter's prefixes (`sys.prefix`, `sys.exec_prefix`, compared after `normcase`/`normpath`) from `site.getsitepackages()`; both judges (`build_sidecar.judge_selfcheck`, `smoke.rs`'s `judge_engine`) read `main_sites` and are unchanged, so one definition fixes the build and the Windows `--smoke-test` alike (the smoke judge had the same false positive, never reached in CI). Why the narrowing keeps the boundary: the prefix on Windows holds only the standard library (`uv pip install` puts the main sidecar in `Lib\site-packages`, which stays compared); an `app` importable from anywhere on the engine's path is still refused directly by `engine_finds_app`; and a report left with no site-packages is refused by both judges (fails closed). Rejected: comparing in the judges against the folder the build installed into (exact, but a second definition in Rust that could drift), and dropping every entry not named `site-packages` (would also drop a `dist-packages` or other real site folder).
- Where fix 2 sits (agent): the matrix's per-OS `known_failure` replaces `fixme` and `continue-on-error`; it reaches the steps through the job's `env` (`KNOWN_FAILURE`, never `${{ }}` inside a script), and each OS's first smoke run is `smoke_packaged.py <pkg> "${known[@]}"`, where `known` is `--expect-fail "$KNOWN_FAILURE"` when set and empty otherwise (checked under macOS's `/bin/bash` 3.2 with GitHub's `-eo pipefail`: the empty array expands to nothing). `--expect-fail` already passes only on a non-zero exit with one `FT_SMOKE_FAIL` line whose reason contains the text, and fails on a pass, a crash, a hang or another reason. Linux's known failure applies to the AppImage run only; the `.deb` smoke and both must-not-pass runs stay strict. Windows has no known failure left (fix 1), so it is strict; BL-0264 stays open until a run shows it green (orchestrator). The S0112 diagnosis step stays: it runs on any failure off macOS, which now includes a first strict Windows failure and any new Linux failure.
- Stated limits (agent): `--expect-fail` matches by containment, so a reason that adds text after the known one still counts as known; the known reason ends at the exception's name, so a different exception does not. The workflow meta-tests read the YAML as text (no parser on the system Python); the matrix parser covers the shape this file uses (checked with Ruby's YAML parser here: the matrix and env parse as intended).
