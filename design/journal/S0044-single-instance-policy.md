# S0044: Single-instance policy; coexistence with a running legacy app dropped

## Brief

## Decisions
- Drop coexistence with a running legacy app; remove Share; single instance of v0.4; detect-only for a held legacy lock (owner: "Drop the coexistence policy; I approve the needed changes to INV-26 and ADR-0020. The rest of the pending work you have identified should be done.", 2026-10-27, in session; prompted by the owner's own words the same day: "we can simplify it by taking the policy decision that no two instances of Finzytrack should be running at the same time; if the user does that, it's on them.").
- portalocker stays pinned at 3.2.0 (agent): the detection is only correct with the legacy primitive and byte range, and 3.2.0 is what v0.2.1, v0.2.2 and v0.3.0 pin in `backend/requirements.txt` (read at the tags with `git show`, nothing written to the legacy worktree); v0.2.0 declares `portalocker>=3.0.0` with no pin, so the version a v0.2.0 build shipped is not known from the tag (stated in ADR-0062). The upgrade gate narrows from the packaged-v0.2.2 interleaving test to the detection test.
- The detection, when it finds the lock free, keeps it for the copy's read or the save and releases it after (agent): the same single non-blocking try, so nothing ever waits, and the old app cannot start a save half-way through our read or write. It opens an existing lock file read-only and never creates one, so INV-26's rule can become "never writes under a legacy root" with no exception.
- A ledger the legacy-root probe matches (under a known legacy root, or named by a legacy `config.yaml`) is brought in by Copy only: neither an in-place `.finzytrack/` (as before) nor an external-ledger reference, which was Share's form (agent, direct consequence of removing Share; otherwise Share returns through "keep my folder untouched"). Consequence the owner should see: the roadmap's M2 dogfood suggestion "Prefer 'keep my folder untouched'" for the legacy ledger becomes "open a copy you made yourself" until Copy adoption ships in M3.
- Save-time detection applies to a workspace whose ledger files a known legacy install's config names, as found by the read-only probe on open (agent). That only happens when the old app is pointed at a v0.4 workspace after the fact, which is unsupported; the old app's rewrites are then caught as outside edits (ADR-0013 fingerprint and swap), not prevented. Verifies, R4 and recovery no longer take the legacy lock.
- Single instance: the process that serves the API (the main sidecar, desktop and headless alike) takes a non-blocking app-instance lock in `app_local_data_dir` before it reads the registry, and holds it for its life; a second process on the same app root exits with "Finzytrack is already running"; Tauri's single-instance plugin forwards a second desktop launch to the running window (agent; built as BL-0100, M2). A headless run beside the desktop app on the same app root is therefore refused; a different `--app-root`, a second installation or another OS account is not excluded and stays unsupported (owner answer 5 of the scheduler review, `design/specs/engine-scheduler.md` §5.6).
- The ledger-set locks (ADR-0012 Q29) and ADR-0012 Q30's second-instance journal rule stay unchanged as defences (agent): they serialize the scheduler's engine processes inside one instance, and they are what still protects a ledger when the instance lock is bypassed.
- The detection test replaces the three-OS interleaving test in INV-26's enforcement list and stays "never deferred" under ADR-0061 (agent; INV-tagged tests are never quarantined, PROCESS.md §9).
- Fact found while checking ADR-0005 (agent): portalocker 3.2.0 takes an exclusive lock on Windows with `msvcrt.locking` over the first 64 KiB (its default `MsvcrtLocker`), not `LockFileEx`, which serves only its shared locks (read from the 3.2.0 wheel's source in the local package cache). Recorded as a fact correction in ADR-0005's amendment and in ARCHITECTURE §2 `Locks`. A consequence for the scheduler spec: §5.6's "the legacy app waits for its lock with no time limit" holds on POSIX only; on Windows `msvcrt.locking` gives up after about 10 tries a second apart and the old app's save fails.
- Engine-scheduler spec, to be updated in draft 3 (not edited here): Orientation (line 33, "ADR-0005: the legacy lock"); §2 (line 153, portalocker joins the engine's environment: still true for the detection, but only for `commit`); §5.2 (lines 346 and 365: "every recorded legacy lock first" for verifies, and the legacy app listed among lock-respecting writers); §5.4 step 1 (line 389: the legacy-lock wait with no deadline and Cancel); §5.5 (line 449: the legacy app as a "superseded" cause, which stays as an outside edit); §5.6 (lines 459-471: the legacy-app bullets, TLA F14, "the legacy lock still excludes both installations on a Share workspace"); §5.8 (line 502, the legacy app after our death); §9.1 (line 767, the `waiting_for_lock` (legacy) message becomes a refusal); §9.2 (line 809, `engine.lock.waiting` with `lock_kind` legacy); §11.1-11.5 (lines 928, 962, 968, 976, 1001: the legacy actor, `Live_fixed_legacy`, `Fixed_legacy`, `LegacyWriterProgress`); §12 (line 1074, the verify waiting for a held legacy lock); §13 items 3 and 9 (lines 1110, 1116); §14 (lines 1152 and 1164: the ADR-0005 reading and the licence list); §15 (line 1176: the owner point on "at least 30 s", now moot); and the second-instance cases (lines 365, 393, 424, 947, 1086), which may simplify now that a second instance is refused at start, though ADR-0012 Q30 stays as a defence.
