# S0065: Saving on a drive without the swap (the no-swap fallback)

## Brief
- Goal: BL-0160 in full. A save, its rollback and recovery work on a volume without `RENAME_SWAP` (exFAT, FAT, HFS+, some network shares), by a write path chosen per volume before any effect, replacing today's up-front refusal (`ledger_engine.ledger.handles.volume_without_swap`, `TODO(BL-0160)`). Owner, 2026-10-29: "Unsafe fallback on such drives"; then "Agreed, fallback as its own slice after slice 4" (ADR-0013 amendment of 2026-10-29).
- Base: 3c168283 (pushed, tree clean).
- **What it builds:**
  - Port: `DirHandle.caps()` (the volume's `RENAME_SWAP` and `RENAME_EXCL`, read separately; it replaces `can_swap`) and `DirHandle.rename` (a plain rename, which replaces an entry at its target). The macOS adapter refuses `swap` and `rename_excl` on a volume whose capabilities do not offer them, before the call (probe below: FAT answers `RENAME_SWAP` with 0 and destroys the second file).
  - `ledger.handles`: the write mode per folder, `write_mode` (`swap`: both; `no_swap`: `RENAME_EXCL` only, HFS+; `plain`: neither, exFAT, FAT, network shares), the one place the choice is made; an exclusive move per mode (`RENAME_EXCL`, or on `plain` a check just before a plain rename); on the no-swap modes a rename or `mkdir` answered `EEXIST` (or a plain rename `ENOENT`) is checked before it is called someone else's: the source gone and the target the same object (`mkdir`: an empty folder), else it fails as before.
  - Writer, per file on a no-swap folder: the new bytes at the staging name, moved exclusively to the temp name and synced (as on APFS); then **the file hashed again just before a plain rename** of the temp onto it (not at its pre bytes: `changed`, nothing replaced for that file); a created file by an exclusive rename of its temp (`no_swap`) or, on `plain`, an exclusive create (`O_EXCL`) of the file itself. Backups and journal first, as on APFS (they are on the Mac's disk, INV-27, INV-30).
  - Restore (rollback and recovery) on a no-swap folder: the pre bytes from the backup at the restore staging name, moved exclusively to the restore temp and synced, the file hashed again (still at post, else `foreign`, nothing moved), a plain rename onto it; **a replaced file missing in the middle of a replace** (a power loss on a volume without a journal) gets its pre bytes back from the backup by an exclusive move.
  - `tests/fakes/memfs.py`: volumes without the swap (with or without `RENAME_EXCL`), a plain rename, and on a volume without `RENAME_EXCL` a rename over an entry that a power loss may split (the entry removed, the rename lost); the crash, power-loss, I/O-error and rollback sweeps run in both no-swap modes.
  - In-app notice: no workspace-open model exists yet (WS-BACKEND-CORE, M2), so the detection (`handles.write_mode`) and the notice's words (spec §11) are built, and a backlog row carries the open's call and the screen.
  - Docs: spec §6.1 step 8, §6.3, §6.4, §8.1, §11, §13 (the model's swap assumption as a limit), §15 (each window, honestly); ADR-0013 amendment (agent details); ARCHITECTURE.md port rows; user-docs warning on the docs repo's `v0.4` branch; `formal/tla/engine-jobs` README text only.
- **The step rule** (written before coding). The no-swap path keeps every rule of the swap path except the swap itself; what changes is listed here.
  - Every port operation may raise `OSError`; the process may die at any effect; a power loss keeps or drops each unsynced entry operation. On `plain` volumes a rename over an existing entry may be split by a power loss (the entry removed, the rename lost): the file is then **missing**, never torn.
  - **"Saved"** rests, as on APFS, on the closed record being durable after the read-back. It claims that our bytes are in every file and that the backups hold the old bytes. It does not claim that no other program's save was lost: in window W1 below an outside save is overwritten without detection, and "saved" is still true of our change. This is the accepted unsafe window, told in §15, the notice and the user docs.
  - **"Not saved"** rests on `NotSaved`: no replace was asked, or the rollback put every file back and resolved the journal. **"Unchanged"** rests only on a re-hash after the failure of every target against its pre bytes (absent for a created file); a missing file is not at pre, so it is never "unchanged". A lost outside save (W1) followed by a rollback leaves the file at pre: "unchanged" is then true of the ledger against its state before the save; the lost outside save is W1's, not a false claim.
  - **"Unfinished"** rests on a readable journal that is not durably closed; each file is at pre, at post, or missing (only after a power loss on a `plain` volume, or a crash inside the volume's own non-atomic replace), and the backups hold every pre. Recovery always restores (a missing file from its backup) or keeps both versions (an outside save met at a name of ours goes to the kept name, as on APFS).
  - **Unsafe windows** (no-swap volumes only): **W1**, between the re-hash and the plain rename (a read and a hash: milliseconds for a large file), an outside save to that file is overwritten, and a program that holds the old file open and writes into it after the rename writes into a file no longer named (lost); the swap would have kept both. **W2** (`plain` only), between the check that a name of ours (temp, restore temp, kept name) is free and the rename onto it, an entry another program puts at that exact name is replaced; these names carry the save's id. **W3** (`plain` only), a power loss on exFAT or FAT can leave a ledger file missing in the middle of a replace (recovery puts the old version back) or damage the folder itself, which no journal protects (macOS's First Aid repairs it; it may drop entries, a kept copy included). **W4** (`plain` only), a crash while the save writes a file it creates leaves part of it at its path; recovery asks the user, as for any file at a created path.

## Probes (before coding; scratch disk images under the session scratchpad, attached with `hdiutil -nobrowse` and detached after; macOS 26.6.2)
- **Capabilities** (`fgetattrlist`, valid and set bits): APFS swap yes, excl yes; HFS+ swap not valid, excl yes; exFAT and FAT (both served by FSKit on macOS 26) swap no, excl no.
- **What the calls do:** exFAT answers `ENOTSUP` to `RENAME_SWAP` and `RENAME_EXCL`. HFS+ answers `ENOTSUP` to `RENAME_SWAP`, and `RENAME_EXCL` works (`EEXIST` on a taken name). **FAT answers `RENAME_SWAP` with 0 and acts as a plain replace: the second file's bytes are gone** (its capabilities say no swap); FAT's `RENAME_EXCL` works though its capabilities say no. So the capabilities, not a try, decide, and the adapter refuses both calls where the capabilities lack them.
- Plain `rename` to a free name and over a file works on all three; the inode number is kept by a rename on all three (exFAT, FAT through FSKit included). `O_CREAT|O_EXCL` answers `EEXIST` on all. `mkdir` on a taken name `EEXIST` on all. Hard links: exFAT and FAT `ENOTSUP` (link count always 1), HFS+ yes. `F_FULLFSYNC` works on a read-only file descriptor and on a folder on all three.
- **ACLs:** exFAT and FAT: `acl_get_fd_np` answers "no ACL" (the adapter's `()`), `chmod +a` fails `ENOTSUP`; `access(W_OK|X_OK)`, `_RMFILE_OK`, `_DELETE_OK`, `_REXT_OK` answer yes. HFS+ stores ACLs. The fail-closed rule (any error other than "no ACL" refuses) stays; no error was met.
- Names: all three case-insensitive, store names in NFD; `F_GETPATH` answers the mount path. exFAT and FAT ignore modes (every file `0700`). Files there carry AppleDouble companions (`._name`, for the extended attribute macOS sets on files we write); the kernel moves and removes them with their file through every step of the no-swap sequence (probed: staging, move to the temp, rename onto the file, removal), so no `._` name of ours is left, and an empty folder the save made is removed. A write through a descriptor opened before a rename lands in the renamed object on all three.
- Not probed: a network share (no server here). SMB and NFS are expected to report neither capability, which makes them `plain`.

## Decisions
- **The fallback replace is a re-hash, then a plain rename** (agent, within the owner's "Unsafe fallback on such drives"; the backlog row's own words: "a re-hash just before a plain rename"). Rejected: a move-aside replace (the file renamed to a fifth name of ours, our temp onto the free path, what was moved aside checked like a swap's displaced object), which would keep both versions in W1 on HFS+ at the cost of two new names of ours per file, a missing-file state after every crash between its renames on every such volume, and a third rename per file. Recorded in ADR-0013's amendment of 2026-10-31; available later if real use shows W1 losses.
- **Three modes, chosen per folder from the capabilities, never by a try** (agent; probe: FAT reports no swap yet answers `RENAME_SWAP` with 0 and replaces the second file; FAT's `RENAME_EXCL` works though not reported). `no_swap` (HFS+) uses `RENAME_EXCL` for our exclusive moves; `plain` (exFAT, FAT, network) a check just before a plain rename (W2). The macOS adapter refuses `swap`/`rename_excl` without the capability before the call (one `fgetattrlist` per call: microseconds).
- **Created files on `plain`: `O_EXCL` of the file itself** (agent; the backlog row: "an exclusive create for created files"). The alternative, staging then a check and a plain rename onto the path, would replace another program's file put there in that instant (a High under the owner's bar); `O_EXCL` never does, at the cost of W4 (part of our own file left at the path after a crash, which the undo already asks about).
- **The staging name and the exclusive move to the temp name stay on every volume** (agent): the temp name must hold our synced bytes with a durable name before the rename onto the file, so an editor's in-place write through the file's name between the rename and its folder sync keeps a durable name (the temp's) when a power loss drops the rename; the temp rule then keeps it (S0061 round 2's property, kept). The cost is the same number of folder syncs as on APFS (measured: 11 for a one-file save on all four file systems).
- **`missing` is judged only on a volume without the swap** (agent): on APFS no step of ours leaves a replaced file absent, so a missing file there was removed by someone and stays `foreign` (the swap path and its tests unchanged). On a no-swap volume a missing file with a good backup is put back without asking (§15 line: a deliberate deletion during an unfinished save is undone; nothing lost).
- **The network retry check applies only on the fallback modes, and only to `EEXIST` and `ENOENT`** (agent; the backlog row: "APFS does not do this"): the swap path keeps its meaning of `EEXIST`; an `EIO` after an effect still fails the save (the "happened but answered an error" sweep runs in both modes). A retried `mkdir` counts as ours when an empty folder stands there: an empty folder another program made in that instant is taken for ours (no bytes; §15).
- **The restore's re-hash also refuses a second hard link** (agent; added with its test, `test_a_hard_link_made_before_the_restores_plain_rename_stops_it`): a link made between the checks and the plain rename would keep the post bytes under the other name, unseen; the try stops `hard_linked`, nothing moved.
- **`volume_no_swap` removed end to end** (agent): the writer's reason, recovery's cause, the sidecar's `NotSavedReason`, its text, the OpenAPI contract and the TypeScript types (regenerated), the protocol's docstring and schema. An engine that still sent it would be mapped to `INTERNAL` (tested), never worded as a refusal.
- **The in-app notice** (agent, as the brief allows): no workspace-open model exists (WS-BACKEND-CORE, M2), so the detection is `handles.write_mode` and the words are spec §11's row; the open's call and the screen are BL-0166. The user-docs page describes the notice as the product will have it at release (the docs' `v0.4` branch is unreleased).
- **User docs:** a new page `src/content/docs/reference/where-to-keep-your-ledger.md` on the docs repo's `v0.4` branch, commit `e07df44` (made with `git commit-tree` on a temporary index, so the owner's checkout, on its `valuations` branch, was not touched; the docs repo has no hooks; not pushed).
- **Measurement** (`engine/scripts/measure_save.py`, new `--app` option so the journal and backups stay on the Mac's disk while the ledger is on the image; the demo generator's 54k ledger, 8.7 MB in one file; 5 runs each, disk images on the Mac's SSD, so the file systems' code paths, not a USB drive's speed): exFAT 1.41-1.43 s, FAT 1.40-1.68 s (one run 2.47 s, its load also slower: 2.1 s against 1.2 s, machine noise), HFS+ 1.32-1.38 s, APFS 1.37-1.43 s. The durable order: 11 folder syncs (45-99 ms), 3 synced creates (22-149 ms), the plain renames 11-25 ms on exFAT/FAT. The restore 0.05-0.14 s. Within ADR-0008's 5 s.
- **Race loops:** the new tests are deterministic (the fake, no clock or threads); the opt-in real-volume tests were run 3× under load (beside the mutant runs) and 20× alone (below).
- **Round 1: a missing file's name on `plain` is claimed by an empty exclusive create, then checked and replaced** (agent; verifier and red team r1 F1, High). The put-back was a check that the ledger path is free, then a plain rename onto it: a file another program created there in that instant was replaced, then "undone", and no window named the ledger path. Now the empty name is taken by `O_EXCL` of an **empty** file (an entry that appeared there: `foreign`, untouched); that empty file is then checked (a regular file, one link, no bytes) and replaced by the plain rename of the synced restore temp, exactly as a file at post is. What another program can still lose is a save onto the claim after its check, which is W1 as already stated for every file the fallback replaces (§15 W1 now says so). An empty file at a replaced path on `plain` is judged `missing` (`core.recovery.judge`, new `plain` argument): the claim of a cut try, or another program's empty file, which holds no bytes. **Rejected: the orchestrator's preferred `O_EXCL` of the file itself from the backup bytes.** It writes unsynced ledger bytes at the ledger file's own name, so a crash leaves a cut ledger file and a power loss can tear it into shapes (zeros, a second half) that recovery cannot tell from another program's bytes: recovery would then stop "foreign" over its own torn write, and Keep would keep a torn ledger, both High under the owner's bar; the "prefix of our bytes" rule covers the crash but not the power loss, and redoing a cut put-back needs a check-then-remove on the ledger path, a new window. The empty claim never puts a byte at the ledger path before the whole, synced restore temp is renamed onto it: whole, missing or empty in every crash and power-loss state (the nested sweep, now a test, walks them). `handles.move_excl`'s docstring and §6.8 no longer call a check-then-rename onto a ledger name exclusive.
- **Round 1: a failed in-place create removes its own part** (agent; verifier r1 F2, High). On `plain`, after `create` of a new file answers an error (a full USB stick, an I/O error; probed on real exFAT and FAT images: a 1 MB file on a drive with 60 KB free now ends "not saved, unchanged" with nothing left), `writer._remove_own_part` removes what stands at its path when it is still ours alone (a regular file with one link whose bytes are a prefix of the post bytes, empty included), and the save answers as on APFS. The orchestrator asked for "still the same object we created": the port's `create` does not return the object's identity, and adding it would only narrow, not close, the instant between the check and the removal (POSIX has no remove-if-same), so the bytes and the link count are the check and that instant is stated in W4. A crash (not an error) while it is written stays W4. The folder sync after the create is not covered: an error there leaves a whole file of ours, asked about as on APFS.
- **Round 1: a try that stops still puts a missing file back** (agent; red team r1 F2, Medium; the simplest truthful of the three options). `restore._missing_back` runs on every `Stopped` from steps 2-3: each replaced file that looks missing (absent, or the empty claim, on a volume without the swap; `_missing` reads only) is checked by `_check` and restored alone (its names of ours cleaned, the put-back, the save's temp last, the folder synced); the put-back writes only into an empty name, so no other program's bytes are at stake. Keep then never leaves the ledger without the file. When that file's own checks stop or fail, the answer names it instead (its backup gone: `backup_bad` naming it). Rejected: refusing Keep while a file is missing (the user is left with a Retry that stops on the other file and a Keep that refuses: no way out), and naming the file in the stop without putting it back (Keep would still leave it missing). APFS is untouched (`_missing` answers no on a swap volume; the swap trace of the verifier's `swap_trace.py` is byte-identical to 7c78838c: 4089 lines, same sha256).
- **Round 1: beside a missing file the save's temp is removed only after the put-back** (agent; red team r1 F4): the round-0 equivalence argument ("cleaning it first loses nothing") missed a backup that turns bad between the checks and the put-back, after which both copies were gone; the slot-0 rule of S0061 r5 O2 now covers both verdicts of `_PUT_BACK`.
- **Round 1: the oracle** (agent; red team r1 F5): `check_disk` allows a missing (or empty) replaced file only in a state a power loss left (`MemFS.lost_power`, set on every power-loss state and kept by what is reached from it), and a created file on `plain` only when it holds a prefix of the post bytes (after a power loss, also a torn shape of one: `worlds.part_of`, `memfs.tears`); `assert_our_created_file` the same.
- **Round 1: docs** (agent; verifier F3-F7, red team F3, verifier Q1, red team overflow 2-3): §15 W1 runs from the re-hash's read to the rename and scales with the drive's read speed, and names the undo's "undone"; W2 says a ledger name is never written by a check-then-rename; W3 adds the never-probed cross-link case of a FAT/exFAT power loss, with the advice to run First Aid before reopening; W4 adds the error removal and its instant; the app's own folder needs the exclusive rename (fails only on exFAT, FAT, network shares); the `mkdir` retry rule applies on every drive without the swap; network shares' capabilities were never probed; ARCHITECTURE.md's `volume_no_swap` and the ADR's "hash,," fixed; the user docs page (docs repo `v0.4`, commit `dc54787` on `e07df44`, again by `git commit-tree` on a temporary index, the owner's `valuations` checkout untouched, not pushed) adds W1's read time, the undo, the open-file loss, W2, the First Aid advice and the full drive.
