# S0160: The oracle's remaining UNEXPLAINED cases on the repo corpora (BL-0274)

## Brief
- Goal: close BL-0274. (1) Extend class I2 to every file a glob match reaches, direct or through plain includes below it (owner, 2026-11-26: "Count it as I2 (Recommended)"), with an ADR-0014 amendment; the copy of such a file's entry into the root is then I2 and undone like the others. (2) Rerun the harness on the repo corpora (nasty, the demo at the default size and at 210 cases, every `load` folder of the write corpus) and give every case still UNEXPLAINED a disposition: an existing class by its own cause, a known legacy defect or harness limit (stated in the row and here), a new class only when it is one cause and cheap, or moved (nasty `ren-coffee`, `ren-rent` with BL-0047 to M4).
- Implements: ADR-0014 (the classes; amendment of 2026-11-16, a class explains a booked difference only by undoing its own cause), a new ADR-0014 amendment of 2026-11-26; spec `design/specs/write-path/README.md` (the `oracle` column).
- Capabilities: none changed (the oracle is M1b tooling; CAP rows unaffected).
- Invariants touched: INV-24 (the harness runs on copies only; unchanged, no guard touched), INV-23 (reports of repo corpora only enter the journal; no real data).
- Kind: a tool: the differential-oracle harness (`scripts/oracle/`), run by agents and the owner on repo corpora and on copies, at each mutator's promotion. Review row: tooling, one verifier round (the stop rule); no guard of real data or privacy changes.
- Real setup / policy: no mechanism added to product code; the class rule follows the legacy's own cause (it knows only the files its literal include walk reaches; `discover_includes_per_file` resolves `years/*.beancount` as a path, finds no file, and routes every entry of a file it does not know to the root). Fix-round history: the oracle's undo (S0124) had one round with a High; this slice changes which files count as glob-reached, not the undo.
- Risk class / lane: Low / light (tooling).
- Acceptance tests (fail on base 6996c012):
  - `test_semantic_diff.py`: a file included by a plain include from a glob-matched file is glob-reached; a file reached by plain includes from the root is not, even when a glob also matches it (the legacy knows and rewrites it).
  - `test_classify.py`: a nested file's entry copied into the root and left in place is I2 (was UNEXPLAINED); an edit of a nested file's entry that lands in the root, the file not rewritten, is I2 twice (was NOT_APPLIED; an edit rather than a rename, since a rename's old name left there is a new Beancount error, BL-0047); must-not-pass: the same copy from a file plainly included from the root stays UNEXPLAINED (existing `test_a_move_out_of_a_plain_include_is_unexplained`, plus a doubly-reached file).
  - `test_booked.py`: the `includes` corpus shape (the lunch under a glob file's nested include, copied into the root) leaves no booked difference after the undo; must-not-pass twin: the same with the lunch's amount changed in the copy stays UNEXPLAINED.
  - Added once the run showed the other causes (Decisions): `test_classify.py` `test_i10_a_renamed_entrys_lot_written_with_its_booked_date` (twins: another date, another cost) and `test_i3_a_plugins_change_to_an_entry_persisted` (twin: a tag the plugin does not add); `test_booked.py` `DocumentTest` (twin: a document whose path changed). Each fails on the base commit.
- Expected doc impact: ADR-0014 amendment; `classify.py` / `semantic_diff.py` docstrings; BL-0274 closed with each cause's disposition; BL-0047's row if its scope grows; roadmap §1 line if it lists BL-0274.
- Open questions: none on the rubric (the class question was the owner's, answered 2026-11-26).

## Decisions
- **I2's files are the files the legacy's literal walk does not reach** (agent, implementing the owner's "Count it as I2 (Recommended)"): `glob_files` = every file of the set minus the files plain includes reach from the root. This is the owner's "every file a glob match reaches, direct or nested" on every case the question covered, and differs only for a file that a plain include from the root also reaches: the legacy knows and rewrites that file (`discover_includes_per_file` walks literal paths), so a copy of its entry is not I2's cause and stays UNEXPLAINED (pinned by `test_a_copy_from_a_file_the_root_also_includes_by_name_is_unexplained`). Read from the legacy's `ledger_manager.save_entries` and `ledger_loader.discover_includes_per_file` (read-only).
- **Three more causes classed with existing classes by their own cause, no new class** (agent; brief step 3, first option; ADR-0014 amendment of 2026-11-26, "Also in S0160"):
  - I10 on a replaced entry's lot (demo ren-002; write `elided-and-reductions` ren-004, `implicit-prices` ren-002; the 210-case demo's ren-* lots): the legacy prints the booked lot `{1.00 USD, <date>}` for a rename's replacement. S0124 round 1 left this out only because it would loosen the parser in a fix round (its journal, Decisions); here it is the planned change. Accepted only when the written lot equals the reference's booked lot exactly (a wrong date or cost stays NOT_APPLIED).
  - I3 on a plugin's change to an entry (write `pythonpath-plugin`, all 6): the legacy writes its loaded entries, so `#seen` from the corpus's local plugin lands in the file. Accepted only when the written entry is exactly the loaded (reference-booked) form; tried after I10.
  - Document paths (write `documents` ren-000 to ren-003): Beancount makes a document's path absolute from its file's folder, so every document of the copy differed from the source's by the folder name: a harness defect, fixed in `canonical_key` (path relative to the holding file's folder; a folder scan's entry is held by the root). With it, the documents the `documents` option's folder scan generates and the legacy persists are I3, as for any generated entry.
- **The new Beancount errors stay UNEXPLAINED and move to BL-0047 (M4)** (agent; brief step 3, the triage's proposal): in nasty ren-coffee, ren-rent and write `includes` ren-000, ren-001, ren-003, every error is "Invalid reference to unknown account" for the renamed account's old name, in a glob-reached file the legacy never rewrites (checked by loading each case's result). That is BL-0047's own example; it is open on M4 (IMP-0070), whose rename work is its first consumer. Not built here: it changes the never-expected rule for errors, which is more than an hour's careful work and is the ADR-0014 rule's one gap.
- **A no-op edit is no change** (agent; the 210-case demo's upd-017, a harness defect): the generator's date edit of an entry dated the 28th gives the 28th again (`min(day, 27) + 1`), so the intended replacement equals its target; the comparison expected a removal and an addition, which a correct write never shows, and reported NOT_APPLIED twice. `compare` now nets each file's intended removals against its intended additions. The generator keeps producing such a case; it is a useful one.
- **The legacy's non-repeatable `custom "budget"` output gets a class, CUSTOM-ACCT** (agent; brief step 3, third option: one cause, cheap; ADR-0014 amendment of 2026-11-26): the 210-case demo run reproduced it (upd-065 and upd-066 write `Expenses:HouseRent` and the other budget accounts as quoted strings; both are the run's slowest cases, about 39 s against about 6 s). Beancount 3.2.0's printer writes an account-typed custom value bare only when its type `is` `account.TYPE` (the string `"<AccountDummy>"`, compared by identity, as the legacy's own `budget_directives` also does); any copy of that string that is not the same object prints the account quoted (a pickle round-trip, for one: checked, equal but not identical). Which path in the legacy makes such a copy on slow runs was not found within the hour IMP-0079 allows: Beancount's own pickle cache is not seen (no `.picklecache` file in any case folder). The eraser accepts only that direction and the same text (an account written as a string of itself); its undo puts the account back. No money depends on a `custom` entry.
- **Write `documents` ren-004 stays UNEXPLAINED, explained as a legacy defect** (agent; IMP-0079): the rename of `Assets:Bank:Checking` makes the legacy write the two documents the folder scan generates (I3) with the new account name; the folder `docs/Assets/Bank/Checking/` still carries the old name, so no load generates them again and they are not the source's generated entries. A class for "a persisted generated entry with the rename applied" would need the rename's mapping in the comparison; not built for one shape with no money (documents only). Stated in BL-0274's closing line.
