# S0136: saves on a Windows network share, best effort (BL-0219's Windows part, M1b)

## Brief
- **Goal:** a ledger on a Windows network share can be saved, rolled back, recovered, created and copied, with reduced guarantees, as the owner decided:
  - 2026-11-19, in session: "For bl-0219, I think we need to ensure that Finzytrack works for ledgers on windows shares, possibly with reduced guarantees".
  - 2026-11-20, in session, asked "BL-0219: how should a save on a Windows network share work?": **"Best effort + open notice (Recommended)"** (`design/inbox/answered/20261120-ledgers-on-windows-shares.md`, option 2).
- **What that decision is, as built here:**
  1. **A drive identity for shares.** `WindowsDir.volume_id` on a remote volume answers as on a local one: the version 5 UUID of `FileIdInfo`'s 64-bit volume serial for NTFS and ReFS (32-bit for FAT32 and exFAT), the server's. `mark`, `drive_of` and `folder_verdict` then work unchanged. The probe (runs 2 and 3, two machines) found it equal through the mapped drive (which names the share by its UNC path), `\\localhost\ftshare`, `\\<machine>\ftshare` and the server's own local path, and stable across a remap and a file-server restart. **Limits stated:** twin server disks cloned sector by sector share a serial and every file ID (as cloned NTFS disks and twin FAT sticks do); one folder has several paths (server spellings, the server's local path) with one identity, and each path is its own path key (below).
  2. **Exactly one refusal tolerated.** A port exception `SyncRefused` (an `OSError`, `EINVAL`), raised by `WindowsDir.sync` only when `FlushFileBuffers` on the folder answers `ERROR_INVALID_FUNCTION` **and** the volume is remote (`FILE_REMOTE_DEVICE`); every other failure, and that code on a local volume, raises the plain `OSError` as today. It is caught in one place, `handles.ledger_sync`, which every sync of a **ledger folder** calls (the save, the rollback, recovery's try, Keep, the blocked screen's two deletes, create and copy, which writes through create). The journal, backups and app folders keep the plain `sync()`, so there a refused sync still fails (they are machine-local, INV-27, INV-30). An architecture test pins both sides: `SyncRefused` caught nowhere but `ledger_sync`, and the inventory of sync sites per module and function (ledger side and app side) by count. A file's own flush (`sync_file`, `create`'s data flush) is never tolerated: it works on a share.
  3. **The rollback's flush skip on a share** (S0135's F1, now on BL-0219's row). Decided, cheapest truthful option: the skip also needs `remote()` not True (a share's file ID comes from the server, Samba's or a NAS's may be reused). On a share every file found at pre is flushed, as recovery does. Cost: a rollback on a share meets the S0128 F1 case again (a file another program holds sharing reading only cannot be opened for writing: the rollback fails, the workspace pauses, fails closed). No owner question: the key no longer rests on the name alone on a share.
  4. **The open's notice for a ledger on a share.** `handles.drive_kind(h)`: `swap`, `best_effort` (`write_mode` without the swap) or `network_share` (`remote()` True, on Windows), so the sidecar can tell a share from a USB stick; `write_mode` (how to write) is unchanged, so no write path branches on the new kind. The text `save_text.BEST_EFFORT_SHARE`, key `msg:save.best_effort_share`, §11's row beside `msg:save.best_effort_drive`, with BL-0166's "Show me how" and "Don't show again for this ledger", tightened from the owner's example on the owner's answer (Decisions): "Your ledger is on a network share. If the file server crashes or loses power right after a save, that save can be lost. For full protection, keep your ledger on your computer's own disk." Showing it at the open is BL-0166's (M2); its row names the share case.
  5. **The durability models state the mode as a limit:** `formal/tla/engine-jobs/MAPPING.md` (as for the no-swap mode), engine-jobs §6.8 and §15: on a share a rename is durable only when the server makes it durable.
  6. **Before landing, two probes with the real code on the CI share** (the probe script, two new commands): (a) a save cut by a network drop (LanmanServer restarted from a hook at chosen effects: after the staging write, between the rename and the folder's flush, before the read-back, before the journal's close), its outcome and recovery after; (b) whether the read-back after the rename reads the server's bytes or the PC's cache (other bytes written through the server's local path between the rename and the read-back). **Stop rule:** a false "saved", a torn or missing file, or a lost byte beyond the accepted limit stops the slice and goes to the orchestrator before any fix.
- **The bytes it protects:** the ledger's bytes on a share, and the truthfulness of "saved", "not saved" and "unchanged" there, under the accepted limit ("a file-server crash or power loss right after a save can undo it").
- **This changes a decided rule:** the save's durable order (engine-jobs §6.1 step 8, §6.8; ADR-0008, ADR-0068 D2) no longer includes the ledger folder's flush on a network share. Decided by the owner's answer above; recorded as an ADR-0068 amendment of 2026-11-20 with the owner's words.
- **Implements:** the owner's answer; ADR-0012 (drive identity), ADR-0013 and its 2026-10-29 amendment, ADR-0068 D2, ADR-0069; engine-jobs §6.3, §6.6, §6.8, §8.1, §11, §15; BL-0219 (Windows part). The macOS and Linux probe of BL-0219 stays M11 (owner, 2026-11-13: "Does my mac have a network share? If not, I want to defer this check"); off Windows a share still refuses `no_drive_id` (`remote()` is not answered there, `SyncRefused` never raised).
- **Capabilities:** none changes status (Windows does not write in the product until BL-0087).
- **Invariants touched:** INV-01 (no committed byte lost or torn; on a share under the stated limit), INV-22 (fails closed: every error but the one refusal), INV-27/INV-30 (journal and backups stay machine-local: their syncs are never tolerated), INV-32 (journals block by path key: the share's several spellings are a stated limit, below).
- **Risk class / lane:** High / full. **Review row: "New write path or write outcome"** (PROCESS.md §3): the verifier plus the data-safety red team; a fresh round after any fix that changes product code; in a fresh round only High and (a)/(b) findings are fixed, the rest become backlog rows; a second fix round on one mechanism needs the owner's options note first.

### The mechanism questions (PROCESS.md §3 step 2)
- **Which real setup needs this, and can a policy forbid the rest?** A ledger on a Windows network share (a mapped drive or a UNC path), which the owner chose to support (2026-11-19). The policy option ("keep refusing saves on shares") was put to the owner as option 1 of the note and declined for option 2. Within option 2 the tolerance is one error code on remote volumes only; every other setup keeps today's rules.
- **Has this mechanism or its family needed two or more fix rounds before?** Yes. The best-effort mode: S0065 (round 1 found a High: a put-back's plain rename could replace another program's new file; fixed by an exclusive create), S0071 (2 rounds). The Windows adapter: S0128 (2 rounds, no High). The share's folder-flush tolerance was built once for the mirror (S0132, 1 round: RT-F2 pinned it to the publish, V4 tested the mapping) and removed in S0134. **So a second fix round on any of these mechanisms needs the owner's options note first** (ADR-0068 D6).

### What each check is a second opinion on (S0122's lesson)
- `WindowsDir.sync`'s mapping (`SyncRefused` only for `ERROR_INVALID_FUNCTION` and `remote()`): a second opinion on "this is the share's known refusal, not a failing disk". Its own test fakes the error on a local volume (plain `OSError`) and on a remote answer (`SyncRefused`); the runner's real share answers it for real.
- `handles.ledger_sync`'s catch: decides nothing itself; the architecture test is the second opinion that no journal, backup or app-folder sync goes through it, and that no other module catches the exception.
- The skip's `remote()` term in `restore._flush`: a second opinion on the type's name, which a share reports as `NTFS`.
- The fake's share sweeps: a second opinion on the code's durable order under the server's own durability, not on the server: the server is modelled, not tested (the runner cannot cut its power).

### Facts verified (code, base 3884fdcf)
- `WindowsDir.volume_id` returns None when `self._h.remote()`; every save on a share stops `no_drive_id` in `writer._prepare` before any effect.
- `WindowsDir.sync` flushes the folder reopened for writing and raises the plain `OSError` (`EINVAL`, Windows' mapping of `ERROR_INVALID_FUNCTION`) on a share; S0132's `SyncRefused` was removed in S0134 (`git show 6b644b34`).
- On Windows `caps().swap` is False on every volume and `caps().excl` True (the share's exclusive create and rename were probed truly exclusive, runs 2 and 3), so a share takes `write_mode` `BEST_EFFORT` with the exclusive rename: the fake's `no_swap` volume, where a plain rename over a file is one entry operation (never missing).
- `remote()` answers only on Windows (`PosixDir.remote` is None), so `SyncRefused` and the skip's new term cannot change macOS or Linux.
- **Sync sites** (`git grep -n '\.sync()'` in `engine/src/ledger_engine` outside `fs/`, each read): 37. Ledger folders 22: `writer` 6 (`_stage`, `_best_effort`, `_replace` ×3, `_remove_temps`), `handles.keep` 1, `restore` 4 (`_put_back` ×3, `_sync_folders`), `recover_all` 2 (`keep`'s folders, `_delete_one`), `create` 9 (`_cleanup` ×2, `_target`, `_sync` ×2, `_manifest`, `_write_temp` ×2, `outcome_of`). App, journal and backups folders 15: `writer` 4 (`_backups` ×2, `durable_commit` ×2), `restore.restore` 2, `recover_all` 3 (`list_journals` ×2, `keep`'s journal), `save` 2 (`_ensure_dir`, `outcome`), `history` 1, `mirror/publish` 3 (a cache folder on a share is refused before any effect, S0134). `copy` has none of its own (it writes through `create`).
- The swap-mode sites (`_stage`, `_replace`'s two swap-mode syncs, `_put_back`'s two) never run on a share (no swap on Windows); they take `ledger_sync` too, so the rule is "every ledger-folder sync", not a list of modes.
- `test_a_network_spelling_of_a_local_folder_has_no_drive_id_so_the_save_refuses_it` (`tests/fs/test_windows.py`) and `test_a_refused_folder_flush_is_a_plain_os_error_on_every_volume` hold today's refusal: both change (Golden changes below).
- Copy cannot finish on Windows until BL-0087 (`tests/windows_pending.COPY_CHECK`: the fresh load's pipe); its writes are create's code (the same sync sites), so the runner tests create on the share and the copy's own runner test waits with BL-0087.

## Decisions
- **The decision itself** (owner, 2026-11-20, in session): "Best effort + open notice (Recommended)"; recorded as ADR-0068's amendment of 2026-11-20 with a note on ADR-0012.
- **One catch, one helper** (agent): `SyncRefused` is caught only in `handles.ledger_sync`, and every ledger-folder sync calls it, rather than an `except` at each of the 22 sites. The rule "which folder is a ledger folder" then sits at each call site, and `tests/architecture/test_share_sync.py` pins both sides by count per module and function (22 ledger, 15 app), so a new sync site, or one moved across, must be classified on purpose. A helper keyed by the handle's role (journal or ledger) inside `Handles` was the alternative: the writer uses one `Handles` for both kinds of folder, so it would need a second role flag; rejected as more state for the same rule.
- **The swap-mode sites take `ledger_sync` too** (agent): they never run on a share (Windows has no swap), but the rule "every ledger-folder sync" is simpler to state and to pin than a list of modes.
- **The blocked screen's two deletes are included** (agent, beyond the brief's list "the save, the rollback, recovery (`recover_journal`, `keep`), create and copy"): a delete removes a file in a ledger folder and syncs it; without the tolerance, "delete the kept copy" could never finish on a share and the workspace would stay blocked. Same rule, same folder kind.
- **The flush skip's key** (agent, the brief's point 3, cheapest truthful option): also `remote()` not True. Not brought to the owner: the key no longer rests on the name alone on a share. Cost stated in §8.1 step 4.
- **The notice's kind is its own function** (agent; deviation from the brief's "(`handles.write_mode`)"): `handles.drive_kind` (`swap`, `best_effort`, `network_share`) beside `write_mode`, which stays the one rule for how to write. Adding a third `Mode` would have made every `is Mode.BEST_EFFORT` branch in the writer, the restore and create a place to miss it. Nothing calls `drive_kind` but tests until BL-0166.
- **The notice's words** (owner, 2026-11-20, in session: **"Tighten the sentence"**). It answered the hand-off report's point 3: the note's example, "Finzytrack keeps a backup of every save, but if the file server crashes or loses power right after a save, that save can be undone", could read as if the backup restores an undone save; it does not (the backup holds the version before the save). The text now, the orchestrator's draft from that instruction: "Your ledger is on a network share. If the file server crashes or loses power right after a save, that save can be lost. For full protection, keep your ledger on your computer's own disk." (`save_text.BEST_EFFORT_SHARE`; its test also asserts no backup clause.)
- **The fake's share model** (agent): the server makes nothing durable for us (a power loss keeps or drops each entry operation made there), the harshest model; a file's own flush works. To keep it honest, the fake's replayed entry operations now act on the object they found (an unlink, swap, rename or move records its inode(s); `tests/fakes/memfs.py` `_apply`): without it, a power loss that dropped one entry let a later rename under the same name move another object, giving an empty ledger file no file system produces (found by the share's rollback sweep; on local volumes the syncs in between hide it). The whole engine suite passes with it.
- **The oracle's relaxation is narrow** (agent): only on a share, only in a state a power loss left; recovery that runs on such a state must still resolve and leave every file at pre in the disk as it left it (`check_recovered`, `check_taken`, `check_told` in `tests/ledger/worlds.py` and `test_writer.py`). Its must-not-pass test: `test_without_a_power_loss_the_share_oracle_is_the_full_one`.
- **After-faults in the fake** (agent): an error injected "after" an effect whose own call failed (a share's refused sync) now answers the injected error (`MemFS._effect`); before, the effect's own error replaced it, so the sweep injected nothing there.
- **The probe replaces the old probe step** (agent): `ci.yml`'s probe step runs `cut` and `readback` instead of `probe` (whose drive-ID patch is now the product), then the identity part as before. Removed after run 9 (Windows iterations, below).
- **BL-0219 moves to M11** with its Windows part done: the rest is the owner's 2026-11-13 deferral of the macOS probe ("Does my mac have a network share? If not, I want to defer this check"), quoted on the row.
- **A new row, BL-0304** (agent): the share's several spellings are several path keys, so a journal that cannot be recovered does not block a workspace registered by another spelling (INV-32's blocking by key). No byte is at risk (recovery stops on a file another save changed), so stated as a limit now and left to the workspace open's slice (M2).

## Probes (the 2026-11-20 run 8, head db7b206b; the brief's questions (a) and (b); stop rule not met)
All 8 `verdict` lines: `within_the_limit: true`, no problems. Every server restart answered exit 0, the service `Running` afterwards.
- **(a) A save of two files on `Z:` cut by a restart of LanmanServer:**
  - `after_staging` (before `inc.bean`'s rename), `after_rename` (before its folder's flush), `before_read_back` (before the first read-back read): each told **"not saved"** (`io_error`), both files at their **old** bytes as the share serves them, the journal `.resolved` (the rollback finished after the restart). "Unchanged" was not claimed (`unchanged: false`: the re-hash could not confirm it in that moment), the cautious answer.
  - `before_close` (after every ledger effect, before the journal's close on the local disk): **"saved"**, both files at their new bytes, the journal `.closed`.
  - So a network drop fails a save like an I/O error, and the rollback works once the server is back; nothing was torn, missing or told falsely.
- **(b) Other bytes written through the server's own path just before the read-back** (`in_place`, `longer`; on `Z:` and on `\\localhost\ftshare`): the read-back read **the server's bytes** (its hash is the server-side write's every time, never the cached post bytes), so each save stopped **`read_back`** (Unfinished, `cause: foreign`, the journal `.open`), and recovery **stopped on the other program's bytes** (`foreign`), leaving them in the file. No "saved".
- Seen beside it (the identity part, as in run 3): a write and flush through a handle held across a server restart fail ("An unexpected network error occurred"): a handle does not survive a restart.
