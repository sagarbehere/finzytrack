# S0022: The INV-21 goldens

## Brief
- Goal: write M1's INV-21 goldens (roadmap §1 "Left" item 3; review:27 §M1a; BL-0021): the expected values the M1a code must reproduce for ledgers released versions (v0.2.0 to v0.2.2) wrote: the TransactionId of every transaction (legacy `id`, legacy `transaction_id`, `k:` + `import-key`, content fallback with ordinals), the content-hash input and hash (`transaction_content_hash`), and the metadata JSON pass-through; plus the inventory of every metadata key a released version wrote, each classified per INV-21 (a) read forever, with its v0.4 reader, or (b) passed through untouched. A test keeps them honest. No product code.
- Implements: ADR-0026 (TransactionId, read-forever keys), ADR-0055 (`transaction_content_hash` computed), ADR-0048 (v0.2.2 ids unchanged); spec `design/specs/mirror/README.md` "Ids" and "Metadata JSON" (S0021), corrected where the goldens show it is wrong or silent.
- Capabilities: none change status (CAP-DATA-MIRROR stays `planned`; the goldens are its future acceptance data).
- Invariants touched: INV-21 (its goldens; it stays `pending` until the M1a code passes them: INVARIANTS.md is not edited, the owner owns its text), INV-23 (synthetic data only).
- Risk class / lane: **High** / full. The goldens pin how existing ledgers' entries are identified (rubric item 1 territory). A wrong golden would make the M1a mirror give an entry a different TransactionId than v0.2.2 did, or pin the wrong `k:` id, and every M1b write addresses entries by that id. It implements accepted ADR-0026 and INV-21 as written, so nothing escalates unless a golden would pin a user-visible v0.4 difference from v0.2.2 that no ADR covers.
- Where expected values come from (EP-29): the released v0.2.2 code itself (`sqlite_exporter._compute_fallback_id_map`, `_get_transaction_id`, `_metadata_to_json` and helpers; `beancount_engine.compute_hash_from_transaction`; `libs/content_hash.compute_content_hash`; `core/constants.SOURCE_ACCOUNT_PREFIXES`), extracted read-only from the tag into the scratchpad and run in the oracle environment (Beancount 3.2.0) on the golden ledgers. The `k:` ids (v0.4 only; no released version wrote `import-key`) come from the spec and are listed per entry as overrides. The keep-honest test re-derives every value independently from the written spec; two derivations agreeing is the check.
- Acceptance tests: `scripts/oracle/tests/test_inv21_goldens.py` (the real goldens pass; one must-not-pass per check). It fails on the base commit (nothing exists there).
- Expected doc impact: new `design/specs/mirror/inv21-goldens.md` (Orientation block); `design/specs/mirror/README.md` "Ids" made exact where the goldens show gaps; `design/specs/README.md`; corpora README; `.gitattributes`; the pre-push hook runs the new test if it is fast (IMPROVEMENTS.md entry); BL-0021's row says what is done and what M1a still owes; roadmap §1. INVARIANTS.md unchanged (owner's text). No user docs (no user-visible behaviour).
- Open questions: none expected to hit the rubric; checked while writing the goldens (recorded under Decisions).
- Base SHA: 9c515852.

## Decisions
- **Risk class High**, full lane (brief): a wrong golden would mis-identify entries of existing ledgers in M1a and every M1b write. One verifier round, more per ADR-0058 (agent).
- **Corpus shape:** a separate `corpora/ledgers/inv21/` rather than extending the S0020 write corpus, whose labels (detected features must equal declared ones) are about write hazards, not ids (agent).
- **The generator is committed** (`scripts/oracle/gen_inv21_goldens.py`) but reads v0.2.2 from this repository's own `v0.2.2` tag, never the legacy worktree; nothing in CI needs it, and the test reruns it only when the tag is in the clone (skipped otherwise), as S0021's `--legacy` check does. Deviation from the coordinator's suggestion (scratchpad-only generator): a scratchpad script dies with the session, and the tag gives the same bytes. On the first version of the corpus, the scratch run (reading the legacy worktree's tag, `scratchpad/s0022/gen_goldens.py`) and the committed generator produced identical `cases`; the committed goldens come from the committed generator (agent).
- **The README "Ids" text was incomplete, not wrong:** every value the spec could state agreed with v0.2.2 on the first run. Made exact where v0.2.2's behaviour was unstated: legacy ids are `str()` of the value (`id: 42` → `42`, `id:` → `None`); a copied legacy id is shared (BL-0059); the ordinal order is Beancount's loader order (date, type, line; files do not count; equal lines keep the read order); padding transactions count; a false-like `source_account` (`""`, `0`) is absent; the amount search compares the untrimmed value; `|` inside payee or narration collides (agent; spec fix, no behaviour change).
- **Pinned as v0.2.2 does, not "fixed":** shared and `None` legacy ids. ADR-0026 says "legacy id if present", and v0.2.2 gives these ids today, so v0.4 must too; non-uniqueness becomes M1b's problem to handle safely (BL-0059), not a reason to renumber users' entries. No escalation: no user-visible difference from v0.2.2 (agent).
- **v0.4-only `k:` edge cases** (no released version wrote `import-key`, so no compatibility at stake): a transaction-level `import-key` is not an identity (ADR-0026 puts it on postings); a posting `import-key` that is empty or not text is skipped; elements are whitespace-separated. Written into the README (agent).
- **`sha256` field name** in the goldens for the content hash: the privacy scan's entropy rule accepts a 64-hex value only as a `sha256`/`checksum` pin; renaming the field keeps the gate intact (no allow marks, no loosening). Synthetic UUIDs avoid 12-digit runs the account-number rule would flag (agent).
- **The pre-push hook runs the test** (under 1 s): IMP-0023, a tightening (agent).
- **Metadata inventory classification:** `read` for every key INV-21 names plus the keys a v0.4 reader shows or matches on (`account_number`, `ifsc_code`, `swift_bic`, `description`, `name`, `asset-class`, `document*`, `reason`); `pass` for `content_hash` (ADR-0055: computed, never read), `source_rule` (nothing reads it), v0.2.0's commodity `type` (v0.2.1 already stopped reading it) and the posting-level `ofx_memo` (beancount-import's; INV-21's alias is transaction-level only) (agent).

## Verifier
- Round 1, head b8902a2 (class High kept): PASS WITH FINDINGS. Fixed in the fix-round commit on top of 55ae244 (the coordinator's owner-decision commit).
- F1 Medium: no golden had an amount `str(Decimal)` writes with an exponent, while the README's "Exact numbers" rule formats money plainly, so an M1a reusing that formatter would change ids with every golden green. Fixed: `source-account` gains a written and a computed `1E-8`-scale amount; README "Ids" says the hash uses `str(Decimal)`, not the mirror's formatter; feature `exponent-amount`; the verifier's mutant now dies.
- F2 Medium: an Amount as `source_account` crashed both v0.2.2 and `inv21.py` although the README said a non-text value "matches no posting". Fixed: v0.4 compares text against text (README "Ids", stated as a v0.4 difference: v0.2.2 failed the whole export, so no released id exists); new case `source-account-amount` with the spec's values hand-written in `cases.toml` (`v022_fails`, `v04_expected`), the generator confirming v0.2.2 still fails, the check refusing a claimed v0.2.2 id there.
- F3 Low: added `id: ""` (TransactionId "") and true-like non-text `source_account` values (`TRUE` → `True`, a date, a number); the verifier's mutants die.
- F4 Low: keys.toml cited `add_ids_to_transaction` and `create_commodity`, which no released route calls (checked at v0.2.0 and v0.2.2: only a test calls the first; nothing calls `create_commodity_directive`). Fixed: `create_transaction` (from the import commit) and the seed ledgers.
- F5 Low: the twin detectors classified a fallback entry by its id's shape. Fixed: by the rule that settled it (`inv21.id_rule`); `ids-legacy` gains a pre-v0.1 hash-shaped `transaction_id` equal to an identical entry's fallback id (feature `hash-shaped-legacy-id`), with a near-miss test; BL-0059 names that collision.

## Retro
- (Implementer's part; the verifier's findings are added after its round.) The two derivations agreed on the first full run: the S0021 spec's formula was right but silent on non-text values, entry order and padding transactions. The mutants found two corpus gaps no reviewer would have seen (no non-ASCII metadata value, no included file outside the root folder) and five checks without a must-not-pass test.
- A cheaper gate: none would have caught the gaps; the privacy scan caught synthetic UUIDs that looked like account numbers and the 64-hex hashes, which shaped the golden format.
- Orientation gap: review:28 §2's key inventory was written against v0.3 and missed v0.2.0's commodity `type`; inventories of released behaviour must be built from the released tags.
- Process cost: one implementer pass plus one fix round; mutation runs of 91, 90, 17+17 and 95 mutants.
- Fix round: the verifier's findings were all of one kind: corner values the corpus did not hold (an exponent amount, an Amount-typed value, an empty-text id, a hash-shaped legacy id). A small fuzz over metadata value types would have found F2 and F3 before hand-off.
