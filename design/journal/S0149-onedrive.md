## Decisions
- **The engine's mode is read by a test-only op** (agent, 2026-11-22): `test.placeholder_mode` (`protocol/server.py`, with `--test-ops` only, not in the protocol schema) answers `this_os.placeholder_mode()` (`RtlQueryProcessPlaceholderCompatibilityMode`; None off Windows). The backend's spawn test starts the engine exactly as the sidecar does (`EngineCommand.for_venv`: `-s -S -B -P`, the bootstrap, its Job Object on Windows) and prints the answer. The query lives in `fs/this_os.py`: only `fs/` may use `ctypes` (`tests/architecture/test_write_port.py`), and a new module in `fs/` would count as an adapter (`tests/architecture/test_platform_selection.py`).
- **The simulation is a test module, not more probe** (agent): `engine/tests/fs/test_windows_cloud.py` runs the product's own jobs through the protocol (`Engine.handle`, as `tests/test_save_ops.py` does) on a ledger in a sync root, which a script could do only by importing the tests' helpers; phase 2 turns its facts into assertions. The provider runs in its own process (`tests/fs/cloud_provider.py`, as S0144: the engine is never the provider), driven by JSON lines. Its structures are copied from S0144's probe; phase 2 folds the probe into the tests or keeps it, and removes the copy either way.
- **The test process plays the engine in each mode** (agent): the mode is per process, so each test sets it (`inherited`: unchanged; `disguise`; `expose`) and puts the previous one back; a separate fact records the test process's own mode, a child's, whether a child inherits a mode its parent set, and the provider's.
- **A cloud-only file at the save** is made by the provider after the setup's load hydrated it (`CfDehydratePlaceholder`, as OneDrive's "free up space"), and after our save, whose rename leaves a plain file at the name, by `CfConvertToPlaceholder` with the dehydrate flag (as OneDrive does after its upload). Each call tried is recorded with its answer (S0146's lesson).
