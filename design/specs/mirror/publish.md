# Mirror: the generation publish

## Orientation
- **What this is:** the rules for how a finished mirror build becomes the mirror that the screens, outside tools and the save's gate read: the folder and what is ours in it, generation names, the build into its own name, the refusal of an incomplete build, the syncs, the link swap, the stale-journal rule, what `meta` carries, the cleanup, what a reader does, what the gate compares, and what a crash at each step leaves. Rules only: why is in ADR-0015 (and its amendments), when and how in the journals (S0085, and the publish's code slice, BL-0113).
- **The bytes it protects:** no ledger bytes: the publish writes only the app's cache folder. It keeps two outcomes truthful: what a reader reads is one whole generation, built from one state the ledger really had; and the save's gate passes only when the published generation describes the disk the plan was made on.
- **Where the code is** (built in S0087, BL-0113): the folder, the cleanup, the name, the publish, the swap, the gate's read and the freshness check `ledger_engine.mirror.publish` (`open_folder`, `clean`, `new_name`, `publish`, `swap`, `read_published`, `fresh_on_disk`, `fresh`); the SQLite build into a created file and the `meta` read `ledger_engine.mirror.store.SqliteStore` (the rows: `ledger_engine.mirror.build`, S0050); the rebuild that publishes `ledger_engine.ledger.rebuild.run` with the sidecar's `app.platform.engine_jobs.rebuild`, and the open `ledger_engine.ledger.opening.run` with `app.platform.engine_jobs.opening` (S0088; what the two share: `ledger_engine.ledger.publishing`); the save's gate `ledger_engine.ledger.save`; the reader's pin `app.mirror.files.pin` and the read-only open `app.mirror.files.open_mirror` (S0052). Tests: `engine/tests/mirror/test_publish.py` (real disk: the link rules, the keep set, the swap under concurrent reads), `engine/tests/mirror/test_publish_crash.py` (§9 over the fake), `engine/tests/mirror/test_publish_conformance.py` (the model's traces replayed through the rebuild and the publish over the fake, S0091), `engine/tests/ledger/test_save.py` (§7's gate tests). **Not built yet:** the switch and the boot that run the open (BL-0154), the sidecar's floor holder (BL-0126), the "Checking…" text (BL-0211), Windows' pointer file (BL-0206, M1b).
- **Decisions it applies:** ADR-0015 (the rebuildable cache; build a new generation, publish it atomically; the grace period; the content-hash fingerprint; the amendment of 2026-11-07, extended 2026-11-08: the folder is ours, grace only with at most 2 extra copies, no pin tracking, tagged names), ADR-0016 (the reads), ADR-0064 (one engine, one job at a time), ADR-0068 D1 (the rebuild after a save is the publish's caller), ADR-0061 (macOS first; the write path's Windows and Linux ports in M1b since its amendment of 2026-11-14).
- **Invariants:** INV-05 (the mirror is a rebuildable cache, published atomically), INV-10 (bounded caches), INV-23 (logs carry no content).
- **Model:** `formal/tla/mirror-publish/` checks §10's two properties (durability only, EP-19); `MAPPING.md` maps it both ways.
- **Traps:** never open `current.db` by that name from our code: resolve it once and open the generation (§7). Never write into a file that has been published, and never use a name twice (§3: the random tag), since readers and outside tools open generations by name. A build that says it is incomplete is never published (since S0086 built the `commodities` rows, BL-0120, every build says it is complete). The gate compares the published generation with the disk on the generation's own ledger set, not with the plan's set (§7).

## 1. Terms

- **Mirror folder:** `<app cache dir>/workspaces/<key>/mirror/`, keyed by the workspace's registry key (ADR-0015).
- **Generation:** one mirror database file, `gen-<N>-<tag>.db` (§3), written once by one build and never changed afterwards.
- **Current generation:** the one `current.db` names. **Previous generation:** the highest-numbered generation file below the current one that has no journal beside it and whose `meta` says `build_complete = 1`.
- **Publish:** making a new generation current (§4). **Cleanup:** removing what is not kept (§6).
- **Committed ledger state:** the ledger files' contents at a moment when no save of ours is half done (no `.open` journal of this workspace, `design/specs/engine-jobs.md` §6.5).

## 2. The folder is ours

- **The whole mirror folder is ours** (owner, 2026-11-07, ADR-0015 amendment): the publish and its cleanup may remove anything in it and replace whatever sits at `current.db`.
- **The folder itself:** first in every job, a link at `mirror/` is removed as a link, and anything else that is not a folder (a file) is removed; then the folder is made if missing (mode `0700`) and its parent synced. The app's folders above it (the cache folder, `workspaces/`, `<key>/`) are made if the OS purged them. The folders above `mirror/` (`workspaces/<key>/`, the app cache dir) are the app's and may be links; they are followed, as the save follows the app's own folder (engine-jobs §6.1 step 8).
- **One descriptor, never through a link:** the job then opens `mirror/` once, as a folder and without following a link (`O_DIRECTORY | O_NOFOLLOW`), and every step works relative to that descriptor: looks (`fstatat` without following), the exclusive create, the link, the renames and the removals (`openat`, `symlinkat`, `renameat`, `unlinkat`; Python's `dir_fd`). A link inside is removed as a link, never what it points to; a folder inside is removed with everything in it, again relative to descriptors, following no link.
- **Never another volume** (S0087 round 1, red team F1): "the folder is ours" never meant another volume's files. A descriptor opened without following a link still enters a mount point, so the cleanup compares devices: an entry on another device than the mirror folder's (a volume mounted inside) is never entered or removed, and is counted as a failed removal; a folder holding one keeps what is on the other volume and is not removed (as `rm -x`). A `mirror/` folder that is itself another volume's mount point refuses the job.
- **The cache folder is the engine's from its start** (S0087 round 1, red team F3): the sidecar starts every engine with the app's cache folder (`--app-cache`), as with the engine lock; no request names a folder, so no request can make a job read, write or clean anywhere else. One running Finzytrack at a time (ADR-0062) means one engine writes a cache folder at a time.
- **The build's own open:** SQLite cannot open relative to a descriptor. The build opens the file it has just created exclusively, by path, with the URI mode `rw` (SQLite never creates a file then: if a path that no longer leads to our folder names no file, the open fails instead of making one elsewhere; SQLite follows a link at the path, which §11 "Limit (the build's open)" states). After the build, the entry at its name, looked at through the descriptor, must still be the file the create made (same device and inode); otherwise nothing is published and the job ends.
- **Only the engine writes it,** inside an engine job (`open` or `rebuild`), holding the engine lock: one job at a time, so no two publishes or cleanups ever run together, and none runs beside a save (ADR-0064). The main sidecar and outside tools only read.

## 3. Generation names and numbers

- A generation is `gen-<N>-<tag>.db`: `N` in decimal from 1, no leading zeros; `tag` 16 lowercase hexadecimal digits from the operating system's cryptographic random source (64 bits). SQLite names its journals after it (`gen-<N>-<tag>.db-journal`).
- **A name is never used twice** (owner, 2026-11-08): whatever is removed or purged, the tag makes each build's name new. So a request that pinned a name (§7), or an outside tool that opens a generation by name, can only ever open the file built under that name. Nothing is written outside the mirror folder to achieve it.
- **`N` only orders generations.** The next `N` is 1 + the largest of: every `N` in a generation name or a journal name in the folder after the cleanup, the current generation's, and the **floor** the sidecar sends with the job: the highest `N` it has seen in this session, published (the engine's answer) or served (a pinned read). So within a session `ledger_version` never goes backwards, even when the OS purges the cache folder under a running app. `N` has at most 12 digits (`publish.MAX_NUMBER`, the floor's bound too): a name with more is not a generation, and the next number stays at the bound (only a name another program made can bring the folder there; the tag keeps every name new).
- **Across sessions** `N` grows while the folder survives. Only after the OS purged the cache between sessions may the next session's numbers start lower; nothing compares versions across that (every reader and screen of the earlier session is gone). This is the one exception to ADR-0015's "monotonic across restarts" (owner, 2026-11-08).

## 4. The publish

Inside an `open` or `rebuild` job. Every try is its own job (the rebuild's tries after a moved ledger too, engine-jobs §6.7, §7), so every try starts at step 1. Step 1 comes before the job's load; steps 2 to 8 follow once the load has a result (the rebuild after a save: `ledger.rebuild.run`'s `loaded`; the open: its overlay load, `ledger.opening.run`, S0088). After step 1 and before any result, the job looks for this workspace's `.open` journal (one: `paused`, nothing loaded; engine-jobs §7). A job that finds the published generation fresh (§8; for the rebuild, also a stamp that names everything its hint names, BL-0212 V1; for the open, only a generation an open published, `meta.published_by`) builds nothing and stops there.

1. **The folder** (§2) and **the cleanup** (§6).
2. **The name** `gen-<N>-<tag>.db` (§3).
3. **The build** writes it with an exclusive create, then SQLite's `mode=rw` open (§2; `build.build`). It writes everything in one SQLite transaction in rollback mode; at its commit SQLite deletes the journal. A build that fails removes its file (`BuildFailed`, or an error); one cut by a crash leaves its file and journal, never published, for the next cleanup. Then the identity check of §2.
4. **Never incomplete:** a build whose result says `complete` is false (`meta.build_complete = 0`) is not published; its file stays for the next cleanup. So a published generation always says `build_complete = 1`.
5. **The file synced** (`durable_sync`: `F_FULLFSYNC` on macOS; SQLite's own syncs do not reach the disk there). This is what keeps a power loss from leaving `current.db` on torn bytes (§10, mutant `no_file_sync`).
6. **The folder synced.** Requirement: availability, not §10's properties. Without it a power loss can keep the link of step 8 while losing the new file's name (`current.db` names no file) or bring back its journal (readers refuse it); either costs a rebuild, never a wrong read. It also makes the previous job's rename of `current.db` durable.
7. **Checked again, just before the swap** (engine-jobs §7): the ledger set the build read, observed again, equals the fingerprint the build is stamped with; and this workspace has no `.open` journal. A moved ledger is not published (the rebuild tries again in a new job, at most 3 tries in a row); an `.open` journal refuses the job (`WRITES_PAUSED {unfinished_save}`). The built file stays for the next cleanup.
8. **The swap:** the current generation's modification time is set to now (`utime`, through the descriptor, without following), so a replaced generation's modification time is the moment it was replaced (§6). Then a symbolic link `current.db.<tag>.tmp` whose target is the relative name `gen-<N>-<tag>.db` (an entry already at that name is removed first: it is ours) is renamed over `current.db` (a folder standing at `current.db` that the cleanup could not remove is first renamed aside whole, `current.db.<tag>.aside`, for the next cleanup: renaming a folder needs no right inside it; S0087 round 1, red team F6). Readers see the old or the new link, never neither. The job answers "published", with `N` and `ledger_version` (§8). The rename becomes durable at the next job's step 6, or earlier by the OS; until then a power loss can put `current.db` back on the previous generation, which the next cleanup keeps (§9).

## 5. The stale-journal rule

ADR-0015: "The live path never sits next to a leftover `-wal`." Renaming a new database over a path that has an old journal or WAL beside it can make SQLite play that journal into the new file. Here no database is ever renamed or rebuilt at a path:
- Readers and the gate never open `current.db` by that name; they open the generation (§7). SQLite itself, when a program opens `current.db`, names the journals after the file the link resolves to (checked with SQLite 3.53 on macOS in S0085: a WAL opened through `current.db` is `gen-1.db-wal`).
- A build always writes a name never used before (§3), so no journal of another file stands beside it. (SQLite 3.53 also discards a stale journal found beside a fresh, empty file, S0085's fidelity review; the rule does not rely on it.)
- Our builds write rollback mode; a reader refuses a file in WAL mode (S0052's header check).
- The cleanup removes `current.db-*` names (a program whose SQLite does not resolve links) and the journals of generations it does not keep (§6).

## 6. The cleanup

First in every `open` and `rebuild` job, before its load (§4 step 1), whether or not the job then builds; so never beside a build of its own.
- **Kept:** `current.db` when it is a link whose target is exactly a generation name and that file is a regular file in the folder (its generation is then the current one); the current generation; the previous generation (§1); and **at most 2 other generations** numbered below the current one whose modification time is less than the **grace period** ago (10 minutes; a configuration value), the newest of them first: when more qualify, the oldest go (owner, 2026-11-08). A replaced generation's modification time is its replacement time (§4 step 8).
- **A journal beside a kept generation is left as it is**: a reader refuses that file (SQLite finds the journal hot and a read-only connection may not roll it back), and the open then builds and publishes a new generation.
- **Removed:** everything else, in any order: every generation numbered above the current one (never published), every other generation and journal, temporary links, `current.db` when it is not a kept link, `current.db-*`, and any other file, link or folder.
- **A removal that fails** is logged (content-free, INV-23) and skipped; the next cleanup tries again. Nothing fails the publish: names are never reused (§3).
- **No pin tracking:** a reader's open connection keeps its file after the name is removed (macOS, Linux), so the cleanup needs to know nothing about readers (owner, 2026-11-07). Windows cannot remove an open file; its pointer file and retry are BL-0206 (M1b, with the Windows port of the write path).
- **Disk:** at most 4 generations stay (current, previous, 2 others), about 320 MB at 54k entries, whatever the pace of saves, plus what one job leaves until the next.

## 7. Readers, and the save's gate

- **A request resolves once:** `readlink(mirror/current.db)`; the target must be exactly a generation name, else there is no published mirror (`MirrorUnavailable("not_published")`, the caller decides on a build). A link at `mirror/` is not followed (the sidecar looks at it first; it only reads, so a link put there between the look and the `readlink` leads that one read elsewhere, where the open's checks still apply). The request pins `mirror/<that name>`, and every read of that request opens that path (`files.open_mirror`: read-only, header and `meta` checked); it never resolves the link again, so its reads all come from one generation, the one built under that name (§3).
- **A pinned file that is gone** (the cleanup removed it, or the OS purged the cache) is `MirrorUnavailable("cannot_open")`; the route answers "try again" (BL-0126) and the next request resolves again.
- **An open connection** keeps reading its file after the cleanup removes the name.
- **Outside tools** open `current.db` read-only (the stable path, CAP-MIRROR-EXTERNAL); SQLite resolves the link when it opens it. A tool that stays connected keeps its generation, even after the app crashed; one that opens again after a publish reads the new one.
- **The envelope's `meta.ledger_version`** is the pinned generation's (§8; BL-0126).
- **The save's gate** (engine-jobs §6.1 step 4). Inside the save job the engine resolves `current.db` once and reads that generation's `meta`. Beside the check it already makes (the disk observed on the plan's ledger set equals the plan's fingerprint), it checks that **the published generation is fresh against the disk**: the generation is this ledger's (its fingerprint's root and the plan's root have one `path_key`; S0087 round 1, red team F2: a generation of another ledger under this key, or of the ledger's old place after it was located elsewhere, is not), and the ledger set in its `meta.fingerprint` is observed now, and that observation's digest equals the generation's. The two checks together say the screens' generation and the plan describe the same disk. The plan's own set is not compared with the generation's: a save that creates a file or adds an `include` names files the published generation never read, and such a save would otherwise be refused for ever (S0085 review, design F1). Only the ledger's bytes count here: a generation built on an earlier day, or by an earlier engine build, is rebuilt by the open and the focus check (§8) but does not refuse a save. No published generation, one that cannot be read, or one that is not fresh refuses `mirror_stale` (`WORKSPACE_NOT_READY {WARMING}`). One job at a time: no publish runs between these reads and the save's commit point. `SaveRequest.mirror`, the sidecar's copy of a digest, goes (BL-0113).
- **The gate's tests** (built in S0087, `engine/tests/ledger/test_save.py`; the model leaves the comparison out, MAPPING.md §3): a save that creates a file and includes it passes when the published generation is fresh; a save that adds an `include` of an existing file passes; a save whose plan was made after an outside edit, while the published generation is from before it, is refused `mirror_stale`; no published generation, and an unreadable one, are refused `mirror_stale`.

## 8. What `meta` carries

- `build_complete` = `1` (always, for a published generation, §4 step 4); `surface_version`; `export_version` (the hash of the DDL).
- `fingerprint`: `ledger_set.encode` of the fingerprint the build is stamped with (the overlay load's, or the rebuild's observation): the ledger set it read and each path's state (the rebuild stamps the set its load read, not the hint it was given: the files, documents roots and `document` files the load used, and of the hint's `include` globs those whose matches include a file the load read or that match nothing, observed after the load and checked against the hint's set once more; S0087 round 1, verifier V1), so the freshness check decodes it, observes the disk (about 3 ms at 54k) and compares digests without a load (BL-0125).
- `ledger_version` = `<N>/<digest>`, the generation's number and `ledger_set.digest` of that fingerprint (`sha256:<hex>`), for example `42/sha256:3f9a…`. Ordered by `N` (ADR-0037: a late response cannot roll the version back; §3 says when `N` grows).
- `engine_build`: the engine build that wrote the rows, so a change in the row logic with the same DDL rebuilds (BL-0125). `as_of`: the build's "today" (ISO date, the user's time zone), since `account_balances` and `lots` stop at it. `built_at`: when it was built. `published_by`: the job that published it, `open` or `rebuild` (S0088 round 1; owner, 2026-11-08, "Open reloads after saves"): the open stamps exactly the bytes its overlay load parsed with every `include` pattern, the rebuild what Beancount's loader read, which can lack a pattern (§11), so the open's fresh shortcut takes only a generation an open published, and after any save the next open loads once (about 1.3 s at 54k entries).
- **Fresh** (BL-0125's check, used by the open and the focus check): the generation is this ledger's (its root's `path_key`), its fingerprint digest equals the disk's, observed on its own ledger set (the plugin code its load imported included since S0099: engine-jobs §1); its `export_version` and `engine_build` are the running engine's; and its `as_of` is today. For the open, also: an open published it (`published_by`). A generation that is not fresh is read with the banner while a rebuild runs (`WARMING`, ADR-0015). The save's gate uses only the first part (§7).
- The keys `engine_build` and `as_of` and the `ledger_version` format are built (S0087, BL-0113; `surface.toml`'s `meta` note). The engine reads no clock (INV-07, EP-10): the sidecar sends `today` (its clock's instant in the local time zone) and `built_at` with the rebuild, and the cleanup's grace period counts from that instant.

## 9. A crash at each step, and what the next start sees

"Death" is an engine death or an app crash (the folder stays as it is; an outside tool goes on reading); "power loss" adds what an unsynced step may lose. File-system assumptions are engine-jobs §13's: a file's data is durable after its sync; a directory entry (made, renamed or removed) after its folder's sync; unsynced operations in one folder may each be kept or lost on their own.

| Cut after | Death: the folder | Power loss may also leave | Readers until the next publish | The next job |
|---|---|---|---|---|
| 1. the folder, the cleanup (part done) | old entries partly removed (a journal may remain without its file); or a link at `mirror/` removed and no folder yet | removed entries back | the current generation; none when the folder was replaced | makes the folder, removes the rest |
| 3. the build, writing | the new file with its journal | either missing, or torn | the current generation (the new file is never linked) | removes both |
| 3. the build, committed | the new file whole, no journal | the file missing or torn, the journal back | the current generation | removes it |
| 4. refused incomplete | the new file whole, incomplete | as above | the current generation | removes it |
| 5. the file synced | the new file whole | the file missing, or its journal back | the current generation | removes it |
| 6. the folder synced; 7. refused | the new file whole | nothing more | the current generation | removes it |
| 8. the modification time set; the temporary link made | the temporary link | the link missing | the current generation | removes it and the new file |
| 8. renamed over `current.db`, "published" | `current.db` → the new file | `current.db` back on the old generation, the new file above it | the new generation; after a power loss, the old one | after a power loss removes the new file (above the current number); else keeps the old one as previous |

- **No step leaves a reader a partial, incomplete or torn generation**: `current.db` names a file only after its data is durable (step 5 before step 8), and the old link stays on a whole file until the new one replaces it; the previous generation is kept, so a power loss that undoes the rename lands on a whole file.
- **The OS purges the cache** (at any moment): the folder and everything in it go. Open connections keep reading; pinned names are gone ("try again"); the next job makes the folder and builds under a new name (§3).
- **The next start** reads the published generation and checks its freshness (§8): a power loss that undid a publish leaves the older generation, which is not fresh, so the open rebuilds.
- **A cut save's `.open` journal** never reaches a reader through the mirror: step 7 refuses it; the open waits for recover-all (INV-32).

## 10. What the TLA+ model checks

**Durability only** (EP-19; BL-0113): `formal/tla/mirror-publish/MirrorPublish.tla`. Its world: a ledger of two files written by an outside program at any time and by a save of ours cut after its first file (its `.open` journal until recovery); the mirror folder with generation names (a database file and its journal each; a name is never created twice) and `current.db`; one engine job at a time (§2); readers that resolve once and open the generation by name twice per request (the screens, the gate, and an outside tool that outlives the app's crash); engine deaths, app crashes, power losses under §9's file-system assumptions, and the OS purging the folder. The cleanup may remove any file it does not keep, at any time in its step, so the grace period and the cap do not matter to the properties.

**Properties:**
- `ReadersSeeCompleteGeneration`: every read a reader accepts reads a whole, complete generation: never a file a build is still writing, one whose build said it is incomplete, or bytes a power loss tore.
- `SnapshotIsSomeCommittedState`: what a reader reads is the build of one committed ledger state that the ledger really had, its `meta` names exactly that state, and the two reads of a request read the same generation. The save's gate is such a reader.

**Seeded bugs, each must fail its property** (`MAPPING.md` §4.1): `no_file_sync`, `publish_incomplete`, `build_in_place` (`ReadersSeeCompleteGeneration`); `no_tag`, `no_recheck`, `no_open_check`, `reresolve_per_read` (`SnapshotIsSomeCommittedState`).

**Not modelled** (checked by BL-0113's tests instead): the grace period, the cap and the modification times (§6), the folder, descriptor and link rules (§2), unknown entries, the floor (§3), the freshness check and the gate's comparison (§7, §8), availability (a reader that finds no file answers "try again"; §4 step 6's requirement), Windows (BL-0206), and Beancount's load itself (the model's load reads two version numbers).

## 11. Honest limits

- **Limit (A-B-A):** the fingerprint is a content hash, so an edit made and undone to the same bytes while the load runs is not seen: the generation's rows can come from the edited bytes while `meta` names the original ones. The rows are still a state the ledger had; the next save's gate and the next build see the disk as it is (the model's editor never writes back earlier bytes).
- **Limit (outside writers):** the mirror is read-only for outside tools (ADR-0015's contract). A program that writes into a generation can make what readers see wrong; a reader refuses such a file only when it left a journal or switched it to WAL mode.
- **Limit (old SQLite):** a program whose SQLite does not resolve links names its journals after `current.db`; the cleanup removes those names, but a write through it is an outside writer.
- **Limit (clock):** the grace period uses file modification times: a clock set forward removes replaced generations early (a pinned request then answers "try again"); a clock set back keeps them longer, never more than the cap.
- **Limit (cleanup only in jobs):** nothing is removed between jobs, so the folder keeps what the last job left until the next open or rebuild.
- **Limit (a removal that failed):** a file the cleanup could not remove (one never published, with its build's modification time) can take one of the 2 extra places for up to 10 minutes; a pinned request whose file went for it answers "try again".
- **Limit (numbers after a purge):** after the OS purged the cache between sessions, the next session's `N` may start lower (§3).
- **Limit (link swapped in):** a program writing inside the cache folder can replace `mirror/` itself between the job's look and its open of the descriptor; the open then fails (no link is followed) and the job ends.
- **Limit (folder moved away):** a program that moves `mirror/` elsewhere while a job holds its descriptor leads that job's remaining steps (the build, the swap, the cleanup's removals) into the moved folder, wherever it now is; they still act only on what that folder holds, which is ours (S0087 round 1, red team F5). The next job makes a new `mirror/`.
- **Limit (the build's open):** SQLite opens the generation by path and follows a link there; Python's `sqlite3` cannot pass `SQLITE_OPEN_NOFOLLOW`, and no URI parameter does it (checked with the bundled SQLite 3.53). A program writing in the mirror folder that replaces the just-created file with a link, in the moment between the exclusive create and SQLite's open, can lead the build's writes to the link's target (an empty file, or an SQLite database without the mirror's tables); the identity check then refuses to publish. Only a program running as the user and writing inside the app's cache folder can do it (S0087 round 1, verifier V3, red team F4). SQLite itself refuses a link at a journal's name (probed).
- **Limit (the stamp's globs):** the rebuild cannot know the `include` patterns of the disk it loaded (Beancount's loader does not report them); an `include` glob the ledger dropped while it matched nothing stays in the stamp, so a file appearing under that pattern later makes the gate refuse until the next rebuild (§8); and a glob an outside edit added between a save and its rebuild (the rebuild's hint did not name it) is missing from that stamp. The next rebuild whose hint names it is not fresh and loads (S0088, BL-0212 V1), and the next open never takes a generation the rebuild published (§8 `published_by`), so it loads and its stamp, which names every pattern, closes the gap. **Limit (the gate's window):** until one of those runs, the save's gate passes on that generation: a file that appears under the missing pattern is not in the screens, and a save planned on the disk with that file is not refused `mirror_stale` (its own fingerprint check still holds: the plan was made on that disk). No byte is lost; the screens lag until the next open or rebuild (owner, 2026-11-08, "The save's own check keeps the rare window until that next open, stated as a limit").
- **Limit (Windows):** this design needs a link that can be renamed over and the removal of open files: BL-0206 (M1b, with the Windows port of the write path).

## 12. Simplification pass (EP-30)

| Mechanism | Requirement it serves | Can a policy forbid the risk instead? |
|---|---|---|
