# Write path: the per-mutator intended-change table

## Orientation
- **What exists:** the table itself (`intent-table.toml` → generated `intent-table.md`); the D1 write corpus beside it (`write-corpus.md`, S0020) and the differential-oracle harness (`scripts/oracle/`, S0002; it compares the parsed entries and, since S0123, Beancount's booked result: lots, gains, balances, BL-0275; since S0124 a class explains a booked difference only when undoing its own cause on the legacy's result gives the intended booked result, ADR-0014 amendment of 2026-11-16), whose three models implement the `intent` column of `txn.edit`, `account.rename` and `import.commit` (`model.INTENT_ROWS`). The write contract is built (M1b: the splicing primitives S0115, the contract's steps and the preview S0116, the sidecar's preview and confirm S0117); no mutator is built yet (`ledger_engine.ledger.preview.PRODUCERS` is empty). Of the `edits` primitives below `insert`, `replace`, `delete` and `replace_token` exist (`ledger_engine.ledger.core.source_edit`); `option_line`, `new_file` and `replace_file` are not built (BL-0312).
- **Entry points:** `design/specs/write-path/intent-table.toml` (edit this); `scripts/gen_intent_table.py`; the structural checks in `scripts/tests/test_intent_table.py` (T1).
- **Decisions it applies:** ADR-0008 (contract steps 2 and 3), ADR-0067 (integrity blocks, accounting advises: step 3's errors are a preview, never a refusal), ADR-0009 (edit primitives), ADR-0014 (clearance kinds, oracle classes), ADR-0026 (metadata list), ADR-0049 (account moves), and the per-area ADRs named in each row.
- **Invariants:** INV-01 (the intent is exactly what step 2 checks), INV-14, INV-15, INV-16, INV-21, INV-22.
- **Traps:** an intent written loosely ("updates the account") lets the contract pass a wrong write; an accounting error (a failing assertion, a booking error, a plugin's error) is never a refusal, only a preview line the user may save anyway (ADR-0067), while a parser error in the text Finzytrack wrote always blocks; `@@` and typed metadata are preserved by merging against the parsed source, never by trusting a request (ADR-0009); a row marked `draft` is not a licence to build, it is confirmed in its vertical's first slice.
- **Main tests:** `scripts/tests/test_intent_table.py` (structure: kinds, primitives, the preview hints' error classes, no accounting error among the refusals, the metadata contract list, known oracle classes and finding IDs, ADRs, capability rows, the legacy map, inbox state, and every ledger-writing capability named, rule 5); later, each mutator's contract tests cite its row id.

## What a row means

Each `[[mutator]]` row is the contract between a use case and the write-safety contract (ADR-0008):

- **`intent`** is the "targeted set" of step 2: the exact entries inserted, replaced and removed. Every other entry of the ledger set must be identical, and options, plugins and includes are unchanged unless the row's edits include `option_line` (that exception is not built: step 2 refuses every option, plugin or include change, `semantic_diff.Reason.OPTIONS_CHANGED`; BL-0312). When a mutator is built, its edit producer returns this intended change and step 2 compares it with the candidate. The wording is precise on purpose: "the one targeted `balance` replaced" means a second matching assertion is a refusal, not a guess.
- **`kind`** is the clearance kind (ADR-0014): `add`, `change-one`, `many`. A row takes the **strictest** kind any of its writes can be: one that may write several entries or several files is `many` (an import of 200 lines, a price fetch, an opening with a pad, a new workspace's files), even when a single write is small. A row whose `old` is `n/a` clears at twice its kind's volume and time.
- **`edits`** are the only primitives the producer may emit (ADR-0009): `insert` (routed by Fava's `insert-entry` options, else the default file, never inside a `pushtag` block), `replace` (a whole entry span), `delete`, `replace_token` (exactly one account token on the posting's or directive's own line), `option_line` (one `option` line in the root; not built: BL-0312), `new_file` (a file that did not exist; not built, and the preview cannot plan a file create: BL-0312), and `replace_file` for the demo only (the one replacement in the system, INV-25, ADR-0022; not built: BL-0312). A change of flag is a whole-entry `replace`. **A metadata line added, removed or changed** is a `replace` of its entry by the same entry with that line added, removed or changed, **spliced into the entry's own text, never re-printed from the parse** (owner, 2026-11-28: "Accept, splice only (Recommended)"; ADR-0009 amendment of that date): every other byte of the entry (comments, spacing, elided amounts, the order of keys) stays as written (I10). Example: setting `bank-id: "1234"` on an account's `open` replaces that `open` and its metadata block with the same text plus one line. Every line changed on one entry, and a `replace_token` on that entry, go into one `replace` (two edits on one entry overlap and the plan is refused). Step 2 checks the replaced entry is exactly the intended one; it cannot see a comment, spacing, a metadata value's quoting or the order of tags and links inside the span, so each producer's tests pin that all four survive (S0167 verifier V2).
- **`files`** bounds where the edits may land; a plan that touches any other file is refused.
- **`meta`** lists the only keys the mutator writes: the ADR-0026 app-written list, or user vocabulary (review:28 §4.2) the user typed. Never client-supplied keys outside the list; every other key already on an entry passes through untouched (INV-21).
- **`ack`** lists the errors the preview is expected to show for this mutator (error class + the entry it is attached to, review:D1 §12.1; or `Warning:` for Finzytrack's own advice): wording hints for the preview, never a permission. Since ADR-0067 (owner, 2026-10-31) **no accounting error refuses a write**: every new error the overlay load reports, booking and plugin errors included, is listed in the preview and the user chooses Save anyway or Cancel. Example: you record that the bank shows 1,200.00 on 31 October while your entries add up to 950.00; the preview says the assertion fails, and you may save it as a reminder. The one exception is job 1's: a parser error in the text Finzytrack wrote, or a semantic diff that is not the intended change, blocks (steps 1, 2, 2b).
- **`refuses`** lists the integrity and policy checks the use case makes before planning, so the user gets a plain reason instead of a contract failure: a target not found or changed since it was read, a name the user did not type or pick, an entry Finzytrack cannot edit, an owner's invariant. Each is written `<kind>: <reason>`, the kind one of `target`, `grammar`, `not-editable`, `identity`, `user-choice`, `consent`, `policy`, `integrity` (or `as <row>`), so a reviewer sees why it may refuse. An accounting reason is never a refusal (ADR-0067): `scripts/tests/test_intent_table.py` refuses an untagged reason, a Beancount error class and accounting words (a failing assertion, a date against `open` or `close`, AVERAGE booking). Example: a reconciliation whose assertion would fail is not refused; the preview lists the `BalanceError` with the residual, and Save anyway records it (ADR-0028 still proposes no failing assertion itself).
- **`oracle`** is the v0.3 expectation when the harness compares the row with the old app: the divergence classes the old app is known to produce (ADR-0014; measured in S0002), or "none: no old endpoint". Every full-rewrite legacy write carries I10, and I2 / I3 on ledgers with glob includes / plugins; on some runs CUSTOM-ACCT, on a `custom` entry with an account value (S0160; not listed per row).
- **`status`**: `decided` when accepted ADRs settle every column; `draft` when the row is the best reading of the ADRs but its vertical has not started (the vertical's first slice confirms or corrects it, and a change to `intent`, `meta` or `ack` there needs the verifier's check against the ADRs); `owner:<inbox file>` when a rubric item 1 question is open.

## Rules

1. A mutator may not be built until its row is `decided`.
2. A new mutator gets a row before its first test. A row is never deleted: a dropped mutator stays with `status` explaining why (as the legacy map's "not built" lines do).
3. A change to a `decided` row's `intent` or `meta` is a change to what is written to the ledger: it needs an ADR that covers it, or the owner (rubric item 1). Since ADR-0067 `ack` changes no write (it is the preview's wording); moving a reason between `refuses` and `ack` follows ADR-0067's rule.
4. The oracle harness's models follow the table, never the reverse; where a row waits for the owner, the model refuses the case as non-comparable.
5. Every capability row that writes the ledger (`writes = "ledger"` in `design/capabilities.toml`) and is planned, partial or built is cited in some row's `caps`, or named in `[ledger_writers]` with why it has no row: `not built: ADR-nnnn (why)`, `machinery: ADR-nnnn (why)` (its writes are the contract's or the lifecycle's own: a save, a backup, a rollback, recovery, the restore of a run's backup) or `pending: BL-nnnn (why)` (its row is not written yet; the open backlog row says when). A row's `caps` cite only capability rows whose `writes` is `ledger`. T1 checks both (`LedgerWriters` in `scripts/tests/test_intent_table.py`; BL-0049, ADR-0057 decision 3). **Limits of the check** (S0157 round 1, V1-1, V1-2): a line's ADR is checked only to exist, so a superseded ADR is accepted (as in the sibling checks); a `not built` line is accepted on any row whatever its status or `release_blocking`, so it may excuse a planned writer that should be cited; review reads whether each line's reason fits (today's only `not built` line is CAP-WS-IMPORT, after v0.4.0 per ADR-0043 item 1).
