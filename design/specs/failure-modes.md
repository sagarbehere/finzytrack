# Failure modes across the four programs

## Orientation
- **What this is:** for each of Finzytrack's four programs and each way it can fail, who notices and how fast, what happens to data on disk and in flight, what the user sees and which action is offered, and the test that holds the row (BL-0090, S0041). It answers the owner's question of 2026-10-26: "how can we be reasonably confident that if one of them (e.g. the ledger engine) crashes or becomes unresponsive, all the other programs will know, will not lose data, and will provide the appropriate feedback and action suggestions to the user?"
- **What exists:** this spec and its check. Built today: the ledger engine and its supervision by the main sidecar (S0035, S0038, S0040), the structured log (S0039), the API served by the sidecar and its stop path (S0048). Not built: the shell's sidecar supervisor, the UI's states, every ledger write. Rows say which.
- **Entry points:** the statechart reference `design/generated/statecharts/engine-supervision.md` (the engine states named below); `app.platform.engine_supervision`, `app.platform.adapters.engine_client.EngineClient`, `app.main`; the engine's `ledger_engine.protocol.server` (`serve`, `watch_parent`).
- **Decisions it applies:** ADR-0054 (two processes; the sidecar supervises the engine), ADR-0007 (the shell supervises the sidecar), ADR-0008 (the write-safety contract), ADR-0012 (the write-intent journal and recovery, with its amendment Q30), ADR-0013 (atomic swap), ADR-0015 (atomic mirror publish), ADR-0039 (errors and logs). It decides nothing new; where a row needs a decision, it names the backlog row that takes it.
- **Invariants:** INV-01 and INV-22 (a write lands whole or not at all, and fails closed), INV-10 (no resident ledger, so a dead engine loses no state), INV-27 (logs and journals live outside the workspace).
- **Check:** `scripts/check_failure_modes.py` (run by `scripts/tests/test_check_failure_modes.py` at every push): every (program, failure) pair has exactly one row, and no row of an unknown program (rows in code blocks and comments do not count); every cited test exists inside the repo; every cited backlog row is open with the stated milestone, so a slice that closes one must cite its test here; `same as` points within the same program, at a row that cites a test; every engine transition named (`From` → `To` on `Event`) is one of the statechart reference. It does not police the tables' formatting (S0043, IMP-0032).
- **Changed by S0057** (BL-0150, the engine-jobs spec §5.2-§5.5; ADR-0064): no time limit on a request, a start or a handshake (the user's Cancel ends a wait), `close()` without waiting for a call or the reap, the engine as the leader of its own process group, drained before the reap, whose watchdog and end of input end that whole group. Rows E1-E3 and E5-E7 describe that built code. **Still coming** with the scheduler shell (S0058): what the user sees for E2 and E3 ("Still working…" with Cancel; "Quit and reopen Finzytrack" when Cancel cannot end an engine stuck on a dead disk) and the quiesce before `close()` (rows M7 and S7 already state the quit, spec §9.3).
- **Traps:** "the engine is ready" in `EngineClient.state` can be stale (rows E1, E4; BL-0094). Nothing can tell a slow engine from a hung one, so nothing ends either by itself: the user's Cancel does (rows E2, E3). The engine's parent-death watchdog cuts a request in hand on POSIX but not on Windows (row E5). On macOS a frozen (SIGSTOP) engine is reported by `waitid` like an exit; the drain does not take it for one (`app.platform.adapters.engine_group`). On macOS `killpg(pgid, 0)` also answers `EPERM` while a member is still exiting with its files (its locks) open; the drain reads the group's process listing instead.

## The short answer

**Today, only two of the four programs work together: the main sidecar and the ledger engine.** The shell opens an empty window and does not start the sidecar yet; the window shows an empty page. No program writes ledger data yet. So:

- **Will the others know?** For the engine, yes, and it is tested. If the engine crashes or is ended by the system (for example for lack of memory), the sidecar knows at once: it writes the stop to the log, ends the rest of the engine's process group, and starts a new engine at the next request, after a short wait (0.5 s, 2 s, then 8 s). After three stops in five minutes it stops trying and calls the engine *unavailable*. An engine that stops answering looks exactly like a slow one, so nothing ends it by a clock (engine-jobs §5.4): the user's Cancel does (rows E2, E3), never for a save past its commit point, which finishes. If the sidecar dies, the engine notices within a quarter of a second (macOS, Linux) and ends its whole process group. **Gap:** an engine that dies while it has no request is noticed only at the next request, and today the running sidecar sends none after the start (it has no routes yet), so it would be noticed only at quit (BL-0094). Beyond that, nothing watches anything yet: nobody notices a sidecar that hangs or is slow, a window that crashes, or a shell that dies. That is the shell's sidecar supervisor in M2 (BL-0095, BL-0096). One known hole there: if the shell dies, the sidecar keeps running on its own (BL-0073).
- **Will they lose data?** Nothing can be lost today, because nothing writes. For writes, the protection is decided but not built yet; it arrives with the write core in M1b and must pass its crash tests there: each file is replaced in one step (old or new, never half), a write that touches several files first records what it will do (the write journal), and if the engine dies in the middle, the next time the workspace is opened the journal puts the files back as they were before (ADR-0008, ADR-0012). Example: you rename an account used in three files; the engine dies after the second file. Your next open finds the journal, sees two files new and one old, puts the two new ones back to their old version, and tells you. If a file matches neither version (someone edited it in the meantime), it changes nothing, turns saving off and shows you both versions. If the app keeps running while this happens, the engine-jobs spec decides it (§6.4, §6.6): the app works out from the disk whether the change was saved, undone, or is still unfinished; an unfinished save pauses saving in that workspace with **Reopen**, which recovers it the way an open does, and reads go on meanwhile (tests: BL-0091 in M1b, BL-0092 in M2). Unsaved edits that live only in the window are lost if the window itself crashes; whether to keep a draft is BL-0097.
- **Will the user get feedback and a next step?** Not yet: there is no user interface. The rows below say what each failure will show and which button it offers (for example "Try again" and "Copy diagnostics" after the engine became unavailable), and each points at the backlog row that will build and test it.

So the honest level of confidence today: the engine's failures, as the sidecar sees them (rows E1 to E7), are tested at every push for what exists today (noticing, stopping, restarting, the bound), on macOS and Linux; Windows is tested only from M1b (BL-0087); the messages those rows will show are planned. On the sidecar's side, only its own part is tested: an exception that leaves it is logged, a refused configuration stops it before it starts, SIGTERM closes its engine, and its engine ends when the sidecar dies (rows M1, M4, M6, M7); nobody restarts it or tells the user yet. The sidecar's own hang, slowness and orphaning (rows M2, M3, M5) are not handled or tested yet (BL-0095, BL-0073). Everything that involves the shell, the window or a ledger write is decided but not built. Each of those has a backlog row with a milestone, and this spec's check fails when a row closes without its test being cited here.

## The programs and the failures

The inventory was built from what runs, not from names (S0041 Hand-off):
- **S, the Tauri shell** (`shell/src-tauri/src/main.rs`): the window, menus, later the sidecar supervisor. Today it opens the window over the frontend bundle; `--smoke-test` (`smoke.rs`) runs a short-lived probe of the bundled Python and engine. It supervises nothing in a normal run.
- **W, the frontend webview** (`frontend/src/`): the Vue app in the system web view (WebKit on macOS, WebView2 on Windows, WebKitGTK on Linux), whose page runs in a separate content process. Today an empty page.
- **M, the main sidecar** (`app.main`): the FastAPI app served by uvicorn on loopback (S0048); its only route so far is `GET /health`. It is started today by the acceptance harness and by tests, never by the shell. It starts and supervises the engine and writes the structured log.
- **E, the ledger engine** (`ledger_engine`): Beancount, later every ledger load and write and the mirror build. Spawned by `EngineClient` (in `app.main`, and in `app.selfcheck` for the packaged smoke test).

Failures. The first five are the backlog row's; the last two are added because they are real and behave differently:
1. **crash**: the program ends without being asked (a bug, a native crash, an unhandled signal).
2. **hang**: it is alive but never answers (a deadlock, an endless loop, frozen by the OS with SIGSTOP).
3. **slow**: it would answer, but later than its caller waits.
4. **killed for memory**: the OS ends it (SIGKILL on macOS and Linux; Windows ends the process too). Mechanically a crash; listed apart because a retry of the same work may run out of memory again, and the message should say so.
5. **parent gone**: the program that started it ended.
6. **fails to start**: it never becomes ready (missing or broken files, another protocol version, a refused configuration).
7. **told to stop**: asked to end (quit, logout, shutdown, an update): the path where an in-flight write must not be cut.

In the tables, **Test** lists existing tests as `` `path::name` ``, and planned tests as the open backlog row with its milestone. `same as` points at a row that behaves identically; `n/a` says why the pair does not occur.

## Decisions on the carry-overs (S0038, S0040)

Each open point the earlier verifiers and journals left for this spec, with what was decided:
1. **An engine that dies between requests is noticed only at the next request or at `close()`** (S0040). Kept for the table (a watcher thread would be new machinery for a state nobody reads yet); the reported state must be fresh when it is shown: BL-0094 (M2) makes `/health` and `/api/boot` notice a dead engine, without starting one and without waiting for a call in flight. Rows E1, E4.
2. **`close()` waits for a call in flight** (S0040). **Closed in S0057:** as the engine-jobs spec decides (§5.5, §9.3; ADR-0064), `close()` signals the engine's group once and waits neither for a call in flight nor for the reap; the quiesce before it comes with BL-0154; a quit cuts a save only by Quit anyway, and the journal covers that cut; nothing has a time limit. Row E7.
3. **A log sink that raises reached the caller after the state had moved** (S0040). **Closed in this slice:** a failing sink now loses its line and changes nothing else (`EngineClient` effect `Log`; test `test_a_log_sink_that_raises_changes_nothing_in_the_supervision`, which failed on the base). The structured log does not raise today (S0039); this makes the client independent of that promise.
4. **An exception inside a `Kill` effect after the state reached a resting state** (S0040, unreachable today). Accepted: only an interrupt (Ctrl-C, a signal's `SystemExit`) can raise there, and interrupts reach only the main thread, which runs no requests; the main thread runs `close()` at exit, where SIGTERM is ignored, and the process ends right after. The process would still end on stdin end of file. Re-checked when the API edge moves `close()` into its shutdown (BL-0095).
5. **The M2 sidecar supervisor must drain the sidecar's stderr** (S0038). Since S0039 the sidecar writes its events to the log file, not stderr, but a native library or Python's own fatal error can still write there, and an undrained pipe blocks the writer. A requirement of BL-0095 (drain stdout and stderr for the sidecar's whole life, never persist raw stderr, BL-0093).
6. **A SIGTERM between `main`'s outer `finally` and `SIG_IGN` skips `engine.close()`** (S0038). **Closed in S0048** (BL-0105): the stop handler only records and never raises, so no signal at any line reaches the stop path as an exception; a storm test sends a SIGTERM at every line of `app.main` and fails on the S0038 code with `SystemExit` at that line, and another test checks the handler is in place when the engine's start is asked for. Row M7.
7. **`EngineClient.state` stays `Unavailable` after the window passes, until the next request** (S0040). Same class as 1: BL-0094. Rows E1, E4.

## What this spec does not cover

Power loss and a full disk are not process failures; they are the write protocol's (ADR-0008 step 5's fsync order and the TLA+ model's `PowerLoss` action, ARCHITECTURE §8.3; BL-0091) and the log's (S0039: a line that cannot be written is dropped with one notice). A second running instance is refused at start by the app-instance lock (ADR-0062, BL-0100; ARCHITECTURE §2.5). The same-app-root case it misses, an orphaned engine still committing after its sidecar died while a relaunch took the instance lock, is covered by the ledger-set locks and ADR-0012 Q30. A second installation has its own app-local data, so neither reaches it: it is an outside editor, detected (ADR-0013), not excluded. A workspace switch while jobs run is not a process failure either: only one workspace is open at a time, and the switch finishes or records what the current one owes before it shuts (ADR-0063; the engine-jobs spec defines the jobs). Outside services (LLM, prices, IMAP) failing are typed "unavailable" errors (ARCHITECTURE §6.1), not processes of ours.
