# ADR-0067: Integrity blocks, accounting advises

This record splits what a save checks into two jobs: checks that Finzytrack wrote exactly what was asked (they always block) and checks of the ledger's accounting (they only advise), and turns R4, the re-check after a save, into a comparison that shows a notice and never pauses saving.

- **Status:** Accepted
- **Date:** 2026-10-31
- **Deciders:** owner. The owner questioned the premise "never write something Beancount would flag as an error": a user may deliberately record a balance assertion that fails (transactions still to enter) and use the failing `bean-check` as a reminder, and refusing by default blocks that intent. The orchestrator proposed this one ADR; the owner answered: **"Yes, draft that ADR. I'm approving it already, so go ahead and implement it."** (2026-10-31, in session, relayed by the orchestrator; S0068). Decisions 1 to 4 are that proposal; what this record adds within it is marked "(agent)".
- **Area:** write path, data safety, engine
- **Supersedes:** in ADR-0008, step 3's refusal rule ("No new errors of any type … except errors the user explicitly acknowledged", with the intent table's per-mutator acknowledgeable keys), the 2026-10-25 amendment's R4 rule ("its re-check … then completes before the **next** write … A failed re-check blocks writes"), the 2026-10-27 amendment's D2 (three failures to run, Resume saving), and the 2026-10-31 amendment's "a save that first finishes the previous save's check is two jobs" (moot: no save runs R4 first; that amendment's dropped parse digest stays); in ADR-0010, guardrail 3 as amended by ADR-0064 ("the next save to that workspace waits for it; a mismatch pauses saving … and shows the backup"); in ADR-0064, decision 7's "gates only the next save" and "The gate is the closed record on disk, re-read before every save", decision 8's "the closed record that … gates the next save" and "R4's confirm by parse in a fresh engine", decision 11 D2, the model amendment's O1 and fidelity review 2's M5 (R4 record renames), and decision 12's "an R4 superseded by an engine-build change publishes the new build's real load" (now the publish's, BL-0113).
- **Unchanged:** ADR-0008 steps 1, 2, 2b, 4, 5, 6 and 7 and "each step fails closed" (INV-22); ADR-0010's overlay load, `LoadPolicy`, guardrails 1, 2 and 4, and its 2026-10-31 amendment (R4's load and the policy); ADR-0012 and ADR-0013; ADR-0064's one engine, the queue, Cancel, the commit point, recovery and every durability rule of a save.

## Context

ADR-0008 step 3 refused any save whose candidate ledger had a new Beancount error, unless the error's class was in the mutator's acknowledgeable list; booking and parser errors were never acknowledgeable. ADR-0008's amendments then made R4 a gate: a landed save left a `.closed` record that paused the next save until R4 had compared Beancount's real load with the save's prediction; a difference or three failures to run paused saving until the user chose Resume saving. Building that gate (S0066, S0067) took two slices, four review rounds and three High findings, all in the gate's own mechanisms (records, attempts, the confirm, the documents prediction).

Two different questions were mixed in "the save is checked":
1. **Integrity:** did Finzytrack write exactly what the user asked, and nothing else, without losing anyone's bytes? A failure here is Finzytrack's fault and can lose data.
2. **Accounting:** does the ledger, after the change, satisfy Beancount's rules (balances, open accounts, booking, plugins)? A failure here is a property of the user's books, which the user may want for a while.

Example: the bank says your account holds 1,200.00 on 31 October, but you have entered only half of the month's transactions, so Beancount computes 950.00. You record `2026-10-31 balance Assets:Bank 1200.00 EUR` anyway: the failing assertion reminds you that 250.00 of transactions are missing. Under ADR-0008 step 3 that save needed the right acknowledgement key; a booking error (for example a sale with no matching lot) could never be saved at all, even though Beancount, Fava and a text editor all let you write it.

## Decision

1. **Job 1, integrity, always blocks; there is no override** (owner). A save lands only when Finzytrack wrote exactly what was asked and nothing else: the new text parses into exactly the intended entries (ADR-0008 steps 1, 2 and 2b), the fingerprint and concurrency checks pass (step 4, and the re-check after the load, spec `engine-jobs.md` §6.1 step 6), and the write is atomic with backup, journal and read-back (steps 5 and 6), with recovery after a crash (ADR-0012). All of this stays exactly as built, failing closed (INV-22).
2. **Job 2, accounting, advises and never refuses** (owner). The pre-write full load (the overlay, ADR-0010) stays, as a **preview**: the new errors are listed and the user chooses **Save anyway** or **Cancel**. No error class is refused, booking errors and plugin errors included. The intent table's acknowledgeable lists (`ack`) become wording hints for the preview, not permissions. **The one exception:** an error showing that Finzytrack's own text did not parse as intended (a parser error in the text we generated, or a semantic diff that is not the intended change) is a job 1 failure and blocks; steps 1, 2 and 2b already catch it.
   - **(agent) A preview that cannot run is not advice.** If the overlay load itself cannot run (it raises, it meets an encrypted file, ADR-0059, or it refuses the candidate), there is nothing to show and nothing to choose: the save is refused, as INV-22 requires of any check that cannot decide. What Beancount reports as errors (validation, booking, a plugin's errors, a plugin's exception that Beancount turns into an error) is advice.
   - **INV-01 reworded** (owner, 2026-10-31, in session, choosing the option "Reword (Recommended)"): its rule now reads "the semantic diff equals the intent; new errors are listed in a preview and written only if the user saves anyway; the hash/fingerprint check passes; the write is atomic with a backup; and the read-back matches", so the old "unless acknowledged" cannot be read as per-mutator acknowledgement lists. The error identity of step 3 (type + canonical entry + message without locations) stays: it decides which errors are new and what the preview lists.
3. **R4 becomes reconcile-and-show** (owner). After a save, Beancount's real load of the disk is the truth for the screens; adopting it is the mirror publish (BL-0113, not built), so until then R4 **compares and records**. On a difference it logs the difference and shows a short notice; **saving continues**. Removed: the pause on a mismatch, the confirm step, the attempt counting (`.r4-attempt-<n>`), "could not check", Resume saving, the `.mismatch` record, `WRITES_PAUSED {check_pending | check_failed | could_not_check}`, R4 run inside the next save, the queue's special cases for R4 (`outcome_owed` for an R4, Resume saving's exemption from another job's Cancel), and the "false checked" class of High finding. This restores ADR-0010's guardrail 3 as first written ("adopts the `load_file` result and shows a notice"), without its rollout-only synchronous mode.
   - **(agent) What R4 keeps:** the fingerprint before and after its load (moved → `superseded`, no notice, since an outside edit and not the prediction made the difference); a build other than the save's → `superseded` (the old prediction cannot be compared); the record's adopted digest and post fingerprint; Beancount's real loader without its pickle cache, never decrypting (BL-0118, ADR-0059). Outcomes: `pass`, `differs` (the notice), `superseded`; a record that is gone or unreadable, and a failure to run, are logged with no notice.
   - **(agent) Records:** `.closed` is terminal ("saved"; spec §6.6 reads it). R4 reads it and writes nothing, so it needs no rename, sync or state of its own; the journal format (3) is unchanged. `.done`, `.mismatch` and `.r4-attempt-<n>` files written by development builds are no longer read by anything, so they cannot block; the history trim (BL-0169) decides whether to delete them.
   - **(agent) R4 is in-memory background work:** queued by the landed save; a quit, a crash, or another job's Cancel before it runs loses only its notice. At most one R4 waits per workspace (INV-10); a newer save's R4 takes the queued one's place, since the newer save is the one whose prediction the disk can still be compared with. Whether an open after a lost R4 must rebuild the mirror from a real load is decided with the publish (BL-0113).
4. **Later, not built:** a quick-entry flow that writes first and shows errors after (backlog row BL-0175). It would need its own decision, since it skips the preview.

## Alternatives considered and rejected

- **Keep step 3's refusal with wider acknowledgeable lists** (agent). Rejected: every class the owner wants to record deliberately (failing assertions, booking errors, plugin errors) would join the list, so the list would end as "everything", with a per-mutator table to maintain.
- **Keep R4 as a gate but cheaper** (for example no confirm). Rejected (owner): the gate protected against a difference between Finzytrack's prediction and Beancount, which cannot lose bytes; the bytes are protected by job 1. A gate that pauses saving for an accounting difference contradicts decision 2.
- **Drop R4 entirely.** Rejected: a difference between the overlay's replica and Beancount's loader (ADR-0010's main risk) would go unseen in the screens; R4 is the runtime half of guardrail 1's equivalence tests.
- **Fava's model** (write, then reload and show errors) for every save. Still rejected as ADR-0008 rejected it, for job 1: an invalid ledger means one that is torn or not what was asked. A ledger with accounting errors the user chose to save is the user's ledger, as in Fava and a text editor; the preview shows them first. Decision 4 records the quick-entry variant for later.

## Consequences

- No save is refused for an accounting reason; the write corpus and the D1 contract tests keep every integrity refusal (steps 1, 2, 2b, 4, 5, 6) and the fail-closed rule.
- Saving never pauses after a save. "Saved" still means the closed record is durable; nothing in R4 can make a save's outcome untrue.
- About one engine and 2.5 s at 54k come off every save whose R4 found a difference (no confirm), and a save never runs the previous save's R4 first (S0067 measured the save alone at 1.89-1.96 s at 54k).
- The data-safety red team's High is again: ledger bytes lost, torn or overwritten (ours or another program's), or a false "saved", "undone" or "unchanged" (PROCESS.md §4).
- The intent table's `refuses` keep only integrity and policy refusals (a target not found, an entry changed since it was read, a name the user did not pick, INV-14/15/21/25/26/29); the reasons that were Beancount errors moved to the preview hints.
- Owner answers made moot: answer 4 on review 2 (2026-10-26, "non-deterministic plugins do not block saving (only a real loader difference pauses; plugin differences show a notice)"): nothing pauses now, and both show the notice; `design/inbox/answered/20261031-r4-deterministic-plugin-drift.md` ("Keep your rule"): no pause exists to add; `design/inbox/answered/20261031-r4-parse-digest-and-5s.md`: the dropped digest stays, the "two jobs" half is moot. Still in force: `design/inbox/answered/20261031-r4-load-policy.md` (R4's load asks the policy nothing per file; ADR-0010's 2026-10-31 amendment).
- S0067's documents prediction (the save's overlay walking a listing with the files it creates) is removed: the preview may miss a `document` entry a save's new file makes under a documents root; R4 then shows its notice, and the screen is corrected by the publish (spec §15).
- The formal model checks durability only (EP-19): R4's record states, the gate and their properties leave `formal/tla/engine-jobs/`; R4 stays there only as a background job with no disk effect.
