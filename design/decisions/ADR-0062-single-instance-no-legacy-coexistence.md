# ADR-0062: One running Finzytrack at a time: no ledger shared with a running legacy app, a single v0.4 instance

This record drops coexistence of v0.4 with a running legacy app on a shared ledger, removes Share workspaces, and makes v0.4 run as a single instance of itself.

- **Status:** Accepted
- **Date:** 2026-10-27
- **Deciders:** owner: "Drop the coexistence policy; I approve the needed changes to INV-26 and ADR-0020. The rest of the pending work you have identified should be done." (2026-10-27, in session), answering the orchestrator's proposal in the same session: "My recommendation: adopt it and drop Share. Copy stays the default, so the old app never touches v0.4's files. v0.4 enforces a single instance of itself. If an old Finzytrack holds a ledger's lock anyway, v0.4 only detects it and refuses the save with "quit the old Finzytrack first"." That proposal followed the owner's own words the same day: "we can simplify it by taking the policy decision that no two instances of Finzytrack should be running at the same time; if the user does that, it's on them." What this ADR adds beyond the approved proposal is marked "(agent)": among it, Copy only also for external references, the lock file never created, the exact message text, the outcomes other than held and free, and the mechanism of the single instance.
- **Area:** workspaces, lifecycle, data safety, desktop
- **Supersedes:** in ADR-0020, the Share adoption mode, the coexistence guard on Share workspaces (its ≥ 30 s legacy-lock waits, the running-legacy-app banner, the after-rewrite damage report) and the lock-interleaving test in its Consequences; in ADR-0005, the legacy-lock waits of at least 30 s and the upgrade gate's packaged-v0.2.2 interleaving test; in ADR-0043, Share mode in the list of release-blocking items; in ADR-0061, INV-26's three-OS lock-interleaving test as an unchanged item (it narrows, below). INV-26 is amended with the owner's approval.
- **Unchanged:** Copy adoption (ADR-0020), now the only mode; INV-26's purpose, that a legacy install keeps working on its own data; the read-only legacy-root probe on every open and at "Choose your old Finzytrack data folder"; tool state copied per workspace; the downgrade note; ADR-0013's detection of outside edits; ADR-0012's ledger-set locks and its second-instance journal rule (Q30); the owner's earlier answer that two installations writing one ledger are not supported in v0.4.0 (stated in the spec's draft 4 §5.6; draft 5, `design/specs/engine-jobs.md`, treats another installation as a lock-ignoring program, detected and not excluded, §15).

## Context

ADR-0020 let v0.4 and a running v0.2.x/v0.3 app write the same ledger file (Share), guarded by taking the legacy app's write lock, `<legacy root>/data/.write.lock`, with the legacy primitive (ADR-0005), waiting at least 30 s for it, and showing a banner while a legacy app ran. Designing the engine scheduler (`design/inbox/answered/20261026-engine-concurrency-and-cancel.md`, `design/specs/engine-scheduler.md` draft 2) showed what that costs: every verify, save, R4 step and recovery takes the legacy lock first and may wait tens of seconds on the old app's re-export; a TLA+ case (F14) lets the old app write over a half-applied v0.4 save before recovery runs; and the model needs a legacy actor with its own liveness property.

The guard also protects little. The legacy app holds its lock only while it saves (`portalocker.lock(fp, LOCK_EX)` around parse, write and export in its `write_lock.py`, at v0.2.2 and v0.3.0), and its damage happens when it writes: it re-renders whole files, drops comments, copies glob-included entries into the root and persists plugin entries (ADR-0020's own reason for rejecting read-only mode). Example: you add a transaction in v0.4 with a comment above it; the old app, still open on the same file, then saves a price; it writes the whole file again from what it parsed, and your comment is gone. No lock order prevents that.

## Decision

1. **No ledger is shared with a running legacy app** (owner, 2026-10-27). **Share workspaces are removed.** Copy is the only adoption mode, so the legacy app never writes v0.4's files and v0.4 never writes the legacy app's. A ledger the legacy-root probe matches (under a known legacy root, or named by a legacy `config.yaml`) comes into v0.4 only by Copy: neither an in-place `.finzytrack/` (as before) nor an external-ledger reference (ADR-0017), which was Share's form (agent: otherwise Share returns through "keep my folder untouched").
2. **A held legacy lock is detected, never waited for** (owner, 2026-10-27: detect and refuse the save; agent: the details). Before Copy reads a legacy ledger set, and before a save to a workspace whose ledger files a known legacy install's config names, v0.4 tries the `data/.write.lock` of **every** legacy install whose config names those files (two installs may share one data folder, for example a source checkout and a packaged install) **once each, without waiting** (`LOCK_EX | LOCK_NB`), with the legacy primitive. Held: the copy or the save is refused, nothing is written, and the user reads "The old Finzytrack app is saving. Quit the old Finzytrack first, then try again." (The lock belongs to the old install, not to one ledger: it is held while the old app saves any of its ledgers.) Free: v0.4 keeps the lock for that copy's read or that save and releases it after, so the old app cannot start a save half-way through (agent: the same single try, so nothing waits). The lock file is opened read-only and only if it exists; v0.4 never creates it (agent: a missing file means the old app never saved, so there is nothing to detect). Verifies, R4 and recovery no longer take the legacy lock.
   - **Fail closed** (agent; INV-22): only "free" and "absent" let the copy or save go on. Any other outcome of the try (the file cannot be opened, the lock call raises something other than "already locked", a file system that cannot lock) refuses it, with the same message and nothing written.
   - **Absent is only true at the check** (agent): the old app creates `.write.lock` on its first save, so that save can start during a copy read that holds nothing. After a read that found the file absent, Copy checks that it is still absent and that the sources' fingerprint equals the one taken before the read; otherwise the copy is discarded and refused. A save that found it absent is covered by ADR-0013's fingerprint check and swap, like any outside edit.
   - The second case only arises when the old app is pointed at a v0.4 workspace after the fact. That setup is unsupported; the old app's rewrites are then caught as outside edits (ADR-0013), not prevented.
3. **v0.4 runs as a single instance per app root** (owner, 2026-10-27: "no two instances of Finzytrack should be running at the same time"; agent, the mechanism): the process that serves the API, the main sidecar in desktop and headless mode alike, takes an exclusive non-blocking app-instance lock in `app_local_data_dir` before it reads the registry or opens a workspace, and holds it for its life; the OS releases it when the process ends, a crash included. A second process on the same app root exits at once with "Finzytrack is already running." In the desktop app, Tauri's single-instance plugin forwards a second launch (and the file it was asked to open) to the running window (ARCHITECTURE §5). The plugin keys on the app identifier, not the app root, so a second desktop launch with another `--app-root` is forwarded too; the running window then shows "Finzytrack is already running with another data folder." and does nothing else (agent). So a headless run beside the desktop app on the same app root is refused. Built as BL-0100 (M2, when the shell starts the sidecar).
4. **Two instances run anyway are unsupported** (owner, 2026-10-27: "if the user does that, it's on them"). The instance lock does not reach a second installation, a different `--app-root` or another OS account (each has its own app-local data); those stay unsupported in v0.4.0, as already decided, and each is an outside editor to the other.
5. **portalocker stays pinned at 3.2.0** (agent). The detection is only correct with the legacy primitive and byte range. In portalocker 3.2.0 an exclusive lock is `fcntl.flock` on POSIX (a `fcntl`/`lockf` record lock is a different lock kind, which on Linux does not see it) and, on Windows, `msvcrt.locking` over the first 64 KiB of the file (its default `MsvcrtLocker`; `LockFileEx` serves only its shared locks; read from the 3.2.0 source, correcting ADR-0005's "LockFileEx on Windows"). v0.2.1, v0.2.2 and v0.3.0 pin `portalocker==3.2.0` in `backend/requirements.txt`; v0.2.0 declares `portalocker>=3.0.0` with no pin, so the version a v0.2.0 build shipped is not known from its tag and is not tested. Upgrading needs a superseding ADR and the detection test (below) passing against a 3.2.0 holder on the three OSes; the packaged-v0.2.2 interleaving test is no longer needed, because nothing interleaves with the old app any more.
6. **INV-26 is amended** (owner approval quoted above): v0.4 never writes under a legacy root, with no exception; a legacy ledger comes in only by Copy; a held legacy lock refuses the copy or the save. Its enforcement narrows from the three-OS lock-interleaving test to the legacy-lock detection test, which stays never deferred under ADR-0061.

## Alternatives considered and rejected

- **Keep Share with the coexistence guard (ADR-0020 as written).** Rejected (owner, by choosing the decision above; the reasons are the agent's): the guard waits on the old app's whole re-export inside every lock-taking step, adds a legacy actor and a recovery gap (TLA F14) to the scheduler, and still cannot stop the old app's whole-file re-render from dropping comments, double counting glob includes or persisting plugin entries.
- **Keep Share and refuse only when the legacy lock is detected.** Rejected (owner, likewise): the lock is held only while the old app saves, a few seconds, so the check misses the old app running idle and then rewriting the file a minute later; the damage happens when the old app writes, whatever v0.4 does.
- **Keep the ≥ 30 s waits for Copy only.** Rejected (agent): a copy needs a consistent read, which one non-blocking try plus holding the lock while reading gives; a wait would only add a status screen for a case the user resolves by quitting the old app.
- **Detect with `fcntl.flock` and a Windows lock call made directly, without portalocker.** Rejected (agent): it reimplements portalocker 3.2.0's choice of call and byte range per OS (ADR-0005 itself named the Windows call wrongly), and a mismatch would silently detect nothing.
- **Exclude other installations and OS accounts too** (a lock beside the ledger). Rejected for v0.4.0 (agent): it would write into the workspace folder and next to legacy ledgers (INV-26, INV-30), and the owner already ruled those setups unsupported.

## Consequences

- **Honest limit of the detection:** it sees an old app that is saving at that moment, not one that is merely open. The protection against a running old app is structural (Copy only), not the check.
- While v0.4 holds a free legacy lock, an old app that starts a save waits for it: on POSIX without limit, on Windows for about 10 s (`msvcrt.locking` retries ten times, once a second), after which the old app's save fails with an error and writes nothing. So v0.4 holds it only for the copy's file reads (the "loads the same" check runs on the copy, after release) or for one save.
- Removed work: the Share plan and its gating, the running-legacy-app banner and its HTTP probe, the legacy-lock waits with status and Cancel, the after-rewrite multiset report, and the legacy actor's waits in the scheduler's TLA+ model and stateful test (CAP-LEGACY-COEXIST `cut`).
- INV-26 enforcement (BL-0026, M3): the adoption corpus test (the legacy config, mirror, backups, import sessions and every legacy ledger file byte-identical after adoption and after a v0.4 session; no file created under the legacy root, `.write.lock` included) and the detection test (a lock held from another process the way the old app holds it is reported held, a free one free, neither waits; an error opening or locking the file refuses; a lock file that appears, or a source that changes, during a copy read whose check found it absent refuses the copy; macOS in the unit tests, Linux and Windows in the manual CI run).
- New work: BL-0100, the app-instance lock and the "already running" exit, with the leftover-sidecar case of BL-0073 (a sidecar whose shell died would keep the lock until it exits).
- `design/specs/engine-scheduler.md` (draft 2) still describes the legacy-lock waits; draft 3 brings it in line (the sections are listed in `design/journal/S0044-single-instance-policy.md`).
- The roadmap's M2 dogfood suggestion changes: open a copy of a legacy ledger you made yourself, until Copy adoption ships in M3.
- A ledger a legacy `config.yaml` names cannot be opened in place while that legacy install is recorded as in use. The way out (owner, 2026-10-27, below): a deliberate action retires the install, after which its ledgers can be opened in place (BL-0101).

## Amendment (2026-10-27): retiring a legacy install

Owner, 2026-10-27, in session, answering the S0044 verifier's question Q3 (a ledger a legacy `config.yaml` names could never be opened in place, even after the old app is retired): "Yes, I agree with the approach of "A deliberate action, something like "I no longer use the old Finzytrack app", would record that install as retired, after which its ledgers can be opened in place.""
- A deliberate user action ("I no longer use the old Finzytrack app", wording to be settled with the UI) records a detected legacy install as **retired** in v0.4's app-local data. It writes nothing under the legacy root (INV-26).
- A retired install's ledgers may be opened in place or as an external reference; its lock is no longer tried. Running the old app again afterwards is unsupported (decision 1: one running Finzytrack at a time).
- The action is reversible (un-retire), shows which ledgers it frees, and is logged. Built with legacy adoption (BL-0101, M3).

## Amendment (2026-10-27): a leftover sidecar after Quit now (ADR-0064)

Agent, within decision 3 (engine-scheduler spec §15, quick check 9 F3). A sidecar stuck in the kernel on a dead disk keeps the app-instance lock until the disk answers, also after the shell's "Quit now". A relaunch is still refused (decision 3 unchanged). When the new shell's single-instance check found no other Finzytrack window, the holder can only be such a leftover, so the shell shows "Finzytrack is still closing from last time. Try again in a moment." instead of "Finzytrack is already running."; headless mode keeps "Finzytrack is already running."

## Amendment (2026-10-31): the legacy lock tried with portalocker's own call on POSIX

Owner, 2026-10-31, in session, answering `design/inbox/answered/20261030-legacy-lock-primitive.md` (raised by S0063) with the option labelled "Direct flock (Recommended)" (that file's option 2): "Direct flock (option 1) is fine."
- On macOS and Linux the engine tries the legacy `.write.lock` with the call portalocker 3.2.0 makes there, `fcntl.flock(LOCK_EX | LOCK_NB)`, on the file opened read-only, never through a link, only if it exists (`ledger_engine.fs.darwin.DarwinLegacyLocks`). The engine does not import portalocker: on Windows it brings pywin32, which the licence gate cannot check on a Mac, and changing that gate would loosen it. This moves the rejected alternative "Detect with `fcntl.flock` ... without portalocker" to the decision for POSIX; decision 5's pin stays as the reference the detection is tested against.
- The rejected alternative's worry (a silent mismatch) is answered by a test: a second process takes the lock with portalocker 3.2.0 (exclusive, and shared) and the engine must see it held, and while the engine holds it portalocker can take neither (`engine/tests/ledger/test_save.py`; portalocker a test-only dependency). Windows chooses its call (portalocker 3.2.0's `msvcrt.locking` over the first 64 KiB) with the same kind of test when Windows arrives (BL-0087).
- Asked in the same answer whether checking for the old app contradicts "one running Finzytrack at a time", the orchestrator's answer (agent): it does not. Decision 2 is the detection the owner approved with that policy (2026-10-27: "If an old Finzytrack holds a ledger's lock anyway, v0.4 only detects it and refuses the save"): one try, never a wait, no support for both running. Owner, 2026-10-31, after that answer: "Let's stay with the plan, unless staying with it means substantially slower development speed. I agree with keeping the save-time check ofr the old app's lock": the save-time check stays.
