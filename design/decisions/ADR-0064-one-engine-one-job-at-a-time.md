# ADR-0064: One engine, one job at a time

This record decides that the ledger engine runs one job at a time in one process, behind a queue in the main sidecar where work the user waits for goes first, and that parallel engines are dropped.

## Context

The area review of the engine core (2026-10-26, F1 and F2) found that "1–2 slots" could not be built inside one Python process and that a time limit was the only way to stop a job, counted as a crash. The owner chose engines as slots with a queue in the sidecar, then asked for a watertight design. Four review rounds of the scheduler design (drafts 1 to 3) each found 3 to 6 High findings, most of them in mechanisms the previous round had added: the engine pool, priorities with inheritance and aging, head-of-line reservation, merging, per-workspace lanes, memory admission and pressure levels, Run anyway, learned "usual" run times, automatic runaway and stall stops, reads beside a rebuild. Nearly all of that served running two engines at once, which serves waiting less, not data safety.

**Parallel engines never make one save faster.** A save is one full load of the ledger plus the durable writes; a second engine can only run some other job beside it. Example: you add a transaction to a 54k-entry ledger. With two engines, a BQL query you start at the same time no longer waits for the save; the save itself takes exactly as long.

What makes a save slow is the work inside it (spike S4, 54k entries, p95, owner's Mac): 5.5 s for a ledger in 12 files and 8.7 s for one 20 MB file with the R4 re-check inside the save; 3.0 s for the 12 files with R4 moved after the reply. ADR-0008's absolutes are at most 1 s at demo size and at most 5 s at 54k. So the order that ADR-0008's amendment already allows (R4 after "saved") brings the 12-file ledger under 5 s. A big single-file ledger near 1 s needs incremental work on the edited file (the bounded parse cache of ADR-0008's amendment), a later performance project, measured first (BL-0082).

## Decision

1. **One engine process, one job at a time** (owner, 2026-10-27). At most one engine exists at any moment; it runs at most one job.
2. **A FIFO queue in the main sidecar where a job the user is waiting for goes ahead of background work** (owner). Background work is R4 and saves the app starts itself (prices). A running job is not interrupted to start another (agent: preempting R4 only moves its cost to the next save, which must run it first).
3. **Cancel ends that job's engine and is not counted as a crash** (owner). A save past its commit point (the moment it asks to start its first durable write) is not cancelled; it finishes (owner, 2026-10-26: "Cancel on a save that has started writing files shows 'Finishing your change…' and lets it complete"; ADR-0063 decision 1 left the rest to the scheduler spec). The commit point is decided in one table step (agent). Cancel on a job queued behind a running background job also ends that background job, unless it is a save past its commit point, so every wait ends on the user's word (agent).
4. **A crash is noticed by the engine's exit, with S0040's bounded restart** (owner).
5. **No automatic killing of slow jobs; after a while a long job shows "Still working…" with Cancel** (owner). The engine client's per-request time limit and the handshake time limit go (agent: a start that never completes is ended by the waiting job's Cancel).
6. **One load at a time bounds memory; there is no admission** (owner). The heavy-load semaphore is superseded by decision 1. ADR-0011's per-workspace write limiter is retired: it has nothing left to serialize, since the queue runs every engine job one at a time (agent, a direct consequence; acknowledged by the owner, review 5: "I agree with all the recommendations. Proceed on that basis."; ADR-0011 amendment). Tool-state files keep their own per-file lock (ARCHITECTURE §9.9).
7. **The save reports "saved" after commit and read-back; the R4 re-check runs right after and gates only the next save** (owner; ADR-0008's amendment allows this order). The gate is the closed record on disk, re-read before every save, so it survives a crash. R4 always runs this way, in every mode (desktop, dogfooding and a future hosted mode), and is never switched off: safety outranks speed, and hosted mode is not built (owner, review 5; ADR-0010 amendment).
8. **Kept from the review rounds** (owner, the hand-off's keep list): macOS `F_FULLFSYNC` for every durable step (owner, 2026-10-27: "I agree with your recommendations for all three questions"); `canonical_path` and `path_key`; one durable order for a save (backups → journal → replaces → close) and for recovery (restores synced → journal renamed `.resolved`); the closed record that survives a crash and gates the next save; R4's confirm by parse in a fresh engine that runs no user code, with `PYTHONHASHSEED=0` and the spawn flags `-s -S -B -P`; the protocol-violation-after-commit-point rule (read and discard, wait for the exit); draining a process group before the reap, never a signal to it after; children's CPU by `RUSAGE_CHILDREN`; the bytecode directory filled once per engine build; the replayable decision log; ADR-0062's legacy-lock outcomes; the workspace switch and recover-all-before-open of ADR-0063.
9. **Agent decisions within that design** (agent; reasons in the spec): no recovery inside a running session: after an engine dies with a half-applied save, the user is offered Reopen, which is ADR-0012 Q30's "ask the user to reopen" and runs ADR-0063's recover-all (spec §6.6); the engine does not delay SIGTERM, and its parent-death watchdog ends the engine's whole process group (decision 10), since the journal makes every cut safe; recovery also checks the temp path of each file, so an outside save displaced by a swap at the moment of a crash is never restored over; a file a save creates is created exclusively; temp files are removed before the journal closes; the engine is started without `-I`, which ignores `PYTHONHASHSEED`; loads read without the ledger-set locks and re-check the fingerprint after the load, which replaces ADR-0012's agent-level F-6 tightening ("snapshot reads take the locks"). These answer BL-0091's open questions.
10. **The review-5 rules** (owner, review 5: "I agree with all the recommendations. Proceed on that basis."), each the uniform application of a rule already in place rather than a new mechanism: every swap (save, rollback, recovery) hashes what it displaced, and a created file is removed only after it is moved aside and hashed; every job that writes (save, `create`, `copy`) has the same commit-point step; a journal whose recovery is cancelled or crashes, and every journal not tried because the engine cannot run, counts as blocking (only the workspaces and copies that use its files, with Retry and "Keep the files as they are now"), and recovery goes on with the others, so no workspace opens over an untried journal; a journal is written as `.part`, synced and renamed `.open`, and recovery deletes a `.part`; the save re-checks the full fingerprint under the locks after its load and before the commit point (ADR-0013); Quit and `close()` signal the engine's group once and exit without waiting for the reap; "no live member" of a process group is defined per OS, ignoring zombies; the engine's parent-death watchdog ends the engine's whole process group; `create` and `copy` (replaced by decision 11: they write the new folder directly and the workspace manifest last).
11. **The review-6 rules** (owner, review 6: "I agree with the four simpler policies and two decisions that you proposed."), four simpler policies that delete mechanism and two decisions:
    - **P1:** a save's temp counts as a displaced outside save only when its file already holds the post bytes; otherwise recovery deletes it, whatever it holds. Rollback and recovery use their own temp names, deleted without a check.
    - **P2:** `create` and `copy` write the new folder directly, read every file back, run the "loads the same" check there, and write the `.finzytrack/` manifest last; a folder without a manifest is not a workspace, so a crash leaves only a folder the user can delete. The manifest write is the commit point; a non-empty target is refused before any write. Review 5's staging folder, exclusive rename and staging record are dropped.
    - **P3:** if an engine fails to start, its bytecode directory is deleted and the engine started once without it, so the directory is rebuilt.
    - **P4:** an engine stuck in the kernel on a dead disk, which Cancel cannot end, is an honest limit: the user is told to quit and reopen Finzytrack; on the next start the orphan's held locks make that journal blocking without touching the disk.
    - **D1:** a refusal because another program changed a file says so and offers Review; reads keep working and the workspace does not enter `RECOVERING` (ADR-0008 and ADR-0012 amendments).
    - **D2:** after the same R4 has failed to run three times (a count, not a time), the user is shown the backup and offered Resume saving with a confirmation, as for a mismatch; the gate is relaxed only by that explicit action (ADR-0008 amendment).
    - Also (agent, the review's small fixes): after a protocol violation past the commit point the engine's input is closed, so it exits after the request in hand; Quit anyway says the change "may be undone", and the next start says whether it was saved or undone; a workspace's records are matched by registry key or lineage id, so forget and re-add keeps an owed R4 and a pause.
12. **After review 7** (0 High, 7 Medium), the owner ended the review loop: "Let's do B. That still enables us to get to a watertight spec and implementation, right? Just that instead of uncovering issues by review, we will uncover them through a formal model checker? And we'll also get an insight into how long that model checking takes?" (2026-10-27, in session, relayed by the orchestrator; PROCESS.md §3, IMP-0038). The fixes (agent, within the decided design): one rule for Cancel (quick check 9): another job's Cancel ends the running job only when nobody waits for it, the user did not confirm it and it has not reached its commit point; otherwise the waiting user's Cancel cancels only their own request and answers that the earlier work cannot be stopped from here and, if it never finishes, to quit and reopen; quit advice appears on a timer only for a process that did not die after we signalled it; after a quit, a sidecar that has not exited can be signalled with "Quit now" and the shell exits at once; a relaunch that finds a leftover sidecar holding the instance lock says it is still closing; a `create` or `copy` stops only on a collision with a name it writes; the quit note has a third branch ("has not been undone yet") and is kept until the journal is resolved or kept; an R4 superseded by an engine-build change publishes the new build's real load; a copy is refused while any `.open` journal names a source; `create` and `copy` create files and folders exclusively; the boot ends on success, failure or block, with Retry, Keep and another workspace; the update refuses with Reopen on an in-session `.open` journal. A targeted review of the changed sections, the convergence audit and the TLA+ model follow.

## Alternatives considered and rejected

- **Parallel engines: engines as slots behind the sidecar's queue, with a computed or fixed slot count** (the 2026-10-26 design). Rejected (owner): it never makes one save faster, and four review rounds kept finding Highs in the mechanisms it needed.
- **Preempt background work when the user starts a job** (agent). Rejected: R4 would only move from before the user's preview to inside the next save, so the save sequence takes as long; it costs an engine start and repeated work, and adds a rule.
- **A time limit per job, or a heartbeat that calls a silent engine hung.** Rejected (owner: "no automatic killing of slow jobs"): neither tells a slow job from a hung one, and a limit is a fixed budget that a slow computer or a big ledger crosses.
- **Recovery inside the session after an engine death** (agent). Rejected: it needs an amendment to ADR-0012 Q30 and a recovery path beside ADR-0063's open path; Reopen gives the same result with one click on a rare path.
- **One long-lived engine across jobs** (agent). Rejected: a plugin can leave threads, patches to Beancount and memory behind, which would reach the next job's checks (the owner's 2026-10-26 decision 5); a fresh start costs 0.05-0.10 s with the bytecode directory.
- **R4 inside the save, before "saved".** Rejected (owner): it adds a full load to every save (S4: 5.5 s instead of 3.0 s at 54k in 12 files), with no safety gain, since R4 still gates the next save.

## Amendment (2026-10-27): fixes found by the model

Owner, on the process (PROCESS.md §3 "Golden specs"): "We'll then produce the model from that, the run it, make any needed changes and run the whole loop again." The TLA+ model of `design/specs/engine-jobs.md` (`formal/tla/engine-scheduler/`) and its independent review found these spec issues; the spec now states each fix (agent, applying that process; a targeted review of the changed sections and the affected model configurations follow):
- **F1:** the outcome check after an engine death (§6.6) and the next start (§8.1, §9.3) read a save's record only after a `durable_sync` of its directory, so "saved" or "unfinished" is never told from a rename a power loss could take back.
- **F2:** the in-engine rollback (§6.4) first applies recovery's checks, the temp rule included, so it never deletes an outside save a swap had just displaced.
- **F3:** a swap-back is synced at once.
- **F4:** a switch or boot that shows its failed or blocked screen frees the queue for app-scoped jobs (§3).
- **O1:** R4's confirm checks the fingerprint once more after the parse; moved → superseded, never a false mismatch (§6.7).
- **N1:** "Keep the files as they are now" syncs the files and folders the journal names before renaming it `.kept`, so what it keeps survives a power loss (spec §8.1, §9.2).
- **N2:** `AppScopedWaitsForRecovery` says a create or copy does not *start* during recovery, matching §3 and §9.1; behaviour unchanged.
- **N3:** the quit advice for a signalled process that holds the engine slot past the display delay is shown whether or not a job still waits, never for work that is merely slow (spec §5.2).
- **Fidelity review 2** (owner, 2026-10-28: "Yes, go ahead"): a restore writes its temp from the backup and syncs the temp's data before the swap (H1); every rename of an R4 record is followed by a sync of the journal directory before its outcome is acted on or shown (M5); a switch's or the boot's own queued job can be cancelled by the user, ending on a failed screen with Retry and Back (or Open another workspace at boot) (M4).
- From the model review: the manifest rename that collides after the commit point has a stated outcome (§8.2 step 7); one quit note per job (§9.3); §13 states the liveness properties as the model must encode them, the file-system assumptions, and `AppScopedWaitsForRecovery`; the engine is spawned when a job needs one (§5.5, convergence audit C29).
