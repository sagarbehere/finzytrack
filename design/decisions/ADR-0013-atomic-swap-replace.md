# ADR-0013: Replace by atomic swap; the external-editor race is accepted with detection

This record decides how a write detects an outside program that saves the same file at the same moment.

- **Status:** Accepted. Amended on 2026-10-29 (S0060): a ledger file with a second hard link refuses the save; what the swap keeps of a file, and what it does not; volumes without the swap are refused until their fallback slice (BL-0160). Amended on 2026-10-29 (S0061): nothing is swapped back; an outside save a swap or a clean-up meets goes to a kept name beside the file. Amended on 2026-10-30 (S0061 round 6, owner): a folder the save or the undo writes in that carries an ACL deny entry applying to us is refused, except a non-inherited one that protects only the folder itself (macOS's own entries). Amended on 2026-10-30 (S0061 round 7, owner): any deny entry refuses, whoever it names; the journal and backups folders are judged by the same rule. Amended on 2026-10-31 (S0065, agent, under the owner's 2026-10-29 answer): the fallback on volumes without the swap is built.
- **Date:** 2026-10-24
- **Deciders:** owner
- **Area:** write path, data safety

## Context

An editor, Fava or a sync client may save a ledger file between our final fingerprint check (under our lock) and our replace. Such tools do not take our locks. Read-back after `os.replace` cannot see it, because `rename` unlinks the displaced inode and its bytes are gone. Full prevention would require locking the user's editor out.

## Decision

(owner, 2026-10-24) **Accept the race, keep its window minimal, and detect it.**
- Re-check the fingerprint immediately before each replace, under the lock.
- **Replace by atomic swap:** macOS `renamex_np(RENAME_SWAP)`, Linux `renameat2(RENAME_EXCHANGE)`, Windows `ReplaceFileW` with a backup name. Then hash the displaced file and compare it with the planned pre-hash.
- **On a mismatch,** an outside save landed: its bytes are kept, and the user is told ("Your editor saved this file at the same moment. Review this file."), with the backup available.
- **Focus check:** when the window regains focus, a file that differs from our last post-hash gets the notice "A change you made in Finzytrack was overwritten by another program", with the backup.
- Where swap is unavailable, the documented window remains, and the user docs say so.

## Alternatives considered and rejected

- **Plain `os.replace` with read-back.** Rejected: it cannot detect the race.
- **Locking the user's editor out of the file.** Rejected: not possible without the editor's cooperation.
- **Ignoring the race.** Rejected: a silent lost edit violates priority #1.

## Consequences

- The TLA+ property is `ExternalEditNeverSilentlyLost`.
- The swap primitive is OS-specific code in the file-system adapter, tested on all three OSes in the packaged matrix.

## Amendment (2026-10-29): hard-linked files, and what the swap keeps (S0060)

- **Deciders:** owner, 2026-10-29, in session, relayed by the orchestrator, answering `design/inbox/answered/20261029-hard-linked-ledger-files.md`: "Refuse to save it (Recommended)". The option as shown: "Before writing anything, a ledger file with more than one hard link refuses the save with a message naming the file: remove the extra link or copy the file first. Reads and reports still work. Simple, fails closed, can be lifted later."
- **Why:** the swap gives the name a new file, so a second hard link to a ledger file would keep the old bytes without anyone being told (S0060 data-safety red team, finding 1). Options 2 (save and warn) and 3 (write in place, losing the swap's crash safety) were rejected by that answer.
- **Decision:** before the save writes anything, a ledger file it replaces whose link count is above 1 refuses the save, naming the file ("not saved", the ledger unchanged after the re-hash). Reads, reports and the other files are not affected. It is checked again when the file is backed up. One function holds the rule (`ledger_engine.ledger.writer._hard_links`).
- **What the swap keeps** (proposed by the agent; owner, 2026-10-29, approving this bullet: "Approve it (Recommended)", the option reading "The bullet stays in ADR-0013, adjusted to your ACL answer, with your approval quoted."; and answering what a save should keep: "Keep xattrs, drop ACLs (Recommended)", the option reading "Copy extended attributes (Finder tags) only; a file's ACL is not kept by a save (stated as a limit). A file whose ACL forbids the swap (deny delete) is refused before anything is written."): the swap keeps the file's mode and extended attributes (Finder tags; copied to the temp before the swap, `fcopyfile` with `COPYFILE_XATTR` on macOS). It does not keep the file's ACL, the owner (the new file belongs to the user running Finzytrack, who owns their ledger files), the BSD flags (`chflags hidden` and the like) or the inode number. A locked file (`uchg`, append-only), and a file or folder whose permissions or ACL would block the swap or its clean-up (a read-only ledger folder, deny delete on the file, deny delete_child on the folder, extended attributes that cannot be read), refuse the save before anything is written. These are stated as limits in `design/specs/engine-jobs.md` §15.
- **Volumes without the swap** (exFAT, FAT, some network shares: no `RENAME_SWAP` or `RENAME_EXCL`). Owner, 2026-10-29, answering what should happen there: "Unsafe fallback on such drives"; then, after the trade-offs and the proposal to build it as its own slice with an up-front refusal until then: "Agreed, fallback as its own slice after slice 4". So such a volume gets a non-atomic fallback write path in a later slice (BL-0160, after BL-0151's slice 4), and until it exists a save there is refused before anything is written (`ledger_engine.ledger.writer._volume_without_swap`, which reads the volume's capabilities).
- **Unchanged:** the swap, the displaced-file check and everything else in this record.

- **Code pointer, S0061** (no change to the decision): the two rules' one function each moved with the restore, which shares them with the save: `ledger_engine.ledger.handles.hard_links` (was `writer._hard_links`) and `ledger_engine.ledger.handles.volume_without_swap` (was `writer._volume_without_swap`). The restore applies the hard-link rule too: a file to restore with a second hard link stops the journal instead of being swapped.

## Amendment (2026-10-29): nothing is swapped back; outside saves go to a kept name (S0061)

- **Deciders:** owner, 2026-10-29, in session, relayed by the orchestrator, answering "Shall I go ahead with the simplification?": "Yes". The proposal as shown:

  > anything we displaced that isn't ours is moved at once to a "kept" name that nothing of ours ever deletes, and the save stops.
  > 1. Swap as today, then check what was displaced.
  > 2. If it is ours, or byte-identical to something we already hold (the pre bytes, which the backup has; or the post bytes we wrote), treat it as ours (deleting it loses nothing).
  > 3. Otherwise do not swap back: rename the displaced object straight to a visible kept name beside the file (e.g. `main.bean.kept-j7`), sync, and stop. Whatever now sits at `main.bean` stays.
  > 4. At clean-up, if a temp we are about to remove holds outside bytes, it is renamed to the kept name instead.
  > 5. Recovery stops while a kept file exists for the journal (the name is derived from the journal, so no new state); the blocked screen shows "the file" and "the kept copy"; once the user deletes the kept copy, recovery can resolve.
  > Removed: the swap-back and its sync, the restore's created-file rename-aside-and-back, the second race window. The review-6 temp rule stays as decided: temps then only ever hold our own bytes or a cut write of ours. In that rare collision the file shows Finzytrack's version and the editor's sits beside it as the kept copy. The instant between our last check and the unlink stays a §15 limit. Touches spec §6.4 and §8.1 and ADR-0013's decision line.
- **Why:** the swap-back opened a second window: a second outside save made in it landed in one of our temp names, and a later ordinary try deleted it under the review-6 temp rule (S0061 data-safety red team round 1, H1 and H2; its M1 was the same family). That mechanism had produced findings in three rounds running.
- **Decision line, as amended:** "Then hash the displaced file and compare it with the planned pre-hash" now reads: then check what was displaced; if it is byte-identical to the pre bytes or to our post bytes, it is ours; otherwise it is an outside save, moved at once to its kept name beside the file, never swapped back, and the save stops. "On a mismatch, an outside save landed: its bytes are kept" holds, in the kept copy.
- **Details (agent, S0061):** the kept name is `<name>.kept-<job>`, then `-2` to `-999` when taken, exclusive (`RENAME_EXCL`), a hash standing in for a name past 255 bytes (`ledger_engine.ledger.core.journal.kept_name`); the save refuses before its first effect an entry already standing at one of a file's kept names and a target at another's; a displaced file with a second hard link still stops the save (the hard-link amendment above). Code: `ledger_engine.ledger.handles.displaced` and `keep`.
- **Unchanged:** the swap itself, the hard-link and no-swap amendments above, and the review-6 temp rule (ADR-0012's amendment of 2026-10-27).

## Amendment (2026-10-30): forward pointer (S0061 round 3)

- The line "**Unchanged:** ... the review-6 temp rule (ADR-0012's amendment of 2026-10-27)" in the amendment above no longer holds: the temp rule was refined on 2026-10-29 and replaced on 2026-10-30 (owner: "Staging name (Recommended)"; ADR-0012's amendment of that date). The swap itself is unchanged; what reaches it changed: the new bytes are written under a staging name, synced, renamed exclusively to the temp name and that rename synced before the swap, in the save and in the restore alike.

## Amendment (2026-10-30): folders with ACL deny entries are refused, except macOS's own (S0061 round 6)

- **Deciders:** owner, 2026-10-30, in session, answering the orchestrator's question `design/inbox/answered/20261030-acl-allowlist.md` (S0061 round 6: data-safety red team F1 High, F2 Medium/High, F3 Medium; verifier F1 and F2 Medium). First the owner asked: "I like option 1, but will it affect usability in the sense that users will need to do something more, in order to write to the typical folders they might use with Finzytrack?". After the orchestrator's check (below), to "Go ahead with the allowlist?": "Allowlist (Recommended)".
- **Why:** round 5 refused a folder whose ACL had an inheritable `deny read` or `deny delete` that applies to us (ADR-0012's amendment of 2026-10-30, Details). Round 6 found more entries that got past it on real APFS: `deny delete_child` on the folder (our staging file could be neither renamed nor removed: the High), an inherited `deny search` into a folder the save makes, inherited `deny readattr` and `deny readsecurity` (our own names could not be `stat`ed), and an entry that appears after a crash, before recovery. The save got halfway, the undo could not remove its own leftovers, and the workspace stayed blocked even after the user removed the folder's entry, because our leftovers had inherited it. Each fix had added a bit to a list.
- **Decision (the allowlist):** the save refuses with the existing `permission` reason, before anything is written, any folder it writes in or makes a folder in when that folder carries an ACL deny entry that applies to us (our user, a group we are in, everyone; a subject the system cannot answer for counts as ours). The one exception: a deny entry that new entries do not inherit (no `file_inherit`, `directory_inherit` or `only_inherit`) and whose bits all protect only the folder itself (`delete`, `writeextattr`, `writeattr`, `writesecurity`, `chown`). Every other deny that applies to us is refused: an inheritable one of any bit, any other bit, an unknown bit or flag, and an ACL the system will not let us read. Allow entries are not weighed (an allow before a deny still refuses: fails closed). The undo (the rollback and recovery alike) applies the same rule at its checks to every folder it would write in (where it removes names of ours, makes a restore temp, or removes a folder the save made), and stops with `permission`, nothing written; once the entry is removed, Retry works, since nothing of ours inherited it. The system's own answer `access(".", _RMFILE_OK)` (may entries be removed here?) is checked beside it on each such folder, and a lock flag on a folder the save made stops the undo before it writes anything (red team r6 overflow 3). The refusal names the folder and, for an ACL entry, the entry in `chmod`'s words without its subject (spec §11).
- **What it covers (facts checked on the owner's Mac, 2026-10-30):** macOS puts `group:everyone deny delete` on the home folder, Desktop, Documents and Downloads, and Desktop and Documents also `deny writeextattr`: neither is inherited, both pass. All 15 subfolders of Documents carry no ACL; iCloud Drive none; the Google Drive root only the same non-inherited `deny writeextattr` / `deny delete` as Documents (passes). Dropbox and OneDrive were not present and are not checked.
- **Cost:** a ledger in a folder with any other deny entry that applies to us cannot be saved until that entry is removed (spec §15).
- **Details (agent, S0061 round 6):** the rule's one place is `ledger_engine.ledger.handles.blocking_entry` (with `acl_denial`, the text for the refusal); the port reads a folder's entries (`DirHandle.acl`, which replaced `inheritable_denial`); the macOS adapter reads each entry's kind, subject (`mbr_uid_to_uuid`, `mbr_check_membership`), permission and flag bits with libc's getters and cross-checks the words they point at (a bit libc does not name, or a disagreement, is `unknown`); `_RMFILE_OK` is `Right.REMOVE_ENTRIES`. Probed on APFS (macOS 26.6.2) before relying on it: `access(W_OK|X_OK)` answers yes and `_RMFILE_OK` no under `deny delete_child`; both no under `deny search` and under a lock flag; `deny readattr` or `deny readsecurity` on a file makes its `lstat` answer `EACCES`, and on the folder itself makes `acl_get_fd_np` answer `EACCES`; a `file_inherit`-only entry is not passed to a subfolder, a `directory_inherit` one is, with `only_inherit` dropped.
- **Unchanged:** "Keep xattrs, drop ACLs (Recommended)": the swap still does not keep a file's ACL; the entries on the files themselves are still judged by the existing checks (`access(_DELETE_OK)`, `_REXT_OK`); everything else in this record.

## Amendment (2026-10-30): any deny entry refuses the folder, whoever it names; the journal and backups folders too (S0061 round 7)

- **Deciders:** owner, 2026-10-30, in session, answering the orchestrator's question `design/inbox/answered/20261030-acl-any-subject.md` (S0061 round 7: data-safety red team F1 High, F2 Medium, F3 Low; verifier F1 Medium): "Any subject (Recommended)". Then, to the orchestrator's proposal that unusual ACLs be handled by policy rather than by defences, that the option's clean-up of our leftovers' ACLs be dropped and recorded as a spec §15 limit, and that one final review round count only lost, torn or overwritten bytes or a false "saved" as High: "Yes. And don't got digging yourself into holes like this one".
- **Why:** to decide whether a deny entry "applies to us", round 6 asked macOS whether we are a member of the entry's subject. For macOS's special subjects `owner` (whoever owns the file) and `group` (the file's group) the membership lookup answers "not a member", yet the kernel applies them to us: we own our files, and every folder under the home folder has group staff. `group:owner deny delete,file_inherit` therefore got past the rule; the save broke half-way and every undo stopped on our own staging file, which had inherited the entry, even after the user removed it from the folder (red team r7 F1, reproduced on APFS). The journal and backups folders were not judged at all (round 6's agent choice (g)), though the owner's round-6 decision covers "any folder they write in" (verifier r7 F1, red team r7 F3).
- **Decision, superseding the round-6 amendment's "that applies to us (our user, a group we are in, everyone; a subject the system cannot answer for counts as ours)" and its "Every other deny that applies to us":** **any deny entry refuses the folder, whoever it names** (our user, a group, everyone, `owner`, `group`, another user, a subject the system cannot resolve). Whom an entry names is never asked. The one exception is unchanged: a deny entry that new entries do not inherit and whose bits all protect only the folder itself (`delete`, `writeextattr`, `writeattr`, `writesecurity`, `chown`), which covers macOS's own entries. The save checks the journal folder and the backups folder by the same rule (write and search, `_RMFILE_OK`, the ACL rule) before it writes the backups or the `.part`, and refuses with `permission` naming that folder; recovery's per-journal try, and the restore's step 0 for the rollback, check the journal folder before a record is read or renamed (`Stopped(permission)`, naming it).
- **Not built (the owner's second answer):** the option's "The undo removes the ACL from a file of ours just before deleting it." An entry added to a folder during a save, after the check, can be inherited by a hidden file of ours, by the saved ledger file or by the journal record; the undo then cannot remove or read it, and the workspace stays blocked; nothing is lost. The way out is to remove the entry from the folder and from that file (`chmod -N`, which works even under an inherited `deny writesecurity`: probed), then Retry; slice 3's blocked screen names the file (`entry`). Spec §15.
- **Cost:** a ledger folder (or the app's journal or backups folder) with a deny entry for another user, on a shared Mac, is refused too until that entry is removed. On the owner's Mac every deny entry found is macOS's own non-inherited kind, which passes (checked again in round 7 through the new rule: the home folder, Desktop, Documents, Downloads, Library, Application Support, Music, Pictures, Public).
- **Details (agent, S0061 round 7):** `AclEntry` carries no subject (`deny`, `perms`, `flags`); the adapter's membership code (`mbr_uid_to_uuid`, `mbr_check_membership`, `acl_get_qualifier`) is gone; `handles.blocking_entry` stays the rule's one place, and `handles.folder_blocked` the folder rule's (write and search, `_RMFILE_OK`, the ACL rule), used by the save's ledger-folder and app-folder checks and the restore's journal-folder check. The in-memory fake keeps the kernel's knowledge of whom an entry applies to as its own (`outside_acl(..., applies=...)`), so tests can show an entry the kernel does not apply to us is refused anyway.
- **Unchanged:** everything else in the round-6 amendment, "Keep xattrs, drop ACLs (Recommended)", and this record.

## Amendment (2026-10-31): the fallback on volumes without the swap (S0065, BL-0160)

- **Deciders:** owner, 2026-10-29 (the amendment of that date above): "Unsafe fallback on such drives"; then "Agreed, fallback as its own slice after slice 4". This amendment records how the agent built it; it changes no owner decision. Spec: `design/specs/engine-jobs.md` §6.8, §15 ("Drives without the swap").
- **Decision (agent, S0065):** the write path is chosen per folder before any effect, from the volume's capabilities (`ledger_engine.ledger.handles.write_mode`): the swap where the volume offers `RENAME_SWAP` and `RENAME_EXCL`, else the fallback. The fallback keeps everything of this record but the swap: the staging name, the exclusive move to the temp name and its sync, then the file **hashed again just before a plain rename** of the temp onto it (the record's "Where swap is unavailable, the documented window remains, and the user docs say so"); a created file by `RENAME_EXCL`, or where the volume has no exclusive rename by an exclusive create (`O_EXCL`) of the file itself; exclusive moves of our own names by a check just before a plain rename there. The undo mirrors it, and puts back from the backup a file that a power loss left missing in the middle of a replace (a volume without a journal): by `RENAME_EXCL`, or where the volume has no exclusive rename by first claiming the empty name with an exclusive create of an empty file, then the re-hash and the plain rename onto that claim (round 1, F1: a check then a plain rename onto the ledger file's own name could replace another program's file). On a network volume, `EEXIST` or `ENOENT` after a retried operation is ours only when the source is gone and the target is the same object (a `mkdir`: an empty folder). The up-front refusal (`volume_no_swap`) is gone. The macOS adapter refuses `swap` and `rename_excl` where the volume's capabilities lack them, before the call: probed on macOS 26, FAT answers `RENAME_SWAP` with success and replaces the second file.
- **The windows that lose atomicity** (spec §15, the user docs and the open's notice say so): W1, an outside save between the re-hash (from its read's start) and the plain rename is overwritten, and so is a write into the old file through a descriptor opened before the rename, in the save and in the undo alike (which still says "undone"); W2, an entry another program puts at one of our derived names between the check and the rename is replaced (no exclusive rename); W3, on exFAT and FAT a power loss can split a replace (the file missing, put back from its backup) or damage the folder; W4, a crash while a created file is written in place leaves part of it there (recovery asks the user); after a write error the save removes that part, checked to hold only our bytes just before.
- **Alternative considered and rejected (agent):** a move-aside replace (the file renamed exclusively to a fifth name of ours, our temp renamed onto the free path, what was moved aside checked as the swap checks what it displaced). It would keep both versions in W1 on HFS+ (which has the exclusive rename), at the cost of two new names of ours beside every file (the save's and the restore's), a missing-file state after every crash between the two renames on every such volume, and a third rename per file. Rejected under the owner's "Unsafe fallback": W1 is milliseconds, the re-hash shrinks it to the read and the hash, and the owner asks that each mechanism be tied to the requirement it serves. It stays available if real use shows W1 losses.
- **Unchanged:** the swap path (APFS), its displaced check, the kept-name design, the temp rule, the hard-link and ACL rules, and everything else in this record.
