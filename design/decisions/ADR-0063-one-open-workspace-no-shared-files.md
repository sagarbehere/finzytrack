# ADR-0063: One open workspace at a time, and every unfinished save recovered before any workspace opens

This record decides that a Finzytrack instance works with one open workspace at a time, that opening another one is a switch, and that every interrupted save in the app is recovered before any workspace opens.

- **Status:** Accepted
- **Date:** 2026-10-27
- **Deciders:** owner: "1. Yes to forbidding two workspaces sharing a file. If it'll help we can simplify further: No sharing anywhere, no multiple instances of Finzytrack anywhere. Period. Finzytrack is just about one instance, working with one workspace at a time. Switching between workspaces should work well, without issues. The switch should do whatever book-keeping that is needed. Fine to tell the user something like, "Just a moment.. switching workspaces." or similar, if the switch takes time." (2026-10-27, in session, after the fourth review of the engine-scheduler design). The owner confirmed three agent decisions: "I agree with the territory rule and am confirming the three decisions the agent wrote in ADR-0063." (2026-10-27, in session, relayed by the orchestrator). The three are: sharing a workspace between users in hosted mode is excluded (decision 3); no idle container is kept warm (decision 1); the overlap check works from the registry alone, without opening other workspaces. That third one is now moot, since decision 2 no longer checks overlap at all. Decision 2, the recovery rule, replaced the territory rule after the S0045 verifier's round 2: the orchestrator proposed it and the owner answered "Yes, write both into the hand-off and give me the prompt" (2026-10-27, in session, relayed by the orchestrator). What this ADR adds beyond those words is marked "(agent)".
- **Area:** workspaces, API, lifecycle, data safety, hosting
- **Supersedes:** in ADR-0018, "several native windows on different workspaces are architecturally allowed" and "browser tabs already work" for different workspaces, and the switch as "after the backend has opened and validated B" while A stays open; in ADR-0012, "recovery runs when the workspace is next opened", which becomes "before any workspace opens, for every journal in the app" (ADR-0012 amendment); in ADR-0021, "Copy to workspace…" writing into a workspace that is not open; in ADR-0041, "sharing a workspace between users" on the deferred list; the scheduler spec draft 3's mechanisms for two workspaces that share a file (`design/specs/engine-scheduler.md` §5.7 and the INV-31 exception it proposed, owner answer (b) of 2026-10-27), which are no longer needed.
- **Unchanged:** the workspace-addressed API (ADR-0018): every workspace-scoped request names its workspace, and a request, response or write never acts on another; "a write started in A always completes in A"; ADR-0017, including the registry deduplicated by canonical root and external-ledger references; ADR-0062's single instance per app root and Copy-only legacy adoption; ADR-0013's detection of outside editors (Fava, a text editor, a sync client); ADR-0012's journal and per-file recovery rule, and Q30; ADR-0011's per-workspace write limiter; copy-based sharing of settings (ADR-0021); content packs shared read-only by reference; INV-25, INV-27, INV-29 and INV-30 as written; INV-28 and INV-31 as reworded with the owner's approval (decision 5).

## Context

ADR-0017 deduplicated the registry by root only, so two workspaces could include the same file, for example a shared `prices.beancount`, and ADR-0018 allowed several workspaces to be open at once (browser tabs, later several windows). The engine-scheduler design had to make that safe. By its fourth review (owner's private archive, `m1a/scheduler-design/review-4/REPORT.md`), most of its High findings sat in mechanisms for two workspaces sharing a file: an app-wide journal index with no durable order, a lock key that changes when a shared file is created, one workspace waiting for ever on another's unrepairable save, a save in one workspace waiting for a rebuild that a save in another made necessary, and an exception to INV-31 so that a closed workspace's save could be repaired from an open one.

Example of the risk: workspaces *Personal* and *Business* both include `prices.beancount`. A save in *Personal* is cut off half-way (the computer loses power). *Personal*'s journal knows how to undo it, but recovery ran only when *Personal* was opened. You open *Business* first: it reads the half-written prices file, and a save there writes on top of it. When *Personal* is opened later, its recovery finds bytes it did not write.

The danger is never the sharing itself; it is reading or writing a file while another workspace's save on it is half-applied. With one open workspace, two saves never run at once, so the only half-applied files are those of a save cut off by a crash or a failed rollback, and every one of them is listed in a write journal in app-local data.

Two attempts to prevent sharing failed review. A file-by-file check missed files a save creates (S0045 verifier round 1, F1): *A* includes `../B/imports/*.beancount`; a save in *B* creates `imports/2027.beancount` and is cut off before *B*'s root names it; *A* then opens over the half-applied file. A territory rule (each workspace owns its folder, and its files stay inside) missed paths that change after the check (round 2, F-W): after *A* opens, an outside program replaces `A/imports` with a symlink to `B/imports`; *A*'s save creates a file there, is cut off, and *B* opens over it. Every new way to reach a file was a new hole: symlinks made later, folders moved, globs, `../` in a documents path, the moment between a check and a registry write. Both examples are harmless when every interrupted save is undone before any workspace opens.

## Decision

### 1. One open workspace per instance (owner, 2026-10-27)

- **A Finzytrack instance has at most one open workspace.** Open means: its `WorkspaceContainer` exists, it accepts requests, and jobs run for it (mirror build, saves, R4, background price fetch). Boot opens at most the last workspace (or the one `--workspace` or a file association names).
- **Opening another workspace is a switch**, which closes the current one first. Requirements (the scheduler spec defines the jobs, their order and the waits):
  1. **The leave guard runs first** (unsaved edits: save, discard or stay; ADR-0018, CAP-WS-SWITCH).
  2. **The target is assessed before anything closes** (agent). A cheap probe and `assess_workspace` read the target without writing it. If the target needs the user (unavailable, newer, invalid config, upgrade consent, an unfinished save that cannot be undone, decision 2), its screen is shown with **Stay**, and the current workspace stays open and untouched. Nothing is recorded (INV-29). A journal that names a file the target uses, and that looks recoverable read-only (every file it names is reachable and holds its pre or post bytes), makes the target report `RECOVERING`. That needs no answer from the user, so the switch goes on, and the recovery runs in step 6.
  3. **The switch does the book-keeping, and never loses or half-applies anything.** New work for the current workspace stops. Work that can end without loss ends (reads, previews, rebuilds, queued background jobs). Work that must finish finishes: a save the user confirmed (closing is not a cancel; whether a save that has not reached its commit point may still be cancelled by the user is the scheduler's), a running recovery. Work owed to the workspace (an R4 check after a save) either runs before it closes or stays durably recorded for its next open, as the scheduler spec decides; it is never dropped. A preview that was not confirmed (a `PlanStore` plan of the current workspace) is discarded, which loses nothing, since nothing was applied. Import sessions, AI threads and UI memory survive (they live in `local/<key>/`, the user container and scoped storage; CAP-WS-RESUME).
  4. **While the switch waits, the user reads "Just a moment… switching workspaces."** Every wait has an exit (agent): until the current workspace has closed, **Stay** cancels the switch and leaves it open; a save past its commit point is never cut off by the switch (if the user quits instead, the journal makes that safe, as for quiesce).
  5. **The current workspace closes completely**: its container, caches and handles are released (INV-31), and closing writes nothing to its folder (INV-30). No idle container is kept warm for a quick way back (agent, confirmed by the owner; this replaces ARCHITECTURE §2.5's "at most 1 idle container kept warm"). A switch is quick when the target's published mirror is fresh, which is on disk and does not need a warm container.
  6. **Every unfinished save in the app is recovered, then the target opens by the normal path** (decision 2): the assessment runs again on the recovered files, the fingerprint check rebuilds the mirror if any file changed (ADR-0015), and "last opened" is recorded only on `READY`/`WARMING` (INV-29). If it fails after the current one has closed (a recovery stopped, its files changed since step 2), its screen offers **Back to <previous workspace>**, which opens that one by the same path.
  - At no moment do two workspaces accept requests or run jobs.
- **A request for a workspace that is not the open one is refused, never served** (agent: the code). Every `/api/w/{ws}/…` request whose `{ws}` is registered but not open, also while a switch is closing it, gets `409 WORKSPACE_NOT_OPEN {open_workspace, switching}`, changes nothing, and is never redirected to the open workspace. An unknown `{ws}` is still `404 WORKSPACE_UNKNOWN`; the open workspace while it warms or recovers is still `409 WORKSPACE_NOT_READY {phase}` (ADR-0018). Example: in headless mode, tab 1 shows *Personal*; tab 2 switches to *Business*. Tab 1's next save names *Personal* and is refused; tab 1 says "Finzytrack switched to *Business* in another window." and offers to switch back. It never writes to *Business*.
- **App-scoped work may read a workspace that is not open, never write it or run its jobs** (agent): the switcher's status probe, the assessment of step 2, and reading files to copy them (a test copy, "New workspace from settings of…"; decision 2 says when a copy is refused). Creating a new workspace (create, adoption, test copy) writes only the new, not yet registered folder, then registers it; it does not open it unless the user switches to it. The one write outside the open workspace is recovery (decision 2).
- **Several native windows on different workspaces are cut** (CAP-WS-MULTIWINDOW). Several windows or tabs may show the one open workspace.

### 2. Recover every unfinished save before any workspace opens (owner, 2026-10-27: the recovery rule)

- **When:** before any workspace opens, that is at start before the first open and at every switch after the current workspace has closed (decision 1 step 6), the app recovers every write journal it holds. Journals live in app-local data (`local/<key>/`, ADR-0012), so all of them are found by listing `local/`, without opening any workspace and whether or not the journal's registry row still points where it did.
- **How:** by ADR-0012's per-file rule, unchanged: a file that holds its pre bytes needs nothing; one that holds the save's post bytes is restored to its pre bytes; anything else stops that journal. ADR-0012's order with lifecycle run records is unchanged.
- **What a journal names** (agent, the condition that makes this work): every file its save replaced or created, each by its canonical path, resolved once when the journal is written, before the first replace; the save then writes exactly those paths (ARCHITECTURE §9.2 step 4). A created file's pre state is "absent", so its recovery removes it only if it still holds the post bytes. Because the paths are fixed at write time, a glob that matches the file later, or another workspace that reaches it through a symlink, does not change what the journal undoes. Recovery writes a recorded path only while it still resolves to that same canonical path, so a folder moved or replaced by a symlink since the crash is never written through; the journal then counts as unrecoverable (below). With ADR-0012's hash check, recovery never overwrites bytes the save did not write (`RecoveryNeverClobbersForeignBytes`). A small model of these cases (S0045 journal, fix round 2) fails without that path check: a link made after the crash sends the restore into another folder.
- **A journal that cannot be recovered blocks only the workspaces that use a file it names** (agent: the code). It cannot be recovered when a file it names is unreachable (an unplugged disk, a share that is offline), no longer resolves to its recorded path, holds foreign bytes, or is locked by a live writer (ADR-0012: an orphaned engine of a crashed session, Q30); a newer journal format is refused too (ADR-0012). It stays, and is tried again before the next open. A workspace *uses* a file when the file is in its ledger set: a file it loads, or a file under one of its documents folders (the `documents` option may name several). Opening any other workspace that uses a file such a journal names is refused with `RECOVERY_BLOCKED {path, workspace}`: "accounts.beancount has an unfinished save from *Personal* that could not be undone. Open *Personal* to fix it." Files are compared by the write path's canonical identity (`path_key`, defined in the scheduler spec). The journal's own workspace opens in ADR-0012's stopped state (writes blocked, both versions shown), which is where the user resolves it; if its folder is unreachable, it reports `LEDGER_UNAVAILABLE` as before. Every workspace whose files the journal does not name opens normally.
- **Why this is enough** (agent): only one workspace is open, so two saves never run at the same time, and each save finishes or is recorded before a switch closes its workspace. The only half-applied files are therefore those of a save cut off by a crash or a failed rollback, every one of them is named in a journal, and every journal is resolved or blocking before any workspace reads files. After that, a file another workspace changed is an ordinary outside edit: the open's fingerprint check sees it and rebuilds the mirror (ADR-0015), and the commit's fingerprint check refuses a save planned on old bytes (ADR-0008). An R4 check owed to a workspace runs at its next open against the files as they then are; another workspace's later save is an outside edit to it, as Fava's would be.
- **Where recovery writes** (agent; the reading of INV-30, INV-31 and ADR-0012): recovery may restore files of a workspace that is not being opened, for example *Personal*'s interrupted save recovered at the start of a session that opens *Business*.
  - INV-31 ("only the open workspace accepts requests or runs jobs") holds as written: recovery runs only while no workspace is open (at start before the first open, and at a switch after the current workspace has closed and before the target opens). It is a step of the app's open path, not a job of any workspace, and nothing else runs meanwhile.
  - INV-30's stated exception is "write-journal recovery on open". This ADR reads it as covering recovery run by the open path, whichever workspace's journal it is. Recovery writes only the bytes the folder held before the interrupted save, the same bytes the journal's own workspace would restore at its next open. It shows the same one-line notice, naming the workspace: "Finzytrack undid an interrupted save in *Personal*." Since INV-30's words can also be read as "the workspace being opened", a clarifying text is proposed to the owner (decision 5); the INV-30 text is not edited here.
  - ADR-0012's "when" changes: recovery runs before any workspace opens, for every journal (ADR-0012 amendment). "Before any other step" still holds for the workspace being opened, and Q30 is unchanged: recovery runs only in the open path, under the journal's file locks taken without waiting, and a held lock means a live writer, so that journal is skipped and stays.
- **Copies read only recovered sources** (agent; S0045 verifier round 2, F-C). A test copy, a Copy adoption and "New workspace from settings of…" read files of a workspace that may not be open. Every journal that could be recovered was recovered before the current workspace opened, and the open workspace's own saves are serialized with the copy's read by its ledger-set lock (ADR-0012 Q29). So the one case left is a journal that could not be recovered: a copy whose source includes a file such a journal names is refused with `RECOVERY_BLOCKED {path, workspace}`, and nothing is written.
- **Forget and Locate wait for recovery** (agent). A workspace whose journal is not resolved can be neither forgotten nor located at another folder. Forgetting would delete the only record of what to undo (the scheduler spec draft 3, §4.9, already refuses it; INV-25 is unchanged: forget deletes no file). Locating would point the workspace at a moved copy of the half-applied files while the journal still names the old paths. The message says: "This workspace has an unfinished save in <old folder>. Reconnect that folder so Finzytrack can finish undoing it."
- **Sharing a file between two workspaces stays not supported** (owner: "No sharing anywhere"), and nothing enforces it: the user docs say so, the app does not check it, and under this rule it is harmless. ADR-0017's deduplication by canonical root stays, so the same root cannot be registered twice.
- **Honest limits** (agent):
  - A journal's canonical paths are those of this machine; the same network share mounted at two places has two identities, so while such a journal cannot be recovered, a workspace reaching its file through the other mount is not blocked and may read the half-applied file. Once the journal is recovered, that workspace's next open sees the change through the fingerprint check.
  - The rule sees only this app root's journals, so a second installation, another `--app-root` or another OS account stays unsupported (ADR-0062); to each other they are outside editors.
  - Files a plugin reads by itself are not in the ledger set (scheduler spec §5.8), so a journal naming one does not block a workspace whose plugin reads it.
  - An unreachable journal folder makes each open try it again; the try uses the switcher's cheap probe (ADR-0019), so it does not wait on an offline share.

### 3. No sharing anywhere: every place the docs allowed it (owner, 2026-10-27: "No sharing anywhere")

| Where | Decision |
|---|---|
| Share workspaces (a ledger written by v0.4 and a running legacy app) | Already removed (ADR-0062). |
| Two workspaces including the same file, a glob of one matching the other's files, a documents folder used by two | Not supported, and not checked: harmless under decision 2, since only one workspace is open and every interrupted save is recovered before any opens. The user docs say "one set of files belongs in one workspace". |
| External-ledger reference (ADR-0017) | Unchanged. |
| Several root ledgers in one folder (CAP-WS-MULTI-ROOT) | Unchanged: one in-place workspace per folder, each other root an external reference or a copy (ADR-0017). |
| A retired legacy install's ledgers (ADR-0062 amendment), with v0.3's `option "documents" "../documents/<stem>-<hash>"` | Opened in place or as an external reference, as BL-0101 promises: nothing requires a file to lie inside the workspace folder. A documents folder outside it makes the workspace not portable (INV-27, `assess_portability`), which is shown, not refused. Several such ledgers sharing `data/ledgers/` or `data/documents/` is the unsupported sharing of row 2, harmless. |
| Several open workspaces: browser tabs, several native windows | Ended (decision 1); CAP-WS-MULTIWINDOW cut. |
| "Copy to workspace…" for a dashboard, rule or theme (ADR-0021) | Kept, carried across a switch (agent): the item is held in the user container, the switch runs, and the target asks "Add <item> from <source>?" and validates against its own accounts. Nothing writes a workspace that is not open. |
| "New workspace from the settings of…", test copies, Copy adoption | Unchanged: they copy, so nothing is shared; refused while an unrecoverable journal names a file they would read (decision 2). Two legacy ledgers that included one common file each get their own copy of it, which then diverge (agent: stated in the adoption preview). |
| Shipped dashboards and widgets by `pack:` reference (ADR-0021) | Unchanged: read-only app content, never written, not a user file. |
| App-level settings, the AI provider and key (`app/`) | Unchanged: app state, not a workspace's file; secrets stay scoped per workspace (ADR-0021). |
| A live app-level library of dashboards and rules (CAP-WS-LIBRARY, deferred) | Stays deferred (agent). It would share tool state, not ledger files, so the write-safety reason does not apply, but the owner's "no sharing anywhere" does: building it needs an ADR that revisits this one. |
| Sharing a workspace between users in hosted mode (ADR-0041's deferred list) | Excluded (agent, applying "no sharing anywhere"; confirmed by the owner, 2026-10-27; it would put one ledger set in two user containers). A future plan for it needs an ADR that supersedes this one. |
| Two app roots, a second installation, another OS account | Unsupported, as before (ADR-0062); to each other they are outside editors, detected (ADR-0013). |
| Outside programs on the same files (Fava, an editor, a sync client) | Unchanged: supported and detected, not excluded (ADR-0013). They are not Finzytrack instances. |

### 4. Hosted mode (not built; ADR-0041, INV-11)

"One instance, one workspace at a time" holds per user (agent). A hosted service is one Finzytrack serving many user containers; each `UserContainer` has at most one open workspace, and a switch closes that user's open workspace only. Other users are not affected. Recovery before an open covers that user's journals; workspaces of different users live under separate user roots that the hosted `LoadPolicy` confines (ADR-0041), so one user's journal never names another user's file. Multi-worker coordination stays deferred; whatever it becomes must keep each user's open workspace served by one process at a time. Nothing here forecloses hosting: the limiters, job queue and containers stay where INV-11 puts them.

### 5. Invariants

- **INV-28 and INV-31 are reworded** with the owner's approval of `design/inbox/answered/20261027-workspace-invariants-one-open-no-shared-files.md`: "reword INV-28 and INV-31 and add INV-32 as proposed", and for INV-28's hosted wording "Yes INV-28 should say the same." (2026-10-27, in session, relayed by the orchestrator). INV-28 says a request is served only for the open workspace (in hosted mode, in its user container) and refused otherwise; INV-31 carries the one-open rule.
- **INV-32 is not applied.** The approval above was for a file-by-file overlap rule, and the territory text applied in its place was wording the owner had not seen (S0045 verifier round 2, F-A). Both rules are gone. The recovery rule's INV-32 text, and a clarifying text for INV-30's exception, are proposed in `design/inbox/20261027-inv-32-recovery-rule.md`. Until the owner answers, decision 2 of this ADR is the rule, and BL-0103 builds its tests.

## Alternatives considered and rejected

- **Keep several open workspaces and only forbid shared files.** Rejected (owner, by choosing the decision above; the agent's reasons): several open workspaces need per-workspace lanes competing for engines and memory, cross-workspace priorities, and a quiesce over several workspaces; the owner asked for the simpler model.
- **Keep shared files and make them safe with several workspaces open** (scheduler draft 3). Rejected (owner): it carried most of review 4's High findings, and still needed an exception to INV-31.
- **Check overlap file by file, against each workspace's recorded ledger set** (this ADR's first version). Rejected after the S0045 verifier's round 1: a file a cut-off save created is in no record, so another workspace's glob or not-yet-existing include can open over it (F1); keeping the records fresh needs registry writes outside a successful open (F3, INV-29); a hard link cannot be seen from a record (F2).
- **Territories: each workspace owns its folder, its files stay inside, and territories never meet** (this ADR's second version). Rejected after the S0045 verifier's round 2 (owner: "Yes, write both into the hand-off and give me the prompt"): a check at open cannot see a path that changes later, so a symlink made after open let a save write into another workspace's folder (F-W, High); a folder moved with a symlink left behind made stored keys stale (F-S); a Locate freed a folder while a journal still named files there (F-L); the check and the registry write were not one step (F-T); and it refused v0.3's `../documents` layout, which every retired legacy ledger that stored a document has (F-D). It also needed a new copy mutator to bring outside files in (BL-0104, removed). Decision 2 needs none of it.
- **Recover only the target's own journal before it opens.** Rejected (agent): F1's file was created by another workspace's save, so the target's set cannot be trusted until every journal that could touch it is resolved, and which journals those are can only be known from the files they name, which recovering all of them makes unnecessary.
- **Allow sharing officially, since it is harmless.** Not adopted (owner: "No sharing anywhere … Period."): it stays unsupported, so nothing is built or tested for it beyond decision 2.
- **Route a request for a closed workspace to the open one, or reopen it silently.** Rejected (agent): routing is the shared-pointer bug ADR-0018 removed (a save built in A would land in B), and a silent reopen would let two tabs switch the instance back and forth under each other.
- **Refuse a switch while another window uses the current workspace.** Rejected (agent): the desktop app has one window (single instance, CAP-WS-MULTIWINDOW cut); in headless mode the other tab is told what happened and can switch back, and a lock-out would leave a user stuck behind a forgotten tab.
- **Open the target before closing the current one** (ADR-0018 as written). Rejected (agent): two workspaces would be open during every switch. The read-only assessment first gives the same protection against switching into a broken workspace.

## Consequences

- **Removed from the scheduler design** (draft 5 rewrites it for one engine; `design/journal/S0045-one-workspace-at-a-time.md` lists what it carries from this ADR): the cross-workspace journal index, `RECOVERING {owner_ws}` as a lane of another workspace, recovery of another workspace's journal while a workspace is open, the INV-31 exception of owner answer (b), owner questions (1) and (2) of review 4, the two-shared-workspace TLA+ configuration, and the quiesce over several open workspaces. The per-file locks on canonical paths stay: they exclude an orphaned engine of a crashed session (ADR-0012 Q30, ADR-0062).
- **New work:** BL-0102 (the switch, M2), BL-0103 (the recovery rule, M2). New capability row CAP-WS-RECOVER-FIRST.
- **Nothing users notice is narrowed:** any ledger Beancount loads opens in place (INV-03), wherever its files live. What changes is that an unfinished save that cannot be undone keeps the workspaces using its files closed until it is fixed.
- **Headless users with several tabs** see one workspace at a time; a tab left on another workspace says so and offers to switch back.
- **INV-28 and INV-31** carry decision 1 (decision 5), tested by BL-0028, BL-0031 and BL-0102; decision 2's tests are BL-0103, and its invariant waits for the owner.
