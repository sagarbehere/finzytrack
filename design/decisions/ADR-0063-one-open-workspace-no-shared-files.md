# ADR-0063: One open workspace at a time, and no file in two workspaces

This record decides that a Finzytrack instance works with one open workspace at a time, that opening another one is a switch, and that no file belongs to two registered workspaces.

- **Status:** Accepted
- **Date:** 2026-10-27
- **Deciders:** owner: "1. Yes to forbidding two workspaces sharing a file. If it'll help we can simplify further: No sharing anywhere, no multiple instances of Finzytrack anywhere. Period. Finzytrack is just about one instance, working with one workspace at a time. Switching between workspaces should work well, without issues. The switch should do whatever book-keeping that is needed. Fine to tell the user something like, "Just a moment.. switching workspaces." or similar, if the switch takes time." (2026-10-27, in session, after the fourth review of the engine-scheduler design). What this ADR adds beyond those words is marked "(agent)".
- **Area:** workspaces, API, lifecycle, data safety, hosting
- **Supersedes:** in ADR-0017, "a ledger root belongs to at most one workspace per machine (registry deduplicated by canonical root path)", which becomes: no file of a ledger set belongs to two registered workspaces; in ADR-0018, "several native windows on different workspaces are architecturally allowed" and "browser tabs already work" for different workspaces, and the switch as "after the backend has opened and validated B" while A stays open; in ADR-0021, "Copy to workspace…" writing into a workspace that is not open; in ADR-0041, "sharing a workspace between users" on the deferred list; the scheduler spec draft 3's mechanisms for two workspaces that share a file (`design/specs/engine-scheduler.md` §5.7 and the INV-31 exception it proposed, owner answer (b) of 2026-10-27), which are no longer needed.
- **Unchanged:** the workspace-addressed API (ADR-0018): every workspace-scoped request names its workspace, and a request, response or write never acts on another; "a write started in A always completes in A"; ADR-0062's single instance per app root and Copy-only legacy adoption; ADR-0013's detection of outside editors (Fava, a text editor, a sync client); ADR-0012's journal, recovery on open and Q30; ADR-0011's per-workspace write limiter; external-ledger references (ADR-0017), now bound by the overlap rule; copy-based sharing of settings (ADR-0021); content packs shared read-only by reference; INV-25, INV-27, INV-29 and INV-30 as written.

## Context

ADR-0017 deduplicated the registry by root only, so two workspaces could include the same file, for example a shared `prices.beancount`, and ADR-0018 allowed several workspaces to be open at once (browser tabs, later several windows). The engine-scheduler design had to make that safe. By its fourth review (review in the owner's private archive, `m1a/scheduler-design/review-4/REPORT.md`), most of its High findings sat in mechanisms for two workspaces sharing a file: an app-wide journal index with no durable order, a lock key that changes when a shared file is created, one workspace waiting for ever on another's unrepairable save, a save in one workspace waiting for a rebuild that a save in another made necessary, and an exception to INV-31 so that a closed workspace's save could be repaired from an open one.

Example of the risk those mechanisms guard against: workspaces *Personal* and *Business* both include `prices.beancount`. A save in *Personal* is cut off half-way (the computer loses power). *Personal*'s journal knows how to undo it, but recovery runs only when *Personal* is opened. You open *Business* first: it reads the half-written prices file, and a save there writes on top of it. When *Personal* is opened later, its recovery finds bytes it did not write.

With one open workspace and no shared file, none of this can happen: a workspace's files are only ever written by that workspace's own jobs, and a half-applied save waits, harmlessly, for its own workspace's next open.

## Decision

### 1. One open workspace per instance (owner, 2026-10-27)

- **A Finzytrack instance has at most one open workspace.** Open means: its `WorkspaceContainer` exists, it accepts requests, and jobs run for it (mirror build, saves, R4, recovery, background price fetch). Boot opens at most the last workspace (or the one `--workspace` or a file association names).
- **Opening another workspace is a switch**, which closes the current one first. Requirements (the scheduler spec draft 4 defines the jobs, their order and the waits):
  1. **The leave guard runs first** (unsaved edits: save, discard or stay; ADR-0018, CAP-WS-SWITCH).
  2. **The target is assessed before anything closes** (agent). `assess_workspace` is read-only, and includes the overlap check (decision 2). If the target needs the user (unavailable, newer, invalid config, upgrade consent, a shared file), its screen is shown with **Stay**, and the current workspace stays open and untouched. Nothing is recorded (INV-29).
  3. **The switch does the book-keeping, and never loses or half-applies anything.** New work for the current workspace stops. Work that can end without loss ends (reads, previews, rebuilds, queued background jobs). Work that must finish finishes: a save the user confirmed (closing is not a cancel; whether a save that has not reached its commit point may still be cancelled by the user is the scheduler's), a running recovery. Work owed to the workspace (an R4 check after a save, a queued recovery) either runs before it closes or stays durably recorded for its next open, as the scheduler spec decides; it is never dropped. A preview that was not confirmed is discarded, which loses nothing, since nothing was applied. Import sessions, AI threads and UI memory survive (they live in `local/<key>/`, the user container and scoped storage; CAP-WS-RESUME).
  4. **While the switch waits, the user reads "Just a moment… switching workspaces."** Every wait has an exit (agent): until the current workspace has closed, **Stay** cancels the switch and leaves it open; a save past its commit point is never cut off by the switch (if the user quits instead, the journal makes that safe, as for quiesce).
  5. **The current workspace closes completely**: its container, caches and handles are released (INV-31), and its folder is not written (INV-30). No idle container is kept warm for a quick way back (agent; this replaces ARCHITECTURE §2.5's "at most 1 idle container kept warm"). A switch is quick when the target's published mirror is fresh, which is on disk and does not need a warm container.
  6. **The target opens by the normal path** (recovery on open, assessment, "last opened" recorded only on `READY`/`WARMING`, INV-29). If it fails after the current one has closed (its files changed since step 2), its screen offers **Back to <previous workspace>**, which opens that one by the same path.
  - At no moment do two workspaces accept requests or run jobs.
- **A request for a workspace that is not the open one is refused, never served** (agent: the code). Every `/api/w/{ws}/…` request whose `{ws}` is registered but not open, also while a switch is closing it, gets `409 WORKSPACE_NOT_OPEN {open_workspace, switching}`, changes nothing, and is never redirected to the open workspace. An unknown `{ws}` is still `404 WORKSPACE_UNKNOWN`; the open workspace while it warms or recovers is still `409 WORKSPACE_NOT_READY {phase}` (ADR-0018). Example: in headless mode, tab 1 shows *Personal*; tab 2 switches to *Business*. Tab 1's next save names *Personal* and is refused; tab 1 says "Finzytrack switched to *Business* in another window." and offers to switch back. It never writes to *Business*.
- **App-scoped work may read a workspace that is not open, never write it or run its jobs** (agent): the switcher's status probe, the assessment of step 2, the overlap check, and reading files to copy them (a test copy, "New workspace from settings of…"). Creating a new workspace (create, adoption, test copy) writes only the new, not yet registered folder, then registers it; it does not open it unless the user switches to it.
- **Several native windows on different workspaces are cut** (CAP-WS-MULTIWINDOW). Several windows or tabs may show the one open workspace.

### 2. No file in two workspaces (owner, 2026-10-27)

- **A workspace's ledger set may not overlap any other registered workspace's.** The ledger set is the root, its glob-expanded includes, the price sidecar and the documents folders (ADR-0017); the workspace folder's `.finzytrack/` is one workspace's by construction. Two sets **overlap** when (agent):
  - a file is in both sets;
  - a file of one set lies inside a documents folder of the other;
  - their documents folders are the same folder or one contains the other;
  - a glob include of one matches a file of the other.
- **Identity is the write path's.** "The same file" is decided by the canonical path identity the write path uses for its locks and fingerprints: `path_key` (one folded spelling per file, the same whether the file exists or not) and `canonical_path`, both to be defined in the scheduler spec draft 4 (review 4 H1). A path through a symlink, a case variant or a Unicode-normalization variant is treated as the same file (on a case-sensitive volume this can refuse two distinct files whose names differ only in case: it only refuses more). In addition, two existing files with the same device and inode are the same file (agent: this catches a hard link; it only refuses more).
- **Registering, adopting, creating or opening a workspace whose set overlaps another's is refused**, with a message that names the shared file and the other workspace, for example: "prices.beancount is already part of the workspace *Personal*. A file can belong to only one workspace. Open *Personal* instead, or make a copy of this ledger." Nothing is written or recorded (INV-29). In `assess_workspace` this is the phase `LEDGER_SHARED {path, other_workspace}`; in the plans (`plan_create_workspace`, `plan_adopt_workspace`, the test copy) it is a refusal with the same code (agent: the names).
- **What it is checked against** (agent): each registry row keeps a machine-local record of its workspace's last known set (the files' `path_key`s, the documents folders, the glob patterns), refreshed whenever the set is computed (at open, and at each rebuild after an outside edit). The check compares a workspace's current set with every other row's record. This needs no other workspace opened or reached, so an unplugged disk does not block an open.
- **An overlap that appears later** (an include edited outside the app, a new file that another workspace's glob now matches) **is detected when either workspace computes its set**, at open and at each rebuild of the open workspace, and refused the same way: at open, the workspace does not open; during a session, the rebuild that found it is not published, reads stay on the last published generation, and saves are refused with the same message until the overlap is gone. Because the record is compared both ways and only one workspace is ever open, a stale record can never let two workspaces write one file: whichever of the two computes the overlapping set is refused.
- **A cut-off save keeps its claim** (agent). While a workspace has a write journal that recovery has not resolved, its record stands, so no other workspace can be registered over those files. Forgetting such a workspace is refused until it has been opened and recovered (the scheduler spec draft 3, §4.9, already says so; INV-25 is unchanged: forget still deletes no file).
- **Honest limits** (agent): the check sees only this app root's registry, so a second installation, another `--app-root` or another OS account can register the same files; that stays unsupported (ADR-0062). The same network share mounted at two places has two identities and is not caught. Files a plugin reads by itself are not in the set (scheduler spec §5.8).

### 3. No sharing anywhere: every place the docs allowed it (owner, 2026-10-27: "No sharing anywhere")

| Where | Decision |
|---|---|
| Share workspaces (a ledger written by v0.4 and a running legacy app) | Already removed (ADR-0062). |
| Two workspaces including the same file | Refused (decision 2). |
| External-ledger reference (ADR-0017) | Kept: one workspace may keep its ledger in a folder outside its own. Its set may not overlap any other workspace's, so the same external ledger cannot be referenced twice, nor by a reference and an in-place workspace. |
| Several root ledgers in one folder (CAP-WS-MULTI-ROOT) | Kept while their sets are disjoint (each root has its own `<stem>.prices.beancount`, and documents folders that are not shared). Two roots that include a common file, for example one `accounts.beancount`, cannot both be workspaces in place: open one in place and the other as a copy (agent). |
| A documents folder used by two workspaces, or nested in another's | Refused (decision 2). |
| Glob includes reaching into another workspace's folder | Allowed only while they match no file of another workspace's set; checked at open and at each rebuild (decision 2). |
| Several open workspaces: browser tabs, several native windows | Ended (decision 1); CAP-WS-MULTIWINDOW cut. |
| "Copy to workspace…" for a dashboard, rule or theme (ADR-0021) | Kept, carried across a switch (agent): the item is held in the user container, the switch runs, and the target asks "Add <item> from <source>?" and validates against its own accounts. Nothing writes a workspace that is not open. |
| "New workspace from the settings of…", test copies, Copy adoption | Unchanged: they copy, so nothing is shared. Two legacy ledgers that included one common file each get their own copy of it, which then diverge (agent: stated in the adoption preview). |
| Shipped dashboards and widgets by `pack:` reference (ADR-0021) | Unchanged: read-only app content, never written, not a user file. |
| App-level settings, the AI provider and key (`app/`) | Unchanged: app state, not a workspace's file; secrets stay scoped per workspace (ADR-0021). |
| A live app-level library of dashboards and rules (CAP-WS-LIBRARY, deferred) | Stays deferred (agent). It would share tool state, not ledger files, so the write-safety reason does not apply, but the owner's "no sharing anywhere" does: building it needs an ADR that revisits this one. |
| Sharing a workspace between users in hosted mode (ADR-0041's deferred list) | Excluded (agent, applying "no sharing anywhere"; it would put one ledger set in two user containers). A future plan for it needs an ADR that supersedes this one. |
| Two app roots, a second installation, another OS account | Unsupported, as before (ADR-0062); to each other they are outside editors, detected (ADR-0013). |
| Outside programs on the same files (Fava, an editor, a sync client) | Unchanged: supported and detected, not excluded (ADR-0013). They are not Finzytrack instances. |

### 4. Hosted mode (not built; ADR-0041, INV-11)

"One instance, one workspace at a time" holds per user (agent). A hosted service is one Finzytrack serving many user containers; each `UserContainer` has at most one open workspace, and a switch closes that user's open workspace only. Other users are not affected. The overlap check runs within one user's registry; workspaces of different users live under separate user roots that the hosted `LoadPolicy` confines (ADR-0041), so they cannot overlap. Multi-worker coordination stays deferred; whatever it becomes must keep each user's open workspace served by one process at a time. Nothing here forecloses hosting: the limiters, job queue and containers stay where INV-11 puts them.

### 5. Invariants (owner's; proposed, not edited)

INV-28's rule says "there is no server-side 'active workspace'", and the open workspace is server-side state, so its text must change; INV-31 is the natural home of the one-open rule; and decision 2, on which the scheduler's safety will rely, deserves its own invariant. The proposed texts are in `design/inbox/20261027-workspace-invariants-one-open-no-shared-files.md`. Until the owner answers, `design/INVARIANTS.md` is unchanged and this ADR is the rule.

## Alternatives considered and rejected

- **Keep several open workspaces and only forbid shared files.** Rejected (owner, by choosing the decision above; the agent's reasons): disjoint sets remove the shared-file mechanisms, but several open workspaces still need per-workspace lanes competing for engines and memory, cross-workspace priorities, and a quiesce over several workspaces; the owner asked for the simpler model.
- **Keep shared files and make them safe** (scheduler draft 3). Rejected (owner): it carried most of review 4's High findings, and still needed an exception to INV-31.
- **Allow sharing files that Finzytrack never writes** (a common `accounts.beancount` that only the user edits). Rejected (agent): which file a save writes depends on routing settings, the price sidecar and the user's next action, so "never written" is not a property the app can rely on; and the owner said no sharing, period.
- **Route a request for a closed workspace to the open one, or reopen it silently.** Rejected (agent): routing is the shared-pointer bug ADR-0018 removed (a save built in A would land in B), and a silent reopen would let two tabs switch the instance back and forth under each other.
- **Refuse a switch while another window uses the current workspace.** Rejected (agent): the desktop app has one window (single instance, CAP-WS-MULTIWINDOW cut); in headless mode the other tab is told what happened and can switch back, and a lock-out would leave a user stuck behind a forgotten tab.
- **Open the target before closing the current one** (ADR-0018 as written). Rejected (agent): two workspaces would be open during every switch. The read-only assessment first gives the same protection against switching into a broken workspace.
- **Check overlap by opening or re-assessing every registered workspace.** Rejected (agent): slow, and an unreachable folder would block every open; the recorded sets, compared both ways, are enough because only one workspace is ever open.
- **Also refuse, at save time, creating a file that another workspace's glob would match.** Rejected for v0.4.0 (agent): it makes the write path read other workspaces' records for a rare case whose outcome without it is a clear refusal at the other workspace's next open, never two writers on one file.

## Consequences

- **Removed from the scheduler design** (draft 4, `design/journal/S0045-one-workspace-at-a-time.md` lists the sections): the cross-workspace journal index entries, `RECOVERING {owner_ws}`, recovery of another workspace's journal, the INV-31 exception of owner answer (b), owner questions (1) and (2) of review 4, the two-shared-workspace TLA+ configuration, and the quiesce over several open workspaces. The per-file locks on canonical paths stay: they serialize a workspace's own engines and exclude an orphaned engine of a crashed session (ADR-0012 Q30, ADR-0062).
- **New work:** BL-0102 (the switch, M2) and BL-0103 (the overlap refusal, M2; create and test copy use the same check in M3). New capability row CAP-WS-NO-SHARED-FILES.
- **A narrowing users will notice:** two root ledgers that include a common file can no longer both be workspaces in place. Beancount parity (INV-03) is not narrowed: every ledger Beancount loads still opens; what is refused is a second workspace over the same files.
- **Headless users with several tabs** see one workspace at a time; a tab left on another workspace says so and offers to switch back.
- **INV-28, INV-31 and a new INV-32** wait for the owner (inbox). The enforcement this ADR needs is listed there and in BL-0102 and BL-0103.
