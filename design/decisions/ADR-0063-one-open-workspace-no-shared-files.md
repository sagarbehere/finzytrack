# ADR-0063: One open workspace at a time, and no file in two workspaces

This record decides that a Finzytrack instance works with one open workspace at a time, that opening another one is a switch, and that no file belongs to two registered workspaces.

- **Status:** Accepted
- **Date:** 2026-10-27
- **Deciders:** owner: "1. Yes to forbidding two workspaces sharing a file. If it'll help we can simplify further: No sharing anywhere, no multiple instances of Finzytrack anywhere. Period. Finzytrack is just about one instance, working with one workspace at a time. Switching between workspaces should work well, without issues. The switch should do whatever book-keeping that is needed. Fine to tell the user something like, "Just a moment.. switching workspaces." or similar, if the switch takes time." (2026-10-27, in session, after the fourth review of the engine-scheduler design). What this ADR adds beyond those words is marked "(agent)". The territory rule of decision 2 replaced a file-by-file overlap check after the S0045 verifier's round 1; the owner agreed to it and confirmed three agent decisions: "I agree with the territory rule and am confirming the three decisions the agent wrote in ADR-0063." (2026-10-27, in session, relayed by the orchestrator). The three are: sharing a workspace between users in hosted mode is excluded (decision 3); the overlap is checked from the registry alone, without opening other workspaces (decision 2, now by territory); no idle container is kept warm (decision 1).
- **Area:** workspaces, API, lifecycle, data safety, hosting
- **Supersedes:** in ADR-0017, "a ledger root belongs to at most one workspace per machine (registry deduplicated by canonical root path)", which becomes: each workspace owns a territory, its ledger set stays inside it, and territories never overlap; in ADR-0018, "several native windows on different workspaces are architecturally allowed" and "browser tabs already work" for different workspaces, and the switch as "after the backend has opened and validated B" while A stays open; in ADR-0021, "Copy to workspace…" writing into a workspace that is not open; in ADR-0041, "sharing a workspace between users" on the deferred list; the scheduler spec draft 3's mechanisms for two workspaces that share a file (`design/specs/engine-scheduler.md` §5.7 and the INV-31 exception it proposed, owner answer (b) of 2026-10-27), which are no longer needed.
- **Unchanged:** the workspace-addressed API (ADR-0018): every workspace-scoped request names its workspace, and a request, response or write never acts on another; "a write started in A always completes in A"; ADR-0062's single instance per app root and Copy-only legacy adoption; ADR-0013's detection of outside editors (Fava, a text editor, a sync client); ADR-0012's journal, recovery on open and Q30; ADR-0011's per-workspace write limiter; external-ledger references (ADR-0017), now bound by the territory rule; copy-based sharing of settings (ADR-0021); content packs shared read-only by reference; INV-25, INV-27, INV-29 and INV-30 as written. INV-28 and INV-31 are reworded and INV-32 added, with the owner's approval (decision 5).

## Context

ADR-0017 deduplicated the registry by root only, so two workspaces could include the same file, for example a shared `prices.beancount`, and ADR-0018 allowed several workspaces to be open at once (browser tabs, later several windows). The engine-scheduler design had to make that safe. By its fourth review (review in the owner's private archive, `m1a/scheduler-design/review-4/REPORT.md`), most of its High findings sat in mechanisms for two workspaces sharing a file: an app-wide journal index with no durable order, a lock key that changes when a shared file is created, one workspace waiting for ever on another's unrepairable save, a save in one workspace waiting for a rebuild that a save in another made necessary, and an exception to INV-31 so that a closed workspace's save could be repaired from an open one.

Example of the risk those mechanisms guard against: workspaces *Personal* and *Business* both include `prices.beancount`. A save in *Personal* is cut off half-way (the computer loses power). *Personal*'s journal knows how to undo it, but recovery runs only when *Personal* is opened. You open *Business* first: it reads the half-written prices file, and a save there writes on top of it. When *Personal* is opened later, its recovery finds bytes it did not write.

With one open workspace and no shared file, none of this can happen: a workspace's files are only ever written by that workspace's own jobs, and a half-applied save waits, harmlessly, for its own workspace's next open.

Comparing files one by one is not enough, because a save creates files. Example (S0045 verifier, finding F1): *A* includes `../B/imports/*.beancount`, which matches no file of *B* today, so a file check lets both register. A save in *B* creates `imports/2027.beancount` and then adds its include line to *B*'s root, children first. Power is cut after the new file is written but before the root. *B*'s file list never named the new file, so nothing claims it. At the next launch the user opens *A*: *A*'s glob now matches *B*'s half-applied file, and *A* opens over it while *B*'s journal still waits to undo it. Decision 2 closes this by territory: *A*'s glob reaches outside *A*'s own folder, so *A* is refused at registration, and every file *B*'s save can create lies inside *B*'s territory, which no other territory contains.

## Decision

### 1. One open workspace per instance (owner, 2026-10-27)

- **A Finzytrack instance has at most one open workspace.** Open means: its `WorkspaceContainer` exists, it accepts requests, and jobs run for it (mirror build, saves, R4, recovery, background price fetch). Boot opens at most the last workspace (or the one `--workspace` or a file association names).
- **Opening another workspace is a switch**, which closes the current one first. Requirements (the scheduler spec draft 4 defines the jobs, their order and the waits):
  1. **The leave guard runs first** (unsaved edits: save, discard or stay; ADR-0018, CAP-WS-SWITCH).
  2. **The target is assessed before anything closes** (agent). A cheap probe and `assess_workspace` read the target without writing it, and the territory comparison (decision 2) uses only the registry. If the target needs the user (unavailable, newer, invalid config, upgrade consent, a territory conflict), its screen is shown with **Stay**, and the current workspace stays open and untouched. Nothing is recorded (INV-29). A target with a pending journal reports `RECOVERING`. That needs no answer from the user, so the switch goes on. Its recovery is the first step of its open (step 6; ADR-0012: "before any other step"), and the check that its ledger set lies inside its territory runs after that recovery, on the recovered files.
  3. **The switch does the book-keeping, and never loses or half-applies anything.** New work for the current workspace stops. Work that can end without loss ends (reads, previews, rebuilds, queued background jobs). Work that must finish finishes: a save the user confirmed (closing is not a cancel; whether a save that has not reached its commit point may still be cancelled by the user is the scheduler's), a running recovery. Work owed to the workspace (an R4 check after a save, a queued recovery) either runs before it closes or stays durably recorded for its next open, as the scheduler spec decides; it is never dropped. A preview that was not confirmed (a `PlanStore` plan of the current workspace) is discarded, which loses nothing, since nothing was applied. Import sessions, AI threads and UI memory survive (they live in `local/<key>/`, the user container and scoped storage; CAP-WS-RESUME).
  4. **While the switch waits, the user reads "Just a moment… switching workspaces."** Every wait has an exit (agent): until the current workspace has closed, **Stay** cancels the switch and leaves it open; a save past its commit point is never cut off by the switch (if the user quits instead, the journal makes that safe, as for quiesce).
  5. **The current workspace closes completely**: its container, caches and handles are released (INV-31), and its folder is not written (INV-30). No idle container is kept warm for a quick way back (agent, confirmed by the owner; this replaces ARCHITECTURE §2.5's "at most 1 idle container kept warm"). A switch is quick when the target's published mirror is fresh, which is on disk and does not need a warm container.
  6. **The target opens by the normal path**: recovery first if a journal is pending, then the assessment with the territory check on the ledger set, and "last opened" recorded only on `READY`/`WARMING` (INV-29). If it fails after the current one has closed (its recovery stopped, its set reaches outside its territory, its files changed since step 2), its screen offers **Back to <previous workspace>**, which opens that one by the same path.
  - At no moment do two workspaces accept requests or run jobs.
- **A request for a workspace that is not the open one is refused, never served** (agent: the code). Every `/api/w/{ws}/…` request whose `{ws}` is registered but not open, also while a switch is closing it, gets `409 WORKSPACE_NOT_OPEN {open_workspace, switching}`, changes nothing, and is never redirected to the open workspace. An unknown `{ws}` is still `404 WORKSPACE_UNKNOWN`; the open workspace while it warms or recovers is still `409 WORKSPACE_NOT_READY {phase}` (ADR-0018). Example: in headless mode, tab 1 shows *Personal*; tab 2 switches to *Business*. Tab 1's next save names *Personal* and is refused; tab 1 says "Finzytrack switched to *Business* in another window." and offers to switch back. It never writes to *Business*.
- **App-scoped work may read a workspace that is not open, never write it or run its jobs** (agent): the switcher's status probe, the assessment of step 2, the territory comparison, and reading files to copy them (a test copy, "New workspace from settings of…"). Creating a new workspace (create, adoption, test copy) writes only the new, not yet registered folder, then registers it; it does not open it unless the user switches to it.
- **Several native windows on different workspaces are cut** (CAP-WS-MULTIWINDOW). Several windows or tabs may show the one open workspace.

### 2. No file in two workspaces: territories (owner, 2026-10-27; the territory rule agreed by the owner the same day)

- **Each registered workspace owns a territory**: its workspace folder (the one holding `.finzytrack/`) and, for an external-ledger reference, also its ledger's folder tree (the folder of the root file and everything below it).
- **Its ledger set stays inside its territory.** Every file the workspace uses must lie inside its own territory: the root, its includes, every glob's matches and the glob's fixed folder part (so a future match is inside too), the price sidecar, the documents folder, and every file a save may create (a routed include file, a new sidecar). "Inside" is decided by the write path's canonical identity: `path_key` (one folded spelling per path, the same whether the file exists or not) and `canonical_path`, both to be defined in the scheduler spec draft 4 (review 4 H1). A path through a symlink, a case variant or a Unicode-normalization variant is judged where it really leads. On a case-sensitive volume, two names that differ only in case may be judged the same. Then a file in `/books/` may count as inside a territory `/Books/`, but the territories `/Books/` and `/books/` also count as the same and cannot both be registered, so no file can still belong to two workspaces (agent). A ledger set that reaches outside its territory is refused, with the outside path named: "accounts.beancount is outside this workspace's folder. Finzytrack only uses files inside it. Make a copy of this ledger to bring the file in." That holds at registration, adoption, creation and open, and whenever the set grows (a rebuild after an outside edit). Precedent: ADR-0020's Copy already refuses an include outside the legacy root's folder.
- **Territories never meet.** The territories of two registered workspaces are never equal, never overlap and never nest; for example, no workspace folder may sit inside another workspace's folder or its documents folder. This compares folders by `path_key` and needs only the registry: no other workspace is opened or reached, so an unplugged disk does not block an open. Registering, adopting, creating or opening a workspace whose territory meets another's is refused, naming the other workspace: "This folder is inside the workspace *Personal* (or contains it). A folder can belong to only one workspace."
- **Codes** (agent): in `assess_workspace`, the phases `LEDGER_OUTSIDE_FOLDER {path}` and `FOLDER_IN_OTHER_WORKSPACE {path, other_workspace}`; in the plans (`plan_create_workspace`, `plan_adopt_workspace`, the test copy), refusals with the same codes. Both record nothing (INV-29).
- **What the registry stores** (agent): nothing new about files. A row already holds its workspace folder and, for an external reference, its ledger's path (ADR-0017); the territory's `path_key`s are derived from those, and are written only when the row itself is written, that is after `READY`/`WARMING` (INV-29) or at a confirmed Locate. No record of another workspace's files is kept or needed.
- **Why this is safe** (agent): a save creates and replaces files only inside its own territory, and no other territory contains them. So a cut-off save's files, created ones included, can never be read or written by another workspace, whether or not they existed when anything was checked. The check also needs no fresh view of the other workspace, because territories change only when a registry row is written.
- **A growing set is caught** (agent): an include edited outside the app that reaches outside the territory is refused at the next open, and during a session at the rebuild that found it. That rebuild is not published, reads stay on the last published generation, and saves are refused with the same message until the include is fixed. The open workspace never writes outside its territory in between.
- **A cut-off save keeps its claim** (agent). While a workspace has a write journal that recovery has not resolved, it cannot be forgotten (the scheduler spec draft 3, §4.9, already says so). Its territory therefore stays registered, and no other workspace can be registered over that folder. INV-25 is unchanged: forget still deletes no file.
- **Honest limits** (agent):
  - A hard link between two territories is not detected: it would need stat calls into the other workspace's files, and an atomic-swap save (ADR-0013) breaks the link at its first save anyway. This is rare.
  - The same network share mounted at two places has two identities.
  - The check sees only this app root's registry, so a second installation, another `--app-root` or another OS account can use the same folders; that stays unsupported (ADR-0062).
  - Files a plugin reads by itself are not in the set (scheduler spec §5.8).
- **The cost, stated plainly:**
  - A ledger whose includes, documents folder or sidecar reach outside its folder cannot be opened in place. A copy brings it in: the files are gathered into a new workspace folder and the copied include lines are rewritten. That copy mutator is new work (BL-0104, M3). Until it lands, such a ledger can be used only after the user moves those files inside the folder or makes such a copy by hand; today's test copy and legacy adoption both refuse an include outside the source folder.
  - Several root ledgers in one folder share one territory, so only one of them can be a workspace in place; each other root comes in as a copy.

### 3. No sharing anywhere: every place the docs allowed it (owner, 2026-10-27: "No sharing anywhere")

| Where | Decision |
|---|---|
| Share workspaces (a ledger written by v0.4 and a running legacy app) | Already removed (ADR-0062). |
| Two workspaces including the same file | Impossible: each file lies in one territory, and territories never meet (decision 2). |
| External-ledger reference (ADR-0017) | Kept: one workspace may keep its ledger in a folder outside its own, and that folder tree joins its territory. So the same external ledger folder cannot be referenced twice, nor by a reference and an in-place workspace, nor nested in another territory. |
| Several root ledgers in one folder (CAP-WS-MULTI-ROOT) | Narrowed: the folder is one territory, so one root is a workspace in place and each other root comes in as a copy (decision 2). |
| A documents folder used by two workspaces, or a workspace folder inside another's documents folder | Impossible: a documents folder lies in its workspace's territory, and territories never meet (decision 2). |
| Glob includes reaching into another workspace's folder | Refused: a glob's fixed folder part must lie inside its own territory (decision 2). |
| Several open workspaces: browser tabs, several native windows | Ended (decision 1); CAP-WS-MULTIWINDOW cut. |
| "Copy to workspace…" for a dashboard, rule or theme (ADR-0021) | Kept, carried across a switch (agent): the item is held in the user container, the switch runs, and the target asks "Add <item> from <source>?" and validates against its own accounts. Nothing writes a workspace that is not open. |
| "New workspace from the settings of…", test copies, Copy adoption | Unchanged: they copy, so nothing is shared. Two legacy ledgers that included one common file each get their own copy of it, which then diverge (agent: stated in the adoption preview). A retired legacy install's ledgers (ADR-0062 amendment) share the legacy `data/ledgers/` folder, so at most one of them can be opened in place. |
| Shipped dashboards and widgets by `pack:` reference (ADR-0021) | Unchanged: read-only app content, never written, not a user file. |
| App-level settings, the AI provider and key (`app/`) | Unchanged: app state, not a workspace's file; secrets stay scoped per workspace (ADR-0021). |
| A live app-level library of dashboards and rules (CAP-WS-LIBRARY, deferred) | Stays deferred (agent). It would share tool state, not ledger files, so the write-safety reason does not apply, but the owner's "no sharing anywhere" does: building it needs an ADR that revisits this one. |
| Sharing a workspace between users in hosted mode (ADR-0041's deferred list) | Excluded (agent, applying "no sharing anywhere"; confirmed by the owner, 2026-10-27; it would put one ledger set in two user containers). A future plan for it needs an ADR that supersedes this one. |
| Two app roots, a second installation, another OS account | Unsupported, as before (ADR-0062); to each other they are outside editors, detected (ADR-0013). |
| Outside programs on the same files (Fava, an editor, a sync client) | Unchanged: supported and detected, not excluded (ADR-0013). They are not Finzytrack instances. |

### 4. Hosted mode (not built; ADR-0041, INV-11)

"One instance, one workspace at a time" holds per user (agent). A hosted service is one Finzytrack serving many user containers; each `UserContainer` has at most one open workspace, and a switch closes that user's open workspace only. Other users are not affected. Territories are compared within one user's registry; workspaces of different users live under separate user roots that the hosted `LoadPolicy` confines (ADR-0041), so their territories cannot meet. Multi-worker coordination stays deferred; whatever it becomes must keep each user's open workspace served by one process at a time. Nothing here forecloses hosting: the limiters, job queue and containers stay where INV-11 puts them.

### 5. Invariants (owner-approved, 2026-10-27)

The owner approved the proposals of `design/inbox/answered/20261027-workspace-invariants-one-open-no-shared-files.md`: "reword INV-28 and INV-31 and add INV-32 as proposed", and for INV-28's hosted wording "Yes INV-28 should say the same." (2026-10-27, in session, relayed by the orchestrator). INV-28 now says a request is served only for the open workspace (in hosted mode, in its user container) and refused otherwise; INV-31 carries the one-open rule; the new INV-32 carries the territory rule of decision 2, which the scheduler's safety relies on. INV-32 keeps the proposal's purpose, why and status; its rule and enforcement state the territory rule, which the owner agreed to, in place of the proposal's file-by-file overlap.

## Alternatives considered and rejected

- **Keep several open workspaces and only forbid shared files.** Rejected (owner, by choosing the decision above; the agent's reasons): disjoint sets remove the shared-file mechanisms, but several open workspaces still need per-workspace lanes competing for engines and memory, cross-workspace priorities, and a quiesce over several workspaces; the owner asked for the simpler model.
- **Keep shared files and make them safe** (scheduler draft 3). Rejected (owner): it carried most of review 4's High findings, and still needed an exception to INV-31.
- **Allow sharing files that Finzytrack never writes** (a common `accounts.beancount` that only the user edits). Rejected (agent): which file a save writes depends on routing settings, the price sidecar and the user's next action, so "never written" is not a property the app can rely on; and the owner said no sharing, period.
- **Route a request for a closed workspace to the open one, or reopen it silently.** Rejected (agent): routing is the shared-pointer bug ADR-0018 removed (a save built in A would land in B), and a silent reopen would let two tabs switch the instance back and forth under each other.
- **Refuse a switch while another window uses the current workspace.** Rejected (agent): the desktop app has one window (single instance, CAP-WS-MULTIWINDOW cut); in headless mode the other tab is told what happened and can switch back, and a lock-out would leave a user stuck behind a forgotten tab.
- **Open the target before closing the current one** (ADR-0018 as written). Rejected (agent): two workspaces would be open during every switch. The read-only assessment first gives the same protection against switching into a broken workspace.
- **Check overlap file by file, against each workspace's recorded ledger set** (this ADR's first version). Rejected after the S0045 verifier's round 1: a file a cut-off save created is in no record, so another workspace's glob or not-yet-existing include can open over it (finding F1, shown in Context); keeping the records fresh also needs registry writes outside a successful open (F3, INV-29), and a hard link cannot be seen from a record (F2). Territories need no record of files at all.
- **Check overlap by opening or re-assessing every registered workspace.** Rejected (agent): slow, and an unreachable folder would block every open.
- **Let the user pick a wider territory** (for example a parent folder holding a shared `accounts.beancount`). Not adopted for v0.4.0 (agent): the territory rule as agreed names the workspace folder and the external ledger's folder tree; a wider territory would still exclude a second workspace there, so it would only help a single ledger, which a copy also serves.

## Consequences

- **Removed from the scheduler design** (draft 4, `design/journal/S0045-one-workspace-at-a-time.md` lists the sections): the cross-workspace journal index entries, `RECOVERING {owner_ws}`, recovery of another workspace's journal, the INV-31 exception of owner answer (b), owner questions (1) and (2) of review 4, the two-shared-workspace TLA+ configuration, and the quiesce over several open workspaces. The per-file locks on canonical paths stay: they serialize a workspace's own engines and exclude an orphaned engine of a crashed session (ADR-0012 Q30, ADR-0062).
- **New work:** BL-0102 (the switch, M2), BL-0103 (the territory rule, M2; create and the test copy use the same check in M3), BL-0104 (the copy that gathers files from outside the folder, M3). New capability row CAP-WS-NO-SHARED-FILES.
- **A narrowing users will notice:** a ledger whose files reach outside its folder cannot be opened in place, and of several root ledgers in one folder only one can be. Both come in by copy. Beancount parity (INV-03) is not narrowed in what is read: a copy of every ledger Beancount loads still opens. What is refused is opening it in place across another folder, or a second workspace in the same folder.
- **Headless users with several tabs** see one workspace at a time; a tab left on another workspace says so and offers to switch back.
- **INV-28, INV-31 and a new INV-32** carry the rules (decision 5); their tests are BL-0028, BL-0031, BL-0102 and BL-0103.
