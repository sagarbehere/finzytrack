# How Finzytrack is developed

The single current reference for the development process. **Owner:** the project owner. Agents propose changes; tightenings may be applied by agents and are approved afterwards; loosenings need the owner first (§9). Founding proposal: review:20 (frozen); adopted by ADR-0001. Its change log is `IMPROVEMENTS.md`.

Agent prompts link to sections of this file instead of restating them.

## 1. Goals

- Catch a defect **in the change that introduces it**, not in a big review weeks later.
- The owner writes a **small set of invariants** (`../INVARIANTS.md`) and answers **high-stakes questions** (§5). Agents decide everything else, and an independent agent verifies it.
- Tests are comprehensive and mostly executable. Docs, dev and user, do not drift from the code (§7).
- The process costs little per change; most of its cost is one-time setup, run by agents.

Non-goals: exhaustive upfront requirements; heavyweight traceability matrices (IDs in tests and docs are enough).

## 3. The slice loop

A **slice** is the smallest change that delivers one verifiable behaviour (hours to two days of agent work). **Batch backlog rows of one lane and one kind into one slice. Never put a loosening, or a mechanism that needed two fix rounds before, into a batch** (IMP-0072).

1. **Orient.** Run the `orient` skill on the request: relevant capability rows, ADRs (with rejected alternatives), specs, code entry points, tests, open backlog items.
2. **Brief**: the first section of `design/journal/<slice-id>.md` (template in `design/journal/README.md`): goal; ADRs and specs it implements; invariants touched; acceptance tests; expected doc impact; risk class and lane; open questions. A question that hits the rubric (§5) goes to the inbox **before** coding. **A write-path brief states in one line "the bytes it protects"** (ledger or user data a mechanism keeps from loss, tearing or overwrite, or the outcome it keeps truthful); "none" means the mechanism is advisory, and EP-30's question "can a policy forbid it?" goes to the owner before coding (owner, 2026-11-01; ADR-0068 D6; IMP-0051). **Every brief that adds or hardens a mechanism answers, in one line each: 'Which real setup needs this, and can a policy forbid the rest?' and 'Has this mechanism or its family needed two or more fix rounds before (journal IDs)?'. When the setup is rare or the family has that history, the policy option goes to the owner before coding. At the first class (a) finding in a rare setup, the orchestrator offers the policy before the first fix round, not the second** (owner, 2026-11-12; IMP-0065).
3. **Tests first.** Write the acceptance and golden tests and see them fail. For behaviour v0.3.0 already has, write characterization tests against the legacy app first (`scripts/oracle/launch_legacy.py`, copies only). New or changed tests must fail on the slice's base commit (the verifier checks it; the T1 check `tests-fail-on-base` is parked, BL-0034, ADR-0058); tests tagged `@characterization` or `@regression-guard` are exempt. For UI whose shape is unknown: **spike, then pin** its behaviour in tests before the slice is done.
4. **Implement** under the gates (§6). **Before hand-off** (ADR-0057), in the journal's Hand-off section:
   - list every check the slice adds or changes that accepts, tags or refuses, each with its must-not-pass test (EP-29);
   - a check that guards ledger data, finance results, real-data privacy or product security gets at least one loosening mutant with `scripts/mutants.py` (optional on tooling); a survivor gets a test, or a one-line reason when it is equivalent;
   - a spec or check that claims to cover a whole population names the inventory it was built from, builds it by behaviour (the capability map row by row, the code that does the thing), never by name, and records the counts in and out.
5. **Verify** with the independent verifier (§4), started by the orchestrator, never by the implementer (owner, 2026-10-26: "make sure that future implementers don't start a verifier themselves. That's a problem if it ever happens."; `.claude/agents/implementer.md` denies the implementer the Agent, Task and SendMessage tools, and `.claude/hooks/guard_agent.py` refuses them and an implementer's Bash command that runs the `claude` CLI). Which reviews run, and when a fresh round follows, is the **review budget** below.
6. **Docs** in the same change: generated docs regenerated, user docs updated on the docs repo's `v0.4` branch (light lane: at milestone end), ADRs for decisions made, the capability row updated.
7. **Land**: commit directly on `next` (no pull requests) when every gate is green and the verifier reports no unresolved High finding. A High is always fixed. In the first round, Medium findings are fixed or get a backlog ID, and Low findings may be dropped with a one-line reason; on a tooling, gates, measurement or docs slice, a missed shape outside the stop rule's points (1)-(3) becomes a line in the check's stated limits instead (IMP-0066); before a second fix round, simplify first (EP-30). What a later fix round fixes, and the stop rule for tooling, are in the review budget below. The commit message carries the slice ID. The journal records the verifier's head SHA, which is the landed commit or its parent (checked by the verifier of the next round or slice; the T1 check is parked, BL-0034).

**Definition of done:** gates green; verifier signed off; every touched invariant has a test that would fail if it broke; `ENGINEERING.md` followed or the deviation recorded; docs updated; no TODO without a backlog ID.

### Review budget

One table decides the reviews of every slice (owner, 2026-11-12: "I agree with your view. Let's adopt it."; IMP-0068, carrying IMP-0066 and IMP-0067; it replaces the round rules of ADR-0058, ADR-0068 D6, IMP-0051 and IMP-0052). **Every finding carries a class** (IMP-0069): (a) bytes or a false outcome: it loses, tears or overwrites a ledger or user byte, or gives a false outcome ("saved", "not saved", "unchanged", "created"); (b) a wrong number or finance result; (c) a gap in our own checks or tests; (d) docs or wording; (e) other.

| Slice kind | Reviews | Fresh round on the fix range | Then, in the fresh round |
|---|---|---|---|
| New write path or write outcome: a new way to write, delete or move ledger or user data, or a new outcome text for a write | verifier + data-safety red team | after any fix that changes product code | only High and (a)/(b) findings are fixed; the rest become backlog rows; a second fix round on one mechanism needs the owner's options note (situation, likelihood, options, recommendation; ADR-0068 D6) |
| New finance meaning or input | verifier + finance red team | after any fix that changes product code | same |
| Hardening an existing write path: a new check, a sync, an identity test, a gate's input | verifier; the data-safety red team joins when the verifier reports an (a) finding | after any fix that changes product code | same |
| Other product code: engine, API, reads, security | verifier; the security red team per §4 | after any fix that changes product code | same |
| Tooling, gates, measurement | verifier | only when the slice or a fix changed a guard of real data or privacy (INV-23, INV-24) | the stop rule below |
| Docs only | verifier on facts and doc consistency | none | none |

- A slice with parts of several kinds takes each part's row; the fresh round covers the fix range of every part that needs one.
- On product rows a fresh round follows any fix that changes product code, since a fix can break what it touches (S0099 R2-F1, S0102 R2-F3; owner, 2026-11-13: "Re-review any product fix (Recommended)"; IMP-0068). The fresh round is the verifier's; a red team's second run follows §4.
- **Tooling, gates, measurement and docs** (no ledger or user bytes, no finance number): one verifier round. The fix round fixes only (1) a shape that the check's own must-not-pass list or docstring promises to refuse, (2) a false statement of fact, (3) a finding in a guard of real data or privacy (INV-23, INV-24). Every other shape a check misses becomes one line in its stated limits, or a backlog row when a real file in the repository has that shape (IMP-0066). A High is always fixed, inside or outside (1)-(3): an unfixed High is unresolved at landing.
- The safety core is unchanged: the verifier on every slice, the red teams on new write paths, new write outcomes and new finance meanings, a fresh round after any product-code fix, and the High data-safety exceptions of INV-01, INV-22 and INV-32.

### Designs checked by a formal model
**Formal models check durability only** (EP-19): no committed change is lost or torn, and recovery returns a committed state. Liveness, truthful outcomes and what the user is told are checked by statechart and stateful tests. Such a design goes to code after a simplification pass (each mechanism, the requirement it serves, and whether a policy can forbid it), one full independent review, the model's small tier and one review of the model against the spec (fidelity both ways, vacuity). Later findings, the owner's long model runs included (they run beside the slice, never before it), become tests or backlog rows unless they are a High data-safety issue (INV-01, INV-22, INV-32). Owner, 2026-10-29: "Yes to Reflection proposals 1, 2, 3, 4, 7, 8, 10 and 12." (IMP-0045, replacing the golden-spec rounds of IMP-0037 to IMP-0044).

### Risk classes and lanes

| Class | Typical slices | Ceremony |
|---|---|---|
| High | Ledger writes, finance semantics, security, migrations, rubric items 1–3 | Full brief; tests first; verifier with neighbourhood context; doc check; red teams per the review budget (§3); capability row; journal and retro; UI smoke session if UI is touched |
| Medium | New behaviour in one area with no ledger, finance or security impact | Short brief; tests first; verifier on the diff plus touched callers; doc check; journal line; smoke session if UI is touched |
| Low | Docs, UI copy, refactors with no behaviour change, test-only changes | Brief of a few lines; verifier on the diff (doc check included); gates |

The verifier may raise a slice's class, never lower it. **Lanes** (owner, 2026-10-24): the **full lane** for anything touching ledger writes; the **specialist lane** for finance and security work, whose specialist red team runs once per area unless a change alters what a number means or adds a new input; the **light lane** for read-only screens and catalogue entries (user docs at milestone end).

**Ceilings only the owner raises:** the 30 s T0 pre-commit budget and the per-change process-cost ceiling (agent passes and wall time per slice, measured per §9).

## 4. Agents and reviews

All agent runs happen **locally in Claude Code on the owner's machine**. CI runs deterministic gates only; nothing in the process uses paid CI AI or hosted agent runs (owner, 2026-10-24).

| Role | Sees | Produces |
|---|---|---|
| Implementer (`.claude/agents/implementer.md`) | Brief, ADRs, specs, code | Code, tests, docs, the journal |
| Verifier (`.claude/agents/verifier.md`, fresh context, adversarial, doc check folded in) | The diff, the brief, `INVARIANTS.md`, `ENGINEERING.md`, the relevant ADRs, the slice's neighbourhood. **Never the implementer's reasoning** | Findings with repros, citing INV/EP/ADR/CAP/SPEC/BUG IDs; the list of attacks tried (High ≥ 5, Medium ≥ 3); the head SHA |

Rules: the verifier tries to **break** the change, and reviews every new or changed test against the spec, not against the code as written (EP-29; owner, 2026-10-25); executable evidence beats argument; implementer–verifier disagreement on a High item is escalated, never settled by the implementer. Red teams (data safety, finance correctness, security, UX), the area reviewer, the drift auditor and the reflection agent are added when first needed, with these decided cadences: data-safety and finance red teams as the review budget (§3) says (IMP-0067), scoped to the slice's new part (not code earlier rounds reviewed); one run by default, a second only after a High fix; High there means ledger bytes lost, torn or overwritten, ours or another program's, or a false "saved", "undone" or "unchanged" (owner, 2026-10-30: "Yes, apply all three"; IMP-0049); the finance red team also once per area; the security red team once per area and for changes that add a new input; the UX red team before each vertical is declared at parity; an area review every 5–8 slices and before parity; the drift auditor weekly (locally); seeded-defect plants at G1, G2, after M8 and at M11 (≥ 20 plants across ≥ 4 classes; at G1 at least half in product code: the write path, the mirror, finance). No red team attacks the gates themselves (§9). **One implementer is on the product critical path at all times**; design and model work runs beside it (worktrees allowed; after creating one, the orchestrator checks `core.hooksPath`).

**Review altitudes:** (1) the slice verifier, every slice; (2) an area review when a vertical reaches a milestone; (3) cross-cutting lens reviews at G1, G2, after M8 and at M11 only; (4) a whole-system review at M11. Findings from altitudes 2–4 are capped per run (at most 15 ranked findings unless the run's prompt says otherwise) and triaged: integrity, security or wrong-number findings become slices at once; the rest join the backlog. **The cap rule holds for every reviewer** (slice verifier, area, lens and whole-system reviews, red teams, spot audits; owner, 2026-10-26: "The cap rule should be a standing one for all reviewers"): a cap never drops a High, every High is reported whatever the count; findings beyond the cap are listed in an Overflow list, one line each (ID, severity, claim, file:line), so nothing found is lost. Spot audits by a fresh Claude context with a different prompt and role run at G1, G2, after M8 and M11, alongside the seeded-defect catch rate.

**UI testing:** scripted Playwright acceptance flows (Chromium and WebKit) are the backbone; exploratory agent sessions with charters find what scripts miss, and every real issue they find becomes a Playwright test. Sessions use an isolated backend, a fresh demo workspace and the LLM stub, never the owner's browser profile or real ledgers. The packaged macOS UI cannot be driven (`tauri-driver` has no macOS support): macOS uses `--smoke-test`, sidecar and API checks, Playwright WebKit against the sidecar-served bundle, and the owner's dogfooding.

## 5. What reaches the owner

The rubric is one file: [`escalation-rubric.md`](escalation-rubric.md). Agents and this document both include it by reference.

Every escalation is a file `design/inbox/<id>.md` with the question, the options, a recommendation in plain language and a **`blocks:`** line naming the slices it holds. **Each options note lists the cheapest option first and, for the recommended option, the mechanism's review history (slices, rounds, Highs). A note never recommends a new slice for a setup that a policy could forbid without offering that policy first** (IMP-0071). A blocked slice parks; the agent continues with unblocked work. Rubric questions go at once; confirmations of recommendations outside the rubric are batched into one message a day. Whether an accepted ADR already covers a change is judged by the verifier.

**Milestone moves by rule** (owner, 2026-11-12; IMP-0070). A backlog row may move to the milestone of its first consumer (the code that will call it) without the owner's words; the row names the consumer, and the move is listed in the daily batch. The citation, on the moved row, is exactly `moves with <ID> (IMP-0070)`, where `<ID>` is another backlog row that is `open` or `in-progress` both before and after the push, on the milestone the row moves to, and that did not itself move later in the push except on an ADR or the owner's words. The moved row stays `open` or `in-progress`: parking, deferring past v0.4 or removing a row still needs a decision. The deferral check (§6) accepts this citation in exactly this form.

**Owner approvals** (clearances, risky changes, changes to rules or checks) are given in the Claude Code session. The agent records each in the slice journal, or in `IMPROVEMENTS.md` for a process change, with the owner's words **quoted verbatim**, the date and the commit it covers. An approval line without a quote is a verifier finding for the change classes that need one (the T1 check is parked, BL-0034).

**Owner-reported bugs:** present the diagnosis (root cause, evidence, proposed fix) and get agreement before editing. This applies to bugs the owner reports, not to defects agents find inside the slice loop.

A check whose time grows with its input (the pushed commits or tag, the new Cargo.lock entries, the Stop hook's changed files) is marked `--size-dependent` and has no history limit, since its history mixes input sizes. The pre-push hook reports each check's time against that usual time, and the total; slowness alone never fails. The Stop hook's own backstop (1500 s) sits below the harness's Stop timeout (1800 s) |
| T1 | Started by hand: before each release, and on demand (`.github/workflows/ci.yml`; ADR-0060). The per-push gate is T0 pre-push | All unit and property tests; licence checks and `THIRD_PARTY_NOTICES` current (a package bundled only on another OS is judged from a reviewed entry for its exact version, each forked version on its own; an editable or path dependency fails closed; S0105); golden corpora; architecture tests; invariant and capability checks; concept counters; doc checks; a risk-selected acceptance subset (flows tagged with the touched capabilities and invariants, plus a fixed integrity core) | ≤ 10–15 min, sharded |
| T2 | Started by hand with T1, before each release and on demand (`nightly.yml`, `packaged.yml`; ADR-0060) | The full acceptance suite in Chromium and WebKit; 54k perf and memory against the baseline; D1 corpus and oracle comparison at full size; packaged builds on three OSes; docs link check. Weekly and before each clearance: mutation testing and the scripted UI tour | Off the critical path |
| T-local | Owner's machine, before promotions and release | The write corpus, oracle and overlay equivalence on copies of the owner's real ledgers (outside the repo) | Off the critical path |

The gates arrive with the code they check. **Built today:** the T0 hooks, and in T1 the check-script meta-tests (the concept counters among them since S0104), privacy scan, staged-file guard, invariant, capability, generated-artifact and licence checks, and the oracle harness's unit tests (its end-to-end runs against the legacy app are T-local); the backend, engine (S0035), frontend and shell jobs, the frontend job running the Playwright flows through the acceptance harness (S0030); in T2 the packaged three-OS build with `--smoke-test` (`packaged.yml`, called by `nightly.yml`). Since ADR-0060 the GitHub workflows (T1, T2) run only when started by hand, before each release and on demand; the T0 pre-push hook is the per-push gate. **Not built yet** (tracked): duplicate-code detection (BL-0251); the other T2 items arrive with the code they check. **Parked until evidence asks for them** (ADR-0058): `tests-fail-on-base`, the verifier-SHA, approval-quote and golden-justification checks (BL-0034), the protected-file guard (BL-0036), the §10b no-drift checks (BL-0038), the stricter invariant check (BL-0040); the verifier covers them meanwhile. **Install the hooks once per clone:** `git config core.hooksPath .githooks`.

**Safety outranks every number.** No performance target, budget or baseline is ever met by weakening, skipping, sampling or deferring past its guarantee a safety check (the write-safety contract and its re-check, INV-01, INV-22, the privacy and real-data guards). An agent that cannot meet a user-facing absolute escalates with the measured numbers. **Thresholds catch accidents.** Performance and memory checks detect regressions against the previous baseline (for example > 20%), not absolute targets. A time limit on a gate check is a hang detector relative to the check's own history, never a fixed budget, since the suites grow (owner, 2026-10-26; S0034). The only absolutes are the owner's user-facing ones: a write takes ≤ 1 s at demo size and ≤ 5 s at 54k entries. Raising a threshold, baseline or cache-bound default is agent-approved with a one-line reason in `IMPROVEMENTS.md`, except the two owner-only ceilings (§3). Size thresholds **report** and never fail CI. Structural checks that fail CI: duplicate-code detection (not built yet, BL-0251), layering contracts, the globals allowlist, concept counters (each kernel concept has one allowed home). No transitional allowlist: copied v0.3 code meets every gate on arrival.

## 7. Docs that cannot drift

Generate it, test it, or keep it to the "why".
1. **Generated:** API reference and error codes, mirror tables and views, the recipe schema and catalogs, the config reference, the capability map, the invariant index. CI regenerates them and fails on any diff (`scripts/check_generated.py`).
2. **Tested examples:** every recipe, SQL, BQL and ledger snippet in the user docs runs in CI; screenshots come from the Playwright suite.
3. **Symbol references:** specs and ADRs cite code as `` `module.symbol` ``; a checker fails on a missing symbol.
4. **Doc impact:** each brief lists its expected doc changes; the verifier compares them with the diff. A slice that changes a flow drawn in a spec or in ARCHITECTURE.md updates its diagram in the same commit; a diagram pictures its text and never adds to it (IMP-0047).
5. **ADRs are append-only:** a new decision supersedes an old one explicitly.
6. **User docs** (`finzytrack-docs`) change on its `v0.4` branch in the same slice (light lane: at milestone end).

**Project memory.** The capability map answers "did we do X?" (cut and deferred rows stay, with their ADR). ADRs answer "why?". The journal answers "when and how?". Look up in that order, then `git log`. Tests carry capability and invariant tags (`@pytest.mark.cap("CAP-…")`, `describe('[CAP-…]')`). The capability check (pre-push and T1) refuses a `built` capability without a real tagged test: the tag on a test, not in a comment or on a helper, in a file with no fixme and no switched-off test; and a row whose `code` or `tests` names a missing path (S0105).

## 8. Tests, goldens and privacy

- **Oracles before opinions:** Beancount itself, `bean-query`/Fava outputs, the legacy app on copies, and hand-checked fixtures for app-specific numbers.
- **Pyramid:** pure unit and property tests (Hypothesis, fast-check); golden corpora; API contract tests; Playwright acceptance flows. Mutation testing weekly and before each clearance.
- **Changing an expected output** (golden, snapshot, characterization assertion) needs a justification line in the journal, a verifier verdict on old vs new side by side, and for a deliberate fix of known-wrong behaviour, the finding ID. A missing justification is a verifier finding (the T1 check is parked, BL-0034).
- **Privacy gate (INV-23).** The T0 scanner (`scripts/privacy_scan.py`) runs on every staged file: card and account numbers (also 6-10 digits right after an account word), PAN, IBAN, emails, UPI addresses, statement excerpts in Markdown, text files and commit messages (three or more dated lines with amounts within six lines; an ISO-dated line whose text has a Beancount account name, or which ends in one amount and an ISO 4217 currency code, does not count, so a price table without currency codes needs the allow mark on its lines; limit: a real statement row in one of those two shapes, ISO-dated, passes), API keys and tokens, detect-secrets' vendor-key, keyword and entropy rules (from its pinned environment, never verifying over the network), home paths, and the owner's amount/name denylist kept **outside** the repo (`$FT_PRIVACY_DENYLIST` or `~/.config/finzytrack/privacy-denylist.txt`). The staged-file guard (`scripts/check_staged.py`) refuses ledgers, env files, mirror databases and app config outside `corpora/` and `fixtures/`, and refuses bank/broker exports unless listed in `corpora/MANIFEST.tsv` with their SHA-256 and the owner's review date; it also sniffs data-like text (UTF-8, UTF-16 or UTF-32) for statement content everywhere, `corpora/` and `fixtures/` included, and validates every MANIFEST row. Only the owner adds MANIFEST rows: the guard hooks refuse agent writes to it (S0026). Real exports enter the repo only anonymized, and only after the owner reviewed the result. The scan's rules are frozen: each workaround for a false positive is one line in the journal, a finding against that rule for the next reflection. Security repros that work against a released version stay in the private archive until a fixed version ships; on `next` a fix lands with a neutral regression test.
- **Agents and real data (INV-24).** Agents never read the owner's live data folder, never write into the legacy worktree, never run `git clean -x/-X`. `.claude/settings.json` and the guard hooks refuse acts aimed at the live data folder, the legacy worktree and the git gates. A heredoc body is data unless a shell word stands on its opener's line, so a message may name a refused command; a script written by a heredoc or by the Write tool and run later is not inspected (§11); any mention of the live data folder is still refused (IMP-0045). **The owner's running app** is not guarded (ADR-0065): agents never stop, start or call it themselves; if it is in their way (a port, a process), they ask the owner to stop it and go on once the owner has. Tests run on copies in isolated data dirs and ports. Real-ledger copies run only in T-local, from a folder outside the repo given by an environment variable, and its output prints counts and case IDs only.

## 9. Reflection and self-improvement

- **Every escape becomes a gate.** An escape is a defect found later than it should have been. Its analysis names the gate that should have caught it and the root-cause class; the fix includes the prevention. The same class must not escape twice. **The gates' self-defence is frozen** (owner, 2026-10-29: "Yes to Reflection proposals 1, 2, 3, 4, 7, 8, 10 and 12."; IMP-0045): no hardening against an agent bypassing a gate on purpose, and a new check script or meta-test class only after a real escape. The freeze is about the gates defending themselves, not about building the enforcement an invariant is due to get at its milestone, which comes with its own check scripts and meta-tests (owner, 2026-11-09, S0092: "Keep the script. Record that the freeze is about the gates defending themselves, not about building the enforcement an invariant is due to get at its milestone; PROCESS.md §9 gets that one clarifying clause, with your words."; IMP-0055).
- **Retro on every slice**, one line in the journal: build minutes, fix minutes, verifier rounds, findings H/M/L, and one sentence on the cheaper gate that could have caught them. It also counts each process check that fired in the slice (invariants, capabilities, retired terms, deferrals, push gate, gate timer, generated): `<check> <n> catch / <n> false positive`, where a catch refused something really wrong and a false positive refused something right and needed a workaround (IMP-0073).
- **Periodic reflection** (about every 5 slices and at milestone boundaries) proposes process changes with a hypothesis and a metric: escapes, verifier findings by class, gate durations and flakes, escalations, owner time, doc-drift hits, onboarding time, **process overhead per slice** and **false-positive rate per check**. When overhead rose, it proposes at least one consolidation. **At G1, each process check (invariants, capabilities, retired terms, deferrals, push gate, gate timer, generated) lists its true catches and its false positives since M1a**, summed from the retro lines (S0107 on) and read from the earlier journals; a check with no true catch and repeated false positives is offered to the owner for retirement (IMP-0073). The data guards (privacy scan, staged-file guard, INV-24 guards) are never offered.
- **Guardrails:** tightening a gate, test, prompt or rubric line is agent-approved and logged (adding or tightening an **invariant** still needs the owner's approval, `INVARIANTS.md`); loosening (removing or weakening a gate, narrowing the verifier, weakening an invariant, changing the rubric) needs the owner; reverting a gate counts as loosening; preventive gates are judged by the seeded-defect catch rate. Check scripts have meta-tests (`scripts/tests/`). Flaky tests are quarantined at most N days with a backlog ID; INV-tagged and integrity-core tests are never quarantined.
- **Records:** routine process changes are `IMPROVEMENTS.md` entries plus the matching edit here, in the same change; invariant changes, rubric changes and the pilot result are ADRs.

## 10. Branches, releases, clearance

- `next` holds v0.4 and grows from an empty tree; `main` is the legacy line (no feature work); tag `legacy-final` = v0.3.0, never released. The read-only legacy worktree is the differential oracle (copies only).
- Commits go directly to `next` and agents push them (owner, 2026-10-24; ADR-0045); there are no pull requests, no agent GitHub account, no CODEOWNERS. **Temporary first-push gate:** until the owner has reviewed the setup of `next`, the pre-push hook refuses pushes unless `git config finzytrack.allowPush true` is set in the clone (only the owner sets it), Once the owner opens it, the decided flow applies: agents push `next` after each landed slice without asking (owner, 2026-10-25); the guard hook refuses force, delete, tag, mirror and `main` pushes, and the pre-push hook runs the owner push gate and every T0 pre-push check.
- **Clearance by kind of edit** (owner, 2026-10-24): each mutator runs only on test copies until its kind is cleared: Add 50 writes / 1 week; Change/delete one entry 100 / 2 weeks; Many entries or several files 30 / 2 weeks with crash tests; twice those for a mutator with no old-app comparison (cleared on Beancount's own checks and hand-checked results). The owner signs one page per milestone. The final dogfood window is 4 weeks with one month-end reconciliation and one broker sync.
- **G1** (after the write core) uses measurable criteria; the owner judges the projected time to finish then (ADR on G1).
- **Release** = merge `next` into `main` when the release gate holds (ADR-0043: every mutator cleared, the real-ledger corpus, the dogfood window, the upgrade matrix from v0.2.2, packaged builds on three OSes, legal advice on the licence applied, architecture checks, the mutation floor, complete release notes). User docs ship from the docs `v0.4` branch.

## 11. Limits, stated honestly

Agents checking agents share blind spots; executable checks, Beancount as the oracle, spot audits, seeded defects and the owner's real use reduce this but do not remove it. The setup cost is front-loaded. Flaky end-to-end tests are the main threat to speed. The guard hooks are a safety net, not a sandbox: they and the gates do not stop a command or edit built on purpose to slip past them (seeded-defect classes b and e; IMP-0045). Code given to `sh -c` or `eval`, and code an interpreter runs (a `-c` or `-e` argument, a heredoc it reads), is not parsed. A heredoc body is parsed as commands only when a shell word stands on its opener's line: a script written to a file by a heredoc or by the Write tool and run by a later line or command (`bash /tmp/x.sh` after the end line, or `chmod +x` and the file run directly) is not inspected, and a `<<EOF` inside quotes or a comment is taken as a heredoc opener. A `cd` right after `(` is not seen, so `(cd <legacy> && rm …)` passes (the parser splits on `)`, not `(`). The stricter check for both is BL-0155, parked until a real escape.
