# How should the ledger engine run several jobs, and how is a slow job told apart from a sick engine?
- Asked: 2026-10-26 by the orchestrator, from the first area review of the engine and backend core (findings F1 and F2, both High; report in the owner's private archive, `m1a/area-review-engine/`)
- blocks: the read core (`beancount_port`, the overlay load and `LoadPolicy`, the mirror build); not the small hang fix (S0042) or the backlog edits
- Rubric item: changes an accepted ADR (ADR-0054 decision 4: "the engine ... owns the heavy-load semaphore") and ARCHITECTURE §2.5's heavy-load row
- ADRs checked: ADR-0054 (decision 4, the semaphore in the engine; Consequences: "a second interpreter costs roughly 40-80 MB while running"); ADR-0041 (the semaphore is the only process-wide state); ARCHITECTURE §2.5 ("1–2 slots, configurable; priority goes to the workspace being opened"); INV-10 (no resident ledger); the memory-frugal hosting decision (bounded memory); S0040 (the supervision statechart: a timeout is a stop; 3 stops in 300 s make the engine unavailable). None decides cancellation or how slots map to processes.

## Context (plain language, an example first)

Today the engine does one job at a time, and the sidecar sends it one request at a time. That was fine while the only job was "ping". The next jobs are heavy: loading a 54,000-entry ledger takes seconds of full CPU.

Example: you open your workspace, and while the mirror is being rebuilt (a full load) the reconciliation check also wants a load, and you run a BQL query. All three queue behind each other, so the query waits for both loads. The design says up to 2 loads may run at once with priority to the workspace you are opening, but a single Python process cannot run two CPU-heavy loads at once (Python runs one thread of Python code at a time), so that design cannot be built inside one engine process as written.

Second problem: the only way to stop a job today is a time limit, and hitting it counts as an engine crash. Three in five minutes and the engine is marked unavailable, so writes and BQL are switched off for up to five minutes. A slow but healthy load on an older laptop, an expensive query, or you pressing Cancel would all count as crashes. It also means every job needs a guessed time limit, which goes against your "no fixed time budgets" rule.

## Options
1. **Slots are engine processes, the queue lives in the sidecar** (recommended). The sidecar keeps a priority queue (the workspace being opened first) in front of 1 to 2 engine processes; each engine still does one job at a time. The second process starts only when two jobs are waiting and ends when idle, so memory stays at one engine most of the time (about 40–80 MB idle, plus a load's own peak while it runs). Cancelling a job ends its process and does **not** count as a crash. A sick engine is detected by the engine itself sending a small "still working" signal every second while it works: silence well past that interval means hung (counted as a stop); a long job that keeps signalling is never cut off by a guessed limit. You can still cancel it.
2. **One engine, a smarter queue.** Keep one engine process; add the priority queue, the cancel that does not count as a crash, and the "still working" signal. Lowest memory, simplest, but a query or a write still waits behind any load in progress (seconds at 54k).
3. **Leave it as it is** and revisit later. Not recommended: every read-core job would be built on the one-lane, crash-on-timeout channel and reworked later.

## Recommendation
Option 1, done as one slice before the read core, with an amendment to ADR-0054 decision 4 and ARCHITECTURE §2.5. It is what the design already intended (1–2 slots, priority to the workspace being opened), made buildable. A separate "cheap questions never wait" lane is not proposed now: no such question exists yet; it can be added when one does.

## Proposal agreed in principle (orchestrator, 2026-10-26), pending an independent design review
- **Option 1 with a computed slot count.** Engines share nothing in memory (each job reads the ledger files, works, answers, forgets), so N engines need no syncing between them; the only thing that must not run in parallel is two writes to one workspace, already serialized by the workspace's write lock (INV-26), and the queue never hands a second write for a workspace that has one running.
- **Slots** = min(CPU cores − 1, free memory ÷ the measured peak of one load of this workspace, a cap of 4), at least 1, overridable in settings. Engines start when jobs wait and end when idle. Spike S4 at 54k: a load about 2 s of one core, about 145 MB retained, write peaks up to about 3.3× retained.
- **The measurement is a by-product,** never a separate run: each load's result carries the engine's peak memory; kept per workspace in app-local data (never in the ledger) as a recent high-water mark; at startup the slot count uses the stored value scaled by the growth of the ledger files' total size since it was measured (a stat, microseconds); a new workspace starts from S4's ratio × file size and corrects after its first load. Open detail: a process's peak RSS is a lifetime high-water mark, not a per-job figure (fresh process per measured job, or a before/after delta).
- **Cancel** ends the job's process and is not a stop; **hang** detection by an engine heartbeat every second while working (silence well past the interval = hung, counted as a stop); no per-job wall-clock limit.
- **Cheap-question lane:** not now (no such question yet).

## Independent design review (2026-10-26) and the owner's answer
- Review report in the owner's private archive, `m1a/design-review-concurrency/` (H1-H6, M1-M7, L1-L5; two of the proposal's claims wrong: engines do share state, and a heartbeat does not tell a slow job from a sick engine). The orchestrator relayed an amended design and five decisions: (1) at most 2 engines by default, a setting, no computed formula; (2) memory for ledger work: a quarter of RAM by default, a setting, and no new job while the OS reports memory pressure; (3) Cancel on a save that has started writing files shows "Finishing your change…" and lets it complete; (4) background jobs far over their usual CPU time for this ledger (about 10x) stop automatically and are logged; a first run can only be cancelled by hand; (5) a fresh engine process per heavy job. Sequencing: the ADR-0054 amendment, the pool, fresh engines, admission, liveness and progress messages, cancel for reads and pool-level stop history now, before the read core; the per-workspace lane and conditional publish with the mirror build; cancelling a save and in-session recovery in M1b with BL-0091.
