# Long numbers: loading at 64 digits also changes numbers Beancount divides. Keep the 2026-10-29 decision, narrow it, or follow Beancount?
- Asked: 2026-11-10 by the implementer, S0098-numbers-beyond-28-digits (BL-0123)
- blocks: S0098-numbers-beyond-28-digits (BL-0123); the mirror publish (BL-0113) only for ledgers that hold a number Beancount rounds or a plugin Beancount's load fails on (as before)
- Rubric item: 1 (how existing ledgers are interpreted), 2 (which number the user sees), 4 (INV-21: a released TransactionId changes)
- ADRs checked: the answered question `answered/20261028-numbers-beyond-28-digits.md` (option 1, "keep numbers beyond 28 digits as exact"), ADR-0010 (the overlay load is Beancount's own), INV-02 (Beancount is the oracle), INV-21 (the TransactionId scheme is read forever), the mirror README "Exact numbers" (the mirror's own sums use 64 digits and fail rather than round). The 2026-10-29 answer assumed that 64 digits changes only numbers longer than 28 digits. It changes more, so none of these settles it.

## Context (plain language, examples first)
Python keeps 28 significant digits by default. Beancount, bean-check and Fava all run with it. The decision of 2026-10-29 was: Finzytrack loads with 64 digits, so a long number the user wrote stays exact, and a warning names the lines where Finzytrack and Fava differ.

When I tried it, 64 digits changed numbers that are not long at all. Beancount **divides** in four places: a total price (`7 TOK @@ 10 USD`: price per token = 10 / 7), a total cost (`7 VTI {{100 USD}}`: cost per share = 100 / 7), and when it fills in a missing price, cost or quantity. 10 / 7 has no exact decimal form, so it is always cut somewhere. Today it is cut at 28 digits, at 64 digits it is cut at 64. Measured on head (8a7dbe11) with synthetic ledgers:

1. **Every `@@` line with an uneven division changes.** `7 TOK @@ 10.00 USD`: today the price per token is `1.428571428571428571428571429` (Fava shows the same). At 64 digits it is `1.428571428571428571428571428571428571428571428571428571428571429`. Screens round for display, so nothing visible changes there, but SQL and exports show the long text. Two corpus ledgers change (`write/total-price`, `oracle/nasty`: `postings.price_number` and `prices`).
2. **A ledger with a total cost stops opening.** `7 VTI {{100 USD}}`: the mirror computes the book value 7 × (100 / 7) exactly, with 64 digits, or fails. With a 64-digit cost per share, the product needs 65 digits, so the mirror build fails (`inexact`) and the workspace does not open. Today this ledger opens. Fixing it means widening the mirror's own exact sums too (for example to 128 digits). That changes the mirror's "64 digits" rule.
3. **A released TransactionId changes.** `Assets:Broker  VTI @ 3 USD` with `Assets:Bank  -10.00 USD`: Beancount computes the quantity, 10 / 3. That number is part of the content fallback id. Its text changes from 28 to 64 threes, so the id changes from the one v0.2.2 computed. INV-21 says that scheme is read forever. This shape (quantity left out, price given) is rare.
4. **The warning would be noise.** "Each line where Finzytrack differs from bean-check and Fava" is then every line of kinds 1 to 3, in ordinary ledgers.

What stays true: the bug is real. A long written number is rounded today. A written `-12345678901.123456789012345678 SHIB` (an 18-decimal token, 29 digits) loads as `-12345678901.12345678901234568`. A long amount whose other leg is left blank crashes the load. bean-check crashes on the same file too: `decimal.InvalidOperation` in Beancount's `quantize_with_tolerance`.

## Options
1. **64 digits for every ledger (the 2026-10-29 decision as written).** Long numbers stay exact. Every `@@` and `{{ }}` division gets 64 digits (example 1). The mirror's exact sums widen so that example 2 opens. The TransactionId of a rare transaction changes (example 3): an INV-21 change you would approve. The warning is limited to lines with a long written number or a long exact sum, not to divided numbers. That limit is narrower than "every line that differs".
2. **64 digits only for ledgers that need it.** A ledger with no number longer than 28 digits loads exactly as bean-check and Fava do, so nothing changes for almost every user. A ledger that has one loads at 64 digits, with option 1's side effects for that ledger only. The cost is two modes. Every load stage must agree on the mode, and the mode has to be found before Beancount reads the file. Adding one long number to a ledger changes the divided numbers and those rare ids of the whole ledger.
3. **Follow Beancount (the old option 2).** Finzytrack loads at 28 digits, like bean-check and Fava, so all three show the same numbers. The load warns on each line whose number Beancount rounded: a long written negative number, a filled-in amount longer than 28 digits. The crash becomes a clear refusal that names the line ("Beancount cannot load this ledger: the number on line N has more than 28 digits; bean-check fails here too"). It never becomes an internal error. Nothing else changes: no golden, no id, no mirror rule.
4. **Refuse (the old option 3).** A ledger with a number Beancount would round does not open, and the message names the line.

## Recommendation
Option 3. The new facts weaken option 1's main argument, "the number in question is one the user wrote". At 64 digits, most of the numbers that change are numbers Beancount computed, in ordinary ledgers. Example 2 shows the risk: a common ledger stops opening, or the mirror's exactness rule widens. Option 3 keeps Finzytrack equal to the tools these users already run. That fits INV-02, Beancount is the oracle. bean-check already shows the same rounded value, so a user with an 18-decimal token sees it there too, and Finzytrack's warning says why. Choose option 2 if exact long numbers matter more to you than one load mode. It is the only way to keep them exact without changing every other ledger.

Not a question for you, decided in the slice: a plugin that adds a `document` whose file name is not text makes Beancount's own load raise (`validate_documents_paths`; bean-check crashes too). Finzytrack's load will return a refusal ("Beancount cannot load this ledger") instead of an internal error. Under option 3, the crash above uses the same refusal.
